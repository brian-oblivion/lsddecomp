## The round-14 diagnosis, and where it was incomplete

Round 14 established that this function owns `D_80011194`, which lives in
rodata slot `0x1908` — a slot ATTACHED to `screen_widgets` so that
`func_8003FB1C`'s jump table could resolve its unit-local `.L` labels. With
`migrate_rodata_to_functions: True`, an attached slot's symbols migrate into
the owning *function's* generated `.s`. While `func_8003FC70` is
`INCLUDE_ASM` that `.s` exists and the layout is retail's; as C there is no
migration target, so the symbol moves and the image goes 1707 bytes off.

All of that is correct. The prescribed way out — "re-segment so `D_80011194`
is not in the attached part of the slot" — is also correct, **and it is not
sufficient**. Round 14 tried exactly the boundary this round used (`0x1994`),
measured **339541 bytes** off, and concluded the boundary needed care:
"likely an alignment constraint on where a rodata section may begin. That is
the open lead."

**There is no alignment constraint.** The split at `0x1994` is byte-neutral
on its own (verified: green build with the function still `INCLUDE_ASM`), and
`asm/data/1994.rodata.s` is generated correctly. Re-running round 14's
experiment reproduces `339541` exactly — the same number, which is what
identifies it as the same failure rather than a near miss.

## The actual mechanism

`D_80011194` is a **string literal**:

```
dlabel D_80011194
    /* 1994 80011194 */ .asciz "not supported light mode %d\n"
```

The preserved C body spelled that string out at its call site:

```c
func_80012C20("not supported light mode %d\n", mode);
```

So once the split gives the symbol its own standalone object, the image holds
**two** copies of the string — the one splat emits from `1994.rodata.s`, and
the one `cc1` emits into `src/screen_widgets.o`'s `.rodata` from the literal.
The duplicate lands at the front of the unit's rodata, and because
`section_order` puts `.rodata` first, everything in the image after it
shifts. That is why the first differing byte is at file offset `0x858` —
thousands of bytes *before* the segment being edited, and before `0x1994`
itself, which is what made the round-14 reading ("the boundary is wrong")
look plausible.

## The fix — both halves are required

1. **Split the slot** so the symbol is not migrated into the function's `.s`:

   ```yaml
   - [0x1908, .rodata, screen_widgets]
   - [0x1994, rodata]   # D_80011194
   - [0x19B4, rodata]   # -> psyq_memset, NOT ours
   ```

2. **Reference the symbol; never re-spell the string.**

```c
extern s32 GsLIGHT_MODE;
extern void func_80012C20(const char *fmt, s32 arg1);
extern const char D_80011194[];

void func_8003FC70(s32 mode) {
    if (mode == 1) {
        goto set;
    }
    if (mode < 2) {
        if (mode == 0) {
            goto zero;
        }
        goto err;
    }
    if (mode == 2) {
        goto set;
    }
    if (mode == 3) {
        goto set;
    }
    goto err;
zero:
    GsLIGHT_MODE = 0;
    return;
set:
    GsLIGHT_MODE = mode;
    return;
err:
    func_80012C20(D_80011194, mode);
}
```

Either half alone fails, and the two failures look nothing like each other:
the split alone is 339541 bytes off, the literal alone (unsplit) is 1707.

### Proposed learning

**A `D_XXXXXXXX` in rodata that holds a string is a SYMBOL to reference, not
a string to retype.** Splat has already emitted those bytes; writing the
literal in C emits them a second time. The tell is a whole-image diff whose
first differing byte is in *rodata*, far ahead of the text you edited — and
because `section_order` puts `.rodata` first, "far ahead" means the number is
enormous and carries no hint of which unit caused it. Check
`asm/data/<slot>.rodata.s` for the symbol before writing any literal; if it
is there, `extern const char D_XXXXXXXX[];` is the only correct spelling.

This is a sibling of the "field insertion with a forgotten pad" hazard in
CLAUDE.md: a clean compile, a red image, and nothing wrong in the function
you were working on.
