## What it does (fully derived — cross-checked against an m2c run)

A per-slot "tick" function for the same `D_800902E8[screen][slot]` array
this unit's already-matched `func_80036410`/`func_800368E8` touch (`extern
Entry90902E8 *D_800902E8[];`, a 172/0xAC-byte record). Two `s32` parameters,
`(a0=screen, a1=slot)` (matches the existing call site in
`code_179d8_i.c`: `extern void func_80036528(s32 a0, s32 a1);` /
`func_80036528(screen16, slot16);`).

Seeded with `tools/m2ctx.py code_179d8_f --sig 'void func_80036528(s32 a0,
s32 a1)' --run asm/nonmatchings/code_179d8_f/func_80036528.s` — the
resulting decompilation was structurally sound (right CFG, right field
offsets once cross-referenced against the struct) and used throughout as
the basis for the hand-written version below.

Behavior:

1. Reads `entry->unk42` (a signed 16-bit "period" count) and decrements
   `entry->unk98` (a 32-bit counter). If `unk42 > 0`, checks whether the
   post-decrement `unk98` is an exact multiple of `unk42` (`% == 0`,
   confirmed unsigned — retail's raw division word decodes to `divu`, not
   `div`).
2. On a hit, decrements `entry->unk40` (a 16-bit counter of remaining
   "beats"), and if it hasn't gone negative, packs `(screen | slot<<8)` and
   calls `func_80030584` (matched, `code_179d8_j.c`: `s32
   func_80030584(s32 p0, s16 *out1, s16 *out2)`, an "XY read" accessor for
   the SAME table) to read two `s16` outputs into stack scratch. If both
   outputs are within `[-1, 0x7E]` (checked as `+1 < 0x80`), calls
   `func_80030404` (still `INCLUDE_ASM`, `code_179d8_j.c`) with the
   incremented values; otherwise falls back to a `(0x7F, 0x7F)` call and
   clears bit `0x10` of `entry->unk90`.
3. When `unk40` goes negative (ran out of beats), or when `unk42 <= 0`
   in a mirrored form with a threshold subtraction instead of `+1`, the
   same `func_80030404`/flag-clear shape repeats.
4. Unconditionally, at the end, calls `func_80030584` again with `&entry->
   unk78`/`&entry->unk7A` as the OUTPUT pointers this time (persisting the
   XY read into the entry itself, rather than a scratch stack buffer).

## Two real levers found, both worth keeping for future rounds

### Lever 1: reusing a subtracted expression across a guard and its call arguments inflates GCC 2.6.3's frame `vars` accounting

The count`<=0` branch's threshold check is, semantically, `if ((sp10 -
thresh) < 0x80 && (sp12 - thresh) < 0x80) { call(f, (sp10-thresh)&0xFFFF,
sp12-thresh, ...); }` — writing the subtraction inline, evaluated fresh in
the condition AND again in the call arguments (which is what a literal
transcription naturally produces, and is ALSO what retail's own
instruction stream does — it recomputes the subtraction for the call
rather than reusing a register from the condition). Doing this raised
`cc1`'s own `.frame` comment from retail's true `vars=24` to `vars=48`
(confirmed via direct `cpp | cc1` probes, isolated from the rest of the
function — see below), pushing the total frame from `0x48` (matching
retail exactly) to `0x60`, and desynchronizing every register-save offset
in the prologue.

**The fix: bind the subtraction to a named local BEFORE the condition,
and reuse that local (not the raw expression) in the call:**

```c
s16 d1 = sp10 - thresh;
s16 d2 = sp12 - thresh;
if (d1 < 0x80 && d2 < 0x80) {
    func_80030404(packed, d1 & 0xFFFF, d2, 0);
}
```

This is EXACTLY what `m2c`'s own output had already done (`var_a1`, `var_a2`
named locals) — the mistake was "cleaning up" m2c's naming into a more
idiomatic-looking inline expression, which silently threw away a
load-bearing detail. **The general lesson: when m2c introduces a named
temporary for a value used in more than one place, treat that as
information about the compiler's OWN internal spill/CSE behavior, not
just a naming artifact to simplify away.** Confirmed isolated (via `cpp |
cc1`, no `as`/`maspsx` needed since the `.frame` comment alone answers it):
a minimal 6-line reproducer with just `if (a - c < 0x80 && b - c < 0x80)
f(a-c, b-c);` against one with `d1=a-c; d2=b-c; if (d1<0x80 && d2<0x80)
f(d1,d2);` shows the same `vars` jump, isolated from every other construct
in this function.

### Lever 2: casting a struct field to `unsigned` in ONE expression can make GCC choose an unsigned LOAD for a DIFFERENT, signed use of the same value

`entry->unk42` (declared `s16`) is used in two places: a signed guard
(`entry->unk42 > 0`) and an unsigned modulo (`(u32)entry->unk98 %
(u32)entry->unk42`, confirmed unsigned because retail's raw word decodes
to `divu`). Writing this as:

```c
s16 count = entry->unk42;
if (count > 0) {
    if ((u32)entry->unk98 % (u32)count == 0) { ... }
}
```

compiles `count`'s OWN load as `lhu` (unsigned half load) instead of
retail's `lh` (signed) — confirmed by direct inspection of `cc1`'s
pre-maspsx output. The `(u32)` cast on `count` inside the modulo
retroactively marks `count`'s pseudo-register as needing an unsigned mode,
and that propagates all the way back to the INITIAL load, even though nothing
about the FIRST use (`count > 0`) needs it. Introducing a second, purely
unsigned-cast local (`u32 ucount = count;`) used only in the modulo, while
keeping `count` itself untouched by any unsigned context, restores the
signed `lh` — but ALSO adds a second live local, which cost frame space
in this instance. The version that actually reached the fewest missing
words used the field directly (`entry->unk42`) a second time in the
modulo instead of reusing `count`, accepting one extra (harmless, size-
neutral) re-load rather than paying for an extra named local:

```c
s16 count = entry->unk42;      /* used only for the signed compare */
if (count > 0) {
    if ((u32)entry->unk98 % (u32)entry->unk42 == 0) { ... }  /* re-read, stays signed at its own site */
}
```

**General lesson: a `(u32)` (or any unsigned) cast on a NAMED local, not
just on a raw field expression, can change the LOAD instruction selected
for every other use of that same local — screen for this whenever a
retail `lh`/`lb` (signed) is observed alongside a `divu`/`sltu`-class
unsigned use of the same source value.**

## What did NOT close: the a0/a1-to-callee-saved-register hop

Retail's own prologue copies `a0` into `a3` (an ARGUMENT register, not a
callee-saved one) immediately, uses `a3` for the first several
instructions (the `D_800902E8[(s16)a0]` index computation), and only
LATER — after several unrelated instructions computing the slot*172
byte offset from `a1` — copies `a3` into `s5` (a callee-saved register,
needed once the value must survive the function's first `jal`). Every
attempt this round produced a DIRECT `move $s3,$a0` (or similar) at
the very top instead — a single hop straight to the callee-saved
register, skipping the argument-register interlude entirely. Tried:

- Introducing vs. omitting a separate `Entry90902E8 **arr` local for
  `&D_800902E8[(s16)a0]` (needed anyway — see below) — no effect on the
  hop pattern either way.
- Reordering the `arr`/`entry` computation relative to each other, and
  writing `entry` as a single combined expression instead of derived from
  `arr` — no effect.

This residue affects a LARGE fraction of the function's register
footprint (every reference to `screen`/`slot` downstream inherits whatever
register GCC settled on), which is almost certainly the dominant
contributor to the remaining 13-word shortfall — GCC's choice of WHEN to
promote an argument-register value to a callee-saved one across a long
stretch of unrelated code does not appear to be controllable from this
kind of source-level restructuring in the attempts tried. Flagging this as
a candidate for a dedicated pass (or permuter search, though this residue
spans structural register ALLOCATION rather than local instruction
ORDERING, which is usually a weak match for the permuter) in a future
round.

## Confirmed correct despite the length gap

- **Frame size matches retail exactly** (`0x48`/72 bytes, `vars=24 regs=7
  args=16`) once Lever 1 above is applied — confirmed via direct `cc1`
  `.frame` comment inspection, independent of the whole-image build.
- **The "cache vs. recompute fresh" split for `D_800902E8[a0][a1]`'s
  address is real and confirmed at instruction granularity**: retail
  caches `&D_800902E8[(s16)a0]` in one register (`$s3`) and reuses it,
  dereferencing fresh, at exactly 3 sites (the initial `entry` derivation
  plus the two `unk40`-went-negative fallback clears); it recomputes the
  WHOLE address from scratch (a fresh `lui`/`addiu`/`addu` sequence, not
  reusing the cached register at all) at the two `sp10/sp12`-out-of-range
  fallback clears. Modeled as a separate `arr` local reused via `(*arr)
  [(s16)a1].unk90 &= ~0x10;` for the former, and the raw
  `D_800902E8[(s16)a0][(s16)a1].unk90 &= ~0x10;` expression for the
  latter — confirmed via `asm-differ` that both classes of site match
  their respective retail instruction sequences exactly (register names
  aside).
- **The struct fields, control flow, and call arguments are all correct**
  — every branch target in the preserved body corresponds 1:1 to a real
  retail branch, and no field offset needed correction after the initial
  m2c-guided pass.

### Proposed learning

Both levers above (subtraction-reuse frame inflation; unsigned-cast load
contamination) are general GCC 2.6.3 codegen quirks not specific to this
function's shape, and are worth adding to `docs/DECOMPILATION_LEARNINGS.md`
if a future round confirms them on a second instance — this report is the
first sighting of either. The a0/a1 register-hop residue is filed as an
open question rather than a lesson: no lever tried this round moved it,
and it may need a permuter search or a differently-shaped source
restructuring not yet tried.
