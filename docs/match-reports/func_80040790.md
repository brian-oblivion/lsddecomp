# func_80040790 — STALL (register-identity residue, 13/26 words)

Unit: `src/code_2cc8c_f.c`. Blocker screen clean (no `gp_rel`, no
`addiu $at,$at,%lo`, no jump table). Retail's own callee-saved count is
0 (no `sw $s*`), so this is NOT the saturated-register-file class either
-- it is a plain caller-saved TEMP register choice.

```c
void func_80040790(Obj6EAC0 *self, u8 *dst, u8 *src, s32 overwrite) {
    u8 *d;
    d = dst;
    if (overwrite) {
        s8 r, g, b;
        r = ((s8 *)src)[0];
        g = ((s8 *)src)[1];
        b = ((s8 *)src)[2];
        d[0] = r;
        d[1] = g;
        d[2] = b;
    } else {
        d[0] += src[0];
        d[1] += src[1];
        d[2] += src[2];
    }
}
```

`self` (a0) is never referenced anywhere in retail's body; the real
signature is 4 args with the first unused (matches the caller,
`func_8004076C`, which forwards its own unchanged `a0`).

## The residue

At correct total length (26/26 words, confirmed via
`objdump -d build/src/code_2cc8c_f.c.o`), every single differing word is
the SAME instruction on a DIFFERENT register: retail caches `dst` into
`$t0` via an unconditional `move $t0, $a1` sitting in the very first
branch's delay slot, then uses `$t0` for every dereference of `dst` for
the rest of the function; every C shape tried keeps using `$a1`
directly and never materialises a second register at all. This is the
project's documented "redundant move" residue class (see
`docs/MATCHING-GUIDE.md`, "A redundant move retail emits and you do not
... resists goto/return spelling, temp placement, barriers and
volatile" -- now a 4th confirmed instance).

## Attempts (7, well under the 30-instruction-body cap)

1. Direct `dst[i] = ((s8*)src)[i]` / `dst[i] += src[i]`, no local --
   WRONG LENGTH (27/26 words): reusing one `$v0` across all three loads
   in the copy arm serialises them into a load-delay-hazard chain
   retail avoids by using 3 DIFFERENT registers (`v0`,`v1`,`a0`) for the
   three loads. **Fixed** by splitting into named `r,g,b` temporaries so
   GCC allocates three independent registers, matching retail's own
   register choice for the loads (not the residue below, a genuinely
   different and now-closed sub-problem).
2. `u8 *d = dst;` (combined declaration+init) before the `if` -- no
   change; GCC 2.6.3 copy-propagates the alias away entirely (`d`
   compiles to a pure re-use of `a1`, no second register at all).
3. Same, with a bare `__asm__("");` immediately after -- no change.
   Confirms the barrier does not stop copy-propagation of a
   register-only alias (consistent with the existing "`__asm__` anchors
   MEMORY operations only, not a pure register assignment" learning).
4. `u8 *d; d = dst;` as two separate statements instead of one combined
   declaration+initializer -- no change.
5. `u8 * volatile d;` -- made it dramatically WORSE: forces `d` to a
   real memory-backed stack slot, adding a whole frame
   (`addiu $sp,$sp,-8`/`sw`/reloads) that retail does not have at all.
   Reverted immediately; recorded as a clear negative so nobody retries
   `volatile` on a bare local-pointer-alias residue in this project.
6. Attempted `func_8001EDAC`-style "mention twice" (had `d` used AND
   `dst` used at different points) -- collapses back to case 2's
   behaviour under copy propagation, no new register appears.
7. Permuter (`tools/setup-permuter.sh func_80040790 <seed>`, no PERM
   macros -- pure randomization): base score 845 (Insertions/Deletions
   4x100 each, dominating over the 9x5 register-diff component), ran
   ~90s of `-j 6` search, best found was 770, never approached zero.
   The insertion/deletion-dominated base score is itself informative
   per `docs/MATCHING-GUIDE.md`'s "base score composition predicts
   viability" -- BUT that base score was taken against attempt #2's
   body (before the load-splitting fix in #1 closed the length gap),
   so it is stale and should be re-run against the length-correct
   13/26 body before trusting it as evidence either way.

attempts 2-4 and 6, but none of those extra mentions were in a
DIFFERENT branch than `d`'s only use -- an extra mention specifically

...`) was not isolated as its own attempt.

### Proposed learning

A 4th confirmed instance of the "redundant move, resists
declaration-order/barrier/volatile" residue class. `volatile` is now
confirmed as an active NEGATIVE for this class (adds a real stack slot)
rather than merely ineffective -- worth stating explicitly since it's
a natural next guess after barriers fail, and it costs a full
build+frame-size regression to learn otherwise.
