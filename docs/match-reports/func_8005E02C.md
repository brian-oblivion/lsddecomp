## What it does

`(Entity *this, s32 arg1) -> s32`. Compares `this`'s own Y position
(`this->unk14->y`) against `this->unk94->unk14->y` +/- `0x200`; returns `0` if
outside that band. Otherwise calls `this->methods->slot144(this)` and returns
`1` if the result is `< arg1`, else `0`.

This function is the primary evidence that `Entity::unk94` is a POINTER TYPE
with its own `+0x14` field readable as `EntityPos *` (same convention as
`Entity::unk14` itself) — see `func_8005E3C4.md` (matched the same round) for
why it is nonetheless NOT another `Entity`, and for the `Unk94Obj`/
`Unk94Methods` struct this function's own evidence fed into.

New vtable slot: `EntityMethods::slot144`, `s32 (*)(Entity *self)` — compared
with `slt` against `arg1`, so value-returning, not `void`.

## Attempt log

Roughly a dozen attempts, in three phases:

1. **Getting the boolean-return SHAPE right (the size-cascading part).** The
   naive `if (cond) return 1; return 0;` got FOLDED by GCC 2.6.3 -O2 into a
   direct `return cond;` (no branch, no `li`/`move` re-materialization) —
   confirmed with an isolated `cpp | cc1` recompile of just this function,
   independent of `ret`-variable reshaping (tried and also folded). Retail
   does NOT fold it: it has an explicit `slt` / `bnez` / `li 1` / `move 0`
   sequence reaching a SHARED epilogue with the two early `return 0;`s. The
   fix was `goto fail;` for the two early exits instead of `return 0;`
   directly — this stopped GCC from applying the return-value fold, and the
   function's LENGTH became correct (33/33 words) for the first time. Before
   this fix, the function was 1-4 words SHORT, which — because this unit
   keeps every function in strict ROM-address order — shifted every later
   function's linked address and made `funcdiff.py` report "1/33 words
   match" and a 6-figure "differs outside this range" warning for EVERY
   OTHER function in the file, not just this one. Getting this shape right
   was the single highest-value fix of the round: it unblocked accurate
   scoring for all 5 other functions attempted alongside it.
2. **The register-identity residue itself.** Tried, all with NO effect on
   which hard register `this->unk94`'s value lands in:
   - Reordering the `oy`/`ty` computation (both directions).
   - Introducing an explicit `Unk94Obj *other;` local vs. inlining the whole
     `this->unk94->unk14->y` chain in one expression.
   - Introducing an explicit `s32 threshold = arg1;` local before first use.
   - A bare `__asm__("")` scheduling barrier as the function's first
     statement, at three different positions (function entry; immediately
     after `other = this->unk94;`; combined with each of the reshapes
     above). The barrier DID fix a separate, now-resolved issue (see below)
     but never moved the `$v0`-vs-`$a1` register choice.
3. Per CLAUDE.md rule 6, this is exactly the register-identity test: none of
   the above changes WHICH REGISTER holds the value only reordered
   instructions, and the register choice was unmoved regardless. Filed as a
   stall rather than spending further budget.

**Note on the barrier's real effect (worth keeping for the next attempt):**
before adding `__asm__("")`, the compiler filled the load-delay slot after
`this->unk94`'s load with the (independent) `move $s0, $a1` instruction
instead of a `nop`, which is VALID scheduling but not what retail does —
retail has `move $s0, $a1` as its own separate instruction earlier (right
after `sw $s0`), with an explicit `nop` filling the delay slot afterward. The
barrier fixed exactly this: it forced `move $s0, $a1` to happen before the
barrier (matching retail's INSTRUCTION ORDER, +1 word) but had no effect on
the `$v0`-vs-`$a1` register CHOICE for `this->unk94` (a register-allocation
decision made in an earlier compiler pass than the one `__asm__` barriers
gate). This is a clean instance of "barrier changes order, not identity" —
consistent with, and reinforcing, the project's existing rule 6 test.

## Proposed learning

**A boolean-shaped `if (cond) return 1; return 0;` at the TAIL of a function
with earlier `return 0;` early-exits can get silently constant-folded by GCC
2.6.3 -O2 into a direct `return cond;` (no branch materialization) — even
though the earlier early-exits keep their own explicit branches to the same
shared epilogue.** Introducing a `ret` variable does NOT prevent the fold
(tried, still folded). Rewriting the early exits as `goto shared_label;`
instead of `return 0;` DOES prevent it, restoring retail's explicit
`slt`/`bnez`/`li`/`move` re-materialization shape. This generalizes the
existing "early exit returning a different value: try goto and return both"
lesson with a THIRD data point on when goto is required, not just preferred:
when goto's absence causes the compiler to elide instructions outright
(changing LENGTH, not just layout) — which is worse than the previously-
documented one-word residue, because it cascades address drift into every
later function in the same translation unit.
