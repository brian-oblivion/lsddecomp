# func_80031CF0 -- STALL (delay-slot filler / register-rescue residue, best reshape 31/31 words compiled length, order-only divergence)

Unit `code_179d8_j`, round 22 (2026-09-06). Not a class method. Sets two
parallel 16-byte-stride record tables (`D_8008D7F0[idx]`, `D_8008D7F2[idx]`)
and ORs a flag byte (`D_8008D970[idx] |= 3`), guarded by the same `(u16)
idx < 0x18` bounds check this unit's other accessors use.

## What it is

```
s32 func_80031CF0(s16 idx, s16 p1, s16 p2)
{
    if ((u16) idx < 0x18) {
        D_8008D7F2[idx].unk0 = p2;
        D_8008D970[idx] |= 3;
        D_8008D7F0[idx].unk0 = p1;
        return 0;
    }
    return -1;
}
```

`D_8008D7F0`/`D_8008D7F2` are modeled as two INDEPENDENT 16-byte-stride
arrays (not two fields of one struct) because retail computes each
field's address through its OWN `lui`/`addiu` pair rather than a single
cached pointer with `+0`/`+2` displacements -- the same discriminator
already used for `D_8006DAD4` (one struct, one address computation, two
displacement offsets) vs. this case (two full address computations
sharing only the multiplied index).

## The residue

Two independent findings, one FULLY closed and one NOT:

### 1. CLOSED: the missing 8-byte stack frame

Retail reserves `addiu $sp,$sp,-0x8` / `+0x8` around the whole function
even though NOTHING is ever stored to or loaded from that frame (`grep
'\$sp'` on the `.s` shows only the two adjustment instructions). This
matches CLAUDE.md's "oversized/unexplained frame is evidence of dead code"
signature, except the frame here is 8 bytes, not the `0x10` minimum an
outgoing-argument reservation would need (confirmed by reproducing a dead
zero-argument call through the pinned pipeline in isolation -- it forces
`0x10`, never `0x8`). The actual cause, reproduced in isolation: a
genuinely UNREACHABLE write to a local array (`if (0) { dead[0] = 1; }`,
with `s32 dead[2];` declared at the top) sizes an 8-byte frame slot at RTL
expansion time and is then eliminated as dead code, leaving the
reservation with nothing in it -- exactly retail's shape. This piece
reproduces byte-for-byte in isolation (verified through the pinned
pipeline before use here).

### 2. NOT CLOSED: delay-slot filler / register rescue

With the frame fixed and the field-store order pinned down with bare
`__asm__("")` barriers (necessary to stop the independent
`D_8008D970` read/write from floating ahead of the `D_8008D7F2` store),
the compiled body reaches the RIGHT LENGTH (31/31 words, matching
retail's `0x7C`) but diverges starting at the branch's delay slot:

- **Retail** fills the `bnez`'s delay slot with an UNCONDITIONAL rescue,
  `addu $a3, $a1, $zero` (saving `p1` out of `$a1` before it's needed as
  scratch), then computes `idx*16` into the now-free `$a1`, and reuses
  `$a0` (freed once `idx` is sign-extended into `$v1`) for the
  `D_8008D970` byte.
- **Every reshape reached here** instead fills that delay slot with part
  of the `idx` sign-extension (`sll $v0,$a0,16`), never rescues `p1`, and
  computes `idx*16` into the now-free `$a0` directly (since `idx`'s own
  register became free first) -- `p1` simply stays in `$a1` the whole
  function, no rescue needed. This is not wrong C; it's a DIFFERENT (and
  arguably more natural) legal scheduling of the same operations, and GCC
  2.6.3 reliably picks it once ANY additional local (the frame-sizing
  `dead[2]` array) is present. **The two fixes destabilize each other**:
  the frame fix changes the delay-slot filler choice as a side effect,
  and every combination tried keeps one and loses the other.

This is a genuine SCHEDULING/delay-slot-filler choice, not a register-
identity error reachable by reshaping expressions -- CLAUDE.md's banned
levers (`register T v asm("$N")`, an operand constraint) would be required
to force `p1` into `$a3` specifically, which is exactly what the ban
exists to prevent. Per the project's classification, this is a STALL, not
a permuter target (the divergence is a real reordering across an entire
function body, not a one-instruction residue).

## Axes tried (for the next attempt)

- Reordering the three field/flag statements (`D_8008D7F0` first vs.
  `D_8008D7F2` first): no effect on the register-rescue choice.
- An explicit `s16 savedP1 = p1;` local, used in place of `p1` at the
  final store: optimized away entirely (GCC proves it's the same value
  and never materializes a separate register for it).
- A bare `__asm__("")` as the function's very first statement: fixes the
  FRAME's position (moves the correctly-sized `addiu $sp,$sp,-8` out of
  the delay slot and to the unconditional top, where retail has it) but
  does not by itself force the `p1` rescue.

**Untested axis:** deliberately increasing register pressure earlier in
the function (e.g. touching one more value before the branch) to see
whether GCC's allocator, forced to free `$a1` for some OTHER reason,
naturally reaches for `p1`'s rescue as a byproduct. Not attempted this
round for lack of remaining budget.

### Proposed learning

**An "unexplained 8-byte stack frame with nothing stored in it" is NOT
always an outgoing-argument artifact.** CLAUDE.md's documented dead-code
signature (a dead call inside `if (0)`) forces the o32 minimum of `0x10`
(16 bytes) regardless of the dead call's own argument count -- verified by
reproducing a zero-argument dead call in isolation. An 8-byte reservation
with nothing in it instead reproduces from a dead WRITE to a genuinely
unreachable LOCAL ARRAY (`if (0) { arr[0] = x; }`), which sizes the array's
frame slot at RTL expansion before DCE removes the write. Screen for which
one applies by the SIZE: `0x10`+ suggests a dead call, smaller (word-
aligned) sizes suggest a dead local.

**A second, unresolved observation worth flagging for the next runner:**
introducing ANY extra local variable (even one that's fully dead-code-
eliminated and produces zero live instructions) can change GCC 2.6.3's
delay-slot filler choice for an UNRELATED branch elsewhere in the same
function. The frame-fixing local here is not "free" the way it looks from
the final byte count alone.
