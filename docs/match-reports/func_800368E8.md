## Two residues, same underlying idiom already seen in func_80036410

1. **Field `unk2B = 0;` and the later resets use the cached local `s0`, but
   the three `unk90` bit-clear/set operations reload through the raw
   `_ss_score[sa0][sa1]` expression** -- except the FIRST one, which uses
   `s0` directly (nothing had happened yet to make a fresh load necessary,
   so the compiler naturally reused what it just computed). Exactly the
   "mirror which accesses are cached vs. reloaded in the disassembly"
   finding from `func_80036410`, applied again: `s0->unk90 &= ~1;` first,
   then three raw-expression accesses.

2. **A genuine double-load: retail reads `+0x8` twice into two different
   registers (`a1` then `a2`) with nothing in between that could plausibly
   invalidate the value**, then uses ONE of the two copies for `unk4` and
   the OTHER for `unkC`. A plain `s32 v8 = s0->unk8; s32 vC = s0->unk8;`
   gets CSE'd by GCC into a single load (proven redundant, since nothing
   wrote through `s0` in between) -- one word short, and everything after it
   shifts.

   Tried and rejected: routing the second read through the raw
   `_ss_score[sa0][sa1].unk8` array expression (recomputes the WHOLE
   two-level index from scratch here, since `sa1`'s register had already
   been clobbered earlier in the function for the `SpuVmSeqKeyOff` argument
   -- badly regressed the function, adding a full multiply-chain
   recomputation retail doesn't have). A pointer-cast re-read,
   `*(s32 *)((u8 *)s0 + 8)`, still got CSE'd with the first read -- GCC's
   value numbering operates on the lowered `MEM[s0+8]` RTL, not the C
   spelling, so an equivalent-but-differently-spelled expression doesn't
   fool it. A full `__asm__ volatile("" ::: "memory")` barrier DID force
   two loads, but as a general memory clobber it also blocked the
   scheduler from interleaving three loop-invariant constant loads
   (`i = 0`, the `0x40`/`0x7F` fill values) the way retail does, landing
   at 78/91 with a pure reordering residue around the barrier.

   **What worked: a `volatile`-qualified read of only the second access**,
   `vC = *(volatile s32 *)&s0->unk8;`. This forces GCC to treat that one
   load as an observable side effect (so it can't be proven redundant with
   the first, ordinary read of the same address) without acting as a
   scheduling fence for anything else in the function -- the surrounding
   loop-invariant constants still got hoisted and interleaved exactly where
   retail has them once this was the only barrier in play.

### Proposed learning

For "retail reloads the same address into two different registers, my C
naturally CSEs it into one load" residues: a full memory-clobber
`__asm__ volatile("" ::: "memory")` barrier works but is a blunt instrument
that can also suppress unrelated, wanted reordering nearby (loop-invariant
hoisting in this case). A `*(volatile T *)&expr` read on just the ONE access
that needs to survive is a scoped alternative -- it forces that specific
load without fencing anything else in the function. Worth trying first when
the residue is isolated to a couple of registers, and falling back to the
full barrier only if a scoped `volatile` read doesn't reach the value (e.g.
if the two reads happen to be on different registers/paths that a single
volatile qualifier can't distinguish).
