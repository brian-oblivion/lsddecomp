**New structural finding: the body is NOT one undifferentiated blob.** It
has three distinct phases, visible directly from branch-target spacing and
register roles:

1. **Preamble (`0x8C64`-`0x8D1C`, ~0x38 words).** Ordinary C: null-check on
   `a0->0x0`, populates a local struct from `a1`/`a2`/`a3` and two calls to
   `func_8001A224` (not carved — likely a per-list-type init helper, called
   once for `D_8008ACD0`/triangle and once for `D_8008AEE8`/quad, matching
   those two globals' existing doc comments in `code_8220.h`). Then reads
   `a0->4->0x48`: if zero, skip a whole matrix block (branch to
   `.L80018698`).
2. **Matrix save/transform/restore block (`0x8D20`-~`0x8E70`, ~0x9C words,
   only when `a0->4->0x48 != 0`).** `cfc2 $0`..`$7` (control regs 0-7,
   the GTE's rotation matrix + translation vector) saved to a local struct
   at `a0+0x38`; a DIFFERENT matrix+translation loaded from
   `*(a0->4->0x48) + 0x24` via `ctc2`; **three** separate
   `mtc2`/`mvmva(sf=1,mx=0,v=3,cv=3,lm=0)`/`mfc2` sequences transform three
   `s16[3]` vectors in place (at `a0->4 + 0x24`, `+0x26`, `+0x28` — three
   half-word-interleaved `s16` triples, stride 0xC each, matching a
   `PolyXY8`-style packed vertex layout already established for this unit).
   **Lead, untested:** `include/psyq/INLINE.H` defines `gte_llir()`
   (`.word 0x133f`/`0x133e`/`0x133e`) — the name (Local matrix, Long IR
   vector) and its neighbors' naming convention (`gte_ll`, `gte_llv0/1/2`,
   `gte_llirtr`, `gte_llirbk`, `gte_llirfc`) match an `mx=0,v=3,cv=3` mvmva
   exactly by Sony's own naming scheme, but **this has not been checked
   against the pinned pipeline's actual encoding of `mvmva 1,0,3,3,0`** —
   do that before trusting it (`tools/binutils/bin/mipsel-linux-gnu-objdump
   -d` on a `.word` test, or decode the mvmva bitfield by hand against
   `GTENOM.H`/`LIBGTE.H`'s field layout comments).
3. **Per-face dispatch, `~0x8F50`-`0x9B18` (~430 words, the bulk of the
   function).** Structured as roughly nine `bnez $v0,X` / `bnez $s4,Y`
   block pairs at near-constant ~0x94-byte (~37-word) spacing, each
   containing one call into the matched tri/quad GTE path plus a
   conditional call into one of the eight not-carved RCpoly wrappers. The
   LAST one or two of these blocks close into a genuine back-edge loop
   (`.L80019300`'s `addiu $s1,$s1,0x2C` / `addiu $s4,$s4,-1` /
   `bnez $s4,.L80019208`, `$s1`/`$s3` both stepping by a 0x2C-byte stride)
   — so this is NOT a uniformly unrolled sequence; at least the tail
   iterates a real small array with a real loop, while earlier ones may be
   distinct named face slots (a fixed small set of body-part attachment
   points, matching the round-39 "model/mesh submit all faces" read) rather
   than loop iterations. **This distinction (which blocks are unrolled
   named slots vs. which are a real loop) is not yet resolved and is the
   single most important thing to nail down before writing C for this
   phase** — get it wrong and the whole phase needs restructuring.

**Why this stayed at analysis, not an attempt:** given the two-tier size gap

## Why this is tractable, not toolchain-blocked, and still deferred

This round's `func_800195EC` (69 instructions, also "Handwritten function")
proved the technique needed here works: no C form exists for `rtpt`/`nclip`/
`avsz3`/`rtps`/`cfc2` in this pinned binutils (confirmed — `as` errors
`unrecognized opcode` on all four "cofun" GTE execute mnemonics, and even
`objdump` disassembles retail's own bytes for them generically), so they go
in as raw `.word` encodings inside whole-block `__asm__` sections, mixed
with ordinary C for everything else. That match report also root-caused and
documents a real `maspsx` behavior (defensive nop-insertion after any
branch/jump mnemonic inside a hand-written asm block, fixed with a tab-
delimited `.set noreorder`/`.set reorder` bracket) that WILL recur here —
`func_80018464`'s ~958 instructions almost certainly contain many branches
inside GTE-adjacent asm regions, so budget for hitting it repeatedly.

At ~14x `func_800195EC`'s size, with GTE and plain-C sections interleaved
throughout rather than segregated (unlike this round's other two GTE
functions, `func_800193C0`/`func_800194A4`, which separated cleanly into a
few `__asm__` blocks around otherwise-ordinary C), this is a multi-round
undertaking on its own, not a single-session target. It should be staffed
deliberately — plan for it as a dedicated round, not a "if there's time
left" queue item, and expect to reuse every lever from
`docs/match-reports/func_800195EC.md`, `func_800193C0.md`, and
`func_800194A4.md` (the `.set noreorder`/`reorder` bracket, dropping bogus
GPR clobbers on `lwc2`/`swc2` blocks, explicit intermediate struct pointers
for reload sequences, `goto`+labeled `return` for early exits whose value
differs from the success path) from word one rather than rediscovering them.
