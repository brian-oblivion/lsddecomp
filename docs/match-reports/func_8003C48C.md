## What it does

A `void`-ish dispatcher on `Obj86B60 *self`: guarded by `self->unk3C != 0`, then
switches on a message code `a2` (range `[0x12, 0x21]`, checked with an unsigned
`sltiu ..., 0x10` after subtracting `0x12`) through a 16-entry jump table
(`jtbl_80011090`), forwarding to one of five of this same class's own vtable
slots (`self->methods->slot74/78/7C/80/84`, i.e. `func_8003C7F4`/`func_8003C858`/
`func_8003C8D0`/`func_8003C944`/`func_8003C9B0` in the base table), passing
`self` and the caller's own `a1` through unchanged. Everything else in the
16-wide index range falls through to a no-op return.

## Why it is blocked, not merely unattempted

`grep -n 'addiu *\$at, *\$at, *%lo' asm/nonmatchings/code_2cc8c/func_8003C48C.s`
hits once, on the jump-table dispatch sequence itself:

```
/* 2CCB0 8003C4B0 0180013C */  lui        $at, %hi(jtbl_80011090)
/* 2CCB4 8003C4B4 90102124 */  addiu      $at, $at, %lo(jtbl_80011090)
/* 2CCB8 8003C4B8 21082200 */  addu       $at, $at, $v0
/* 2CCBC 8003C4BC 0000228C */  lw         $v0, 0x0($at)
```

That is retail's **unfolded**, four-instruction address resolution
(`lui`/`addiu %lo`/`addu`/`lw 0x0($at)`). **This IS an instance of the
`addiu_at` blocker in `docs/research/addiu-at-blocker.md`, not a different,
matchable construct.** The symbol at `%lo(...)` being a `jtbl_*` label rather
than a `D_*` data global does not change the mechanism: measured through the
pinned pipeline, cc1 emits the identical generic pseudo-op shape for an
indexed *global* load (`lbu $2,D_80089EAC($4)`) and an indexed *jump-table*
load (`lw $2,$L13($2)`), and the fold from four instructions down to three
(`lui`/`addu`/`lw %lo(...)($at)`) happens in maspsx, strictly below cc1 —
maspsx has no way to distinguish "this `%lo` feeds a jump" from "this `%lo`
feeds a data load". A dense switch that lowers to a jump table is exactly as
exposed as an indexed data-global read.

**This function and `func_8003C63C` are the reason that correction exists.**
Both were originally screened as "matchable, false positive on the blocker
grep" (by this unit's carve-time header comment and by an early head
broadcast this round) on the reasoning that a `jtbl_*` symbol was a
structurally different, safe construct. That reasoning was never checked
against a reproducer; it turned out to be wrong, and the corrected
discriminator is: **the blocker is about what feeds the fold (any `%lo`
address resolution GCC/maspsx narrows to three instructions), not about
whether the symbol is code or data.** No attempt was spent on this function
before the correction landed — it is filed as blocked, not as a burned
attempt.

## Proposed learning

`grep -n 'addiu *\$at, *\$at, *%lo' <file>.s` catches BOTH the indexed-global
blocker and a dense-switch jump-table dispatch when GCC 2.6.3 lowers it densely
enough to need the folded three-instruction `%lo($at)` form. The `jtbl_*` vs.
`D_*` symbol name is not a valid discriminator — both route through the same
maspsx fold and are equally blocked. Do not screen a `jtbl_*` hit as safe;
screen it exactly like a `D_*` hit. (This retracts the opposite claim
recorded in this unit's own carve-time header comment in `src/code_2cc8c.c`
and in CLAUDE.md's `grep -v '%lo(jtbl'` guidance — the head is correcting
both on main off the back of this unit.)
