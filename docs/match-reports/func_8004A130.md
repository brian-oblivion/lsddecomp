# func_8004A130

**Unit:** class_39e08 · **Size:** 27 words (0x6C bytes) · **Status:** STALLED 26/27

## What it does

The `New_X` allocator for the sibling class `D_80086668` (resolved with
`tools/classtable.py --scan`; the vtable getter is `func_8004A4B8`, owned by
`class_3ac78`, which returns `&D_80086668`). Allocates a 0x38-byte instance
via `func_80017B34`, and on success calls the class's constructor -- slot
`+0x008` of its own method table, `func_8004A19C` (this unit, still
`INCLUDE_ASM`, not this round's) -- through that table. Returns the
allocated pointer regardless of whether the constructor ran, matching the
`New_DreamSys` / `new_class_6d3c8` shape from
`docs/research/class-framework.md`.

## Residue

**Class: delay-slot filler choice on a `malloc` NULL-check branch, not a
register-identity mismatch.** This is the SAME documented residue class as
`new_class_6d3c8` (`docs/match-reports/new_class_6d3c8.md`, STALLED 23/24)
and its round-3 follow-up: a `beqz` guarding a freshly-malloc'd pointer,
where GCC 2.6.3's `fill_eager_delay_slots` steals a value-equal register
move from the fallthrough thread instead of materializing the constant
retail uses. `new_class_6d3c8`'s writeup already exhausted `if`/`goto`
reshaping (both directions), a bare `__asm__("")` in every position tried,
and `volatile` -- all confirmed unhelpful or actively worse there.

**This round's own attempts (2, both negative), before recognizing the
precedent and stopping:**

1. **Bare `__asm__("")` immediately after the malloc call, before the
   `if`.** No effect: still 26/27, identical residue (`move v0,s0` where
   retail has `move v0,zero`).
2. **`if (self == NULL) { return NULL; } ...; return self;`** (early return,
   no `if`/braces wrapping the constructor call) -- this is the "genuinely
   different return value per exit" case documented on `new_class_6d3c8` as
   NOT merging into one epilogue. Confirmed here too, and much worse: GCC
   emitted a full SECOND epilogue (function grew from 27 to 42+ words,
   funcdiff flagged 140396 bytes differing outside range from the whole
   image shifting). Reverted immediately.

**Conclusion: same class as the existing `new_class_6d3c8` stall, not a new
lead.** Not spending further budget re-deriving the same ~20 already-tried
shapes; see that report's "Root-cause hypothesis" section for the
`reorg.c`-level explanation. If a permuter run ever closes that residue
class, this function is a second, independent confirmation site.
