`UnkStruct80035F3C` back into the two 16-bit words it was originally
unpacked from.

### Residue: the very last instruction, register identity only

Diffed against retail with `asm-differ`, **every instruction from the top of
the function through the second-to-last matches exactly**, including the
control flow, the sign/mask idiom (`-(x != 0) & mask` compiling to
`sltu`/`negu`/`and` rather than a shift), the split `<< 5` / `<< 3` shape for
the `<< 8` term, the pointer-indirected `unk8` read, and the mid-block
`t0 = 0x4000; t0 = t1 | t0;` two-step form for the conditional `| 0x4000`.
The ONLY remaining diff is the destination register of the function's final
`or`:

```
retail:  or   t0,v0,v1     built:  or   v0,v0,v1
retail:  sh   t0,0(a2)     built:  sh   v0,0(a2)
```

Same operands, same values, same store target -- purely which physical
register the allocator picked for the accumulator's last update. This is
CLAUDE.md's register-identity class exactly ("if removing it changes WHICH
REGISTER holds a value, it is banned"), and the banned fix
(`register T v asm("$N")` or an operand-constrained `__asm__`) is not
available here since `hi` has an ordinary C form -- there is no COP2/GTE-style
exception to reach for.

## Attempts (bounded at this point, not the full 30 -- see permuter section)

Manual, before reaching praise this shape:

1. Straightforward field-by-field translation in struct-offset order:
   0/35, wrong control-flow shape entirely (GCC folds `x ? 0x8000 : 0` into
   a `sll ...,0xf` shift instead of retail's `sltu`/`negu`/`and`+shared-mask
   idiom).
2. Switched the boolean-to-flag idiom to `-(cond) & mask` with `mask` as a
   real local (not a literal) -- reproduces retail's `sltu`/`negu`/`and`
   shape exactly (confirmed against a from-scratch reproducer through the
   pinned pipeline, independent of this function). Landed at 11/35 with a
   pure control-flow-order residue: GCC scheduled the unconditional `v1=a0`
   equivalent -- actually the STORE ORDER of the two masked values --
   differently from retail.
3. Restructured to match retail's `if (cond) { t0 = t1 | 0x4000; }` as an
   `if`/no-`else` block on the SECOND mask value rather than an early
   return; single biggest structural fix, jumped straight to 31/35.
4. Renamed/reordered the `t0`/`t1` locals (declaration order, chained
   assignment `t1 = t0 = ...`) by hand -- score never moved off 31/35.
   GCC's register choice for two same-lifetime temps is not sensitive to
   either the C variable's name or its declaration position once the data
   dependencies are fixed.

Axes varied by hand: control-flow shape (early-return vs if/else), the
boolean-to-mask idiom (ternary vs `-(cond)&mask`), declaration order,
variable naming, chained vs separate assignment. All of them are exhausted
at 31/35 except one: a genuinely redundant THIRD computation of the same
value, which is not something a human reviewer would naturally write and is
exactly the kind of lever the permuter exists to find blind.

**Interesting finding along the way**: two permuter-produced "noise"
artifacts turned out to be load-bearing and NOT cosmetic. Simplifying

- `(((a0->unk0 << 5) << 3) & 0x7F00)` instead of the semantically identical

- `p8 = &a0->unk8; ... hi |= *p8 & 0x1F;` instead of the semantically
  identical `hi |= a0->unk8 & 0x1F;`.

Both are included in the inlined body above for exactly this reason -- they
look like permuter noise and are not.

**Conclusion: this residue class is permuter-exhausted for this function.**
Three separate runs (two seeded near the final residue, one from further
back) covering on the order of 20000 combined iterations across roughly 70
minutes of wall time never found anything better than the single-register
`or` destination diff. This is consistent with CLAUDE.md's own
classification of a pure register-identity residue as a STALL, not
something reshaping resolves. Re-running the same search is not expected to
produce a different outcome; if this function is revisited, a different
lever (not local reshaping, not more permuter iterations on this same
seed) is needed, or it should be accepted as unmatchable under the pinned
toolchain.

## Process note for whoever reads this next

Two of these three permuter runs were launched without a `timeout` wrapper
and had to be killed by hand once `--stop-on-zero` clearly wasn't going to
fire. `timeout <seconds> permuter.py ...; echo "exit=$?"` should be the
default for any single-function permuter invocation from here on --
GNU `timeout`'s own exit code (124 for its own deadline, vs. 137 for an
external `SIGKILL`) turns "did my bound fire, or did something else kill
it" into a fact instead of a guess, and it means a long search resolves
itself instead of sitting there consuming CPU indefinitely.

### Proposed learning

A permuter-produced "artifact" that looks like noise (a split shift, a
pointless intermediate pointer) is sometimes load bearing -- verify by
reverting it back to the clean-looking equivalent and re-measuring before
assuming it's safe to simplify away. Two independent instances in this one
function's search.

Round 19's brief was explicit: "reported 33/35, claims exhausted -- verify

Tried three more variations targeting specifically the final accumulator
register, since none of round 16's permuter seeds appear to have tried
reusing the `t0` pseudo's name for the final store (as opposed to a fresh
`hi` variable) or retyping it:

1. Reused `t0` itself as the final accumulator (`t0 |= (...); t0 |= (...);
   *a2 = t0;`) instead of a separate `hi`, keeping the two stores
   (`*a1 = lo; *a2 = t0;`) at the end in the original order. **Much
   worse**: 0/35 in-range plus 257751 bytes of outside-range drift --
   completely different instruction scheduling (the compiler moved the
   `sh a0,0(a1)` store to a different point in the sequence and
   renumbered nearly every register in the tail). Reusing a pseudo's name
   across a value's "natural end of life" is not a neutral hint to GCC
   2.6.3's allocator in this body; it changes scheduling wholesale.
2. Same idea but with the `lo` store moved earlier (right after `lo` is
   computed, matching retail's actual instruction order where `sh a0,0(a1)`
   happens before the final two `or`s) instead of batched at the end.
   Also much worse: 13/35, again with major instruction-order and
   register-identity changes cascading from the reorder.
3. Retyped `hi` from `s16` to `s32` (axis 1, applied to a local rather than
   a parameter, since the value the retail asm carries through registers
   is naturally 32-bit before the final truncating `sh`). Regressed by
   one word: 32/35 (an `lh`/`lhu` sign-extension difference appears at
   `0x267FC` in addition to the pre-existing tail residue). Reverted.

None of the round-19 axes (retype, whole-struct, split-statement,
wrong-void-return) closes this function; the closest, axis 1 on the local
accumulator, is a strict regression rather than a neutral or improving
change. **The 33/35 register-identity tail residue is confirmed stable
under a fourth round of manual attempts on top of the three permuter runs
already on file.** Restored to `INCLUDE_ASM`, no change kept in `src/`.
