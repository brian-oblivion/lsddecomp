## What it does

Sets up a row-major 2D array of "entry" objects living in a flat buffer
`arg0`, `arg1` rows by `arg2` columns, object stride `0xAC` (172) bytes:

1. Stores `arg1`/`arg2` into `D_80090B68`/`D_80090B6C`.
2. Fills `D_800902E8[row] = arg0 + row*arg2*0xAC` for `row` in
   `0..arg1` -- i.e. one pointer per row, to that row's first object.
3. For every row (bounded by the *stored* `D_80090B68`, not the
   parameter directly) and every column (bounded by `D_80090B6C`),
   zeroes/initializes a fixed set of fields of each `0xAC`-byte object:
   `unk90=0, unk3C=0xFF, unk0=0, unk3E=0, unk40=0, unk94=0, unk98=0,
   unk42=0, unkA4=0, unkA0=0, unk9C=0, unk44=0, unk74=unk76=unk78=unk7A
   =0x7F`.

## Two solid, reusable fixes found en route (both worth keeping regardless of the final stall)

Starting point after a first straightforward `for`-loop translation:
**5/120**, with a wrong CFG (an extra duplicated range-check per loop)
and a wrong constant-multiplication expansion. Two fixes, applied in
order, took this to the reported 60/120 with a CORRECT CFG and a
byte-perfect inner field-init sequence:

1. **`for` -> explicit `if (n > 0) { i = 0; do {...} while (++i, i <
   n); }` eliminates a duplicated range guard.** The naive `for (i = 0;
   i < n; i++)` translation compiled to TWO range checks per loop (one
   upfront "skip the whole loop" guard, one at the bottom) where retail
   has exactly one. This is the SAME `blez`/guard-clause idiom already
   established for the SetRCnt family this round, now confirmed on a
   totally different function shape (loop trip-count guard, not an
   early-return). Applied to all three loop nests in this function;
   fixed the CFG completely -- after this alone, only content-level
   diffs remained (constant multiplication and register/operand order).
2. **A loop-carried multiply where GCC recognises the induction-variable
   pattern and strength-reduces it, when retail's source apparently
   didn't give it the chance to.** First attempt wrote the classic
   accumulator form (`v1 = 0;` before the loop, `v1 += arg2;` inside) for
   computing `row*arg2`. Standalone reproducer under the pinned toolchain
   confirmed `v1 * 0xAC` alone compiles to retail's exact 5-instruction
   shift/add/sub decomposition (`sll,addu,sll,subu,sll,subu,sll`) --
   but as soon as that expression sits inside a loop where `v1` is
   ALSO a simple `+=`-accumulated induction variable, cc1 additionally
   strength-reduces the `*0xAC` into a SEPARATE running accumulator
   (computed via `arg2*3` combined into the loop step), producing a
   totally different, shorter instruction sequence than retail's
   every-iteration recompute. Rewriting the source to compute
   `v1 = i * arg2;` freshly at the top of each iteration (using the
   LOOP COUNTER, not a separate persistent accumulator) reproduced
   retail's non-strength-reduced multiply exactly, even though cc1 still
   internally accumulates the counter-derived value -- confirmed via a
   4-file standalone reproducer sequence (see below) before touching the
   real function, isolating the loop-carried-accumulator trigger from
   the multiplication expression itself.

   Reproducers (`/tmp/multtest{2,3,4}.c` this session, pinned toolchain):
   `v1 * 0xAC` outside any loop, and even embedded in one-shot pointer
   arithmetic, matches retail. The SAME expression inside a loop where
   `v1` is a `+=`-accumulated induction variable does not; recomputing
   `v1` via multiplication from the loop counter each iteration does.

## Residue: a per-field operand-order mismatch in `addu`, resistant to source-level operand reordering

The entire inner field-init sequence (all sixteen field stores, in
retail's exact order) is CONTENT-correct after fix #2 -- same fields,
same values, same order, same `lw`/store instructions. What's left: for
every field access, retail encodes `addu $v0,$a0,$v0` (colOff first
operand, row-base second) where this build encodes `addu $v0,$v0,$a0`
(row-base first, colOff second) -- same two registers each time (`$a0`
for `colOff`, `$v0` for the freshly-loaded `*rowPtr` value, both
confirmed identical across every instance), so this is NOT the
register-identity class seen elsewhere this round; it is purely which
operand slot (`rs` vs `rt`) the encoder chose for a commutative `addu`.

**Confirmed NOT reachable by swapping the C source's operand order**:
rewriting every field access from `(u8 *)(*rowPtr) + colOff` to `colOff
+ (u8 *)(*rowPtr)` (15 sites, mechanical) produced a byte-IDENTICAL
build to before the change -- cc1 canonicalises pointer+integer addition
to a fixed internal order regardless of which operand was written first
in source. This matches the documented residue class "prologue callee-
save stores in the wrong order... not reachable from C" in
`docs/MATCHING-GUIDE.md`, generalised here to a commutative pointer
addition instead of a register save.

**A second experiment -- reintroducing a per-outer-iteration copy of
the row pointer** (`curRow = rowPtr;` at the top of each outer
iteration, mirroring an EXTRA `move` instruction retail has at the
equivalent point that this build lacks) -- was tried on the theory that
retail's source uses a fresh copy inside the loop rather than the
persistent pointer directly. It regressed catastrophically (5/120,
whole-function restructuring) by adding register pressure; reverted
immediately. Not a viable lever here, unlike the analogous "reset a
pointer inside a loop" fix that worked for `func_8003221C`'s first loop
-- the difference is that fix there had a REAL semantic purpose (a
loop-invariant base pointer that itself is not otherwise touched by the
loop), whereas here `rowPtr` already IS what would be copied, so the
"copy" is genuinely redundant and just adds a live range.

The `D_80090B68`/`D_80090B6C` reload-based loop-2 setup (register
choice for the persistent row-pointer: `$t1` in retail vs `$a1` in this
build, plus instruction-scheduling differences in where `move a3,zero`
/ `li t0,0x7f` land relative to the sign-extension) is a separate,
smaller residue on top of the operand-order one, not further
investigated once the operand-order class was identified as the larger
and non-reshapeable blocker.

## Answering the head's question: did the register-count screen influence where this stopped?

No. The screen reported 0 callee-saved registers for this function
(the best possible band), and it was never a factor. What actually
consumed the attempt budget was STRUCT-SHAPE reconstruction (16 field
offsets across 3 field widths, derived purely from store instruction
widths and immediate values, no existing struct to reference) and the
induction-variable/constant-multiplication investigation, which required
building and testing 4 standalone reproducers under the pinned toolchain
to isolate the actual trigger before touching the real function. Those
were both worthwhile costs -- the multiply fix alone took the function
from 5/120 to (post the do-while fix) 60/120. What stopped further
progress was a genuine operand-order residue that resisted the one
source-level lever available (operand reordering, confirmed inert) plus
one register-pressure experiment that regressed. This matches the
project's documented "not reachable from C" residue class, not a
register-count-driven abandonment.

### Proposed learning

1. `for (i = 0; i < n; ...)` can compile to a redundant DUPLICATE range
   guard (upfront skip-check AND a bottom-of-loop re-check of the same
   condition) under this compiler; an explicit `if (n > 0) { ...
   do-while ... }` guard eliminates the duplicate. Already known for
   early-return guard clauses (`SetRCnt` family); this confirms it
   applies equally to loop TRIP-COUNT guards, a different C shape.
2. A loop-carried `+=`-accumulated induction variable multiplied by a
   compile-time constant gets strength-reduced by cc1 into a running
   accumulator, changing the instruction sequence from the "expected"
   shift/add/sub constant-multiply expansion into something shorter and
   structurally different. If retail's disassembly shows the FULL
   expansion happening fresh every iteration (not an accumulator), the
   source likely recomputes the multiplicand from the loop COUNTER each
   iteration (`v = i * step`) rather than accumulating it
   (`v += step`), even though both are semantically identical -- the
   counter-multiply form doesn't trigger the same strength-reduction on
   the SEPARATE constant-multiply expression. Confirmed via isolated
   reproducers under the pinned toolchain before touching real source;
   recommended default technique for any "array of structs with
   confirmed constant stride, computed inside a loop" pattern.
3. A commutative pointer+offset addition's ENCODED operand order
   (`addu $d,$a,$b` vs `addu $d,$b,$a`) is a cc1-canonicalised property,
   not controllable by writing the C addition in either operand order --
   confirmed by a mechanical no-op edit across 15 sites. Add this to the
   "not reachable from C" residue list alongside prologue save order.

## Round 19 verification and follow-up (runner charlie)

Per the head's mid-round drift-check broadcast: rebuilt this report's
exact 60/120 body and confirmed via `objdump` the function compiles to
exactly 120 instructions, matching retail's length, with no
outside-range drift from `funcdiff.py`. **Recorded score is real and
survives the check.**

Picked up the report's own "not further investigated" thread: the
loop-2 setup's register choice (retail computes the row-pointer base
into `$t1` first, THEN `move`s it into `$a1`; this build computes it
directly into `$a1`, no intermediate register or extra `move`). Tried a
bare `__asm__("")` barrier immediately after `rowPtr = D_800902E8;` on
the theory that it might force a real intermediate register the way it
has elsewhere in this project -- **no effect at all, byte-identical
60/120**. This is consistent with the barrier only affecting
instruction ORDER, not register SELECTION (CLAUDE.md's own test for
when a barrier is the right tool) -- the residue here is which
register cc1 picks, not where an instruction lands, so a barrier was
never going to move it. Reverted; not a new lever. The operand-order
class (`addu $v0,$a0,$v0` vs `$v0,$v0,$a0`) that dominates the visible
diff is a downstream CASCADE of this one unresolved register-choice
defect (every field-store `addu` inside the loop references the same
swapped operand roles), not sixteen independent instances of the
"not reachable from C" class -- worth knowing if a future attempt is
tempted to treat each `addu` site as its own experiment.

**Also checked against this round's aggregate-assignment lever
(runner alpha's finding, broadcast mid-round): this function's field
inits are NOT a same-type struct-to-struct copy** -- each field is set
to a DIFFERENT literal (`0`, `0xFF`, `0x7F`) rather than copied from a
matching source struct, so there is no whole-struct assignment to
substitute for the field-by-field sequence. The lever does not apply
here; noted for completeness, not tried.
