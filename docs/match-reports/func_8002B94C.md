## What it computes: this is PS1's `CD_newmedia`

Confirmed by the rodata strings (`asm/data/120C.rodata.s`): `"CD_newmedia:
Read error in cd_read(PVD)\n"`, `"CD001"` (the ISO9660 standard identifier),
`"CD_newmedia: Disc format error..."`, `"CD_newmedia: Read error
(PT:%08x)\n"`, `"CD_newmedia: sarching dir..\n"` [sic, retail's own typo],
`"\t%08x,%04x,%04x,%s\n"`, `"CD_newmedia: %d dir entries found\n"`. This
reads the CD's Primary Volume Descriptor (PVD), validates the "CD001"
signature, then walks the root directory's ISO9660 directory-record chain,
populating a 128-entry directory table (`D_8008B9F4[]`, this unit's own
local view of `code_179d8_d.c`'s already-matched `Entry8008B9F4` struct)
that `func_8002BC40`/`func_8002B640` (this same pass) search by name. Called
by `func_8002B640` (`CdSearchFile`) whenever its directory-cache generation
number is stale.

1. `func_8002BFA8(1, 0x10, D_8008CFF0)` (matched, `code_179d8_d.c`) reads
   sector 0x10 (the PVD) into the `D_8008CFF0` scratch buffer; must return 1.
2. `func_8002C0AC(D_8008CFF0+1, "CD001", 5)` validates the standard
   identifier at PVD offset 1; must be zero (match).
3. Reads a 4-byte field from `D_8008D07C` (an UNALIGNED access inside the
   byte-packed PVD structure — the same `lwl`/`lwr` idiom CLAUDE.md
   documents, reproduced here via a local alignment-1 struct type, see
   below) — this is the root directory record's extent LBA. Re-reads that
   same sector via `func_8002BFA8(1, lba, D_8008CFF0)`; must return the
   SAME value as step 1's call (both should be 1 — this reuses the
   register/variable from step 1 rather than a fresh literal, confirmed via
   `objdump`: the compare is `beq v0,s1` against the FIRST call's result,
   not a fresh `li`+compare).
4. Walks the ISO9660 directory record chain starting at `D_8008CFF0`
   (reused as a scan cursor once the setup succeeds): each record's first
   byte is its length (0 terminates the list); writes `D_8008B9F4[i].unk4`
   (an unaligned 4-byte field from record+2 — the extent LBA again, this
   time per-entry), `.id` (a byte from record+6 — file/directory flag byte),
   and `.name` (copied via `func_8002C014`, matched, from record+8, length
   = record's own name-length byte, NUL-terminated). Also writes
   `D_8008B9F0[i] = i+1` — a SEPARATE table, 4 bytes before
   `D_8008B9F4` and NOT part of that struct (per `code_179d8_d.c`'s own,
   already-matched reading, where `D_8008B9F4` itself is the struct's
   `.id` field) — holding this function's own 1-based record ordinal.
   Advances the cursor by the ISO9660 record length rounded up to even,
   plus 8. Stops at 128 entries or when the cursor reaches `D_8008D7F0`
   (an address-only bound, borrowed from a symbol other units type
   locally for their own purposes).
5. Zero-terminates the table at the stopping point (`D_8008B9F4[count].id
   = 0`, matching `func_8002BC40`'s own empty-slot check), clears
   `D_8006D938`, and returns 1.

Every diagnostic print is gated behind `D_8006D608` (0 = silent, >=1 =
errors, >=2 = verbose per-entry trace) — same verbosity convention as
`func_8002B640`.

## What went right on the first pass

- **Both unaligned 4-byte accesses (the PVD LBA read and the per-record
  extent-LBA read) matched exactly, first try**, using a local

  here to generalize to an ARBITRARY misaligned 4-byte value, not just a
  struct member.
- **The magic `i * 0x2C` multiply** (shift-add sequence: `t=i*3; t=t*4;
  t=t-i; t=t*4`) reproduced exactly from plain C multiplication
  (`count * 0x2C`), no manual shift-add needed — consistent with this
  project's established finding that GCC 2.6.3's small-constant-multiply
  strength reduction is faithfully reproducible from ordinary `*`.
- **The register threading across `func_8002BFA8`'s two calls**

## The two-word length gap: two identified, mostly-unresolved causes

Confirmed via `tools/asm-differ/diff.py`, isolating lines with NO
counterpart on either side from the (much larger) set of register-rename
and drift-induced address markers:

1. **One extra saved register** (this build saves `s0`-`s6`, 7 registers;
   retail saves `s0`-`s5`, 6). Tried collapsing two single-use locals
   (`pad`, `recSize`) into one inline expression — this INCREASED the
   compiled length by one more word instead of reducing it (191 -> 192),
   so reverted; the extra register is not simply "too many named
   temporaries," and no combination tried freed it. This is the dominant
   residue and the most likely place a further attempt should start,
   but no working lever was found this session.
2. **A genuinely redundant re-read of the scan cursor's first byte is
   present in retail but absent here.** Immediately before the loop's
   real emptiness check (`lbu $v0,0($s1)` feeding the real `beqz`),
   retail has an EARLIER, separate `li $v0,0x1` / `beqz $v0,<same
   target>` (provably always false — a dead check, same class as
   `func_8002A75C.md`'s "provably-redundant constant re-materialization"
   finding) immediately followed by ANOTHER `lbu $v0,0($s1)` / `nop` /
   `beqz` pair before the loop body actually starts. **Tried reproducing
   the dead check directly** (`if (result2 == 0) goto emptyList;`, with
   `emptyList:` placed at the loop's own exit point) — GCC's own
   dead-code elimination proved this condition false at compile time
   (from the two already-checked `!= 0`/`!= s1` guards earlier) and
   removed it entirely, exactly reproducing this build's ORIGINAL
   omission rather than retail's kept check. This confirms the check is
   NOT foldable from a literal in the way I tried — whatever retail's
   source did to keep it alive is not a plain `if (constant)`.
3. **A related but distinct issue near the pad/record-size computation**:
   retail computes `andi $v0,$v1,1 / addiu $v0,$v0,8 / addu $v1,$v1,$v0`
   as one contiguous block right after the length byte's SECOND use; this
   build's compiled output has the equivalent `andi` at a DIFFERENT point
   in the instruction stream (paired with the `func_8002C014` call setup
   rather than immediately after the NUL-terminate store). Not
   root-caused before time ran out — flagged as the next concrete lead

### Redundant-raw-copy-elision investigation (this round's assigned question)

Residue 2 above (the dead check + the doubled cursor re-read) is this
function's own instance of the class this round investigated: GCC proved a
comparison always-true/false at compile time and removed BOTH the check
AND a load that retail's own compiler evidently could NOT prove redundant
in the same way (or chose not to fold even if it could). This is slightly
different in kind from the OTHER instances found this round
(`func_8002AEE0`, `func_8002B640`, and the three `code_179d8_l` reductions)
in that it is not a `__asm__("")`-testable scheduling residue at all —
it is a DEAD-CODE-ELIMINATION difference, not an instruction-ordering one,
so the barrier was never even applicable here (confirmed by trying the
direct C reproduction and watching GCC eliminate it regardless). See the
shared writeup in `docs/match-reports/func_8002AA6C.md` for the round's
overall mechanism-level answer.

### Proposed learning

**A "provably redundant" residue is not always a scheduling question the
`__asm__("")` barrier could address even in principle** — when the
redundancy is in whether a BRANCH/CHECK exists at all (not merely where an
already-scheduled instruction sits), GCC's own dead-code elimination at
-O2 will remove a directly-reproduced `if (constant)` check regardless of
barriers, because DCE runs on a proven-constant condition independently of
instruction scheduling. If retail keeps such a check, the original source
expression must not have been immediately foldable to a literal by this
compiler — i.e. it depended on something not statically resolvable from
the two lines the redundant read happens to be adjacent to. Chasing this
further needs a source expression that is NOT a plain `if (knownconst)`,
not a barrier.
