## Original report

# func_800293F8

**Unit:** code_179d8_b · **Size:** 32 instructions · **Status:** MATCHED (32/32 words)

## What this function does

CD-ROM MSF (minute/second/sector-in-frame) timecode to absolute sector
(LBA) conversion, the classic `((min*60+sec)*75+frame)-150` idiom. The
argument is a pointer to three packed-BCD bytes at offsets 0/1/2 (named
`MSF179D8` locally in this file — no shared header, per the unit's own
convention). Each byte decodes as `(byte>>4)*10 + (byte&0xF)`.

## The C

```c
typedef struct {
    u8 minute;
    u8 second;
    u8 sector;
} MSF179D8;

s32 func_800293F8(MSF179D8 *arg0)
{
    u8 minute;
    u8 second;
    s32 decodedMinute;
    u8 sector;
    s32 total;

    minute = arg0->minute;
    second = arg0->second;
    decodedMinute = (minute >> 4) * 10 + (minute & 0xF);
    total = decodedMinute;
    total = total * 60 + ((second >> 4) * 10 + (second & 0xF));
    sector = arg0->sector;
    return (total * 75 + ((sector >> 4) * 10 + (sector & 0xF))) - 150;
}
```

`char` is unsigned on this target (`-funsigned-char`), so the BCD byte
fields are plain `u8`; a signed byte load would emit `lb` instead of
retail's `lbu`.

## Derivation, and why the permuter was the right tool here

Debug-mode confirmed early that this was a **pure register-identity
residue, never a shape defect**: `--debug` on every seed variant reported
`Reorderings: 0, Insertions: 0, Deletions: 0` — only `Register
Differences`. That's exactly MATCHING-GUIDE's criterion for reaching for
the permuter rather than continuing to hand-reshape.

The naive translation (`total = (minute>>4)*10+(minute&0xF); total =
total*60 + decode(second); ... total = total*75 + decode(sector); return
total-150;`) has a real structural bug, not just a residue: GCC sinks the
`second` byte's load down to just before its first use instead of keeping
it adjacent to `minute`'s load, so retail's delay-slot-filling pair (`lbu
v1,0(a0)` / `lbu a2,1(a0)`, no `nop`) becomes `lbu v1,0(a0)` / `nop` — a
genuine extra instruction, confirmed via `objdump -d build/src/....o`
against a bare toolchain reproducer (`tools/gcc263/cpp | cc1 | maspsx |
as`) before ever touching the real file. That's the "extra word" class,
not the "same length, different registers" class, and the two need
different tools.

**A bare `__asm__("")` scheduling barrier fixed the extra-instruction
shape** (pins the two loads adjacent, matching retail's word count
exactly, verified via the toolchain reproducer first) **but failed
CLAUDE.md rule 6's own test**: removing it changed WHICH register held
`minute`'s raw byte (`$v1` without the barrier, `$a1` with it) — not just
instruction order. That is explicitly the banned case, so the
double-barrier form (10/32, correct length, wrong registers throughout)
was rejected as a candidate fix, not just as an imperfect one.

**The permuter, seeded with that rejected (but zero-insertion/deletion)
near-miss, found the actual fix in under 7000 iterations, twice**:

1. First pass (score 205 → 0 not reached in this seed, best 55/15) found
   that hoisting the minute-decode into its own named local
   (`decodedMinute`), computed as its own statement immediately after the
   two loads, gets the compiler to place both loads adjacently ON ITS OWN
   — no barrier needed at all for that half. Re-seeding with this
   (barriers still present for the tail) dropped the base score from 205
   to 135 and matched retail's first 18 instructions exactly.
2. Second pass (score 135 → 0 in 9 iterations) found the remaining
   residue was **not a register problem at all**: `diff.txt` showed the
   mutation was merging the trailing `total = ...; return total - 150;`
   into a single `return (...) - 150;` expression. Once applied, BOTH
   `__asm__("")` barriers turned out to be unnecessary — removing them
   still scores 32/32 (verified: `funcdiff` and the whole-image SHA1 both
   green with the barriers deleted), so the final C carries none.

## Residue class

Genuinely two entangled issues that read as one when only inspecting the
byte diff: an instruction-count defect (load scheduling) fixed by
restructuring which sub-expression gets its own named local, and (after
that was fixed) a pure register-identity residue whose actual cause was
**statement count**, not register choice — merging `total = ...; return
total - 150;` into one `return` statement removed a `move` the two-
statement form was forcing into a callee-saved register. This is a
DIFFERENT flavour of the project's "redundant move" family
(DECOMPILATION_LEARNINGS' "count how many times your SOURCE mentions the
value") — here the mentions were of `total` specifically at the function's
very end, not mid-body.

### Proposed learning

**A load that GCC 2.6.3 sinks away from an adjacent sibling load (costing
a real instruction via an unfilled load-delay slot, not just a scheduling
cosmetic) can sometimes be pinned back into place by hoisting its
CONSUMING expression into its own named local computed as the very next
statement — with no `__asm__("")` barrier at all.** Tried before reaching
for a barrier, this is strictly cheaper (no register-identity risk per
rule 6) and worked here for the `minute`/`second` adjacent-byte-load pair.
Only reach for the barrier if this doesn't fix the count, and then apply
CLAUDE.md rule 6's test before keeping it — it may still fail that test
(as it did here) and point to a further restructuring instead.

**When a permuter zero comes from merging a trailing `x = expr; return
x;` into `return expr;` (or vice versa), and it changes REGISTER IDENTITY
rather than instruction count, that's the "how many times does the source
mention the value" family from DECOMPILATION_LEARNINGS — worth checking
this shape specifically before accepting a two-statement tail as
idiomatic. It also often makes a previously-necessary scheduling barrier
elsewhere in the function unnecessary, so re-test without barriers once a
new merge-based fix lands rather than assuming they're still needed.**
