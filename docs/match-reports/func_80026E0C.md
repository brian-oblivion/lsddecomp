# func_80026E0C

**Unit:** code_171e0 · **Size:** 11 instructions · **Status:** STALLED, class TOOLCHAIN (0/11 words at time of stall; see below)

## Residue — this is a TOOLCHAIN finding, not a source-shape one

Retail's access to `D_8008A84C` is a single instruction:

```
lw    $v1, %gp_rel(D_8008A84C)($gp)
```

Writing the obvious C (`extern s32 D_8008A84C; if (D_8008A84C == 0x13) ...`)
compiles under this project's pinned flags to a **two-instruction absolute
load** instead:

```
lui   $v1, %hi(D_8008A84C)
lw    $v1, %lo(D_8008A84C)($v1)
```

Same value, wrong instruction count — an unrecoverable size mismatch (not a
residue you can reshape away), and it also shifts every function's address
after it in the unit.

**Root cause, isolated with the pinned reproducer** (CLAUDE.md "Escalate, do
not experiment" — this was extracted to a standalone `.c` and run through the
exact pinned `cpp | cc1 | maspsx | as` pipeline, nothing about the project's
own flags was touched):

- `cc1`'s `%gp_rel` addressing for a symbol comes from cc1 itself emitting
  either `.sdata`/`.sbss` (for objects *defined* in the file) or an
  `.extern NAME, SIZE` hint (for objects merely *declared* `extern`) —
  **gated by cc1's own `-G` value**, which this project's `CC_FLAGS` pins at
  `-G0`. At `-G0`, cc1 never emits either, for any object, defined or not.
  Verified directly:
  ```
  # -G0 (this project's CC_FLAGS): no .sdata, no .extern hint, ever
  # -G8: cc1 emits ".sdata" for a same-file definition, or
  #      ".extern D_8008A84C, 4" for an extern declaration
  ```
- Once cc1 emits that hint (`-G8`), the rest of the pinned pipeline (same
  `maspsx --dont-force-G0 --expand-div`, same `as ... -G8`) reproduces
  retail's exact single-instruction `lw $v1, %gp_rel(D_8008A84C)($gp)` byte
  for byte. So the mechanism is well understood; only the `-G` value differs
  from what retail's own compilation must have used for this data.
- `AS_FLAGS`' own `-G0` is not the gate — gas with `-G8` on an object where
  cc1 already decided (at `-G0`) to use absolute addressing still produces
  the two-instruction form. The decision happens in cc1, not later.
- This is not a one-off: **14 of this unit's 26 `INCLUDE_ASM` entries**
  reference `D_8008A84C`, `D_8008A850`, or `D_8008A854` via `%gp_rel`
  (`grep -l gp_rel asm/nonmatchings/code_171e0/*.s`), so this blocks over
  half the unit's queue, not just this one function.

This is a toolchain/flags question (CC_FLAGS pins `-G0` project-wide per
CLAUDE.md rule 5), not something a runner is supposed to fix by changing
pinned flags. Escalating with this reproducer rather than experimenting
further.

## Proposed learning

**Any `INCLUDE_ASM` whose disassembly shows `%gp_rel(D_sym)($gp)` for a
symbol outside your own unit's data is very likely blocked by the same
`-G0` issue, project-wide, not just in `code_171e0`.** Check with
`grep -l gp_rel asm/nonmatchings/<unit>/*.s` before spending attempts on any
such function — the fix is an operator-level toolchain decision (what `-G`
value reproduces retail's `.sdata` placement), not a per-function C reshape.
This is a strong candidate for a head-level investigation across the whole
project, since `.sdata` (file `0x7b008`, `0x7b3c0`, `0x7b3f8` per the splat
yaml) is shared/global — many other units almost certainly hit the exact
same wall.
