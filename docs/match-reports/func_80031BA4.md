# func_80031BA4 -- STALL (stack-argument-load scheduling residue, 57/61 words by position -- see note on alignment below)

Unit `code_179d8_j`, round 22 (2026-09-06). Not a class method. A
"compare-then-commit" function: verifies three `s16` fields of a
52-byte-stride record table against the caller's `p1`/`p2`/`p3`, and only
if ALL THREE match, writes two new `u16` values (`p4`, `p5`, passed on the
stack -- 5th/6th arguments) into a pair of 16-byte-stride tables and sets
two flag bits.

## What it is

```

{
```

`D_8008D994`/`D_8008D99A`/`D_8008D99E` are modeled as three independent
52-byte-stride arrays (same "own address computation per field" reasoning
as `D_8008D7F0`/`D_8008D7F2` in the `func_80031CF0` report -- this unit's
`func_8003069C`, not attempted this round, touches a fourth field of the
apparent same underlying struct at `D_8008D996`). `D_8008D7F8`/`D_8008D7FA`
are the same family as `D_8008D7F0`/`D_8008D7F2` (16-byte stride, offset
`+8`/`+0xA` from that base rather than `+0`/`+2`).

## The residue -- unusually narrow

Applying `func_80031CF0`'s two fixes here (an `s32 dead[2]` local written
only inside `if (0)` to reproduce the correctly-sized-but-empty 8-byte
frame, plus a leading `__asm__("")` and barriers between the three
post-verification writes) reaches the EXACT right length (61/61 words,
matching retail's `0xF4`) with the stack-argument loads landing at the
CORRECT displacement (`0x18($sp)`/`0x1C($sp)`, which only happens if the
local frame is genuinely 8 bytes -- confirms the frame fix is right here,
not just coincidentally sized).

**Every single instruction from the branch onward matches retail
byte-for-byte** (verified by walking both instruction streams in lockstep:
all three field comparisons, all three table writes, the flag OR, the
success/failure paths and the epilogue are identical, register-for-
register). The ENTIRE divergence is 4 instructions at the very top:

- Retail order: `addiu $sp,-8` / `andi` / `sltiu` / `lhu $t1,0x18($sp)` /
  `lhu $t2,0x1C($sp)` / `beqz`.
- Every reshape reached here: `addiu $sp,-8` / `lhu $t1,...` / `lhu
  $t2,...` / `andi` / `sltiu` / `beqz`.

Same four instructions, same registers, purely REORDERED as a block --
GCC schedules the two stack-argument loads (independent of the bounds
check) as early as possible, while retail's compile keeps them after.
Tried: a bare `__asm__("")` immediately after computing the bounds-check
condition (before referencing `p4`/`p5` at all), and explicit `u16 v4 =
p4; u16 v5 = p5;` locals placed textually after that barrier (to try to
anchor the loads' scheduling position) -- neither moved the loads' position
by even one instruction. This suggests the loads are materialized at
argument-reload time (function entry), before the scheduler's ordinary
list-scheduling pass runs, and are therefore NOT reachable by an ordinary
mid-body scheduling barrier.

This is the same STALL class as `func_80031CF0`/`func_80031DF8`
(delay-slot / instruction-scheduling choice, not register identity), just
narrower: 57 of 61 words match by raw position, and the other 4 are a
clean block-reorder of instructions retail also has, not a missing or
extra one.

### Proposed learning

**Stack-passed argument loads (5th/6th ABI slots and beyond) appear to be
materialized at a scheduling stage an ordinary mid-body `__asm__("")`
barrier cannot reach** -- neither a barrier placed before their first
reference nor an explicit early local capture (`u16 v4 = p4;`) moved their
position by even one instruction, in contrast to every other independent-
operation reordering seen elsewhere in this unit (all of which barriers DO
fix). If a future attempt wants to pursue this, the next axis to try is
whatever controls PROLOGUE-level argument reload order specifically,
not general instruction scheduling -- this may be a genuine toolchain
characteristic rather than a source-shape question, but has NOT been
verified in isolation through the pinned pipeline and should not be
escalated without that reproduction first.
