## Residue

One instruction, in the NULL/allocation-failure path only: retail sets the
return value with `addu $v0, $zero, $zero` (materializes the literal 0
directly from `$zero`); every version I could produce for the same C shape
instead emits `addu $v0, $s0, $zero` (copies the already-zero `$s0`/`self`
register). Both hold the same *value* (0) at that program point — this is
the "redundant move, same value, different register" residue class from
`docs/MATCHING-GUIDE.md`, just with the register roles reversed from that
class's usual description (here retail is the one avoiding an unnecessary
same-register copy, using the constant register instead).

Reshapes tried (all either reproduce the exact same 26/27 residue, or worse):
- `if (self != NULL) { ctor(...); } return self;` — 26/27, this residue.
- `if (self != NULL) {...} else { self = NULL; } return self;` — 26/27, same residue.
- `if (self != NULL) {...} else { ret = NULL; } return ret;` (separate `ret` local) — 26/27, same residue.
- Early-return guard clause (`if (!self) return NULL; ctor(...); return self;`)
  — **worse**: two return statements caused GCC 2.6.3 -O2 to emit two full,
  separate epilogues (stack restore + `jr $ra` duplicated) instead of the
  single shared one retail has. Confirmed by a 139671-byte out-of-range
  diff — a real size regression, not just a residue.
- `if/else` with a distinct `result` local reassigned in each arm, single
  `return result;` — **also worse**, byte-identical blowup to the guard-clause
  attempt, confirming the epilogue duplication is triggered by *any*
  additional control-flow split here, not specifically by an early `return`.
- Ternary with comma-expression (`return cond ? (ctor(...), self) : NULL;`)
  — **worse**, same blowup.

Only the single "if () {...} return self;" shape (one `if`, one trailing
`return`, `self` doing double duty as both the allocated pointer and the
return value) keeps the merged single epilogue that retail has. Within that
shape, no local reordering, intermediate variable, or NULL-reassignment
changed which register feeds `$v0` on the NULL path.

## Proposed learning

A single-instruction "same value, different register" residue can appear on
either side: usually it's *our* C emitting a redundant same-register copy
retail avoids, but here retail is the one substituting the constant register
for an already-zero variable, and the reverse substitution didn't fall out of
any reshape tried. Also: for this toolchain (GCC 2.6.3 `-O2`), introducing a
*second* `return` statement (guard clause, `if/else` with a shared trailing
return, or a comma-expression ternary) reliably duplicates the function's
entire epilogue rather than merging it with the existing one — a much bigger
tell than the single-word residue being chased, and worth checking for early
via the "size change outside range" warning before spending more attempts on
that family of reshapes.
