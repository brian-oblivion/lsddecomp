`0x1E8` bytes, and if that succeeds fetch the class's method table and call

## History: this was reported as a STALL, and the classification was wrong

The first pass reached 26/27 with

```c
	Class866E8 *self = func_80017B34(0x1E8);

	if (self != NULL) {
		Class866E8Methods *vt = func_8004D244();
		vt->ctor(self, arg0, arg1);
	}
	return self;
```

whose sole residue was retail's `addu $v0, $zero, $zero` (`move v0, zero`) in
the `beqz` delay slot against a built `addu $v0, $s0, $zero` (`move v0, s0`) —
same value, since `$s0` is NULL on that path. That was filed as a fourth
instance of the documented **"genuine redundant move"** class.

**It is not that class, and the discriminator is cheap to state.** The
redundant-move class is retail materializing a value the compiler would have
had for free — the two instructions are semantically interchangeable *given
the same source*. Here they are not: `move v0, zero` and `move v0, s0` come
from different **return expressions**. Retail has two of them (`v0 = 0` in the
delay slot, `v0 = s0` after the ctor call), which is positive evidence for a
source with two `return` statements, one of which returns a literal NULL. The
26/27 body has one `return self;`, and no amount of barrier or temp placement
can conjure a second return expression out of it.

That reframing is what makes it fixable. Four shapes were measured, all under
the pinned toolchain:

| shape | result |
| --- | --- |
| single `return self;` (the reported stall) | 26/27, `move v0,s0` in the slot |
| `if (self == NULL) return NULL;` early return | worse — GCC lays the NULL block *after* the body and needs a `j` to skip it, +1 instruction |
| `if/else` with `ret = NULL;` in the `else` | identical to the early return, same extra `j` |
| separate `ret` local assigned `NULL` before the `if` | **retail's exact instruction sequence**, but GCC allocates `ret` to `$v1` and adds a `move v0,v1` at the epilogue |

The fourth is the informative one: it proves the *structure* was reachable and
that only register allocation stood in the way. `ret` is assigned before the
branch, so its live range spans the two calls, so GCC keeps it out of `$v0`
(which the calls clobber) and pays for a copy.

The shape that wins gives the NULL path its own `return` without creating a
live range at all — and it was already in the tree, matched, in another unit.

## The actual lever: copy the shape from a matched instance of the same idiom

`func_80025B34` in `src/class_16334.c` is the same `New_X` wrapper — allocate,
NULL-check, dispatch the ctor through the class table, return the object — and
it has been matched since an earlier round using `goto fail;` with the
`fail: return NULL;` label last. Transplanting that shape verbatim took
func_8004A4C8 from 26/27 to a whole-image match on the first attempt.

### What the discriminator actually is: TEXTUAL POSITION, not `goto`

Runner alpha reached the same conclusion independently and from the other
direction in `code_2c054`, matching two `New_X` allocators (func_8003B854 at
36/36, func_8003BE94 at 31/31) with a `goto`-free spelling. Both shapes were
then measured against THIS function, and both give 27/27, whole-image green:

```c
	/* equivalent -- also 27/27 */
	self = func_80017B34(0x1E8);
	if (self != NULL) {
		func_8004D244()->ctor(self, arg0, arg1);
		return self;
	}
	return NULL;
```

So `goto fail;` is not load-bearing. **What matters is that `return NULL;`
comes textually LAST, after the success return.** Put it first --
`if (self == NULL) { return NULL; } ... return self;` -- and GCC 2.6.3 lays
the NULL block out after the body and pays a `j` to skip it. That is the
+1-instruction failure charlie and the head each measured separately, and it
is the whole content of the rule.

The `goto`-free form is the one left in the tree, since it is the better C and
the bytes are identical.

### Proposed learning

**Before classifying an allocator-wrapper residue, grep the tree for an
already-matched instance of the same idiom and copy its source shape.** The
project has ~60 class method tables and every class has a `New_X` wrapper, so
these are among the most repeated function shapes in the executable — the
first one matched pays for all the rest, but only if the next person looks for
it instead of reasoning forward from the residue.

**And a discriminator for the "genuine redundant move" class, which this was
misfiled under:** that class requires the two instructions to be
interchangeable *given the same source*. Two different constants or two
different source operands mean two different return expressions, which is a
source-shape question, not a toolchain one. `move v0,zero` vs `move v0,s0` is
the second thing, not the first.
