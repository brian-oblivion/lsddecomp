## A genuine miscompile-shape residue, not a stall -- read this before touching any other `New_X` wrapper in this project

This function's FIRST attempt was the more "natural"-looking C:

```c
StreamTask *self = func_80017B34(0xDC);
if (self != NULL) {
    func_8003BE84()->ctor(self, a0, a1, a2, a3);
}
return self;
```

This compiles to the RIGHT SIZE (36 words) but the WRONG delay-slot
content at the `beqz` guarding the ctor call: GCC computes `v0 = self`
(`move v0,s0`) in that slot (semantically fine, since `self` is null on
that path anyway), where retail has `move v0,zero`. A SECOND attempt using
an early return --

```c
StreamTask *self = func_80017B34(0xDC);
if (self == NULL) {
    return NULL;
}
func_8003BE84()->ctor(self, a0, a1, a2, a3);
return self;
```

-- compiles to 38 words (TWO TOO MANY): GCC 2.6.3 places the null case's
`move v0,zero` as a separate block AFTER the ctor-call block and needs an
extra unconditional `j` for the ctor-call path to skip over it, rather
than falling straight through. Neither shape matches. The shape that
does -- confirmed both via the toolchain reproducer
(`tools/gcc263/cpp | cc1 | maspsx | as`, see CLAUDE.md's "Escalate, do not
experiment" pipeline) and via the real build -- is `return self;` placed
**INSIDE** the `if`, with an explicit `return NULL;` after the block, as
shown above. This is the ONLY one of the three that reproduces retail's
exact instruction sequence: `move v0,zero` in the `beqz` delay slot (a
literal, not a copy of `s0`), then a single `move v0,s0` right before
falling into the shared epilogue, with no extra jump.

### Proposed learning

For the "`malloc; if (ptr) { ctor(ptr, ...); } return ptr;`" `New_X`
shape (CLAUDE.md's "Writing a class method" allocation pattern), GCC
2.6.3 -O2 wants the return-on-success **inside** the `if` block and an
explicit `return NULL;` (or `return 0;`) as the function's trailing
statement -- NOT a shared `return self;` after the `if`, and NOT an early
`if (!ptr) return NULL;` guard before the constructor call. Try this
shape FIRST for any `New_X` allocator in this project; the other two
"obvious" shapes both fail, in opposite directions (one wrong-content,
one two-words-too-long). Confirmed again by func_8003BE94 in the same
unit (identical shape, identical fix). Given `docs/PARALLEL-RUNS.md`
already names `new_class_6d3c8` as the first permuter target for this
exact `New_X` shape, this specific residue is worth cross-checking there.
