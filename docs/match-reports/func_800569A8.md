## Findings that closed real distance (119 of 120 words, from a from-scratch
implementation)

### 1. `&D_8008780C[self->unk70]` must be cached in a local BEFORE the first call, not re-indexed

The bounds-check ordering (`self->unk6C != 0`, then `D_8008780C[unk70] !=
0`, then `self->unk24 < 0x1F5`) matches a plain sequence of nested `if`s.
But naively re-writing `D_8008780C[self->unk70]` at each of its three uses
(the guard, inside the loop, and the final division) forced a fresh
address recomputation after the intervening `self->methods->slot44(...)`
call, since GCC cannot prove a struct field survives an opaque call.
Retail computes the pointer ONCE (into a register that survives the call)
and reuses it inside the loop, only reloading fresh for the FAR-AWAY final
division. The fix needed an explicit local pointer (`tab70`) assigned
right where retail's own address computation sits, used only inside the
loop -- and a SEPARATE local (`idx = self->unk70;`), computed BEFORE even
the outer `self->unk6C != 0` check (unconditionally, at the very top),
since retail loads `self->unk70` eagerly alongside `self->unk6C` in one
pair before the first branch. Skipping either half of this (caching just
the pointer, or just the index) reproduced only PART of retail's register
set and cascaded into a whole-function register renumbering (`s2`
becoming `s1` throughout) -- a single added or removed local anywhere in
this function visibly shifts which physical register `self` itself lives
in, confirmed by reverting one variable at a time.

### 2. The volume-pan-style stores duplicate; the modulus check does NOT share a division

Two different generalizations of "shared code" pulled in opposite
directions here, and getting the DIRECTION right for each mattered:

- The per-branch stores in this unit's earlier `func_80056858`/sibling
  functions duplicate identical instruction pairs across branches rather
  than merging through a shared local (already documented in
  `code_179d8_j`'s reports as a general GCC 2.6.3 tendency). This function
  has none of that shape itself, but the SAME "do not assume merging" bias
  applies to point 2 below.
- **The `divq < 0 ? -divq : divq` absolute-value idiom must NOT be
  factored into one shared division.** A clean `u32 udivq = (divq < 0) ?
  -divq : divq; if (self->unk24 % udivq == 0) ...` compiles to ONE `divu`
  reached from both branches via a shared join -- correct C, wrong shape.
  Retail duplicates the ENTIRE `divu`/`mfhi`/trap-check/`bnez` sequence
  inside BOTH the `divq < 0` and the `divq >= 0` arms independently (two
  separate `divu` instructions, two separate remainder checks, two
  separate calls to `func_80056858`), which only a literal `if (divq < 0)
  { ... } else { ... }` with the modulus check REPEATED in each arm
  reproduces.
- **The negation itself must be spelled `~divq + 1`, not `-divq`.** A
  plain `-divq` (or `(u32) -divq`) compiles to a single `subu`/`negu`
  instruction; retail's negative arm is `nor $v0,$zero,$a0` (bitwise
  complement, computed UNCONDITIONALLY in the `bltz` branch's delay slot,
  before either arm is chosen) followed by `addiu $v0,$v0,1` only inside
  the taken arm -- i.e. `~divq` first, `+1` second, as two separate
  instructions matching two separate C-level operations. Writing
  `u32 adivq = ~divq + 1;` inside the `divq < 0` arm reproduced this
  exactly.
- **`self->unk24` needs to be cached in a local (`modend`) before the
  branch**, not re-read from the struct in each arm -- retail loads it
  ONCE (`lw v1,0x24(s2)`, right after the `mflo` that produces `divq`) and
  reuses that register in BOTH arms. Reading `self->unk24` fresh inside
  each `if`/`else` body compiled an extra, duplicate load.

## NOT CLOSED: two residues, 1 word and otherwise pure register identity

- **The `&D_8008780C[idx]` pointer computation's TWO temp registers are
  swapped** (`v0`/`v1` hold the shift-result and the base address in the
  opposite roles from retail), and this swap propagates: the register that
  ends up holding the cached pointer is `s4` here versus `s1` in retail (an
  arbitrary consequence of which temp got promoted to a saved register
  first), which in turn flips the loop counter's identity (`s1` here,
  `s3` in retail) and the accumulator's. Tried: `tab70 = D_8008780C + idx;`
  (pointer-arithmetic form instead of `&D_8008780C[idx]`) -- byte-identical
  output, no effect. This is the same class of "commutative operand order,
  not independently reachable" residue documented at length in
  `code_179d8_j`'s `func_80031280` report, which needed the permuter (a
  type-width fix, not an operand reorder) to close a superficially similar
  case -- see below.
- **The `divq < 0` guard's branch polarity is flipped** (`bgez` here where
  retail has `bltz`, i.e. my compiled code makes the `divq < 0` arm the
  JUMP target and `divq >= 0` the fallthrough, the reverse of retail's
  layout). Tried swapping the C-level `if`/`else` order (put the `divq >=
  0` arm first, textually) -- this is the OPPOSITE of what fixed similar
  polarity residues elsewhere and it made the match WORSE (18/121 versus
  23/121), confirming per `code_179d8_j`'s "the arm that must jump" lesson
  that neither ordering is reliably predictable from source alone for this
  construct.
- A `for`-loop-to-`while`-loop rewrite of the `arr7C` loop (moving `i = 0;`
  before `p = self->arr7C;` to try to match a small instruction-order
  difference in the loop's own prologue) also regressed the score (16/121)
  and was reverted.

### Proposed learning

**A newly-discovered vtable slot one word off from an already-established
one (here, `slotBC` at +0xBC immediately after `slotB8` at +0xB8) is easy
to misassign as the wrong slot rather than a missing one, because the
resulting compile error is silent -- it's not a type error, just a
one-word-short function with an otherwise-plausible-looking call.** The
tell was the exact SIZE deficit (short by exactly the words a whole call's
worth of `lw ... jalr` sequence would NOT explain) combined with cross-
checking the raw hex offset in the `.s` (`0xbc` vs the struct's declared
`0xb8`) rather than trusting that "the call looks the same shape as an
already-matched sibling's" meant it used the same slot.

**Confirmed again in a second, unrelated function: adding or removing ANY
local variable in a function already close to its final register
allocation can renumber EVERY saved register in the function, including
the one holding `self`/`this`.** This was already documented for
`code_179d8_j`'s functions this round; here it recurred in a completely
different unit and class, on a much smaller function (121 words, versus
that unit's 250+-word functions), which argues this is a general GCC
2.6.3 allocator property rather than something specific to large or
call-heavy bodies.
