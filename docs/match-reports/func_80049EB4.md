## The jump-table question, now MEASURED rather than asserted

This report's original claim -- that the blocker "covers every jump-table
switch, not just indexed arrays" -- was correct, but it rested on reading
CLAUDE.md rather than on evidence, and it is the kind of claim a later reader
naturally doubts: a jump table loads a CODE address and jumps to it, an
indexed global loads a DATA value, and nothing in the disassembly connects
them.

Round 10's head doubted it, "corrected" the screening grep to exclude
`%lo(jtbl_*)`, reclassified this function as ordinary ground, broadcast the
correction to five live runners, and then measured it and had to retract all
of it. The measurement:

```
cc1 output, indexed global:      lbu $2,D_80089EAC($4)
cc1 output, switch jump table:   lw  $2,$L13($2)
```

The same generic pseudo-op. cc1 expresses no opinion about addressing; the
folding happens in maspsx, below cc1, which cannot tell the two apart. Run a
dense 10-case switch through the pinned pipeline and it comes out FOLDED
(three instructions) where retail has the UNFOLDED four -- the blocker,
exactly.

So this function is blocked, and the reason is now reproducible in under a
second rather than inherited. **Do not reclassify it again without running
that reproducer first.**

## Proposed learning

A blocker's SCOPE is measured, not reasoned. This one covers two constructs
that share nothing visible in the disassembly and everything in the pseudo-op
cc1 hands to maspsx. Promoted to CLAUDE.md under "Open toolchain blockers".
