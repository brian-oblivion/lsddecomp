## Derivation

Same shape as `func_8005A700` (immediately preceding, this runner's), but
its link lookup goes through `func_8005BE90` instead of `Test4TunnelLinks`.

**The one real trap, worth flagging for future runners on this file:**
`func_8005BF48` is called with a bare `nop` in its `jal`'s delay slot --
retail sets up NO arguments for it. The `$a0`-`$a3` register writes that
immediately follow the call (`this`, `result`, `0x10`, `0`) are argument
setup for the *following* `ExecuteLink` call, not for `func_8005BF48`.
Reading the raw `.s` linearly, it is easy to misattribute those four
register writes to the call directly above them instead of the call below.
The tell is the delay slot: a real 4-argument call to `func_8005BF48` would
put its own last argument in the delay slot, not a `nop`. The first attempt
here declared `func_8005BF48` with a false 4-argument signature; GCC then
emitted real `move`/`li` argument-setup code immediately before that call
(since the arguments genuinely were live registers at that point, just not
this call's own), growing the function by two words and cascading a
~136KB-of-drifted-bytes false read on every downstream function until
caught by `build-and-verify.sh`'s whole-file SHA1 (never trust a
per-function funcdiff read while its "differs outside this range" warning
is nonzero -- this is CLAUDE.md's rule 3 in the "three ways a score lies"
list, encountered live here).

`func_8005BE90` is typed straightforwardly from its own register setup
across two calls in this runner's range (`func_8005A700` calls the sibling
`Test4TunnelLinks` with the same `(target, currentPos, stage)` shape,
reinforcing the parameter identification).

`this->unk_0x880` was `s8 unknown_values_0x880[4]`; retyped to `void *` in
`include/DreamSys.h` since `func_8005BF48` returns either `NULL` or

## Proposed learning

- **A `jal` whose OWN delay slot is a bare `nop` takes no arguments from the
  surrounding register writes** -- any `$a0`-`$a3` setup adjacent to such a
  call belongs to a DIFFERENT call (usually the next one down). Declaring a
  false argument count for it makes GCC synthesize real setup code for the
  false arguments, which is silently plausible (it compiles, it is even
  correct C in the sense that the registers do hold those values) but grows
  the function and cascades a false-full-match read into every function
  after it in the unit, masked until the whole-file SHA1 is checked. Worth
  promoting to DECOMPILATION_LEARNINGS.md's residue list: the discriminator
  is the delay slot instruction of the specific `jal` in question, not
  "these registers are set near this call."
