## Residue

Retail loads `arr[0]` and `arr[1]` together at function entry (both `lw`
back to back, before any branch) -- reproduced exactly (words 0-11 byte
identical, including the "default value, then conditionally negate" delay-slot
idiom for both).

From `arr[2]` onward, retail's pattern per element is:

```
lw   v0, N(a0)      ; fresh load into v0 (scratch)
nop
bgez v0, L
 move v1, v0         ; delay slot: unconditional copy into v1 (the "candidate" register)
negu v1, v1          ; only reached if v0 was negative
L:
slt  v0, a1, v1      ; a1 = running max
...
```

The body above instead loads DIRECTLY into v1 (skipping the v0 stage) for
every element from `arr[2]` on -- i.e. it reaches the SAME final value with
one fewer `move`. This is a genuine per-element instruction COUNT difference
(insertion/deletion), not a pure register swap: `permuter.py --debug` on
this exact body reports "Register Differences: 10, Reorderings: 1,
Insertions: 5, Deletions: 5" (base score 1110), confirming it is 5 elements
each missing one `move`, not a renaming problem.

## Attempts (4, all failed to move past 33/50)

1. Natural single-`v`-reused body above: 33/50, matches through `arr[1]`'s
   comparison, diverges starting `arr[2]`'s load.
2. Renamed each iteration's temp to a distinct local (`v1`..`v5`, no reuse):
   WORSE (30/50) -- rules out "shared register across iterations" as the
   cause; the compiler still coalesces them.
3. Wrapped each of the `arr[2..5]` iterations in its own `{ }` block with a
   block-scoped local: no change at all (30/50, identical bytes to attempt
   2) -- rules out block scoping as a lever here.
4. Permuter (`tools/setup-permuter.sh`, no `PERM()` macros, pure
   randomization since nothing directed which axis to explore): ~10,000
   iterations, never reached a lower score than the manual 1110 base and
   frequently produced broken (non-compiling) candidates. Abandoned --
   without a `PERM_VAR`/`PERM_TERNARY` hint pointed at the actual construct in
   question, blind randomization does not converge on a 50-word function this
   tight.

## What I did NOT try, and why

- **A macro-expansion origin for the per-element block** (e.g. an
  `ABS_MAX(m, x)`-shaped statement expression or `do { } while(0)` macro
  invoked identically for `arr[2]`..`arr[5]` but NOT for `arr[0]`/`arr[1]`,
  which are handled specially since they are the initial pair). Reasoning:
  the retail asm's discontinuity (elements 0-1 loaded eagerly as a pair with
  no v0 detour; elements 2-5 each individually routed through v0 first) is
  consistent with the special-cased initial pair being ordinary sequential
  statements while the remaining four are a macro-expanded, textually
  identical block -- but attempt 3 (block-scoping the exact same statements
  by hand) produced NO change, which is weak evidence against this actually
  mattering at the C level for THIS toolchain. I did not pursue a literal
  `#define`-based version because C89 macro expansion happens before `cc1`
  ever sees it, so a `#define ABS_MAX(...) do {...} while(0)` expands to
  textually identical statements to what attempt 3 already tried by hand --
  I now believe this reasoning was WRONG to stop on, since a macro's use as
  a STATEMENT EXPRESSION at the call site (rather than a manually-inlined
  block) could still differ in how GCC 2.6.3's RTL generator numbers
  temporaries per macro-body instantiation, which block-scoping alone does
  not replicate. Worth trying first on any re-attempt.
- **Permuter with `PERM_VAR`/`PERM_TERNARY` macros** targeting specifically
  the per-element `if (v < 0) v = -v;` shape and the final `if (max < v) max
  = v;` shape, seeded from the near-match body above rather than fresh
  randomization. Not attempted due to time budget within this round; the
  bare-randomization run was a cheap sanity check, not a real permuter
  search.

## Proposed learning

A "missing `move` on 4 of 5 structurally-identical unrolled iterations,
present on the first" residue does NOT respond to renaming, reuse, or
manual block-scoping of the repeated statement -- all three were tried and
either had no effect or made it worse. Flag as a permuter target with
explicit `PERM_VAR`/`PERM_TERNARY` macros around the per-element abs/compare
shape, not bare randomization.
