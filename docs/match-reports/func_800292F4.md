## What this function does

The inverse of this unit's `func_800293F8`: converts an integer sector
count (LBA) back to a CD-ROM MSF (minute/second/sector-in-frame) timecode,
packed BCD, written into the caller-supplied `MSF179D8 *` (same local
struct type `func_800293F8` defined — offsets 0/1/2 = minute/second/sector).
`arg0 + 150`, then `/75` and `%75` (magic-multiply constants
`0x1B4E81B5` and `0x66666667`, GCC 2.6.3's standard signed-divide-by-
constant expansion — `mult`, `sra ...,31` sign fix, `mfhi`, shift, `subu`),
then the /75 quotient (total seconds elapsed) is further split `/60` and
`%60` into minute and second. Each of the three fields (minute, second,
frame) is then packed to BCD via the standard `(x/10)<<4 | x%10` idiom
(re-using the `/10` magic constant `0x66666667` for all three). Returns
the destination pointer unchanged (retail never touches `$v0` after it's
set to `arg1` early — a `return arg1;`-shaped tail, matching this
project's established "byte match proves nothing about return type on its
own, but a value already resident in the return register with nothing
overwriting it is exactly the shape of an intentional `return`" reading).

## The C

```c
MSF179D8 *func_800292F4(s32 arg0, MSF179D8 *arg1)
{
    s32 lba;
    s32 totalSeconds;
    s32 frame;
    s32 minute;
    s32 second;
    s32 frameTens;

    lba = arg0 + 150;
    totalSeconds = lba / 75;
    frame = lba % 75;
    frameTens = (frame / 10) << 4;
    minute = totalSeconds / 60;
    second = totalSeconds % 60;

    arg1->second = ((second / 10) << 4) + (second % 10);
    arg1->sector = frameTens + (frame % 10);
    arg1->minute = ((minute / 10) << 4) + (minute % 10);
    return arg1;
}
```

## Derivation: the naive translation was a scheduling residue, closed by the permuter

The naive per-field `((x/10)<<4) + (x%10)` translation, written inline in
each of the three store statements in retail's own STORE order
(second, sector, minute), reached 27/65 with **zero length drift**
(compiled to exactly 65 words both sides) — `--debug` confirmed
`Insertions: 4, Deletions: 4, Reorderings: 4` alongside `Register
Differences: 47`, i.e. a real-but-local scheduling defect, not a shape
defect. `asm-differ` showed retail starts the FRAME's `/10` division
(`mult`+`mfhi`) *before* it starts the total-seconds `/60` division, even
though frame's BCD value isn't STORED until the second of the three
`arg1->` assignments — GCC's scheduler hoisting an independent multiply
whose operand (`frame`) is ready earlier, to hide its latency, ahead of a
division whose operand (`totalSeconds`) isn't computed yet at that point.

**Permuter, seeded with the 27/65 near-miss, found zero in 232
iterations** (`Insertions`/`Deletions`: present in the base debug score,
so this is exactly the class MATCHING-GUIDE flags as needing more than a
register-identity permuter pass — worth noting since it succeeded anyway).
The winning mutation hoists `(frame / 10) << 4` into its own named local,
computed as its own statement immediately after `frame` itself — forcing
the compiler to schedule that computation early, exactly mirroring the
observed retail behaviour. Translated idiomatically (`frameTens`, matching
this unit's `func_800293F8` naming style) and reproduces byte-exact.

### Proposed learning

**A second confirmed instance (after `func_800293F8` this same round) of
"hoist ONE sub-expression into its own named local, computed immediately
after its operand is ready, to match GCC 2.6.3 hiding a multiply's
latency ahead of an independent, later-ready division."** Both instances
involved exactly the SAME shape: three structurally parallel BCD-pack (or
BCD-decode) computations where one field's INPUT is available earlier
than the other two's, and retail starts that one field's `mult`
instruction early while leaving its shift/sign-fix for later (right
before the value is actually stored/used) — i.e. the multiply's LATENCY
gets hidden, but its RESULT's consumption stays at the natural point.
When translating a multi-field pack/unpack where fields are NOT all ready
simultaneously, try hoisting the earliest-ready field's multiply-based
sub-expression into its own statement before reaching for a permuter
search — it may resolve on the first attempt (as it did on
`func_800293F8`'s first re-seed), and even when it doesn't fully close the
gap by hand, it substantially narrows what the permuter has to find (from
`Insertions: 4/Deletions: 4` this function is only ONE hoisted expression
away from zero).
