## Role

Raw byte-copy loop (`memcpy`-shaped, no NUL handling, no return value):

```c
void func_8002C014(char *dest, char *src, s32 count)
{
    s32 i;

    for (i = count - 1; i != -1; i--) {
        *dest++ = *src++;
    }
}
```

Countdown-to-`-1` loop form (rather than a `0`-count-up or `while
(count--)`) is deliberate: it's what reproduces retail's actual comparison
(`bne $v1, $a2, ...` against a register pinned to the constant `-1`,
computed once outside the loop) rather than a comparison against zero.

## The same redundant-guard trap as Class86F88__RefreshRows, in a new register shape

First attempt wrapped the loop in `if (count != 0) { for (...) }`,
reasoning that `count == 0` needs to skip the loop entirely (matching
retail's `beqz $a2, .L8002C03C` before the loop). That produced a
DUPLICATE `beqz a2, ...` check -- the explicit guard AND the `for` loop's
own natural entry test (on `i = count - 1 != -1`, which GCC folds back to
a check on `count` itself) both survived, compiling to the identical
`beqz` instruction twice in a row. Dropping the explicit `if` and letting
the bare `for` loop's own entry check do the work (same fix as
`Class86F88__RefreshRows`'s report, this unit's sibling `class_3bb8c_k`, same round)
resolved it in one step. Worth stating as a general rule now that it has
recurred twice in one round on two different loop shapes: **GCC 2.6.3
does not deduplicate an explicit `if` guard against a `for`/`while`
loop's own implicit entry check, even when they are provably the same
condition** -- never wrap a loop whose own header already excludes the
empty case.
