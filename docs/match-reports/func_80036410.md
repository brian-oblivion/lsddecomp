## Summary

`func_80036410(a0, a1)` reaches a 172(0xAC)-byte record via
`_ss_score[(s16)a0][(s16)a1]` (an array of pointers to arrays of these
records -- `sll 16`/`sra 14` on `a0` is the standard "sign-extend a 16-bit
index and scale by 4" idiom for indexing a *pointer* array, and the
1-2-4-subtract-shift chain on `a1` is strength-reduced `* 172`), sets two
fields, clears five individual bits in a flags word, copies one field into
another, sets a byte flag, then sets one more bit in the flags word.

```c

extern Entry90902E8 *_ss_score[];

void func_80036410(s32 a0, s32 a1)
{

    p->unk48 = 0;
```

## The key observation: two different access patterns, not one

Retail's disassembly computes `&_ss_score[a0][a1]` **once** into `$a3` and
reuses that register for the `unk46`/`unk48` stores AND (much later) the
`unk8`-read/`unk4`-write/`unk2B`-write -- but it independently **reloads**
`_ss_score[a0]` fresh through `$a0` for every single access to `unk90` (six
separate reloads: five clears plus the final `|= 1`), even though nothing
between them could plausibly alias the array-of-pointers slot itself.

Rather than fight this with a single cached pointer (which would have
under-produced retail's reloads) or no pointer at all (which would have
over-produced reloads on the fields that stayed cached), the fix was to
write it exactly as it reads: a local `Entry90902E8 *p =
&_ss_score[a0][a1];` for the fields accessed through `p`
(`unk46`/`unk48`/`unk4`/`unk8`/`unk2B`), and the raw `_ss_score[a0][a1].unk90`
array-index expression, uncached, for every `unk90` access. GCC 2.6.3's
weak/absent alias analysis for computed-pointer stores is enough on its own
to force a fresh load at each uncached site -- no extra tricks needed once
the C mirrors which fields go through the named local and which don't.

Matched on the first attempt once this shape was identified from the
disassembly (register `$a3` staying constant across the cached accesses,
`$a0`+reload appearing fresh at every `unk90` site).

### Proposed learning

When a function reloads the SAME computed array/pointer expression at some
access sites but not others, don't reach for one cached local pointer (or
none at all) -- read which specific accesses share a register in the
disassembly and mirror exactly that split in the C (a named local for the
cached ones, the raw indexing expression repeated for the reloaded ones).
GCC 2.6.3's alias analysis for stores through a computed pointer is weak
enough that a plain repeated array-index expression naturally reloads on its
own, no barrier or trick required.
