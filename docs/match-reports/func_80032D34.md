## What changed since round 25

The round-25 report banked the algorithm at high confidence and explicitly asked the next attempt to "verify each claim against a build rather than inheriting it." Doing that surfaced **two real errors** in the derivation, both confirmed directly from the raw `.s` (not reasoned about):

1. **The per-VAG shift test reads `hdr->ver` (offset 4), not `hdr->attr`.** The derivation's pseudocode wrote `buf[i] = rawSize << (hdr->attr < 5 ? 2 : 3)`, but `VabHdr` (this unit's own local struct, established earlier in this file for `SsUtGetVabHdr`) has no `attr` field at all -- it has `attr1`/`attr2` as single bytes near the end. The actual instruction at this point is `lw $v0, 0x4($a0)` -- offset 4, which is `ver`, the exact SAME field already read a few lines earlier (`lw $v0, 0x4($a0)` again) for the `maxProgs` 0x40-vs-0x80 decision. The derivation's own text for THAT earlier use correctly says `hdr->ver`; the second use silently drifted to `hdr->attr`, most likely a transcription slip that would have sent the next attempt looking at the wrong field entirely (a single byte at a completely different offset) had it been trusted.
2. **`D_80090C1C[slot]` is `vagSizeTable + 0x200` (a FIXED 256-halfword advance), not `vagSizeTable + numVags*2`.** The derivation's guess is the intuitively "correct" formula (skip past exactly the `numVags` entries actually present) but is not what retail computes. The `buf[]`-filling loop's own bound check (`slt $v0,$a3,$a1; bnez $v0,SKIP`) only gates whether the loop BODY runs; the loop's OWN CONTINUATION test is against a completely different, fixed bound (`addiu $t0,$sp,0x410`, unconditionally compared every iteration), and the `vagSizeTable`-walking pointer (`$a2`) is advanced by 2 bytes in the branch's OWN delay slot -- which executes on EVERY one of the loop's 256 iterations regardless of whether the body ran. So the pointer always ends up `vagSizeTable_start + 256*2 = vagSizeTable_start + 0x200`, completely independent of `numVags`. This is confirmed purely from MIPS delay-slot semantics (a delay slot always executes once, taken or not), not from any assumption about intent -- and it means the scratch region the loop walks is fixed-size (256 halfwords) regardless of how many VAGs the VAB header actually declares, which in turn explains why the local scratch buffer is exactly `0x400` bytes (256 words) rather than being provisioned per-`numVags`.

Both corrections are load-bearing for a byte-exact reconstruction: getting either wrong would have compiled to a plausible-looking but structurally different function.

## Why this is a STALL and not a match

Every remaining word of the 3-word gap is one of two already-characterized, not-fixable-by-hand GCC 2.6.3 residue classes this project has hit repeatedly (documented in `docs/DECOMPILATION_LEARNINGS.md` and in this round's other reports for `libcd_bios`):

1. **Dead-code elimination of a provably-redundant guard.** Retail's `numVags < 0` check (`andi $v1,$s4,0xFF; slti $v0,$v1,0; bnez ...`) is DEAD IN PRACTICE -- `numVags` is populated from a single byte read (`0..255`), so the check can never fire, and GCC in this build correctly proves the mask+sign-check is a no-op and elides it (`bltz $s4,...` directly, no mask). This is the SAME mechanism as `CD_ready`'s stalled `andi` masks this round: the optimizer removes a genuinely dead instruction before scheduling runs, and no `__asm__("")` barrier can rescue an instruction that never reaches the scheduler. Tried a barrier immediately before and inside the loop anyway (cheap to verify); no effect, confirming the diagnosis.
2. **The same dead-code class hits the odd/even tail loop's sign-adjustment.** Retail computes `(i + (i>>>31)) >> 1` (the general signed-divide-by-2-with-truncation-toward-zero idiom) SEPARATELY in each of the two branches (even/odd), even though the loop index `i` is providably non-negative (`for (i = 0; i < numVags; i++)`), making the `i>>>31` sign-adjustment term always zero. GCC proves this and folds it to a plain `i >> 1`. Tried a barrier at the loop top; no effect.

One residue in the OPPOSITE direction -- a case where a barrier DID help, worth recording as a positive result for the next attempt on a similarly-shaped function: **the "mark active programs" loop's counter increment.** Retail keeps the loop-counter `i++` as its own dedicated instruction at the loop's merge point (after the `if (tones != 0)` body, whether or not that body ran); this build's first attempt instead fused the increment into the `if`-guard's own branch-delay slot (semantically identical, one instruction cheaper). A bare `__asm__("");` placed as the LAST statement in the loop body (after the `if`, forcing the compiler to keep the `if`'s delay slot empty rather than filling it with the next loop iteration's counter update) restored retail's exact instruction, at no cost elsewhere. This is the "genuine ORDERING decision" class the round-20 barrier writeup describes as a real win, not the "register CHOICE" class where the same lever regresses.

Given the whole 274-word algorithm is now verified correct end-to-end (every branch, every global, every call argument checked directly against the disassembly) and the entire remaining gap is these two well-documented, previously-unfixable-by-hand classes, this is being filed as a characterized stall rather than continuing to search for a fourth lever.

### Proposed learning

- **A parameter that every existing caller passes as a compile-time literal cannot be width-disambiguated from caller evidence, but the callee's OWN internal comparison codegen can be the tell.** A `sll $reg,16 / bnez` (or `bltz`) pair testing a parameter is retail truncating it to 16 bits before comparing -- direct evidence the SOURCE parameter is `s16`, independent of anything a caller's argument values could show. This is the same family as CLAUDE.md's existing "read the callee's body for the width it actually uses" entry, but for a PARAMETER'S OWN internal use rather than a forwarding call site.
- **A loop's OUTER bound and an INNER cutoff test can be governed by two completely different variables, and only the disassembly's actual delay-slot advancement proves which one controls how many times a side-effecting pointer gets incremented.** Guessing "the loop obviously only runs `numVags` times" here would have been wrong by construction; the loop runs a FIXED 256 times with `numVags` only gating whether each iteration's body does real work.
