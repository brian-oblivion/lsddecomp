## What it does

A "commit a voice/channel parameter record" function, in the SPU-driver
family this unit's neighbours (`code_179d8_i.c`, `code_179d8_j.c`,
`code_179d8_l.c`, `code_179d8_m.c`) already touch:

1. Validates channel `a0` against `D_8008EA2C[(s16)a0]` (a per-channel
   state byte this unit's sibling `code_179d8_i.c` already reads/writes
   the same way — `if (D_8008EA2C[vabId] != 1)` there). If the state
   isn't exactly `1`, returns `-1` immediately.
2. Otherwise calls `func_80032148((s16)a0, (s16)a1)` — an existing,
   already-prototyped sibling function (`extern s32 func_80032148(s16 a0,
   s16 a1);`, matched in `code_179d8_c.c`, called the same way from three
   other units) that validates/selects a channel.
3. Computes `idx = (s16)(a2 + (D_8008EA13 << 4))` — the exact same
   `<index> + (D_8008EA13 << 4)` idiom `code_179d8_l.c`'s
   `func_8002E038` already uses for the same table (there with a global
   `D_8008EA18` in `a2`'s role; here it's this function's own parameter).
4. Copies 18 individual fields (14 bytes + 4 halfwords) from `a3` (a
   source record) into `D_8008E978[idx]` (a table slot), one field per
   statement, **in retail's own field order, not sorted-by-offset order**
   — offset `0x7` copies before offset `0x6`. Every other offset is
   sequential (`0x0`-`0x5`, `0x8`-`0xD`, then `0x10,0x12,0x14,0x16`).
5. Returns `0` on success.

## The struct: `Rec32E978`, a new LOCAL view of an already-known table

`D_8008E978` (a pointer to a 0x20-byte-stride table) already has two
independent local views elsewhere in the project — `code_179d8_l.c`'s
`D8008E978Entry` (fields `unk0[4]`, `unk4`, `unk5`, `unk6[6]`, `unk12`,
`unk13`, `unk14[18]`) and `code_179d8_m.c`'s `Tbl32E978` (only `unkC`/
`unkD` named). This function's own view needs INDIVIDUAL byte fields at
every one of offsets `0x0`-`0xD` (not the coarser `unk0[4]`/`unk6[6]`
arrays those two views use) because it copies each one with its own
statement, in an order that isn't offset-sequential — an array field
can't express that. Per project convention (multiple independent local
views of one struct are expected, `docs/DECOMPILATION_LEARNINGS.md`),
this is a THIRD local view, kept in `code_179d8_f.c` only, not exported to
a shared header:

```c
typedef struct {
    u8 unk0;
    u8 unk1;
    u8 unk2;
    u8 unk3;
    u8 unk4;
    u8 unk5;
    u8 unk6;
    u8 unk7;
    u8 unk8;
    u8 unk9;
    u8 unkA;
    u8 unkB;
    u8 unkC;
    u8 unkD;
    u8 padE[0x10 - 0xE];
    s16 unk10;
    s16 unk12;
    s16 unk14;
    s16 unk16;
    u8 pad18[0x20 - 0x18];
} Rec32E978;

extern Rec32E978 *D_8008E978;
```

The source argument `a3` is typed as `Rec32E978 *` too (not a different
struct) — every field it reads is at the identical offset the destination
writes, confirmed byte-for-byte against the disassembly, so this is a
same-type record copy (e.g. "commit a pending parameter set into the live
table slot"), not a conversion between two distinct layouts.

**Why the destination is re-indexed (`D_8008E978[idx].fieldN = ...`) on
every single statement instead of cached into one pointer local:** retail
reloads `D_8008E978` (the global pointer's VALUE) from memory before
every field store, while `idx`'s own byte-scaled offset is computed
exactly ONCE and reused unchanged across all eighteen stores. Confirmed
by reading the disassembly directly: one `lbu` of `D_8008EA13` total,
one `sll`/`addu`/`sll`/`sra` producing the offset, then eighteen repeats
of `lui/lw $v0,D_8008E978` immediately before each individual `addu`.
This project's own `code_179d8_f.c` already has this exact idiom
established one function up (`func_80036410`, matched earlier, repeats
`D_800902E8[(s16)a0][(s16)a1].unk90 &= ~0x100;` five times rather than
caching the computed address into a local) — GCC 2.6.3 at `-O2`
apparently does not CSE a global POINTER's value across an intervening
indirect STORE (conservative aliasing: it can't prove the store didn't
modify the pointer variable itself), while a purely-arithmetic offset
with no intervening memory write to alias against stays cached. Writing
`D_8008E978[idx].fieldN` fresh on every line reproduces this for free;
caching a `dst` pointer local and reusing it produces the wrong
(cached-load) shape.

## The residue that mattered: block ORDER of the early-return guard

This is the interesting part, and it is exactly the block-order class
the head's round-25 broadcast flagged (`CheckDreamAuxTriggerCondition`'s basic-block-
LAYOUT closure) — caught here on FRESH ground rather than an existing
stall, which is worth recording since the broadcast's examples were all
stalls.

**First attempt** — the naturally-obvious translation:

```c
if (D_8008EA2C[(s16)a0] != 1) {
    return -1;
}
func_80032148((s16)a0, (s16)a1);
... (the 18-field copy body) ...
return 0;
```

Built clean, but **19/115 words, no drift** — every single field-copy
instruction matched (confirmed via `asm-differ`, they're just shifted by
one instruction pair), and the only real diff was at the very top: retail
emits `beq $v1,$v0,.L80036270` (branch-if-SUCCESS, skipping FORWARD over
a compact two-instruction `j .L800363E4 / li $v0,-1` fail block that sits
immediately after the test) — my build instead emitted `bne $v1,$v0,
<far label>` (branch-if-FAIL, jumping AWAY to a relocated `li $v0,-1`
sitting right before the shared epilogue, letting the SUCCESS path fall
straight into the field-copy body with no gap at all).

**Two structurally-inert rewrites, both byte-identical to the first
(19/115), confirming the CFG — not the surface syntax — decides this:**

- `if (cond_success) goto main; return -1; main: ...` (explicit
  goto/label forcing the fail block to sit textually between the test and
  the body) — identical result. GCC builds the same control-flow graph
  from an `if`-with-implicit-fallthrough and a `goto`-to-a-following-
  label; the front end does not preserve which surface form produced a
  given CFG shape.
- Wrapping the whole body in an explicit `else` block instead of relying
  on fallthrough — also identical. Same reasoning: same CFG.

**The fix: swap which side is the `if`-body.** Put the big success body
inside the `if (D_8008EA2C[(s16)a0] == 1) { ... }` directly (not reached
via `goto`, not an `else` — just the plain `if`-true branch), with the
`return -1;` as a single statement AFTER the closing brace, not before
anything:

```c
if (D_8008EA2C[(s16)a0] == 1) {
    func_80032148((s16)a0, (s16)a1);
    ... (18-field copy) ...
    return 0;
}
return -1;
```

**115/115, byte-exact, whole-image SHA1 green.** This is a DIFFERENT
CFG from the three variants above (confirmed by the different result,
not assumed) — with the big body as the `if`-true arm and the small
`return -1;` as the unconditional statement following the whole `if`,
GCC's block-layout naturally produces retail's exact shape: branch-on-
success skips forward over a compact fail block sitting right after the
test, and that fail block's own `return` reaches the shared epilogue via
a short local jump — instead of relocating the fail block's return-value
assignment away to sit beside the epilogue.

### Proposed learning

**"Put the small/early-exit case first, guarded by its own negated
`if`" and "put the small/early-exit case last, letting the big case own
the `if`-true branch" are NOT interchangeable CFGs in this compiler,
even though they're semantically identical C** — and unlike the
goto/label vs. natural-fallthrough distinction (which really doesn't
matter, confirmed above), THIS structural choice does. When a function's
early-return guard doesn't reproduce retail's block order with the
"guard-then-return, body-follows" phrasing, try inverting which side
owns the `if`-body (put the LARGE case inside `if (positive-condition)`,
move the early return to a bare statement after the closing brace)
before reaching for a `goto`/label restructure — the goto restructure
looks like it should matter and, empirically, does not; the if/else
polarity swap does. This is the same *family* of fix as the head's
`CheckDreamAuxTriggerCondition` example, but the specific lever (`goto` placement) that
closed that case did nothing here, while a lever that case didn't need
(if-body polarity) is what closed this one — block-order residues need
their placement lever discovered per-instance, not pattern-matched from
one prior fix.
