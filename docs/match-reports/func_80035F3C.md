## Summary

A pure bit-unpacking leaf: takes two register values (`a0`, `a1`) and spreads
9 masked/shifted sub-fields into a 9-halfword output struct pointed to by
`a2`. No branches, no calls. Field semantics are unknown (this region is
low-level driver code, not class-framework code -- confirmed no
`tools/classtable.py` hit nearby), so the output struct is named by offset:

```c

    s16 unk2;  /* +0x2,  (u16)a0 >> 4  & 0xF  */
    s16 unk4;  /* +0x4,  a0 & 0xF             */
    s16 unk6;  /* +0x6,  (u32)a1 >> 6  & 0x7F */
```

## Two real residues found and fixed

1. **`(a1 >> 6) & 0x7F` needs an UNSIGNED shift.** `a1` is a plain `s32`
   parameter; a signed `a1 >> 6` compiles to `sra`, but retail uses `srl`.
   Cast to `(u32)` before the shift to force the logical form. (Every other
   shifted field in this function is already masked down through a `u16`
   truncation first, which is why only this one needed an explicit cast.)

2. **A repeated-immediate CSE that GCC 2.6.3 applies unconditionally, and
   retail's source apparently avoids.** `a2->unkA = a0 & 0x8000;` immediately
   followed by `a2->unkC = a1 & 0x8000;` (same literal `0x8000` twice in one
   function) makes this compiler ALWAYS hoist the mask into a register and
   reuse it (`li v0,-0x8000` / `and v1,a0,v0` / `and v0,a1,v0`), no matter how
   the two statements are separated, reordered, wrapped in locals, or given a
   `volatile`-qualified destination. Confirmed with a minimal reproducer run
   directly through the pinned pipeline (cpp | cc1 | maspsx | as) -- see
   below. Retail's own bytes are two independent `andi ...,0x8000`
   instructions, so this CSE did NOT fire for the real source.

   **The permuter found the lever: route exactly ONE of the two masked
   values through a plain `int` temporary before the store.**
   `t = a1 & 0x8000; a2->unkC = t;` (leaving the OTHER occurrence,
   `a2->unkA = a0 & 0x8000;`, untouched) is enough to stop GCC from
   recognizing the two AND operations as the same reusable subexpression.
   Both fields still lower to plain `andi ...,0x8000` in the output, matching
   retail exactly. Nothing about *why* this specific asymmetry defeats the
   CSE was established (this is GCC 2.6.3 RTL-CSE internals, not something
   traceable to any documented project blocker) -- it was found by permuter
   search after several manual attempts (locals, `__asm__("")` and
   `__asm__ volatile("" ::: "memory")` barriers, reordering, negative-literal
   spelling of the mask) all failed to stop the merge.

### Reproducer for the CSE (for anyone who doubts it)

```c
struct S { short a; short b; };
void f(int a0, int a1, struct S *out) {
    out->a = a0 & 0x8000;
    out->b = a1 & 0x8000;
}
```
run through
```sh
tools/gcc263/cpp -Iinclude -Iinclude/psyq -undef -lang-c -nostdinc -Dmips -D__GNUC__=2 t.c \
  | tools/gcc263/cc1 -mips1 -mcpu=3000 -quiet -G0 -O2 \
  | .venv/bin/python3 tools/maspsx/maspsx.py --aspsx-version=2.34 --dont-force-G0 --expand-div \
  | tools/binutils/bin/mipsel-linux-gnu-as -march=r3000 -EL -no-pad-sections -G0 -o t.o
```
produces `li v0,-0x8000` / `and a0,a0,v0` / `and a1,a1,v0` regardless of
locals, `volatile`, or negative-literal spelling (`(short)0x8000`) of the
mask -- the front end normalizes to the same low-16-bits-only mask before CSE
runs either way.

### Proposed learning

GCC 2.6.3 -O2 unconditionally CSEs two `x & IMM` expressions sharing the
same-valued immediate within a function -- confirmed via a from-scratch
minimal reproducer through the pinned pipeline, independent of statement
order, intervening code volume, local-variable indirection, or a
`volatile`-qualified store target. When retail's bytes show two independent
`andi` with the same immediate (no shared-register CSE), the fix found here
was routing exactly one of the two occurrences through a plain scalar
temporary before the store; the permuter found this in under a minute of
search after manual attempts (barriers, reordering, sign tricks) all failed.
Worth trying early on any similar "retail has N independent immediate loads,
my C gets them merged" residue.
