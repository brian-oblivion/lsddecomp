# func_80031D6C -- STALL (register-identity residue; length EXACT at 35/35 words -- CORRECTED, see round 30 rebuild; raw word-match 4/35; first real diff at word 0 / retail 0x80031D6C, the very first instruction)

Unit `code_179d8_j`, round 21 (2026-09-06). Not a class method
(`D_8006DAD4` is a plain global pointer, same table
`func_80031C98`/`func_80031280` (blocked, elsewhere) use).

## What it is

The "divide by 129" sibling of `func_80031C98`'s raw getter: same
0x18-entry bounds check on `idx`, same `D_8006DAD4[idx]` table with two
leading `s16` fields, but each field is divided by a runtime constant
(129) before being written to `*out1`/`*out2`. Confirmed the divisor
arithmetically rather than guessed, per CLAUDE.md's standing rule:

```sh
echo 'int f129(int x){return x/129;}' > /tmp/probe_div.c
tools/gcc263/cpp -Iinclude -Iinclude/psyq -undef -lang-c -nostdinc -Dmips -D__GNUC__=2 /tmp/probe_div.c \
  | tools/gcc263/cc1 -mips1 -mcpu=3000 -quiet -G0 -O2 \
  | .venv/bin/python3 tools/maspsx/maspsx.py --aspsx-version=2.34 --dont-force-G0 --expand-div \
  | tools/binutils/bin/mipsel-linux-gnu-as -march=r3000 -EL -no-pad-sections -G0 -o /tmp/probe_div.o
tools/binutils/bin/mipsel-linux-gnu-objdump -d /tmp/probe_div.o
```

produced `lui v0,0xfe0` / `ori v0,v0,0x3f81` / `mult a0,v0` / `sra
a0,a0,0x1f` / `mfhi v0` / `sra v0,v0,0x3` / `subu v0,v0,a0` -- an exact
instruction-for-instruction match (down to the register assignment)
against retail's own magic-multiply sequence for both fields. The
divisor is 129, not a guess.

## The residue

Best-reached body (four rebuild attempts, three distinct source
reshapes, all producing byte-IDENTICAL output to each other):

```c
#if 0
/* Base pointer for a table of 0x10-byte entries, indexed by a 0..0x17
 * id.  Only the two leading s16 fields this unit's own accessors touch
 * are named. */
typedef struct EntryDAD4 {
    s16 unk0; /* +0x0 */
    s16 unk2; /* +0x2 */
    u8 pad4[0x10 - 0x4];
} EntryDAD4;
extern EntryDAD4 *D_8006DAD4;

s32 func_80031D6C(s16 idx, s16 *out1, s16 *out2)
{
    EntryDAD4 *e;

    if ((u16) idx < 0x18) {
        e = &D_8006DAD4[idx];
        *out1 = e->unk0 / 129;
        *out2 = e->unk2 / 129;
        return 0;
    }
    return -1;
}
#endif
```

This gets the CONTROL FLOW and the POINTER CACHING right (confirmed via
`asm-differ`): retail computes the entry pointer ONCE (`v1 = D_8006DAD4
+ idx*16`) and reuses it for both `lhu`s, exactly like the code above --
the naive "index twice" version (first attempt) instead reloaded the
`D_8006DAD4` global a second time between the two field reads, which is
wrong here (unlike `func_80031C98`, where retail genuinely does reload
between reads because there's an intervening store the compiler can't
prove doesn't alias the global -- in `func_80031D6C` BOTH loads happen
before either store, so no such reload is warranted, and giving the
entry pointer its own local variable is what reproduces that).

What's left, per `asm-differ`, is a REGISTER-IDENTITY swap, not a
missing/extra instruction:

- Retail preserves the incoming `out1` pointer (`$a1`) into `$a3`
  UNCONDITIONALLY, as the function's very FIRST instruction (before the
  bounds check even runs), and preserves `out2` (`$a2`) into `$t0` in the
  bounds-check branch's delay slot. It then reuses the now-free `$a0`
  (dead `idx`) and `$a1` (freed by the rescue) as SCRATCH for the two
  loaded field values, and materializes the magic-multiply constant
  (129's reciprocal) into `$a2`.
- Every build from this source instead preserves ONLY `out1` (into
  `$a3`, in the branch's delay slot -- not at the very top), never
  touches `$a2`/`out2` as a rescue target at all (it stays live in `$a2`
  untouched until the final store), uses `$v1`/`$a0` as scratch for the
  field values, and materializes the constant into `$a1`.

That's ONE fewer `move` instruction overall (retail has two rescues,
every build here has one), which is the entire size difference -- 34
words built vs 35 words retail, and it is what cascades into "different
register on every line after the branch" once diffed.

## What was tried and ruled out

Three reshapes, all producing byte-IDENTICAL machine code to each other
(confirmed via `asm-differ`, not just eyeballing the C):

1. Direct `*out1 = .../129; *out2 = .../129;` with the cached `e`
   pointer above (the version preserved).
2. Explicit early `s16 *p1 = out1;` outside the `if`, `s16 *p2 = out2;`
   assigned as literally the first statement inside the `if` -- intended
   to force `out1`'s rescue to the top and `out2`'s rescue into the
   branch, mirroring retail's exact placement. No effect: identical
   output to (1).
3. The mirror image of (2) (`p2` assigned unconditionally outside,
   `p1` assigned first inside the `if`) -- also no effect, identical
   output to (1) and (2).
4. Swapping which field is READ first (`e->unk2` before `e->unk0`,
   while still storing to `*out1` first) -- changed which offset the
   FIRST `lhu` targets (as expected) but the `$a3`/`t0`/`$a1`/`$a2` role
   assignment was unchanged from (1)-(3).

Four attempts across three genuinely different statement orderings
produced three identical machine-code outputs (only (4) changed
anything, and only the thing it was expected to change). This is strong
evidence the register role assignment for this specific shape is
independent of source-level variable ordering -- exactly the kind of
"different registers, same instructions" case CLAUDE.md rule 6
classifies as a STALL: **"if removing it changes WHICH REGISTER holds a
value, it is banned; if it only changes instruction ORDER, it is
allowed."** There is no ORDER lever available here to try (a scheduling
barrier can't retarget which of two live incoming pointers gets rescued
to which physical register), so no `__asm__("")` experiment was run --
per the rule, that lever is not applicable to a register-IDENTITY
question in the first place, and the entry it comes from
(DECOMPILATION_LEARNINGS' "prologue callee-save order" note) is itself
about STORE ORDER, not this.

## Classification

Register-identity residue, not addiu-$at/gp-rel/nop-mflo-mfhi (all four
canonical screens are clean on this function -- it was staffed as
workable for a reason). File as STALL per CLAUDE.md rule 6 rather than
reaching for a register-pinning `asm` operand, which is explicitly
banned for exactly this shape of problem.

### Axes varied (per MATCHING-GUIDE's "a long attempt list is not a
broad one" check)

- Pointer-caching axis (direct double-index vs cached local pointer):
  tried, and IS load-bearing (fixed the CSE, moved the score from

- Declaration/assignment-order axis for the two output pointers: tried
  three ways, confirmed NOT load-bearing for the residue that remains.
- Field-read order axis: tried, confirmed it only affects the expected
  thing (which offset the first `lhu` targets), not the residue.
- NOT tried: whether the function's actual real-world signature omits
  one of the "obvious" parameters (e.g. a different index type, or the
  two outputs being fields of one struct rather than two pointers) --
  ruled out by the fact retail's `sh`s target two INDEPENDENT registers
  at offset 0 each, which only two separate pointer arguments produce.

## Proposed learning

**A register-identity residue that survives BOTH orderings of a
two-pointer-argument rescue (which one gets saved unconditionally at
top vs in a branch's delay slot) is very unlikely to be reachable by
further reordering -- GCC 2.6.3's rescue-target choice for this shape
looks like it is driven by something other than declaration or
assignment order** (physical register number of the incoming argument,
maybe, given retail always rescues the LOWER-numbered live pointer
first regardless of use order). Worth a corpus check if another
function in this project shows the same "one rescue `move` short, at
the top of a two-output-pointer function" shape.

## ROUND 30 (runner delta): rebuild CORRECTS the length figure -- it is exact, not one word short

Rebuilt the preserved body verbatim through the current pinned pipeline.
**`build/lsdde.map` shows `func_80031DF8` (the next function in ROM order)
still at its correct retail address after this build (0x80031df8), i.e.
this function compiled to exactly 0x8C bytes = 35 words -- the SAME length
as retail, not 34/35 as this report's "one fewer move instruction overall"
paragraph concluded in round 21.** `funcdiff.py` independently confirms
this: it reports the comparison range as `0x2256C-0x225F8`, which is
exactly 140 bytes / 35 words, and the raw word-match is **4/35**.

The "one fewer `move`" analysis in the residue section above was not
wrong about the MECHANISM (retail really does rescue both `out1` and
`out2`; this build's compiled form really does rescue only `out1`), but
it was wrong to conclude that costs a whole word of LENGTH. `tools/asm-
differ/diff.py`, re-run this round, shows the actual shape is more
tangled than "one instruction short": several instructions the built
version emits (a duplicated-looking mid-body divide-idiom cluster
computing the first field's magic-multiply result immediately after its
own `mult`, before the second field is even loaded) are things retail
defers to the very end, and retail's own tail contains a same-sized
cluster of instructions (two `sra ...,0x1f` sign-fixups plus a final
`subu`/`sh` pair) that this build's version does not have in the same
place -- these differences are a WASH in total count, not a net deficit.
The residue is a genuine full-body register/scheduling reshuffle, not a
one-word gap with the rest as ripple; `4/35` raw is a real measurement of
how far that reshuffle has diverged by the end, not an artifact of a
length mismatch.

This does not change the STALL classification or the register-identity
diagnosis in "The residue" above (both rescues are still register-
identity choices, not reachable by the source reshapes already tried in
round 21) -- it only corrects the LENGTH figure that was carried in the
title and in "That's ONE fewer `move` instruction overall" above. No new
reshape was attempted this round; the four round-21 attempts already
demonstrate the residue does not move with source-level statement or
declaration reordering, and this function has no untested axis flagged
worth spending a fresh attempt on beyond what round 21 already covered.
Restored to `INCLUDE_ASM`.

### Proposed learning

**"Length EXACT/short/long" must be measured from the built object's own
span (`build/lsdde.map`, or an explicit `objdump` byte count), never
inferred from "this many instructions look like they're missing" in a
hand-read register-identity diff.** This function's round-21 report
inferred a one-word deficit from "retail has two rescue `move`s, this
build has one" without checking whether some OTHER instruction elsewhere
in the reshuffled body made up the difference -- it did. The same
lesson `func_80030404`'s report already recorded (a 3-vs-5-words-short
miscount) generalizes to the "declared exact but actually short" direction
too, not just short-vs-shorter.
