## The one residue that blocked a match: register allocation, not instruction order

With everything above in place, the function's CONTROL FLOW and FIELD
ARITHMETIC are correct (the `mult`/`sra`/`mfhi`/`sra`/`subu`/`sll` chain
for the division and the two subsequent field computations reproduce
retail's instructions exactly once the divisor is 20). The blocking
defect is structural: retail keeps `self` (the incoming `arg1`, mapped to
`$a1`) alive by MOVING it into `$a3` right at the top
(`move $a3, $a1`) and reuses `$a1` itself as the resolved `desc` pointer's
register for the rest of the function. Every attempt tried keeps `self`
in `$a1` (its natural incoming-parameter register) throughout and
allocates a FRESH register (`$a3`) for `desc` instead -- the exact
opposite pairing. Both allocations are valid; they simply assign the two
long-lived pointers to the two available scratch registers in opposite
order.

**This is a register-IDENTITY difference** (which register holds `self`
vs `desc`), squarely in CLAUDE.md's BANNED category for a fix -- no
`register T v asm("$N")`, no operand constraint was used or considered.

**Tried, no effect on the register choice:**
- Introducing an explicit `self = arg1;` local-copy statement (mirroring
  retail's own `move $a3,$a1`) -- GCC recognized it as a trivial dead
  copy and eliminated it, keeping `self`/`arg1` unified in `$a1` exactly
  as before.
- Caching `self->unk34` into its own named local (`cached`) before the
  branch, rather than re-testing the field expression directly -- no
  effect on which register `self` or `desc` end up in.
- Reordering the `if (index < 0x190)` guard's polarity (early-return
  form vs `goto`-past-the-guard form) -- affects only the entry branch's
  own polarity (also not reproduced -- see below), no effect on the
  `self`/`desc` allocation.
- A bare `__asm__("");` placed at the top of the post-guard block -- no
  effect.

**A second, independent residue at the very top:** retail unconditionally
executes `sw $ra, 0x10($sp)` as its OWN instruction before the entry
branch; every C form tried here compiles it into the entry branch's delay
slot instead (semantically identical -- $ra is saved on both paths either
way -- but a different instruction position). This is the same
class of residue as `func_8002C048`/`func_8002C0AC`'s stalls in this
unit (pure scheduling, not register identity) but was not chased further
given the larger, register-identity residue makes the function
un-mergeable regardless.

**Classification:** genuine register-allocation-order stall, not a
reshaping problem -- the two structural facts (register-identity pairing,
plus a secondary scheduling difference) are independent of each other and
neither responds to the levers available. Not a permuter target in the
usual sense (the permuter mutates C source under the pinned toolchain and
COULD stumble onto a source shape that induces retail's allocation order,
but the search space here is much larger than the 1-2-instruction swaps
that made `func_8002C048`/`func_8002C0AC` good permuter candidates).

### Proposed learning

When two independently-derived pointer values (an incoming parameter and
a value resolved from it) both need to stay live across a large function
body, GCC 2.6.3's register allocator's choice of WHICH gets the
parameter's native register and WHICH gets a fresh one is not obviously
steerable from C source structure -- neither an explicit alias
assignment nor caching sub-expressions changed it in this instance. Flag
functions with this shape (long-lived parameter pointer + long-lived
derived pointer, no intervening calls to force spills) as a register-
identity risk before investing heavily in matching them precisely.

## Round 19 re-examination (runner charlie)

Re-entered the exact body from this report and re-confirmed 11/76,
byte-for-byte identical residue set to what's documented. Went further
than the existing report by tracing the EXACT mechanism from retail's own
disassembly rather than just describing it abstractly:

```
retail                                    built (this report's body)
addu  a3,a1,zero    (self -> a3, unconditional)
lw    a1,0x34(a3)   (self->unk34 loaded INTO a1 -- reusing the
                      just-vacated parameter register as scratch)
...
addu  a1,v1,a1       (desc's final address ends up in a1)
                                           lw    a3,0x34(a1)   (self stays
                                                                 in a1; desc's
                                                                 scratch is a3)
                                           addu  a3,a3,v1       (desc ends up
                                                                 in a3 instead)
```

So the mechanism is exactly the parameter-coalescing pattern documented
elsewhere in this round (`func_80032BB8.md`): retail moves the incoming
parameter (`self`) OUT of its native register at the top and lets the
FIRST value computed FROM it (`desc`) inherit that now-free register;
this build instead leaves `self` parked in its native register for its
whole lifetime and gives `desc` a fresh one. Both are valid allocations
of the same two long-lived pointers; retail chose the "evict the
parameter first" ordering and this build's compiler chose the opposite,
and every attempt across two rounds -- explicit alias copies, cached
sub-expressions, barrier placement -- leaves that choice unchanged.

**New finding: the guard's `if`-vs-`goto` polarity, which fixed
`func_80032AD0`'s block-order mismatch and is independently confirmed to
matter for `func_80032BB8`/`func_80032C60` (see those reports), does
**not** transfer here either way.** Tested both `if (index >= 0x190)
return 0;` (plain early-return) and the report's original `if (index <
0x190) goto process; return 0; process: ...` (goto form, matching
retail's actual `beqz`-to-shared-return-0-label shape): **both compile to
literally the same instruction sequence** for the guard itself, and it is
NOT retail's shape either way -- retail computes `slti` then `beqz
v0,<return-0 label>` directly (negative-first, no duplicated code), while
both of this build's forms produce `slti`/`bnez v0,<continue>` followed by
an inline `j` to the shared epilogue with `move v0,zero` inlined at the
jump site (see the `asm-differ` excerpt below). This is a NEW negative
data point for the guard-polarity lever's boundary: it's not just "guard
clauses want negative-first" (already known) -- in a function this size,
with return statements at multiple later points as well (`return -1;` in
the middle, `return ctx->...` at the end), GCC 2.6.3 does not appear to
reproduce retail's single-shared-exit shape from EITHER polarity spelling.
Whatever produces retail's exact `beqz`-direct-to-label shape here is not
reachable by flipping the guard; it may depend on something about how the
OTHER early return (`return -1;`) shares (or doesn't share) the same
exit block, which is a different lever than polarity and wasn't tested
further given the register-identity residue dominates the diff regardless.

```
retail:  slti v0,a2,0x190 ; beqz v0,<return-0 label>              (2 insns)
built :  slti v0,a2,0x190 ; bnez v0,<continue> ; j <epilogue> ; move v0,zero
         (4 insns -- both `if` and `goto` spellings produce this identically)
```

None of the round-19 axes (retype, whole-struct assignment, split-
statement, wrong-void-return) apply new leverage here: the parameter
types already match their access widths exactly (confirmed by the
original report's field-width derivation), there's no single-field
whole-struct copy in this function's shape, the cached-value logic is
already maximally split (separate `cached`/`desc`/`self->unk30` per
branch), and the return type is genuinely `s32` (verified: it returns
`ctx->unk2C->methods->slot80(...)`'s own `s32` result at the tail, a real
value consumed by other stalled call sites into this same dispatch
family, not a `void` masquerading as a value). **Confirmed stall, no
change kept in `src/`.**
