### Proposed learning

**A parameter copied into `$a3` (or `$a2`) at entry is a call argument
until proven otherwise.** Round 19, 31 and 60 all read retail's
`move $a3,$a1` as "cc1 evicts the parameter so the derived pointer can
inherit its register" and filed it as register identity. It was the
fourth argument of the only call in the function, forwarded untouched
from the caller. The screen is cheap: at every `jalr`/`jal`, list what
is live in `$a1`-`$a3` and ask whether each one could be an argument;
a value loaded into `$a1` immediately before a method call (here
`lhu a1` then a store of the same register) is the tell for the second
argument. This is round 75's argument-count family, landing on a
function whose report explicitly tested a "dummy 4th PARAMETER" -- the
arity that mattered was the callee's, not the function's own.

## The one residue that blocked a match: register allocation, not instruction order

With everything above in place, the function's CONTROL FLOW and FIELD
ARITHMETIC are correct (the `mult`/`sra`/`mfhi`/`sra`/`subu`/`sll` chain
for the division and the two subsequent field computations reproduce
retail's instructions exactly once the divisor is 20). The blocking
defect is structural: retail keeps `self` (the incoming `arg1`, mapped to
`$a1`) alive by MOVING it into `$a3` right at the top
(`move $a3, $a1`) and reuses `$a1` itself as the resolved `desc` pointer's
register for the rest of the function. Every attempt tried keeps `self`
in `$a1` (its natural incoming-parameter register) throughout and
allocates a FRESH register (`$a3`) for `desc` instead -- the exact
opposite pairing. Both allocations are valid; they simply assign the two
long-lived pointers to the two available scratch registers in opposite
order.

**This is a register-IDENTITY difference** (which register holds `self`
vs `desc`), squarely in CLAUDE.md's BANNED category for a fix -- no
`register T v asm("$N")`, no operand constraint was used or considered.

**Tried, no effect on the register choice:**
- Introducing an explicit `self = arg1;` local-copy statement (mirroring
  retail's own `move $a3,$a1`) -- GCC recognized it as a trivial dead
  copy and eliminated it, keeping `self`/`arg1` unified in `$a1` exactly
  as before.
- Caching `self->unk34` into its own named local (`cached`) before the
  branch, rather than re-testing the field expression directly -- no
  effect on which register `self` or `desc` end up in.
- Reordering the `if (index < 0x190)` guard's polarity (early-return
  form vs `goto`-past-the-guard form) -- affects only the entry branch's
  own polarity (also not reproduced -- see below), no effect on the
  `self`/`desc` allocation.
- A bare `__asm__("");` placed at the top of the post-guard block -- no
  effect.

executes `sw $ra, 0x10($sp)` as its OWN instruction before the entry
branch; every C form tried here compiles it into the entry branch's delay

class of residue as `func_8002C048`/`func_8002C0AC`'s stalls in this

### Proposed learning

When two independently-derived pointer values (an incoming parameter and
a value resolved from it) both need to stay live across a large function
body, GCC 2.6.3's register allocator's choice of WHICH gets the
parameter's native register and WHICH gets a fresh one is not obviously
steerable from C source structure -- neither an explicit alias
assignment nor caching sub-expressions changed it in this instance. Flag
functions with this shape (long-lived parameter pointer + long-lived
derived pointer, no intervening calls to force spills) as a register-
identity risk before investing heavily in matching them precisely.

of the same two long-lived pointers; retail chose the "evict the
parameter first" ordering and this build's compiler chose the opposite,
and every attempt across two rounds -- explicit alias copies, cached

### The inherited verdict was true but not decomposed, and that was the whole cost

The standing report called the residue "one pervasive register-allocation
residue" plus a secondary `sw $ra` scheduling note. Rebuilt unchanged,
that body reproduces exactly: **11/76, insertions 7 / deletions 7,
length-exact**. But `asm-differ` shows the 7/7 was not one defect — it
was **four separable ones**, three of which are ordinary C and fall to
ordinary source shapes. Attributing all of them to the banned
register-identity category is what kept the function closed for four

### Lever 1 — the guard's `return 0` must be the function's LAST statement

Retail's `beqz $v0, .L8002C394` jumps FORWARD to a block that sits below
everything, after the `return -1` block, and falls into the shared
epilogue. Round 19 tested `if (index >= 0x190) return 0;` against
`if (index < 0x190) goto process; return 0; process:` and correctly
reported that **both produce the same non-retail shape** — an inlined
`j <epilogue>` with `move v0,zero` in its delay slot, up at the top.
Round 19's conclusion ("whatever produces retail's shape here is not
reachable by flipping the guard") is right; what it missed is that the
lever is not polarity at all. Wrap the whole body:

```c
if (index < 0x190) {
    /* ... everything ... */
}
return 0;
```

The guard's return is then the last statement in the function and cc1
lays its block out last, exactly as retail does. This also fixes the
`sw $ra` position as a side effect *once lever 4 is applied* (see below).

### Lever 2 — the same treatment for the second early return

Retail's `beqz $v0, .L8002C38C` likewise jumps forward to an out-of-line
`j <epilogue>; addiu $v0, $zero, -1`. `if (desc->unk0 == 0) return -1;`
inlines it instead. Invert the test and make `return -1;` the trailing
statement of the outer block:

```c
if (desc->unk0 != 0) {
    /* ... main body ... */
    return ctx->unk2C->methods->slot80(ctx->unk2C);
}
return -1;
```

Levers 1+2 together took 11/76 -> **24/76** and 7/7 -> 4/4.

### Lever 3 — the `+ 8` grouping, a plain C association bug

Retail: `sll/addu/sll` for `index*12`, then `addiu $v0, $v0, 8`, then
`addu $a1, $v0, $v1`. That is `base + (index*12 + 8)`. The inherited body
wrote `ctx->unk10 + index * 12 + 8`, which parses as
`(base + index*12) + 8` and compiles to `addu` then `addiu` — the two
instructions in the opposite order. Spell it `index * 12 + 8 + ctx->unk10`.
Not a register problem at all; it had been inside the "pervasive
register-allocation residue" for four rounds.

### Lever 4 — statement ORDER drives cc1's load-delay scheduling

`lh $v0, 6($a1)`:

```
sll   v1,v1,0xb ; sw v0,0xc(a3) ; lh v0,6(a1) ; addiu v1,v1,0x400
sw    v1,0x14(a3) ; sll v0,v0,0xb ; sw v0,0x10(a3)
```

Source order `unkC, unk14, unk10` gives `... sw 0xc ; sw 0x14 ; lh ; nop
; ...` — one instruction longer, because the scheduler never hoists the
load. Writing **`unk10` BEFORE `unk14` in the source** — i.e. against the
order the stores appear in the output — makes cc1 hoist the `lh` and fill
its delay slot with the `unk14` chain, reproducing retail's sequence
exactly and dropping the `nop`. The emitted store order is then the
reverse of the source order, which is why this is not guessable from the
output.

### Lever 5 — an explicit alias of the parameter, from the permuter

With levers 1-4 the function is 75 words against retail's 76 and the
entire delta is retail's `addu $a3, $a1, $zero` — cc1 coalesces the
parameter copy away and keeps `self` in its incoming `$a1`, letting
`desc` take a fresh `$a3`; retail evicts `self` to `$a3` at the top and
lets `desc` inherit `$a1`.

The standing report records, as a closed negative, that "introducing an
explicit `self = arg1;` local-copy statement — GCC recognized it as a
trivial dead copy and eliminated it". **That is false on the reshaped
body.** All six of the permuter's joint-best candidates independently

```c

...

```

With it, cc1 emits the parameter copy. Score 24/76 -> **54/76**, length

the function is now retail's instruction, in retail's order.

### What is still wrong, and why it is a stall

The alias buys the copy but not the assignment. Retail has **two**
long-lived pointers (`self` in `$a3`, `desc` in `$a1`); the best body here
has **three** (`self` in `$a1`, `desc` in `$a3`, the alias `p` in `$t0`).
Twenty-two instructions differ by register name only. Using the alias for
*every* `self` access collapses it back to two pointers — and cc1 then
coalesces again, returning to the 75-word form. There is no spelling found
that produces retail's two-pointer assignment.

That is a register-IDENTITY residue, CLAUDE.md's banned-fix category. No
`register T v asm("$N")` and no operand constraint was used or considered.

### The mechanism, as far as it was measured

cc1 gives `self`'s pseudo a copy preference for `$a1` from the parameter
copy, so `self` wins `$a1` unless some other allocno is assigned first.
GCC 2.6.3's `allocno_compare` orders by
`floor_log2(n_refs) * n_refs / live_length`, so the way to make `desc` (or
`cached`) go first is to raise its refs or shorten its range relative to
`self`'s. **That model was tested and FALSIFIED**: removing a `self`-only
store (fewer refs on the parameter pseudo, which should have tipped the
ratio) changed nothing. Whatever orders these two allocnos is not captured
by the ref/length ratio alone, and the next attempt should not re-derive
the arithmetic — it is in this paragraph and it does not predict the
outcome.

### Proposed learning

**A near-miss's recorded CAUSE decomposes; run `asm-differ` over the
inherited body before believing the verdict, even when the verdict is
correct.** This report said "one pervasive register-allocation residue"
and was not wrong — register identity *is* the residue that survives. But
7 of the 7 opcode deltas were four independent defects, three of them
plain C (block placement of two early returns, an operator-association
slip on `+ 8`, and a statement-order effect on load-delay scheduling).
Because the headline named the one banned category, three rounds in a row
declined to look underneath it — round 31 explicitly judged a
re-derivation lower value than other work, on the strength of the
headline. The cheap discriminator is `insertions N / deletions M`: a
pure register-identity residue is **0/0**, so any non-zero pair proves
there is non-register work left no matter what the title says. This one
was 7/7.

Two sub-lessons, both independently reusable:

- **`return` placement is a source-position lever, not a polarity lever.**
  To get cc1 2.6.3 to lay an early-exit block out at the BOTTOM (retail's
  usual shape: `beqz` forward to a block that falls into the shared
  epilogue), make that `return` the last statement of its enclosing block
  and wrap the rest in the `if`. Flipping `if (c) return X;` between its
  spellings does not move it — round 19 measured that correctly and drew
  the boundary one step too tight.
- **Statement order is a scheduling lever whose effect is INVERTED in the
  output.** Writing the store whose value comes from a load *earlier* than
  a store whose value is pure arithmetic lets cc1 hoist the load and fill
  its delay slot with the arithmetic — so the emitted store order comes
  out the reverse of the source order. If a `nop` sits after a load that
  retail fills, try moving that load's statement earlier in the source,
  not later.
