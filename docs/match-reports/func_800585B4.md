## The function

A backwards scan of a 365-entry day ring, run once for each of the four
halfword targets in `D_80087BD4`, recording for each target the most recent
day at which it occurred. Bails returning 0 the first time a target is not
found at all; on success marks the log scored, resets the object's cursor and
returns 1.

## The single residue: cc1 strength-reduces the table access, retail does not

Retail forms `&D_80087BD4[i]` **inside the inner loop**, every iteration, as
cc1's indexed-global pseudo-op (`lh $v1, D_80087BD4($t3)`, which maspsx
expands to `lui`/`addiu`/`addu`), with `$t3 = i * 2` recomputed by an `sll`
once per OUTER iteration. The build instead hoists the address into an
induction variable `$t4` before the loop and bumps it by 2 per outer
iteration:

```
TARGET                                    CURRENT
                                    >     48df0:  lui     t4,0x8008     <- +2 words
                                    >     48df4:  addiu   t4,t4,0x7bd0
48e04:  sll     t3,t1,0x1           |     48e0c:  move    t3,t4
48e18:  addu    v0,a1,v0            r     48e20:  addu    v0,v0,a1      <- see below
48e1c:  lui     at,0x8008           <                                   <- -3 words
48e20:  addiu   at,at,0x7bd4        <
48e24:  addu    at,at,t3            <
48e28:  lh      v1,0(at)            r     48e24:  lh      v1,0(t3)
```

Net **-1 word**, which is the whole length gap. Everything from `bgez a2` to
the epilogue is otherwise identical.

Why this is not a spelling accident: the access is loop-invariant in the inner
loop, so hoisting it is a legitimate -O2 decision, and retail's cc1 simply did
not make it. In retail there is nothing for LICM to hoist, because the load is
a SINGLE cc1 instruction -- the three-instruction address form is created by
maspsx, BELOW cc1. So the question is why this cc1 chose a pointer instead of
the indexed-global form, and the answer is not in the address expression's
spelling.

## What was ESTABLISHED and should not be re-derived

- **`D_80087AACUnkA4Result` is a DAY-LOG object**, and the type in
  `src/class_3bb8c_t.c` has been extended additively to say so: `+0x04` a
  full-window mode flag, `+0x08` the live day count and ring cursor, `+0x18`
  a **365**-entry `s16` year ring, `+0x467` the scored byte. The array length
  is not a guess -- the ring index resets to `0x16C` (364) when it goes
  negative, which fixes it at 365. Existing offsets `+0x4`/`+0x8` were left in
  place, so `func_800580E0`'s codegen is untouched (whole-image SHA1 stayed
  green across the struct edit).
- **`D_80087BD4` is exactly four halfwords** -- `0x01FF`, `0x0101`, `0x0000`,
  `0xFD00`, read straight out of `asm/data/76DC8.data.s`. So the `i < 4` bound
  is the table's own length, not a magic number.
- **`i` is UNSIGNED.** Retail's `sltiu v0,t1,4` is an unsigned compare; with
  `s32 i` the build emits `slti` and loses that word. This was worth 1 word and
  is already in the preserved body below.
- **The three `return 0` exits share ONE block at the BOTTOM of the function**,
  which retail's success path jumps over (`j` + `sw` in its delay slot). Two
  separate `return 0;` statements let GCC merge them but place the merged block
  at the FIRST one's position, which cost 2 words and mis-shaped the entry
  branch. A single `goto fail;` with the label last reproduces retail exactly.
  This took the score from 5/56 to 15/56 and fixed every word of the prologue.

### Proposed learning

**A shared `return` block's PLACEMENT follows the first return in source
order, so N separate `return 0;` statements and one `goto fail;` with the
label last are NOT equivalent** -- GCC merges the duplicates either way, but
puts the merged block where the first one was. Retail's shape here (success
path `j`umps OVER the failure block, which sits immediately before the
epilogue) is the `goto`-with-trailing-label form. Worth 2 words directly and
it re-shaped the entry branch, taking this function from 5/56 to 15/56 and
making the whole prologue exact.

The diagnostic is cheap and specific: if the entry test's branch POLARITY is
inverted against retail (`beqz` where retail has `bnez`) and there is a stray
`j` + `move v0,zero` pair early in the function, the failure block is in the
wrong place -- do not go looking for a condition you spelled backwards.
