## The residue, precisely

Every VALUE, every TARGET OFFSET, and every REGISTER matches retail
exactly -- confirmed via `tools/asm-differ/diff.py`: 30 words in, 30 words
out, no address drift. The only difference is that my compile hoists
entry N+1's `frac = 1` store to happen ONE INSTRUCTION EARLY (right after
its own field load, before entry N's `whole` computation finishes),
whereas retail keeps strict per-entry order: load field, store `frac`,
compute, store `whole`, THEN move to the next entry. Concretely, retail's
per-entry block is fully self-contained before the next begins; my
compile interleaves the next entry's `frac` store into the tail of the
current entry's compute sequence.

## What was tried (9 real full builds)

1. **Baseline** (source above): 24/30, pure reorder as described.
2. **Named `s16 one = 1;`** reused for all three `.frac` stores instead of
   the literal `1` three times. No change (still 24/30) -- retail's own
   `li a0,1` reload-avoidance is a red herring; it doesn't come from
   sourcing the constant through a variable.
3. **Load the field into a named local BEFORE the frac store**
   (`v = src->unk10; out[0].frac = 1; out[0].whole = v * 45 >> 9;`, one
   `v` reused across all three entries) -- matching retail's LOAD-before-
   STORE-frac order. Catastrophically worse (6/30, with drift): this
   changed the multiply-by-45 strength-reduction shape entirely, and (per
   the raw hex) turned the field load into an UNSIGNED `lhu` rather than
   signed `lh`. Reverted immediately; not a viable axis for this compiler.
4. **`__asm__("")` barrier after each `.frac = 1` store.** No change.
5. **`__asm__("")` barrier after each `.whole = ...` store** (attempting
   to block the NEXT entry's frac store from crossing into the current
   entry's tail). Made it drastically worse (10/30, WITH drift) -- the
   barrier did not just block reordering, it disrupted delay-slot filling
   and forced real `nop`s into the output, growing the function. Reverted.

Attempts 2 and 4 are genuine "order-only" reshapes per CLAUDE.md's
permitted-barrier test and moved nothing; attempts 3 and 5 both changed
more than order (a wrong-signedness load, and real added `nop`s
respectively) and are excluded from further consideration on those
grounds alone, not just because they scored worse.

### Proposed learning

**A scheduling barrier is not guaranteed to be a pure no-op lever even
when CLAUDE.md's register-identity test says it should be allowed.**
Here, inserting `__asm__("")` at a plausible reorder-blocking position
did not just fail to help (attempt 4) -- placed elsewhere it actively
grew the function by disrupting delay-slot filling (attempt 5), which is
a different failure mode than the banned "changes which register holds a
value." Test a barrier's effect on WORD COUNT, not just position,
before trusting it as available leverage; a barrier that adds `nop`s is
exactly as disqualifying as one that changes register identity, just for
a different reason (CLAUDE.md's test names identity specifically, but
the underlying rule -- "does not reproduce retail's bytes" -- applies to
either failure mode equally).
