## What it is (fully derived, high confidence)

A PSX CD-ROM controller interrupt-cause dispatcher. Confirmed via the
debug/log strings it references (all verified against `asm/data/FD8.rodata.s`
before use, per the project's string-literal rule):

- `D_800109D8` = `"CDROM: unknown intr"` -- the default-case message.
- `D_800109B0` = `"DiskError: "`, `D_800109BC` = `"com=%s,code=(%02x:%02x)\n"`
  -- the cause==5 (error) diagnostic, printing a command-name string looked
  up from `D_8006D620` (the same string table `func_80028CF8`, matched
  earlier this round, indexes) plus two raw status bytes.
- `D_800109EC` = `"(%d)\n"` -- appended to the unknown-cause message.

Control flow, fully reconstructed and verified structurally byte-exact
(every branch, loop, and case boundary lines up 1:1 with retail -- the
residue described below is a pure *register-identity* difference, not a
missed condition or wrong constant anywhere):

1. Write 1 to a command/latch port (`D_8006D8C0`, a `volatile u8 *`), read
   the status/cause port (`D_8006D8CC`, masked to 3 bits) with a debounce
   loop (read until two consecutive reads agree), returning 0 immediately
   if the debounced cause is 0.
2. Read up to 8 response bytes from a data port (`D_8006D8C4`) while a
   "data ready" flag (bit `0x20`) is set on `D_8006D8C0`, zero-filling the
   rest of an 8-byte stack buffer if fewer than 8 arrived.
3. Re-arm the ports (write 1/7/7 to `D_8006D8C0`/`CC`/`C8`).
4. Unless cause==3 with a false `D_8006D7C0[D_8006D61D]` lookup (a per-mode
   flag table, same selector family as `D_8006D620`/`D_6006D6A0`), update
   an error counter (`D_8006D614`) when a flag bit turns on across the
   read, latch the two response bytes into `D_8006D60C`/`D_8006D610`, and
   compute a `flags` value (`resp[0] & 0x1D`) used by cases 1-3 below.
5. On cause==5, log the diagnostic strings above.
6. Dispatch on cause (1-5, via `jtbl_800109F8`; 6/7/out-of-range and the
   post-mask 0 case fall to a "CDROM: unknown intr (%d)\n" default),
   writing a small status byte (`D_8006D8D8[0]` and/or `D_8006D8D9`,
   depending on the case and mirrored between them in cases 4/5) and
   copying the 8-byte response into one or two of three contiguous 8-byte
   mailboxes (`D_8008B3CC`, `D_8008B3D4`, `D_8008B3DC`), returning a small
   bit-flag-shaped result (0, 1, 2, 4, 6, or -1) -- confirmed against
   caller sites in `asm/code_179d8_mid.s`, which `andi` the result against
   `0x2` and `0x4`, consistent with a flag word.

`s32 func_80029478(void)` -- confirmed against three call sites
(`asm/code_179d8_mid.s`, `asm/nonmatchings/code_179d8_g/func_8002B3F4.s`,
`asm/nonmatchings/code_179d8_g/func_8002AEE0.s`), all `jal` with a `nop`
delay slot and no argument setup, and against `code_179d8_g.c`'s own
existing forward declaration (`extern s32 func_80029478(void);`).

## The residue: pervasive register-identity mismatches, not a logic gap

The function's **size matches retail exactly** (`0x544` bytes, function end
at vram `0x800299BC`) once its ~14 fold-vs-unfold and reload-elision
mismatches were resolved (see "What closed cleanly" below). What remains at
219/337 words is **entirely a matter of which physical register GCC 2.6.3
chose to hold a given live value** at the copy-loop and status-write sites
inside the `switch` -- same instructions, same operands, same immediates,
different register field. Concretely: retail consistently assigns the
copy-loop's destination pointer to `$v1`, its source pointer to `$a1`, and
its counter to `$a0` in most (not all) of the six `COPY_RESPONSE8`-shaped
call sites; my build assigns the same three roles to a different, and
internally inconsistent, permutation of `$a0`/`$a1`/`$v1` depending on
which case body precedes it -- confirmed via direct disassembly comparison
(`objdump -d` on the linked `build/lsdde.elf`) at every one of the five
case bodies, not just eyeballed off the colorized differ output (which,
with the function's size initially mismatched, was actively misleading
about which retail instruction corresponds to which built one -- see
"Method note" below).

This is CLAUDE.md's named case: *"if removing it changes WHICH REGISTER
holds a value, it is banned; if it only changes instruction ORDER, it is
allowed. A register-identity mismatch is a STALL."* No extended-asm operand
constraint or `register T v asm("$N")` was used anywhere in this attempt --
the rule was respected throughout; the mismatch is a stall precisely
because the only remaining lever (source-level restructuring) was tried
repeatedly and did not converge across all six sites simultaneously.

### What closed cleanly (all confirmed via direct before/after size deltas)

- **The bounds-guard/table-lookup idiom already established by
  `func_80028CF8`/`func_80028D30` this round applies here too**, for the
  debounce loop, the response-length loop, and the two per-selector flag
  tables (`D_8006D6C0`, `D_8006D7C0`).
- **`switch (cause)` with cases written in retail's own PHYSICAL layout
  order (3, 2, 1, 4, 5, default -- not ascending numeric order) is
  necessary**, confirmed by reading the label addresses directly out of
  the original `.s` (`.L800296D4` at `19ED4` precedes `.L800297D8` at
  `19FD8` precedes `.L80029824` at `1A024`, etc.) -- GCC 2.6.3 lays out a
  jump-table switch's case BODIES in source declaration order, not value
  order, for this shape.
- **The 8-byte response-mailbox copy is `for (i = 7; i != -1; i--)`**,
  the SAME idiom this file already uses in `func_80029274`
  (`for (i = 3; i != -1; i--)`), not `for (i = 0; i < 8; i++)` (which
  strength-reduces to an ascending pointer-vs-limit comparison, a
  different and larger instruction sequence) and not
  `do { ... } while (count-- > 0)` (the `class_3bb8c_*`/`code_8220_b.c`
  idiom for a different loop shape, which compiles to yet a third,
  also-wrong form here: a saved-copy-plus-`bgtz` test rather than
  retail's direct `bne $reg,-1`).
- **`D_80010840`-style string-symbol referencing extends to four more
  rodata strings** (`D_800109B0`, `D_800109BC`, `D_800109D8`, `D_800109EC`)
  -- all confirmed as real `.asciz` symbols in `FD8.rodata.s` before use.
- **A value that is written to a global and then immediately read back
  from that SAME global needs the global declared `volatile`, or GCC's own
  CSE elides the reload entirely** (reusing the still-live register
  instead of re-issuing `lui+lbu`) -- diagnosed by comparing instruction
  counts directly against retail's own `.s`, which always re-loads.
  `D_8006D8DA` was already `volatile` (matching `code_179d8_g.c`'s
  existing reading) and its case (case 4) needed no fix; `D_8006D8D9`
  needed the same qualifier added for case 5 to reload correctly.
- **A CONSTANT-returning arm as the early guard clause, matching
  `func_80028CF8`'s branch-polarity finding**, was not directly reusable
  here (no simple bounds-guard shape), but the general principle --
  writing control flow in the shape that keeps the SIMPLE case as the
  branch target and the COMPLEX case as the fall-through -- underlies why
  `if (cause == 0) return 0;` at the very top matches retail exactly.

### What did NOT close, and the specific experiments that failed

The `D_8006D8D8[0] = <value>;` / `D_8006D8D9 = <value>;` status-byte writes
inside the switch come in two retail flavors that look, from the C source,
identical in shape:

- **Cases 1 and 2** (a value merged from an if/else or ternary) compile,
  in retail, to the CHEAP folded form: `lui $at,hi(sym); s* $val,lo(sym)($at)`
  (2 instructions, address computed directly into the assembler temporary).
- **Case 3's three sub-branches** (a straight-line constant, no merge) and
  **the "mirror" write in cases 4/5** (a value freshly reloaded from
  ANOTHER global) compile, in retail, to the EXPENSIVE unfolded form:
  `lui $real,hi(sym); addiu $real,$real,lo(sym); s* $val,0($real)` (3
  instructions, address materialized into a real, non-`$at` register).

Five separate restructurings were tried to make MY C reproduce this split
consistently:

1. **Address-of a local pointer, then dereference**
   (`u8 *p = D_8006D8D8; *p = 5;`) for case 3 -- no effect whatsoever on
   the generated code (byte-identical before/after, confirmed via
   `build/lsdde.map`'s `func_80029478`/`func_800299BC` boundary not
   moving). GCC 2.6.3 treats this identically to a direct
   `D_8006D8D8[0] = 5;`.
2. **An intermediate scalar local** (`u8 v = 5; D_8006D8D8[0] = v;`) for
   case 3 -- also no effect.
3. **`volatile`-qualifying the global's declaration** (both
   `D_8006D8D8` and `D_8006D8D9`) -- fixed case 3 (all three sub-branches
   now unfolded, exactly matching retail, closing a 3-word deficit) but
   BROKE case 2 (which retail wants folded, and which my code had
   correctly folded up to that point), regressing it by 1 word. The two
   cases need OPPOSITE codegen for what is, from the C source, the exact
   same kind of statement.
4. **`volatile`-casting only the specific case-3/case-5 access sites**
   (`*(volatile u8 *)D_8006D8D8 = 5;`) instead of the global declaration --
   fixed case 3 without breaking case 2 (since case 2 keeps its plain,
   non-cast access), but on case 5's READ side (`*(volatile u8 *)&D_8006D8D9`)
   this introduced an extra `addiu` that a plain qualified-declaration
   read does not need (a cast-through-pointer forces GCC to materialize a
   full address before the `lbu`, 3 instructions, where a directly-`volatile`-
   qualified declaration's read folds address+load into 2, matching
   retail). Switching case 5's read back to a plain access of a
   `volatile`-declared `D_8006D8D9` (keeping the WRITE side's cast) closed
   that gap.
5. **Rewriting case 2 from a ternary
   (`D_8006D8D8[0] = (flags != 0) ? 2 : 5;`) to an explicit if/else into a
   local, then a single store** did independently matter and fixed a
   real, different problem: it closed a separate 1-word regression where
   the ternary form was compiling to the UNFOLDED shape (matching neither
   my case-3 nor case-2 needs at the time). This fix is orthogonal to and
   compatible with fix 4.

After all five, the FUNCTION SIZE matches retail exactly (**confirmed**:
`build/lsdde.map` shows `func_80029478` ending at vram `0x800299bc`,
identical to retail) -- every case body is now the RIGHT LENGTH. What is
left is register CHOICE within that correct length: the copy loops'
`$v1`/`$a0`/`$a1` role assignment still differs from retail's own choice at
most of the six call sites, in a pattern that did not resolve through
argument-order changes to the `COPY_RESPONSE8` macro, through moving the
`flags = 0` initialization earlier (which DID fix one specific
`$s0` vs `$v0` mismatch at the very top of the function, gaining 3 words,
confirming the lever is real but not sufficient to reach the remaining
sites), or through any further reordering tried within the remaining
budget. Attributing this to "the wrong C shape" is not falsifiable without
literally reproducing GCC 2.6.3's own register allocator's internal
history through the whole function -- which is exactly the register-
identity stall CLAUDE.md describes, not a shape that a documented idiom is
known to fix.

### Method note: read the differ's output only once the SIZE already matches

For a large chunk of this session, `asm-differ`'s colorized diff was
actively misleading, because the function's overall SIZE did not yet match
retail: every byte after the first size-changing edit is at a shifted
address, so the tool's heuristic realignment was comparing retail
instructions to UNRELATED built instructions several cases away. The
reliable technique that actually worked: read `jtbl_800109F8`'s own words
directly out of the linked `build/lsdde.elf` (`objdump -s`), which give
each case body's actual entry address in the CURRENT build regardless of
overall drift; compute each case's byte span from consecutive entries;
and diff each span's SIZE against retail's own (from the un-edited `.s`
file's addresses) BEFORE trusting any instruction-level comparison. Only
once every span's size matched did instruction-level `objdump -d` diffing
against retail's own `.s` become trustworthy. This generalizes past this
function: a differ tool that realigns automatically can silently swap
which two chunks it is comparing when sizes disagree, and the fix is to
verify sizes independently first, per the project's own repeated point
about address drift invalidating in-range readings.

### Proposed learning

- **A differ's realignment is only trustworthy once the function's overall
  SIZE already matches.** Read the owned jump table's own words directly
  out of the linked ELF to get real per-case-body addresses in the CURRENT
  build, and compare SPAN SIZES against retail's own `.s`-derived addresses
  before trusting any instruction-level diff. This generalizes the
  existing "address drift invalidates in-range reading" point to the
  sub-function granularity of one `switch`'s case bodies.
- **GCC 2.6.3's fold-vs-unfold choice for `global = value;`
  (2-instruction `$at`-relative store vs. 3-instruction real-register
  address store) is sensitive to something beyond the visible C shape at
  the store site** -- confirmed NOT sensitive to address-of-then-deref,
  NOT to an intermediate scalar local, but genuinely responsive to
  `volatile` qualification (in one direction) and to merged-vs-straight-
  line value provenance (in a direction this session could not
  characterize precisely enough to generalize; two structurally-identical-
  looking call sites, one merged (case 2, wants folded) and one
  straight-line (case 3, wants unfolded), needed OPPOSITE treatment, and
  a THIRD merged-looking site (case 2's original ternary form) needed
  explicit if/else-into-a-local rewriting to reach the same result as the
  award-winning unfolded form reached via a cast). Worth another
  function's worth of evidence before writing this up as a firm rule.
- **A write-then-immediate-read-back of the same global needs that global
  `volatile`, or GCC's own CSE elides the reload** -- confirmed cleanly (2
  independent sites, `D_8006D8DA` already volatile and correct,
  `D_8006D8D9` needed the qualifier added), and worth generalizing: any
  "mirror" store pattern (`B = A;` right after `A = <computed>;`) in this
  driver-style code should be screened for whether `A`'s declared type
  already carries `volatile` before concluding a reload residue is
  register allocation rather than a missing qualifier.
- **A dense switch's case body LAYOUT ORDER follows source declaration
  order, not case-value order, for a jump-table switch** -- distinct from
  the already-documented case-VALUE-SET sensitivity for a comparison-tree
  switch (`func_80049CA8`'s report). Read the labels' own addresses out of
  the retail `.s` before writing the switch, and declare cases in that
  physical order.
