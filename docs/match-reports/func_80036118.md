## Summary

Rescales two signed 16-bit inputs from a `0..127`-ish range to a
`0..32767`-ish range (`x * 32767 / 127`) and pokes the results, plus a
constant `6`, into the same SPU-ish struct `func_80036064` writes
(`D_8008E258`, and two new fields `gMasterVolL`/`gMasterVolR`), then calls
`func_80036B20` on it.

```c
extern s16 gMasterVolL;
extern s16 gMasterVolR;

void func_80036118(s32 a0, s32 a1)
{
    s16 sa0 = (s16)a0;
    s16 sa1 = (s16)a1;
    s32 *p = &D_8008E258;

    *p = 6;
    gMasterVolL = (s32)sa0 * 32767 / 127;
    gMasterVolR = (s32)sa1 * 32767 / 127;
    func_80036B20(p);
}
```

## Finding the divisor

Retail's division-by-constant sequence uses magic multiplier `0x81020409`
with a post-shift of 6 (`mult`/`mfhi`/`addu`/`sra 6`/`sra 31`/`subu` -- the
standard GCC signed-division-by-constant idiom when the multiplier needs a
sign correction). Rather than reverse-deriving the divisor from the magic
constant by hand, brute-forced it through the pinned pipeline: compiled
`int f(int n) { return n / D; }` for every `D` in `2..4000` and grepped the
objdump for the `8102` half of the magic constant. First (and smallest) hit:
**`D = 127`**, and it reproduces retail's exact instruction sequence
byte-for-byte in isolation. 127 reads as a MIDI/hardware-style
0..127 volume-or-pan range being rescaled into a wider signed range, which
fits the SPU-adjacent globals this whole file pokes.

`n * 32767` itself needed no special handling -- GCC 2.6.3 -O2 already
strength-reduces multiply-by-`(2^15 - 1)` into the `sll 15` / `subu` pair
retail has, from a plain `* 32767` in the source.

## One residue: address materialized late, not early

A first pass wrote `D_8008E258 = 6;` and `func_80036B20(&D_8008E258);` as
two independent expressions. That compiles correctly but computes
`&D_8008E258` (a `lui`/`addiu` pair) **twice**, and late -- once right
before each use. Retail computes it **once, early** (right after the frame
is set up, before either division finishes) and keeps it alive in a single
register through both the store and the call at the end. Introducing an
explicit local pointer,

```c
s32 *p = &D_8008E258;
*p = 6;
...
func_80036B20(p);
```

reproduces this exactly: the compiler now has one real variable (`p`) whose
first use is the store and whose last use is the call, so it materializes
the address once and keeps it live across the whole function body, matching
retail's register footprint word-for-word.

### Proposed learning

When retail computes `&global` once and reuses the register across a store
and a later call, but a straightforward `global = x; ...; f(&global);`
computes the address twice (once per use site), try binding an explicit
local pointer to the address and using it for both accesses. This is a
distinct (and, so far, more common) cause of "address computed late/twice"
residues than the divisor or control-flow issues that dominate this file's
other functions.
