## What it does

Index-to-pointer helper over the same `D_8008A868` string-record table used
by `func_80028448`/`func_800284C4`: returns `D_8008A868 + index * 0x1C`,
bracketed by the unit's lock/unlock pair. `index * 0x1C` is computed via
strength reduction (`(index << 3) - index) << 2`) in both retail and every
C shape tried here -- that part always matches byte-for-byte. The stall is
purely a **register allocation** difference, not a logic error.

## The stall

Retail's register plan: `$s0` holds `D_8008A868` (loaded *before* the lock
call, survives across both the lock and unlock calls) and `$s1` holds
`index` (copied from `$a0` only after the lock call returns, dead well
before the unlock call). The final `base + offset` add happens in the
delay slot of the `jal func_800280E0` (unlock) instruction.

Every C shape tried here that computes `base` before the lock call gets it
allocated to `$s2` instead of `$s0` (and needs a third callee-saved
register the retail code doesn't use), costing 4-8 bytes. Every shape that
lets `base` be loaded fresh late (right before the final add) gets the
*index* promoted into `$s0` instead (matching retail's register class
choice but the wrong operand), producing the length-correct but
content-differing residue below.

### What was tried (all within budget, all rejected as non-byte-exact)

- `char *base = D_8008A868;` declared/assigned before `func_800280D0()`,
  `offset` computed between the two calls, `return base + offset;` after
  -- allocates `base` to `$s2` (an unused third saved register in retail),
  4 bytes longer.
- Same shape with `s32 base = (s32)D_8008A868;` (integer instead of
  pointer arithmetic throughout) -- identical `$s2` allocation, no change.
- `base` fetched *after* the lock call instead of before -- also `$s2`,
  also 4 bytes longer, and additionally reorders the multiply relative to
  the lock call.
- Multiply spelled explicitly as `(index * 8 - index) * 4` instead of
  `index * 0x1C` -- purely cosmetic, GCC strength-reduces both identically;
  no effect on register allocation.
- The body above (`base` computed late, inline in a single expression
  after the lock call) -- length-exact (0x4C bytes both sides, confirmed
  via `tools/asm-differ/diff.py`, no out-of-range drift), but `index` (not
  `base`) lands in `$s0` and `D_8008A868` is re-read into `$v0` right
  before the final add, instead of into `$s0` across both calls. 9/19
  words match; the diff is a clean register/instruction-order swap, not a
  structural mismatch.

None of the tried source shapes reproduce retail's specific choice of
*which* value gets the long-lived callee-saved register. This reads as a
GCC 2.6.3 -O2 register-allocation heuristic difference tied to something
about the original source this session could not identify (not a
toolchain blocker -- no `gp_rel`/`addiu_at`/`mflo` construct is involved,
and the surrounding sibling functions in this same unit, including the
much larger `func_8002858C`, compiled byte-exact on the first attempt with
directly comparable shapes). A future attempt could try the permuter
(`tools/setup-permuter.sh`) seeded from the 9/19 body above, or try
spelling the return as a `Node`-typed pointer arithmetic instead of raw
`char *`, since none of that was tried here.

### Proposed learning

Add to the reshaping repertoire: when a value that needs to survive two
back-to-back "critical section" calls (lock/unlock or similar) keeps
landing in the *wrong* saved register relative to a sibling temporary, the
issue may not be fixable by reordering statements alone -- GCC 2.6.3's
allocator here consistently preferred the register-copied parameter over
the memory-loaded global for the low-numbered saved register, regardless
of which was declared or computed first in source order.
