**Unit:** code_d294 · **Size:** 31 words · **Status:** MATCHED (31/31 words)

## What it does

`Class6B5CC` vtable slot `+0x054`, called by this unit's own dtor
(`func_8001CBA4`). Repeatedly calls `self->methods->slot58` (`+0x058`,
`func_8001D280`, also matched this round -- see its own report), which
writes a found-entry pointer and advances a persistent list cursor through
its 2nd/3rd arguments, and for each non-NULL entry found calls
`entry->methods->slot50(entry)` on it. Loops until the cursor (reused as
the loop's own continue flag) goes to zero.

## Residue: an explicit initializer for an address-taken, immediately-overwritten local

First attempt left `entry` uninitialized (its address is taken and passed
to `slot58`, which unconditionally writes through it before it's ever
read) -- reasoning that GCC would treat the initial value as dead and drop
the store. Retail keeps it: `sw $zero, 0x10($sp)` right before the loop,
one instruction this compiler does NOT eliminate even though the value is
provably dead on entry to the loop body. The fix was writing
`entry = NULL;` at the declaration. Read as: GCC 2.6.3 at `-O2` does not
do dead-store elimination through an address-taken stack slot here, so if
retail's source initialized a local whose address escapes to a callee
immediately after, that initializer survives to the object code and has to
be written explicitly, even though it looks logically redundant.
