## Round 31 update (runner bravo): closed via decomp-permuter

Re-verified round 25's baseline reproduces exactly before touching
anything: 36/44 raw word-match, length exact, same residue (an
independent value scheduled one position too early relative to the
cursor read).

Set up `tools/decomp-permuter` against the preserved near-miss body
(base score 635 confirmed via `--debug --stack-diffs`: 7 register
differences plus 3 insertions/3 deletions -- the permuter's line-based
diff apparently could not recognize this residue as a pure reorder and
scored some of the shuffle as insert/delete pairs instead, which is why
the base score reads much higher than "8 words differ" would suggest;
the underlying retail-vs-built byte diff was still exactly the 8-word
residue this report already documents). A 16-way search
(`--stop-on-zero --best-only`) found a **score-0 candidate at iteration
13552** out of a run that induced up to 436 simultaneous errors along the
way:

```c
int new_var;
Entry90902E8 *rec = &D_800902E8[a0][a1];
u8 *cursor = rec->unk4;
u8 b;
u8 vol;
b = rec->unk12; rec->unk4 = cursor; new_var = (a1 << ((unsigned long long) 8)) | a0; rec->unk4 = rec->unk4 + 1;
vol = *((((u8 *) rec) + b) + 0x2C);
b = *cursor;
SpuVmPitchBend(new_var, rec->unk4C, vol, b);
rec->unk88 = func_80035E80(a0, a1);
```

**The two ingredients that matter, once the permuter's cosmetic noise
(the `unsigned long long` shift width, the single compound statement) is
stripped out:**

1. **`rec->unk12` is read into a temporary BEFORE the cursor store-back,
   not folded into the pointer expression at its point of use.** Every
   round-24/25 attempt at this had hoisted `rec->unk12` (or the whole
   `p[0x2C]` read) into a named local positioned AFTER the cursor
   store-back and the packed-id computation, or left it inline at the
   call site -- never BEFORE the store-back. Moving it first is the
   untested ordering.
2. **The cursor store-back is split into a redundant self-store followed
   by a separate re-read-and-increment: `rec->unk4 = cursor;` then
   `rec->unk4 = rec->unk4 + 1;`, instead of the single `rec->unk4 =
   cursor + 1;` every prior attempt used.** This forces the increment to
   be computed from a fresh MEMORY READ of `rec->unk4` rather than from
   the already-in-a-register `cursor` value, which changes what the
   scheduler has available at that program point and is exactly the kind
   of "give the compiler a different dependency chain, not a different
   named variable" axis this report's round-25 update flagged as
   untried ("no attempt tried varying whether the four reads should be
   structured... via nested comma-like sequencing").
3. **Reusing the same variable (`b`) for both the offset byte and the
   final cursor byte** (rather than two separate locals) is likely
   cosmetic -- the permuter's mutation reused a pseudo slot -- but was
   kept in the translated version below since removing it was not
   re-tested (diminishing-returns judgement call given the fix already
   verified byte-exact; the two roles are temporally disjoint so reuse is
   safe either way).

Translated toward idiomatic C, but NOT all the way: a first attempt gave
the offset role its own separate `u8 offset` local (instead of reusing
`b`) AND typed the packed id as `s16 packed` (matching this unit's other
functions' own convention for that value, rather than the permuter's
`int`/`s32`). **That attempt regressed badly** -- 265622 bytes of
outside-range drift, i.e. the compiled length grew. Since it changed TWO
things at once (the extra local AND the narrower type), it does not by
itself pin down which one mattered; not re-split further given the
working form below was already byte-exact. Kept `packed` as `s32` (the
permuter's own type) and `b` reused for both roles (the permuter's own
choice) in the version actually verified:

```c
void func_80035A7C(s16 a0, s16 a1)
{
    Entry90902E8 *rec = &D_800902E8[a0][a1];
    u8 *cursor = rec->unk4;
    s32 packed;
    u8 b;
    u8 vol;

    b = rec->unk12;
    rec->unk4 = cursor;
    packed = (a1 << 8) | a0;
    rec->unk4 = rec->unk4 + 1;
    vol = *((u8 *)rec + b + 0x2C);
    b = *cursor;
    SpuVmPitchBend(packed, rec->unk4C, vol, b);
    rec->unk88 = func_80035E80(a0, a1);
}
```

Byte-exact, 44/44, no drift; `./build-and-verify.sh` whole-image SHA1
green. Note `packed` had to stay `s32` (matching the permuter's own
`int`) -- an `s16 packed` regressed, consistent with this report's
existing "argument width must be enforced with an explicit narrower type"
family being about the CALL SITE's cast, not this local's own
declaration.

### Proposed learning

When "hoist X into a named local at various positions" is exhausted and
inert (as round 24/25's history for this function shows in detail), the
next axis is not a fourth position for the SAME single-assignment
temporary -- it is whether the STORE-BACK itself should be a single
fused expression (`rec->unk4 = cursor + 1;`) or split into a redundant
self-store plus a re-read-and-increment from memory. The two compile to
the same VALUE but not the same DEPENDENCY GRAPH, and GCC 2.6.3's
scheduler evidently keys off the latter. This is a distinct axis from
every "declaration order" and "named temporary placement" variation this
report's round-24/25 history already tried, which is why decomp-permuter
found it and six hand attempts across two rounds did not.

## Original stall report (rounds 24-25, runner alpha), preserved below

## What it is

A per-channel/slot "dispatch event" function. Reads the active state
block's `unk2C` byte (via `rec + rec->unk12`, this unit's recurring
runtime-offset idiom), the record's `unk4C` field, and the current byte
at the sequencer cursor, packs `(slot << 8) | channel` into one word, and
calls a cross-unit function (`SpuVmPitchBend`, defined in `code_179d8_m`,
NOT YET MATCHED there as of this round -- so its real prototype is
unverified) with those four values. It then calls the shared
`func_80035E80` VLQ-decode helper and caches the return into `rec->unk88`,
same pattern as every other function in this family.

```c
void func_80035A7C(s16 a0, s16 a1)
{
    Entry90902E8 *rec = &D_800902E8[a0][a1];
    u8 *cursor = rec->unk4;
    u8 b;
    u8 *p;

    rec->unk4 = cursor + 1;
    b = *cursor;
    p = (u8 *)rec + rec->unk12;
    SpuVmPitchBend((a1 << 8) | a0, rec->unk4C, p[0x2C], b);
    rec->unk88 = func_80035E80(a0, a1);
}
```

## Levers that closed most of the gap

1. **`&D_800902E8[a0][a1]`, not a named `tbl` temp** (same fix as
   `func_80034614`'s family) fixed the prologue register-order mismatch.
2. **Statement order matching retail's own read-byte-AFTER-store-back
   sequence.** The first attempt read `b = *cursor;` in the SAME
   declaration as `cursor`, before the `rec->unk4 = cursor + 1;`
   store-back -- retail's own disassembly stores the incremented cursor
   back FIRST, then reads the OLD cursor's byte via a register that
   survived the store (the store and the byte-load target different
   memory, so this is a pure scheduling choice, not a correctness one).
   Splitting `b`'s declaration from its assignment and moving the
   assignment to AFTER the store-back reordered several nearby
   instructions to retail's exact selection and moved the raw word-match
   from 24/44 to 36/44 in one rebuild.

## The residue that did not close (8 words)

```
262d8: TARGET lw v1,4(s0)         CURRENT lh a1,0x4c(s0)        )
262dc: TARGET lh a1,0x4c(s0)      CURRENT lw a3,4(s0)           ) reordered + register-renamed,
262e0: TARGET addiu v0,v1,1       CURRENT lbu v1,0x12(s0)       ) not a length or CFG difference --
262e4: TARGET sw v0,4(s0)         CURRENT addiu v0,a3,1          )  every value retail computes is
262e8: TARGET lbu v0,0x12(s0)     CURRENT addu v1,s0,v1          )  still computed exactly once here,
262ec: TARGET lbu a3,0(v1)        CURRENT sw v0,4(s0)            )  just in a different register and
262f0: TARGET addu v0,v0,s0       CURRENT lbu a2,0x2c(v1)        )  a different order relative to
262f4: TARGET lbu a2,0x2c(v0)     CURRENT lbu a3,0(a3)           )  the OTHER three field reads.
```

Retail reads the four call arguments in a fixed order (cursor pointer,
`unk4C`, cursor-increment-and-store, `unk12`, byte-at-cursor, pointer
combine, `ptr->0x2C`) and this project's C reproduces that PARTIALLY: two
attempts at forcing the exact retail read order via extra named
temporaries (a separate `note = rec->unk4C;` local; a further split into
`offset`/`status` locals for the `unk12`/`+0x2C` reads) both REGRESSED the
compiled length (44 -> 45+ words, confirmed via `funcdiff`'s drift
warning firing at tens of thousands of bytes each time) rather than
tightening the match, and were reverted. The remaining residue is a
register-choice/scheduling difference across four independently-loaded
values (`unk4C`, cursor, `unk12`, the byte), not a single missing or
extra instruction, and not yet reduced to one axis.

**Axes tried, all inert or regressive:** hoisting `(a1<<8)|a0` into an
early separate `s32 packed` local (no change to the score, only moved
where the reordering happened); hoisting `rec->unk4C` into an early named
local (regressed length); hoisting `rec->unk12`/`p[0x2C]` into named
locals in retail's read order (regressed length). Every attempt so far
varies WHICH VALUE gets an early named temporary; none has varied whether
the four reads should be structured as a single call expression at all
(e.g. as nested comma-like sequencing via a helper, or the reads issued
through pointer parameters) -- flagging this as the untested axis per
`docs/MATCHING-GUIDE.md`'s "a long attempt list is not a broad one"
caution, since three of the four attempts (this report's and the
`func_80034D90.md`/`func_80035E80.md` companions) share the same "add a
named temporary" axis.

## Round 25 update (runner alpha): re-verified, one new axis found, still stalled at 36/44

**Rebuilt and confirmed the round-24 figure reproduces exactly**: 36/44
raw word-match, length exact (44/44), same first real diff at word 23.
The preserved body above is unchanged from round 24's own finding.

**Explicit answer to the round-25 head's block-order broadcast: the lever
does NOT apply here, and here is why.** This function has ZERO branches
of any kind -- no `if`, no loop, no unconditional `j` to a shared join.
It is single straight-line code from entry to the two trailing `jal`s.
Both of the broadcast's shapes (an if/else arm that must jump over a join;
a duplicated assignment kept as two copies reaching a merge point)
require at least two CONTROL-FLOW PATHS converging somewhere, and this
function has exactly one path. Grepped the `.s` for `j\b` outside the two
`jal`s and the trailing `jr $ra`: no hits. This is a genuinely different
residue shape -- an INSTRUCTION SCHEDULING preference within a SINGLE
basic block, not a question of which source block falls through to which.

**New axis tried this round, and its negative result is itself the
finding:** declaring `rec->unk4C` as a separately-named local (`s32 note`
or `s16 note`, tried at three different positions in the declaration
list: first, immediately after `rec`, and immediately after `cursor`)
does change the SCHEDULING of the `unk4C` read -- it moves from `lh` at
the retail-matching position to an earlier `lhu` + manual sign-extend
(2 extra words, regressing length to 46/44) OR, once forced back to
`s32` to avoid the widening, keeps the length correct but ALSO shifts an
entirely UNRELATED, EARLIER computation (the channel/slot index
arithmetic for `&D_800902E8[a0][a1]`, words 5-10) that matched perfectly
in the baseline. This reproduced identically across all three
declaration positions, which rules out "declaration order" as the
mechanism -- **merely giving the compiler an extra independent live
range for `unk4C`, regardless of where, perturbs an unrelated earlier
scheduling decision.** This is a second, DIFFERENT source of instability
from the one already documented (axes that regress length by adding named
temporaries for the call arguments) -- that one was about the call-site
reads specifically; this one shows the disruption reaching backward past
the entire `&D_800902E8[a0][a1]` computation, three statements earlier in
the function and with no data dependency on `unk4C` at all. Reverted;
inlining `rec->unk4C` directly into the call (as in the preserved body)
avoids both problems but leaves `unk4C`'s own read scheduled ONE position
too early relative to the cursor read, which is the residue's actual
content at word 23.

**Also tried and inert:** swapping the textual order of the `vol`/`b`
reads (retail computes the `unk12`-based `vol` read before the cursor's
own byte read, `b`; the preserved body above now matches that order) --
no change to the score, confirming (again) that these two reads' RELATIVE
order to each other is not what the compiler's scheduler is keying off;
only `unk4C`'s placement relative to the cursor load is live.

**Proposed learning:** a source-level reorder that fails to move an
instruction can still be diagnostic. Trying every combination of WHICH
statement gets a name and WHERE it's declared, and getting the identical
early-region regression regardless, is itself evidence that the
perturbation is caused by the mere EXISTENCE of an additional live range
crossing the `&D_800902E8[a0][a1]` computation's own scheduling window,
not by any property of statement position CLAUDE.md's existing levers
(read order, named-temporary placement) address. This may be a case
where GCC 2.6.3's local list scheduler's tie-breaking is sensitive to
the total pseudo-register count already in flight at a given program
point -- worth a dedicated toolchain-reproducer investigation (not
attempted here; out of scope for a per-function match attempt) if this
shape recurs.
