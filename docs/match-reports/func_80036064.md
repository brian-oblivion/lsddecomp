## Residues found and fixed

1. **Unsigned compare needed.** `(v1 & 0xFFFF) < 10` must compile to
   `sltiu`, not `slti`. `v1`'s declared type has to be `u32` (a `u16` cast
   promotes back to plain `int` under C89 integer promotion and doesn't force
   an unsigned compare) so the AND result stays unsigned through the
   comparison.

2. **Control-flow shape: no early return.** Writing `if (cond >= 10) return
   -1;` up front puts the "return -1" code inline where the check is, and
   GCC lays the rest of the (much bigger) body out after it. Retail's -1
   case sits at the very END of the function with a forward branch from a
   *positive* `sltiu ... < 10` test guarding the main body -- i.e. the
   source is `if (cond < 10) { <big body> } else { result = -1; } return
   result;`, an if/else with a single tail return, not an early return. This
   was the single biggest structural fix; everything else in this function
   fell out once the control flow matched.

3. **A genuine "retail has an extra redundant `move`, my C doesn't" residue,
   fixed by a permuter-found trick.** Retail keeps `a0`'s raw value alive in
   its own register (`move v1,a0` at the top, then never touches `$a0`
   again) even though only `v1` (possibly negated) is used from then on. A
   straightforward `u32 v1 = a0;` lets GCC prove `a0` dead immediately after
   and fold `v1` onto `a0`'s own register, dropping the `move` entirely --
   one word short, everything after it shifted.

   Manual attempts that did NOT work: reordering, extra locals, a bare
   `__asm__("")` barrier placed either right after the `if` block or right
   before `u32 v1 = a0;` (the latter, tried first, over-corrected and merged
   *differently*, still one word short). A bare `__asm__("" :: "r"(a0))`
   *did* preserve the `move`, but was dropped as a candidate fix: CLAUDE.md's
   register-identity rule bans "an extended-asm operand constraint" outright
   for any value that has a plain C form, and only carves out an exception
   for hardware ops (GTE/COP2) that have no C spelling at all -- `a0` here is
   an ordinary `int` parameter, squarely outside that exception, regardless
   of how harmless the generic `"r"` constraint looks.

   The permuter (`tools/setup-permuter.sh func_80036064 <seed>`, `-j 6
   --stop-on-zero --best-only`) found a zero at iteration 599 using **pure
   C**: an `if (a0) { func_80038D74(0); } else { func_80038D74(0); }` with
   identical bodies in both arms, guarding the existing `if (s0 == 0)` call.
   Referencing `a0` again here -- even in a branch whose two arms do the same
   thing -- is enough to convince the register allocator `a0` needs to
   survive in its own register past the point `v1` is computed, reproducing
   retail's extra `move` and every register choice downstream of it (the
   `sll`/`negu` at the top also read `$a0` rather than `$v1` in retail, and
   flip back once the liveness is restored). This is legitimate: it's plain
   C with no register pinning of any kind, just a liveness nudge that
   happens to look like dead code. The permuter's own emitted form used an
   unnecessary intermediate `new_var` local; that was dropped as noise.

### Proposed learning

The documented "redundant move" residue class (DECOMPILATION_LEARNINGS: "It
resists goto/return spelling, temp placement, barriers and volatile") has at
least one instance where a working fix DOES exist in pure C, just not
through any of those four levers -- re-referencing the value that needs to
stay live, in a branch whose arms are otherwise identical, worked here after
barriers failed. Worth trying before writing off a redundant-move stall,
and cheap to find with the permuter specifically (manual search of this
shape is not an obvious thing to try by hand).
