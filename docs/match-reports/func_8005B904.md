## Two residues, both closed

1. **Caching `this->unk_0x14` in a local, not re-reading the field.** Retail
   loads `unk_0x14` into a register ONCE and keeps it alive across the
   entire first copy loop specifically so the second block's `+0x44` load
   (`lw a2, 0x44(t0)`) can reuse it directly. Writing `this->unk_0x14->unk_0x44`
   a second time (instead of caching the first dereference in a local)
   produced a fresh `lw v0,0x14(t0); lw a2,0x44(v0)` -- a redundant reload
   retail does not have. Introducing `DreamSysUnk14 *u14 = this->unk_0x14;`
   and referencing `u14` from both statements closed this immediately.
2. **A byte-array-only struct (`u8 raw[N]`) has alignment 1, and GCC 2.6.3
   inserts a RUNTIME alignment check for any struct assignment through a
   pointer whose target type doesn't guarantee word alignment** -- even
   when the two addresses involved provably ARE 4-aligned at runtime. The
   first `DreamSysUnk14Ext` definition (`typedef struct { u8 raw[0x28]; }`)
   triggered exactly this: retail's second copy has no `or`/`andi`/`beqz`
   alignment dispatch at all, just the same LOAD-LOAD-LOAD-LOAD /
   STORE-STORE-STORE-STORE shape as the first copy, but the byte-array
   version compiled to a guarded aligned/unaligned pair (matching NEITHER
   path exactly, since retail has neither the check nor the unaligned
   fallback). Changing the sole member to `s32 raw[0x28 / 4]` (word-array,
   4-byte-aligned by construction) removed the check entirely and matched
   byte-for-byte. This is the SAME mechanism as the already-documented
   `unknown_values_NxN[k]` byte-array pattern used throughout this header
   for genuinely-unconfirmed padding, but it is NOT interchangeable with a
   word array when the field is actually used as a struct-assignment
   source/destination through a typed pointer -- only then does the
   member's own alignment leak into codegen.

## Proposed learning

- **A block-copy struct whose only confirmed fact is its SIZE should be
  declared with `s32` members (or `s32 raw[N/4]`), not `u8 raw[N]`, whenever
  it is used as the operand of a whole-struct assignment through a pointer**
  -- not merely as an opaque `sizeof`-only placeholder that is never
  dereferenced. A byte array gives the type 1-byte alignment, and GCC 2.6.3
  responds to that by inserting a genuine runtime `or`/`andi`/`beqz`
  aligned-vs-unaligned dispatch around the copy that retail's binary does
  not have wherever the true struct is actually word-aligned (which,
  looking at this codebase's other confirmed structs, appears to be always
  -- nothing found so far is genuinely byte-packed). Fixed here for
  `DreamSysUnk14Ext`; worth checking any OTHER `u8 raw[N]`-only placeholder
  struct in this codebase that participates in a struct assignment (not
  just `sizeof`), since the same alignment-check residue would recur
  identically.
