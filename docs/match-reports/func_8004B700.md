## IMPORTANT correction discovered late this round: the function is genuinely
## 2 INSTRUCTIONS (8 bytes) SHORT, not merely misaligned

`funcdiff.py`'s denominator ("140 words") reads as if the compiled body
occupies the SAME byte range as retail (`0x3BF00`-`0x3C130`), and early in
this round's work that was misread as confirmation the body's length was
already correct. **It is not.** Direct inspection of the compiled `.o`
(`mipsel-linux-gnu-objdump -d build/src/class_3bb8c.c.o`, function
`func_8004B700`) shows the body spans `0x374`-`0x59c`, i.e. `0x228` = 138
words -- 2 words (8 bytes) SHORT of retail's 140. This is why an unrelated-
looking data reference late in the function (the `%hi`/`%lo(D_80086838)`
load) resolves to `0x80086830` instead of `0x80086838` in the FINAL LINKED
image: the whole tail of this build's OWN function is 8 bytes short, so
everything addressed via an absolute link-time constant from that point
onward (including a completely unrelated DATA symbol later in the image)
reads 8 bytes low. **Do not trust `funcdiff`'s window/denominator as proof
of correct length** for a function with this large a residue -- diff the
`.o` file's own instruction count against `retail_len/4` directly first.

## Residue: if/else branch LAYOUT (not values) is backwards, independent of
## the missing-2-instructions issue

Retail's `bnez self->unk68->unk4, SUBTRACT_BLOCK` places the `!= 0`
(SUBTRACT, `arg2 - 0x5000`) arm as the BRANCH TARGET (positioned second,
adjacent to the merge point) and the `== 0` (ADD, `arg2 + tbl`) arm as the
FALL-THROUGH (positioned first). Written the natural way --
`if (self->unk68->unk4 != 0) { SUBTRACT } else { ADD }` -- this compiles
with the OPPOSITE layout (SUBTRACT as fall-through, ADD as branch target);
inverting the C condition (`if (... == 0) { ADD } else { SUBTRACT }`)
DOES flip the compiled layout to match retail's polarity exactly (verified
via direct `.o` inspection, not just the diff score), but the overall
score got WORSE (49 vs 52), meaning something else regresses when the
layout is "more correct" locally -- almost certainly downstream register
allocation changes cascading from the swap, not evidence the swap itself
is wrong. **Whoever picks this back up: try the `== 0` / SUBTRACT-as-
`else` form FIRST** (it's the one that matches retail's actual branch
polarity) and diagnose the regression it causes rather than reverting to
the naturally-worse-polarity form that happens to score higher on this
one metric.

### Proposed learning

**`funcdiff.py`'s reported byte RANGE for a function is not proof its
compiled length matches retail, even when the diff shows no explicit
"differs outside this range" WARNING for small function-body checks done
mid-investigation** -- the warning fires reliably for a *linked, checked*
build, but a function can still be internally short in a way that only
shows up as a downstream absolute-address constant (a `%hi`/`%lo` pair
against a data symbol, in this case) resolving to the WRONG value. When any
LUI/ADDIU pair or absolute load in a diff shows a constant offset by some
NUMBER-OF-BYTES from the expected symbol, and that number is a small
multiple of 4, suspect the CURRENT function is that many bytes short (or
long) BEFORE suspecting the referenced symbol or the header. Confirm by
counting the compiled `.o`'s own instructions
(`mipsel-linux-gnu-objdump -d build/src/<unit>.c.o`, find the function,
subtract start from end) against the retail length from the `.s` file's own
`nonmatching <func>, 0x<LEN>` header line.
