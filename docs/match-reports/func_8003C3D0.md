## What it does

Shared verbatim between StreamTask's own vtable and the base task class's
vtable at slot `+0x050` (an unoverridden inherited slot, confirmed by
`classtable.py` showing the identical function address at that offset in
both `D_8006E5F8` and `D_8006E730`). Ticks two slots (`+0x090`, `+0x074`)
on the `unk18` sub-object, one slot (`+0x050`) on the `unk78` sub-object,
then, only when `unk34` is set, dereferences `unkC` (a pointer-to-pointer
field) and dispatches ITS OWN slot `+0x078` with the address of this
object's own `unk93` byte (only its address is used -- the field's true
extent is not derived here) and a literal 0.

## Same "cache the vtable pointer" residue as func_8003C11C

The first attempt wrote `self->unk18->methods->slotXX(self->unk18)`
twice (once per slot). That reloads `self->unk18` fresh via `lw
$a0,0x18($s0)` at EACH call site (two total), where retail loads
`self->unk18` into a saved register ONCE and reuses it for both
dispatches. Caching it in a local (`Obj18 *obj18 = self->unk18;`) fixes
it exactly -- see func_8003C11C.md's "Proposed learning" for the general
pattern; this is the second confirmation of it in the same pass. Note
`self->unk78` (used only once, for the third dispatch) did NOT need this
treatment -- the fix only matters when the SAME field is dispatched
through more than once in a row.
