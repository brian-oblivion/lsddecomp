### The 9 words: a load-delay `nop` maspsx does not emit (TOOLCHAIN, escalated)

Round 26 filed these as "Missing load-delay-slot NOPs in the two field-copy
blocks" and attributed them to cc1: *"GCC's delay-slot filler always finds
the following store's OWN `lui` (provably independent of the just-loaded
value) and schedules it into the load-delay slot instead of wasting the
cycle."*

**That attribution is wrong, and it is wrong in the way that costs rounds:
cc1 never emits that `lui` at all.** Dumping the pinned pipeline stage by
stage shows cc1 emitting the bare Sony macro form:

```
lbu	$3,0($2)
sb	$3,G1          <- one macro; the lui $at does not exist yet
```

The `lui $at, %hi(G1)` appears only when the macro is expanded. So the
choice is made **below cc1**, and no C shape can reach it. Four rounds have
been sent looking for a source trigger that cannot exist.

**What actually differs.** ASPSX 2.34 decides the load-delay hazard on the
*unexpanded* next instruction: `sb $3, G1` reads `$3` immediately after the
`lbu` loads it, so it inserts a `nop`, and only then expands. maspsx decides
it on the *expanded* stream, sees `lui $at` interposed, and suppresses the
`nop`. maspsx states its own rule in its debug output -- the suppression is
conditioned on whether the next instruction uses `$at`:

```
lw	$2,P
nop # DEBUG: Reuse of '$2'. 'lbu	$3,0($2)' does not use $at
lbu	$3,0($2)
sb	$3,G1                       <- no nop: 'sb $3,G1' DOES use $at
```

**Minimal reproducer, through the pinned pipeline with the flags read from
the Makefile (never retyped) -- it REPRODUCES:**

```c
typedef unsigned char u8;
struct S { u8 a; };
extern u8 G1;
extern struct S *P;
void f(void) { struct S *p = P; G1 = p->a; }
```

```
retail/ASPSX:  lbu v0,0(v0) ; nop ; lui at ; sb v0,0(at)
this pipeline: lbu v0,0(v0) ;       lui at ; sb v0,0(at)
```

**Census over the whole retail image** (`objdump` of `disk/SLPS_015.56`,
pattern `<load R> [nop?] lui $at,.. ; s{b,h,w} R,..($at)`):

| | count |
| --- | --- |
| **with** the `nop` (retail's shape) | **40** |
| **without** the `nop` (this pipeline's shape) | **0** |

The rule is universal in retail, not contextual -- which is what makes this
a blocker rather than a curiosity.

**Why the image is still green, measured rather than assumed.** Every one of
the 40 sites was attributed against the real extents of the compiled-C
functions (`nm --print-size` over `build/src/*.c.o`, linked addresses from
`build/lsdde.map`), not by nearest-symbol guessing -- the first attempt at

## Findings (all measured against the `.s`, not guessed)

### 1. The volume-pan computation must store directly per-branch, not through a shared local

`func_800302DC` (already matched, same unit) computes an identical
`outA`/`outB` pair and returns them as call arguments -- there, a shared
pair of locals is correct because there's a single subsequent use. Here,
each of the three branches only ever STORES to `D_8008EA10`/`D_8008EA11`,
with no shared subsequent use, and retail's disassembly shows the two `sb`
stores duplicated verbatim in EACH branch (not once after a merged `if`).
Introducing `u16 outA, outB;` and storing once after the `if/else` compiled
to a single shared store reached through a `j` from each branch --
CORRECT semantics, WRONG shape (retail never merges these stores). Writing
the two globals directly inside each arm reproduced retail's byte pattern
in this branch exactly.

### 2. `D_8008EA18` (and transitively `D_8008EA24`) need `volatile` to force a genuine reload, but ONLY where a fresh read is actually taken

`D_8008EA18` is written once near the top (`D_8008EA18 = (u8) p2;`) and
read again ~40 instructions later for `D_8008D99C[result].unk0 =
D_8008EA18;`. Retail performs a REAL `lbu` reload there rather than reusing
the register that still holds `p2` (`s3`) -- store-to-load forwarding a
non-volatile global would otherwise let GCC skip the reload. Declaring it
`volatile u8` was necessary to reproduce the reload.

`D_8008EA24` is trickier and the two sites behave OPPOSITELY:
- The immediate post-field-copy check (`if ((s16) note == 0)`) reuses the
  REGISTER the field copy already loaded (`a0`), with NO reload -- so this
  site wants a plain LOCAL (`note`), not the volatile global.
- The `==0xFF` check (after the `func_8002D6A4()` call) needs a fresh `lh`
  (SIGNED) read from memory, and the plain copy into `D_8008D988[result]`
  a few statements earlier needs a fresh `lhu` (UNSIGNED) read -- confirmed
  from the raw opcode bits (`0x25`=LHU at one site, `0x21`=LH at the other,
  same symbol).
- Declaring `D_8008EA24` `volatile u16` broke the `(s16)` cast: a
  volatile-qualified load combined with a narrowing/widening cast compiled
  to a real `lhu` PLUS an explicit `sll`/`sra` sign-extend (3 instructions)
  instead of retail's single `lh`. **A non-volatile global with a `(s16)`
  cast at the point of use compiles the cast straight into the load
  instruction (`lh`)** -- this is the version that matches. The
  non-volatile declaration still produced the needed fresh reload at both
  later sites (apparently because of the intervening `func_8002D6A4()`
  call, which is enough of a barrier on its own without `volatile`).

**Net: `D_8008EA18` is `volatile`, `D_8008EA24` is plain `u16`, and the very
first use goes through a plain local (`note`) instead of rereading the
global.** Getting this combination right (after two wrong combinations)
closed a large fraction of the register-identity residue in the tail half
of the function.

### 3. Independent global stores get freely reordered/batched by GCC unless barred

Nine independent one-line assignments (`D_8008D996[result].unk0 = 0x21;`
… `D_8008D99C[result].unk0 = D_8008EA18;`) compiled, unbarred, into an
order the compiler chose for its own convenience: it clustered every
"already in a register" store first (the literals and the `p0`/`p1`/`p3`
copies) and deferred every store that needed a FRESH GLOBAL READ
(`D_8008EA13`, `D_8008EA24`, `D_8008EA18`) to the very end, batching all
three loads together right before their three stores. Retail's actual
order interleaves them (each fresh read happens immediately before -- or, in
`D_8008EA18`'s case, several statements before -- its own store, never
batched with the others). A bare `__asm__("");` between (most of) these
nine statements pinned them to source order and reproduced retail's exact
sequence, including the position of `D_8008EA18`'s read (hoisted early,
stored late -- solved by reading it into a local `pending18` at the point
retail's disassembly shows the `lbu`, then storing `pending18` nine lines
later) and one single-instruction (`li v1, 0x1`) placement that needed the
adjacent barrier REMOVED rather than added (see below).

**Barrier placement is not uniformly "more is better."** The literal `1`
loaded for `D_8008D9A3[result].unk0 = 1;` needed to float UP into the
delay slot right after `D_8008EA18`'s `lbu` (retail: `lbu a0,...; li
v1,0x1; ...; sh s5,...(p3's store); ...; sb v1,...(the 1)`). A barrier
sitting between the `p3` store and the `1`-store PREVENTED that float in
one attempt and had no effect once removed -- i.e. the two statements
around a delay-slot-filler-eligible constant needed to be barrier-free
relative to EACH OTHER while still being barrier-separated from their
neighbors. This was reached by direct experimentation, not derived.

### 4. NOT CLOSED: three residues survived every reshape tried

- **Busy-lock guard branch polarity.** `if (D_8008E934 == 1) return -1;`
  as the function's first statement compiles, here, to `beq
  v0,v1,FAR_LABEL` with the whole rest of the function as the fallthrough
  (locked case jumps far away). Retail's ACTUAL shape is the reverse: `bne
  v0,v1,NEAR_LABEL` (not-locked branches a few instructions forward) with
  the locked-case `return -1` inlined immediately after the test, reached
  by falling straight through when locked. The identical `if (locked)
  return -1;` construct produces the "near/inline" shape for
  `func_80031280` in THIS SAME unit (confirmed: this round's other match)
  but the "far" shape here. Tried: plain guard, `goto`-based guard to a
  dedicated `fail_nolock:` label, and a full inversion (`if (!locked) {
  ...entire 200-line body... } return -1;`, moving the busy-check's own
  failure arm to the textually-LAST position per the project's documented
  "arm that must jump has to be written not-last" rule) -- the inversion
  produced **byte-for-byte IDENTICAL output** to the plain guard, proving
  cc1 canonicalizes the two source forms to one IR before this layout
  decision is made, so this specific lever (which closed several
  functions per `DECOMPILATION_LEARNINGS.md`) does not apply here. This
  looks like a function-size- or context-sensitive REORG heuristic, not
  anything reachable from this construct's source shape.

- **Missing load-delay-slot NOPs in the two field-copy blocks
  (`SlotE968`, `RecordE978`).** Retail inserts an explicit `nop` after
  most `lbu`/`lhu` loads in these two blocks, immediately before the
  paired `lui at,%hi(target)` that computes the store address. My build
  never emits these nops -- GCC's delay-slot filler always finds the
  following store's OWN `lui` (provably independent of the just-loaded
  value) and schedules it into the load-delay slot instead of wasting the
  cycle. **This is not a cross-statement reordering** (confirmed: a bare
  `__asm__("")` immediately after each load, before its own store, had
  ZERO effect -- the `lui` that fills the slot is the very next
  instruction of the SAME statement's own codegen, not something pulled
  forward from later code, so a scheduling barrier has nothing to block).
  Also tried: caching the struct pointer vs. not (no effect), declaring
  the struct pointer(s) `volatile` (measured ZERO byte difference from the
  non-volatile version -- GCC 2.6.3 apparently does not let a
  volatile-qualified POINTER TARGET suppress this specific delay-slot
  optimization). This constitutes roughly 7-9 of the 13 missing words and
  is the single largest contributor to the remaining gap. If retail's
  build genuinely emits a wasted cycle here that a matching, differently-
  shaped C source would also produce, the trigger has not been found.

- **`result`'s register-identity ordering after the `func_8002CF18()`
  call.** Retail masks the call's return value to a byte IMMEDIATELY
  (`andi s0,v0,0xff`) into its long-lived (callee-saved) home, then makes
  a disposable WIDENED copy (`move v1,s0`) purely for the immediate
  comparison and the subsequent index multiply. My build does the reverse:
  an unmasked raw copy into a long-lived register first (`move s1,v0`),
  with the byte-mask (`andi s0,s1,0xff`) computed lazily, only when
  actually needed for the comparison. Both are semantically identical
  (`result` is always 0-255) and cost the same instruction count locally,
  but the difference is a genuine register-identity swap per
  CLAUDE.md rule 6, not reachable by reshaping (no combination of
  `u8`/`s32` typing for `result` was tried that changed this -- typing it
  `s32` and casting `(u8)` only at point of use was not attempted this
  round due to time; flagged as the one somewhat-promising untested axis
  below).

### Proposed learning

**A `volatile` qualifier's effect on codegen is not uniform across sites
using the same-shaped global, and is not even uniform in DIRECTION.** For
`D_8008EA24`, marking it volatile ADDED instructions (broke a cast-folds-
into-load optimization); for `D_8008EA18`, marking it volatile was
NECESSARY to force a reload that would otherwise be optimized away. Test
both directions on any "does this global need rereading" question, and
re-measure the cast-folding cost specifically when a narrowing/widening
cast is involved -- `volatile` plus a cast on a load is worth checking as
its own combination, not assumed to compose from the two effects
separately.

**A `__asm__("")` scheduling barrier only blocks CROSS-STATEMENT movement,
not a store's own address computation filling ITS OWN preceding load's
delay slot.** A barrier immediately after a load, before its paired store,
has no effect on this pattern -- the candidate instruction being placed in
the delay slot is not "pulled forward from later code" in the sense a
barrier prevents, it is the next instruction cc1 already generated for the
SAME source statement. If retail shows a wasted nop in this exact shape,
the trigger (if one exists) is not a barrier of this form.

This report's residue #1 concludes the guard polarity "looks like a

### The polarity IS reachable from source shape

Probes through the pinned pipeline, each a guard `if (LOCK == 1) return -1;`

| probe | fallthrough body | first branch |
| --- | --- | --- |
| A | straight-line stores, constant tail return | `beq` FAR |
| B | straight-line, tail return is a call's result | `beq` FAR |
| C | straight-line, guard also sets/clears the lock | `beq` FAR |
| D | straight-line, lock declared `volatile` | `beq` FAR |
| E | straight-line, a SECOND `return -1` in the body | `beq` FAR |

refuted**: F/G/H/I flip it with an ordinary source-level change.

The simple rule the table suggests — *straight-line fallthrough sinks the

branches near* — **cannot be what is happening here.** `func_80030E90`'s

result — it proves the toolchain innocent and the trigger contextual.* That
is the disposition here. Something in this function's real context dominates
the effect the probes isolate, and the probes do not capture it.
