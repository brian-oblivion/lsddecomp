## What it computes: this is PS1's `CdSearchFile`

Confirmed by the rodata strings this function references
(`asm/data/120C.rodata.s`): `"CdSearchFile: disc error\n"`,
`"CdSearchFile: searching %s...\n"`, `"%s:  found\n"`, `"%s: not found\n"`,
`"%s: dir was not found\n"`, `"%s: path level (%d) error\n"`. This is the
Psy-Q/retail reimplementation of the BIOS CD-ROM directory-search routine,
not an original LSD function — the game links its own copy rather than
calling through the BIOS jump table.

`arg0` is an output record pointer (`dst`), `arg1` is a `\`-delimited path
string (`path`), e.g. `"\SCUS1234;1"` or a nested `"\DIR\FILE;1"`.

## The `D_8008B3F8`/copy-source-offset-by-8 anomaly (important for the next attempt on this OR any sibling touching this table)

The flag-byte check and the name-compare call both use `D_8008B3F8 +
i*0x18` directly (matches the symbol splat named). The COPY, and the
returned pointer, use `D_8008B3F8 - 8 + i*0x18` — eight bytes EARLIER.
Confirmed by hand from the raw `.s` (`asm/nonmatchings/code_179d8_g/func_8002B640.s`,
around `.L8002B820`): `s0 = &D_8008B3F8 - 8`, `s3 = &D_8008B3F8`, both
advance by `0x18` per iteration; the flag/name reads use `s3`
(and a THIRD fresh `at = &D_8008B3F8 + off` computed independently for the
flag read alone), the copy and return value use `s0`.

**Reading is: `D_8008B3F8` is splat's name for the NAME/FLAG portion of a
record whose TRUE C-visible base sits 8 bytes earlier**, i.e. the actual
struct is `struct { u8 unk0[8]; char name[16]; }` (8+16=24=0x18, matching
the stride exactly) and splat picked its symbol from the more common
access pattern (the name/flag reads, which appear more often in the
disassembly scan) rather than the record's true base. This is NOT
established with the same confidence as e.g. the `CD_readm`
unfolded-addressing findings — it is a plausible reading that reproduces
the exact byte offsets, not something independently cross-checked against
a second consumer of the same table. **A future attempt should verify this
against whatever OTHER function reads `D_8008B3F8`'s neighbourhood** before
trusting it further; if confirmed, the natural fix is a single `extern
u8 D_8008B00xxx[]` declared 8 bytes before `D_8008B3F8`'s current address
and a real struct type spanning both.

## How this got from 16/186 (first compiling draft) to 183/186 compiled length

1. **The `id` parameter to `func_8002BC40` is NOT a constant `1` re-passed
   each iteration — it is the PREVIOUS call's return value, read straight
   out of the register it returned in.** The raw `.s` shows `a0` set to
   `1` exactly once (a delay-slot instruction at the function's very
   first branch) and never re-materialized before any later
   `func_8002BC40` call; `a0` is overwritten with the return value
   immediately after each call and left there until the next one. This
   makes the path-splitting loop a genuine hierarchical id-threading walk
   (root=1, each component resolves to its own id, fed to the next), not
   8 independent lookups under a fixed root — recognizing this is what
   made the whole loop's register behavior (a0 persisting across
   iterations without a reset) reproducible at all.
2. **The final struct copy needed a WHOLE-STRUCT ASSIGNMENT
   (`*(Rec8008B3F8Copy *)dst = *(Rec8008B3F8Copy *)copySrc;`), not six
   manual `*(s32*)(dst+N) = *(s32*)(copySrc+N)` statements.** The manual
   form compiles to interleaved load/store pairs (load-store-load-store);
   retail's actual shape is four loads into four DIFFERENT registers
   (`v0,v1,a0,a1`) followed by four stores, then a second load-pair/
   store-pair for the trailing 8 bytes. Only the whole-struct-assignment
   spelling produces this batched shape — this is the same "alignment-2
   struct copy compiles through `lwl`/`lwr`" family CLAUDE.md documents
   for unaligned copies, generalized here to an ALIGNED 24-byte copy that
   still needs the struct-assignment idiom rather than manual fields to
   get GCC's batching.
3. **The table-search loop's flag-byte read needed to stay an INDEXED
   GLOBAL (`D_8008B3F8[off]`) with `off` a separately-tracked running byte
   offset, not a dereferenced pointer sharing the loop's other
   incrementing pointers.** Using `rec[0]` (dereferencing the same pointer
   passed to the name-compare call) let GCC fold the flag-byte address
   into the SAME incrementing register, eliminating retail's
   `lui/addiu/addu` recompute-every-iteration and costing several words.
4. **The separator constant (`0x5C`) needed to be threaded through a
   NAMED local (`sep`) used consistently for the OUTER top-of-loop check**
   — an inline literal there let GCC drop the persistent register retail
   keeps for it (`$s4` across the whole outer loop), even though nothing
   else in the reshape touched that check.
5. **The inner char-copy loop needed its OWN, separately-declared
   constant (`sep2`, block-scoped) for its `!= 0x5C` comparison**, distinct
   from the outer `sep` — using the SAME variable let GCC unify them into
   one register and drop retail's separate (and, per the next point,
   apparently redundant) reload of the constant into a second register.

   lever tried moved it (the assignment is a single plain global-to-global
   copy; there is no smaller C form to try).
2. **A missing "genuinely redundant" reload, vram `0x8002B640`+0x1A0
   area/file `0x1BEE0`.** Retail keeps a SEPARATE constant-load (`li
   $v1,0x5c`) immediately after `addiu $s1,$sp,0x10`, BEFORE the first
   character reload (`lbu $v0,0(s0)`), then a real `nop` (the load-delay
   slot for that reload). This build's compiled output has both the
   constant load and the reload, but GCC's scheduler places them in the
   OPPOSITE order (reload first, then the constant load filling what
   retail leaves as a bare `nop`) — net one word shorter. **Both the
   original declaration order (`sep2` before the reload) and the reverse
   (reload before `sep2`) produce the IDENTICAL scheduled output**, and a
   `__asm__("")` barrier between them also made no difference — confirmed
   by direct measurement, not assumed. This is a scheduler
   delay-slot-filling PREFERENCE (retail's compiler chose not to move an
   independent, ready instruction into an available load-delay slot);
   CLAUDE.md's own test for the barrier's scope ("if it only changes
   instruction order, it is allowed") applies, but the barrier's failure
   here shows the order it would need to enforce is not the order any
   tried C phrasing produces.

   vram `0x8002B830`/file `0x1C030`.** The three loop-init assignments

### Redundant-raw-copy-elision investigation (this round's assigned question)

Residue 2 above (the missing constant-reload nop) and residue 3 (the

### Proposed learnings

- **A hierarchical id-threading argument (`func_8002BC40`'s first
  parameter here) can be recognized purely from a register's absence of
  re-materialization** — if a call's argument register is never freshly
  loaded between one call and the next occurrence of the same call site,
  and it IS overwritten with the previous call's own return value in
  between, the source almost certainly threads the return value forward
  as the next call's argument, even with no other textual hint. Worth
  checking this pattern before assuming a "constant" argument really is
  one.
- **Whole-struct assignment is the correct idiom for batched-register
  copies even when the struct is fully WORD-aligned** (not just the
  already-documented unaligned/`lwl`-`lwr` case) — manual per-field
  `*(s32*)(p+N)=` statements compile to interleaved load/store pairs
  regardless of alignment, and only `*(StructT*)dst = *(StructT*)src;`
  reproduces GCC's own batched-load-then-batched-store shape.
- **An indexed-global read sharing an increment with an otherwise-unrelated
  incrementing pointer gets folded into that pointer's register** — if
  retail's disassembly shows a freshly-recomputed `lui/addiu/addu` address
  for one field while a NEARBY, same-stride pointer is a real incrementing
  register, give the freshly-recomputed field its OWN separately-tracked
  index/offset variable rather than deriving it from the incrementing
  pointer, even though they are mathematically the same value at every
  iteration.
