## A real "must be a switch, not an if-chain" residue

The first attempt wrote this as a hand-rolled `if`/`else if` chain
mirroring retail's own branch polarity as closely as I could read it by
eye (`a1 == 7`, else `a1 < 8` with a nested `a1 == 5`, else `a1 == 8`,
else `a1 == 0x12`). That compiles to the RIGHT overall shape (grouping
5/7 behind a `slti $v0,a1,8` the same way retail does) but 4 WORDS SHORT
-- GCC does not synthesize the same `<8` grouping from hand-written
`if`/`else if` the way it does from an actual `switch` statement. Writing
it as a real C `switch` (case order 5, 7, 8, 0x12 -- NOT the "natural"
7, 5, 8, 0x12 top-to-bottom order retail's assembly seems to suggest at
first glance, which places the cold blocks in the wrong relative order
and costs 4 words the OTHER way, landing on 49/48 -- one too many)
reproduces retail's `slti`/`beqz`-grouped compare chain exactly at 56/56
words. This is a SPARSE switch (cases 5/7/8/0x12), so per CLAUDE.md's
`addiu_at` blocker note it compiles to compare-and-branch, never a jump
table -- confirmed by the object dump showing no `%lo($at)` jump-table
load anywhere in this function.

### Proposed learning

When retail assembly groups several small case values behind a
relational test (here: `slti $v0,a1,8` funnels 5 and 7 together before
testing which one), that shape is diagnostic of an ACTUAL C `switch`
statement in the source, not hand-rolled `if`/`else if` -- GCC 2.6.3's
switch lowering produces this grouping, but equivalent hand-written
`if`-chains do not reproduce it byte-for-byte even when the logical
control flow is identical. Try `switch` first for any multi-way branch
on a small integer in this project, even a sparse one. Case ORDER inside
the `switch` also matters for which cold block lands first in the
output -- if the word count comes up wrong by roughly the size of one
case's out-of-line block, try reordering the case list before
suspecting anything else.
