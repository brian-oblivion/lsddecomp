## Two distinct, diagnosed residues (not one)

Per DECOMPILATION_LEARNINGS' warning ("one instruction short" describes the
score, not the defect count) — this really is two separate things, and
fixing the first does not touch the second.

### 1. `CD_shell` genuinely takes ZERO arguments — the natural reading is arity 1, and it's wrong

The wrapper's naive read (`andi $a0,$s4,0xFF` sits right before ONE of the
two `jal CD_shell` sites, and DECOMPILATION_LEARNINGS' own "value in
an argument register live at the next call IS an argument" rule would say
pass it) is a trap here specifically. Read `CD_shell`'s own body
(`asm/code_179d8_mid.s`, `glabel CD_shell`): it never reads `$a0`
before overwriting it (first read of any register is `$v0`/`$v1` off two
globals). The `andi $a0,...` before the SECOND call site is dual-purpose —
it's ALSO the argument setup for the *next* instruction pair's call to
`CD_cw` reached via the branch's OTHER edge (`beq $s2,$v0,.L80028ED0`),
so its presence before `CD_shell`'s `jal` is incidental, not a real
argument. Declaring `CD_shell(void)` closed most of the instruction
mismatch but is not sufficient alone (see part 2).

### 2. A value survives the WHOLE loop in a dedicated callee-saved register (`$s7`) despite being a proven compile-time constant at every use, and a from-scratch reproducer shows GCC 2.6.3 folds the equivalent shape away

`$s7` is set to `0` once before the loop (`addu $s7,$zero,$zero`), read
exactly once inside the loop via `addiu $v0,$s7,1` (giving `1`, the
loop's early-success return value), reassigned to `-1` only in the
loop-exhausted tail (`addiu $s7,$zero,-1`), and read once more via the same
`addiu $v0,$s7,1` idiom (giving `0`, the final-failure return value). That
is a `status`-style local initialised to 0 and finalised to -1, always
returned as `status + 1`.

**Reproduced through the pinned toolchain in isolation** (not just
theorised): a minimal function with the identical shape —
`x = 0; if (cond) { opaque(); return x + 1; } x = -1; return x + 1;` —
compiles at `-O2` to a PLAIN `li v0,1` / `li v0,0`, with `x` never
materialised in any register at all, even across the opaque call. This
reproduces regardless of whether the surrounding shape includes a loop
with a back-edge (tested both ways). So the naive translation of this
idiom is a REAL residue, not a scheduling artefact: GCC 2.6.3, given this
shape, does NOT need a persistent register for it, and every reproducer
built from the natural reading of retail's control flow scores an object
that's exactly the right number of words SHORT (`$s7`'s own
save/restore pair, 2 words) of retail's.

**Not resolved.** No source-level restructuring tried (reordering the two
assignments, `volatile`, `__asm__("")` at either write site) reproduced a
persistent, unfoldable register for this value without introducing a
DIFFERENT defect (`volatile` forces a stack spill and a frame retail
doesn't have; unbarriered forms fold to nothing). This may mean the real
source's `status` value is NOT actually a compile-time-provable 0/-1 from
GCC's perspective — i.e. my reading of "always literally 0 then -1" may
itself be an oversimplification of a genuinely runtime-computed value that
merely EVALUATES to 0/-1 for this disassembly window. Flagging this as the
open question for the next attempt, rather than a closed dead end.

### Also unresolved: prologue register-to-parameter mapping

Independent of the two residues above, retail's prologue assigns
`$s1`=`arg1`, `$s3`=`arg2`, `$s4`=`arg0`, `$s2`=tag(`arg0&0xFF`) — i.e.
`arg1` gets processed into a callee-saved register BEFORE `arg0`, even
though `arg0` is referenced first in every natural C reading (computing
`tag`). This exact same pattern (`arg1` prologue-first) recurs in

driver's source, not noise in one function. **Six different local

never landed on retail's specific one. This reads as a genuine graph-

something controllable from the C source in any way tried so far.

### Proposed learning

**Before crediting an argument-register setup as evidence of a real
parameter (DECOMPILATION_LEARNINGS' "live at the next call IS an
argument" rule), check whether that same setup ALSO feeds a DIFFERENT
call reachable via the other edge of an intervening branch.** A delay-slot

incidental on the other — and the callee's own body (does it read the
register at all before overwriting it?) is the only reliable
discriminator, not the caller-side setup.

every use site, per hand-tracing, is not proof GCC will fold it — but a
FROM-SCRATCH REPRODUCER of the identical shape through the pinned

allocation on that reproducer is itself evidence the hand-traced value
claim is wrong, not that the toolchain is being inconsistent.** Build the
isolated reproducer before spending further attempts reshaping the real
function around an assumed-constant value.

### The real lever: write the retry loop as a genuine `for`, not `goto`-and-labels

This report's own residue #2 (the `errorCode`/`$s7` persistence gap)
concluded with an open question: "my reading of 'always literally 0 then
-1' may itself be an oversimplification... flagging this as the open
question for the next attempt." Investigated that open question directly
rather than accepting it as unresolved. The salvaged body's control flow
uses `goto`/labels throughout (`L_E4C`, `L_EE8`, `L_EF0`, `L_F08`); tried
rewriting it as a genuine `for (i = 3; i != -1; i--) { ... continue; ...
}` loop instead, mapping each `goto L_EE8`/`goto L_EF0` to `continue`
(the `for`'s own post-expression absorbs the explicit `i--` that used to
precede each of those gotos) and the one `goto L_F08` to a direct `return
errorCode + 1;`:

```c
s32 func_80028DF0(s32 arg0, s32 arg1, s32 arg2)
{
    s32 tag;
    s32 saved;
    s32 i;
    s32 byte0;
    s32 result;
    s32 errorCode;
    s32 *slot;

    tag = arg0 & 0xFF;
    slot = &D_8006D57C[tag];
    saved = D_8006D5FC;
    errorCode = 0;

    for (i = 3; i != -1; i--) {
        if (tag == 0x10 && !(D_8006D60C & 0x20)) {
            CD_shell();
            continue;
        }

        byte0 = arg0 & 0xFF;
        if (tag != 1) {
            D_8006D5FC = 0;
            CD_shell();
            if (arg1 != 0 && *slot != 0 && CD_cw(2, arg1, arg2, 0) != 0) {
                continue;
            }
            D_8006D5FC = saved;
            byte0 = arg0 & 0xFF;
        }

        result = CD_cw(byte0, arg1, arg2, 0);
        if (result == 0) {

        }
```

`errorCode` now DOES persist in a real callee-saved register
(`$s7`-equivalent, `move sN,zero` at the prologue, `addiu v0,sN,1` at
both use sites, `li sN,-1` at the tail) -- matching retail's mechanism

value's foldability was never really in doubt (a from-scratch reproducer
of the naive `goto`-labelled shape does fold it, confirmed again this
round independently) -- the actual lever was the LOOP'S OWN C-level
SHAPE, not anything about `errorCode` itself. A `goto`-threaded
retry-loop and a structurally-identical `for`-loop are NOT equivalent
inputs to GCC 2.6.3's optimizer for this purpose, even though they
produce the same control-flow graph: the `for` form lets GCC's
loop-recognition pass see this as a genuine loop with a live-out value

### What's left: a single extra instruction from a branch-polarity/tail-duplication difference, not `errorCode` itself

With `errorCode` now correctly persisted, the ONE remaining defect is a
`j <epilogue>` this build inserts that retail does not need. Retail's
early-success check (`beqz v0,<epilogue>` with `addiu v0,s7,1` in the
delay slot) branches DIRECTLY to the shared epilogue on success, reusing
the SAME conditional branch instruction to both exit the loop and reach
the return sequence. This build's equivalent check branches to the
LOOP-CONTINUE path on failure instead (opposite polarity) and falls
through into a SEPARATE unconditional `j` to reach the far-away epilogue
on success -- one extra instruction, a branch-target/tail-duplication
choice rather than anything about register content.

**Three narrow fixes tried against this specific instruction, all
negative:**
1. `if (result == 0) { return errorCode + 1; }` vs `if (result != 0) {
   continue; } return errorCode + 1;` (explicit inverted early-continue
   instead of an inline early-return) -- **byte-identical output either
   way**; GCC 2.6.3 canonicalizes both spellings to the same code here.
2. A bare `__asm__("")` between `errorCode = -1;` and the final `return
   errorCode + 1;` at the tail, on the theory that the SAME kind of
   barrier that (per this report's original residue #2) failed to
   prevent folding might at least affect ordering -- **no effect at
   all**, length unchanged. Confirms scheduling barriers cannot prevent
   constant-propagation folds; that pass runs earlier in the pipeline
   than instruction scheduling, so a scheduling-only barrier has nothing
   to act on here.
3. A block-scoped `volatile s32 tmp = errorCode; return tmp + 1;` at the
   tail (narrower than declaring the whole `errorCode` variable
   volatile, which round 16 already found forces a stack spill) --
   **regressed** to 22/82 with the SAME spill defect (frame grew to 86
   instructions), confirming the volatile-forces-a-spill finding
   generalizes even to this much narrower scope.

Not yet tried: varying which of the two exit conditions (success vs.
loop-exhaustion) is written as the "special" branch target at the SOURCE
level, independent of the return-vs-continue spelling (e.g. restructuring
so the FAILURE path is the one with an inline `continue` written FIRST in
program order, forcing GCC's fallthrough-preference heuristic to treat
the OTHER path as the branch target) -- flagging as the next candidate
rather than a closed question.
