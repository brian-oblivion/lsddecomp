## What this function does

A retry loop (up to 4 attempts) around a shared "poll/upload" call
(`func_80029F10`), gated by a byte "tag" (`arg0 & 0xFF`) that selects
special-case handling at value `0x10` and `0x1`, guarded by a driver flag
byte `D_8006D60C`, and bracketing every attempt with a save/clear/restore
of the global `D_8006D5FC` (the same global this unit's own
`func_80028DA8`/`func_80028DC0` expose as swap-setters, and that
`func_8002A400`, `func_8002ADE8` etc. in the still-uncarved sibling
`code_179d8_mid.s` also touch — this whole window is one driver's state
machine). Fully reverse-engineered control flow, confirmed against m2c's
independent read and against the raw bytes instruction-by-instruction (see
below); the STALL is entirely in reproducing retail's exact instruction
COUNT and REGISTER ALLOCATION, not in understanding what the function does.

`D_8006D57C` is a word array indexed by `tag`, and `arg1`/`arg2` are
forwarded generically (no dereference evidence beyond the call sites — see
`func_80029274`'s report for the same reasoning applied to a sibling).

## Two distinct, diagnosed residues (not one)

Per DECOMPILATION_LEARNINGS' warning ("one instruction short" describes the
score, not the defect count) — this really is two separate things, and
fixing the first does not touch the second.

### 1. `func_8002A400` genuinely takes ZERO arguments — the natural reading is arity 1, and it's wrong

The wrapper's naive read (`andi $a0,$s4,0xFF` sits right before ONE of the
two `jal func_8002A400` sites, and DECOMPILATION_LEARNINGS' own "value in
an argument register live at the next call IS an argument" rule would say
pass it) is a trap here specifically. Read `func_8002A400`'s own body
(`asm/code_179d8_mid.s`, `glabel func_8002A400`): it never reads `$a0`
before overwriting it (first read of any register is `$v0`/`$v1` off two
globals). The `andi $a0,...` before the SECOND call site is dual-purpose —
it's ALSO the argument setup for the *next* instruction pair's call to
`func_80029F10` reached via the branch's OTHER edge (`beq $s2,$v0,.L80028ED0`),
so its presence before `func_8002A400`'s `jal` is incidental, not a real
argument. Declaring `func_8002A400(void)` closed most of the instruction
mismatch but is not sufficient alone (see part 2).

### 2. A value survives the WHOLE loop in a dedicated callee-saved register (`$s7`) despite being a proven compile-time constant at every use, and a from-scratch reproducer shows GCC 2.6.3 folds the equivalent shape away

`$s7` is set to `0` once before the loop (`addu $s7,$zero,$zero`), read
exactly once inside the loop via `addiu $v0,$s7,1` (giving `1`, the
loop's early-success return value), reassigned to `-1` only in the
loop-exhausted tail (`addiu $s7,$zero,-1`), and read once more via the same
`addiu $v0,$s7,1` idiom (giving `0`, the final-failure return value). That
is a `status`-style local initialised to 0 and finalised to -1, always
returned as `status + 1`.

**Reproduced through the pinned toolchain in isolation** (not just
theorised): a minimal function with the identical shape —
`x = 0; if (cond) { opaque(); return x + 1; } x = -1; return x + 1;` —
compiles at `-O2` to a PLAIN `li v0,1` / `li v0,0`, with `x` never
materialised in any register at all, even across the opaque call. This
reproduces regardless of whether the surrounding shape includes a loop
with a back-edge (tested both ways). So the naive translation of this
idiom is a REAL residue, not a scheduling artefact: GCC 2.6.3, given this
shape, does NOT need a persistent register for it, and every reproducer
built from the natural reading of retail's control flow scores an object
that's exactly the right number of words SHORT (`$s7`'s own
save/restore pair, 2 words) of retail's.

**Not resolved.** No source-level restructuring tried (reordering the two
assignments, `volatile`, `__asm__("")` at either write site) reproduced a
persistent, unfoldable register for this value without introducing a
DIFFERENT defect (`volatile` forces a stack spill and a frame retail
doesn't have; unbarriered forms fold to nothing). This may mean the real
source's `status` value is NOT actually a compile-time-provable 0/-1 from
GCC's perspective — i.e. my reading of "always literally 0 then -1" may
itself be an oversimplification of a genuinely runtime-computed value that
merely EVALUATES to 0/-1 for this disassembly window. Flagging this as the
open question for the next attempt, rather than a closed dead end.

### Also unresolved: prologue register-to-parameter mapping

Independent of the two residues above, retail's prologue assigns
`$s1`=`arg1`, `$s3`=`arg2`, `$s4`=`arg0`, `$s2`=tag(`arg0&0xFF`) — i.e.
`arg1` gets processed into a callee-saved register BEFORE `arg0`, even
though `arg0` is referenced first in every natural C reading (computing
`tag`). This exact same pattern (`arg1` prologue-first) recurs in
`func_80028F38` and `func_80029074`, so it is a real property of this
driver's source, not noise in one function. **Six different local
variable/statement orderings were tried** (see `func_80029074`'s report,
which documents the experiment matrix in full since it was the cleanest
test bed) and NONE reproduced retail's exact mapping — every reordering
attempt shifted the "which register gets which argument" outcome, but
never landed on retail's specific one. This reads as a genuine graph-
colouring/priority tie-break internal to GCC 2.6.3's allocator, not
something controllable from the C source in any way tried so far.

### Proposed learning

**Before crediting an argument-register setup as evidence of a real
parameter (DECOMPILATION_LEARNINGS' "live at the next call IS an
argument" rule), check whether that same setup ALSO feeds a DIFFERENT
call reachable via the other edge of an intervening branch.** A delay-slot
or pre-branch register load can be dual-purpose — required by one path,
incidental on the other — and the callee's own body (does it read the
register at all before overwriting it?) is the only reliable
discriminator, not the caller-side setup.

**A local that is providably 0 (or another compile-time constant) at
every use site, per hand-tracing, is not proof GCC will fold it — but a
FROM-SCRATCH REPRODUCER of the identical shape through the pinned
toolchain is normative, and disagreeing with retail's real register
allocation on that reproducer is itself evidence the hand-traced value
claim is wrong, not that the toolchain is being inconsistent.** Build the
isolated reproducer before spending further attempts reshaping the real
function around an assumed-constant value.
