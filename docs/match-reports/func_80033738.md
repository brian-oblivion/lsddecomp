## Summary

A reentrancy-guarded "process all sound slots" dispatcher: a global latch
(`_snd_ev_flag`) makes it a no-op on re-entry, otherwise it calls
`SpuVmFlush()` once, then walks a `screen x slot` grid
(`D_80090B68 x D_80090B6C`, both `s16` counts) skipping any screen whose
bit is clear in an active-screen mask (`_snd_openflag`), and for each
`[screen][slot]` record in `_ss_score` (the array this unit's other
functions already established -- see `func_800339AC`'s report) tests six
independent bits of `unk90` and dispatches to the matching handler, four of
them (`Snd_play`/`Snd_crescendo`/`Snd_decrescendo`/`func_80033AB0` x2)
nested *inside* the `unk90 & 1` case rather than as six flat siblings.

## How the disassembly was read (worth recording -- this is the load-bearing
part, not the plumbing)

- **The four `unk90 & 0x10/0x20/0x40/0x80` tests are NESTED inside the
  `unk90 & 1` case, not six flat sibling `if`s.** Retail's branch when
  `unk90 & 1` is *clear* jumps straight past all four nested tests to the
  `unk90 & 2` test. A flat reading (six independent ifs at one level) would
  have the `& 0x10` test's own address reachable regardless of bit 1, which
  is not what the branch target shows -- lining up branch TARGETS (not just
  delay slots) before trusting a control-flow reading is exactly the
  MATCHING-GUIDE residue-reading discriminator, and it mattered here.
- **`unk90` is reloaded via fresh `_ss_score[screen][slot].unk90` array
  indexing before *every* test, even when the previous test's call did not
  execute.** This is not caching-then-invalidating a pointer; it is simply
  what a straight-line sequence of separate `if (_ss_score[screen][slot].
  unk90 & MASK)` statements compiles to once the compiler cannot prove the
  global array is unmodified across an intervening call. No pointer
  variable was introduced for this reason.
- **Two different call-argument idioms coexist in one function, and the
  choice is what reproduces retail's induction-variable reuse:**
  - The four calls inside the `unk90 & 1` block reuse two `s16` locals
    (`screen16`, `slot16`) assigned *once* at the top of that block. Retail
    keeps this pair live in one register pair across all four calls with no
    re-truncation -- matching a named local read repeatedly, not a fresh
    cast each time.
  - The `func_800339AC`/`func_80033FB8` calls (bits `0x2`/`0x8`, outside
    that block) instead use fresh `(s16)screen`/`(s16)slot` casts at each
    call site. Retail recomputes the truncation (`sra` off a shared
    `screen<<16`/`slot<<16` accumulator, itself strength-reduced across the
    whole loop) at *each* of these two sites rather than reusing the
    `screen16`/`slot16` register pair, even though the values are
    numerically identical and `screen16`/`slot16` are still live and
    unclobbered. Writing these two calls with fresh casts (not through the
    named locals) is what reproduces this — using the cached locals here
    instead collapses the induction variable and mismatches.
  - The `func_800368E8` call (bit `0x4`) passes the raw `s32` loop
    counters with no cast at all, matching its known `(s32, s32)`
    prototype (already established in the sibling unit `code_179d8_f.c`).
- **The outer `D_80090B6C <= 0` skip retail has is NOT a second explicit
  guard** -- writing one produces a redundant duplicate check (the
  documented "GCC does not dedupe an explicit guard against a for loop's
  own implicit entry test" pattern). Leaving it out and trusting the
  `for (slot = 0; slot < D_80090B6C; slot++)` loop's own -O2 rotation
  (guard + do-while) to emit that single check by itself reproduced retail
  exactly on the first attempt.
- **The `_snd_openflag` active-screen-mask skip IS a real, independent `if
  (...) continue;`**, not part of the for-loop's own rotation -- it tests a
  different condition than the loop bound, so no redundancy applies there.

### Proposed learning

When a `switch`-like sequence of independent bit tests on the same flags
word has SOME calls sharing a cached, explicitly-named local across several
call sites and OTHERS re-deriving the same numeric value via a fresh
explicit cast at each site, don't normalize to one idiom for the whole
function. Read which register survives across which calls in the
disassembly (does the argument register's value persist unchanged across
an intervening `jal`, or does a fresh `sll`/`sra`
truncation reappear right before each call): the former is a named local
reused; the latter is a cast expression written fresh at each site, and
GCC's own strength reduction/CSE will still share the *linear* part of that
computation (e.g. a `loopvar << 16` induction variable) across all such
sites even though the final truncation is repeated.
