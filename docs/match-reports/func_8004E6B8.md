# func_8004E6B8 (ORIGINAL REPORT, rounds 14/19 — see ROUND 37 note above: this residue description does not reproduce against today's toolchain and this exact preserved body; kept for its correct CFG/value derivation, which IS still accurate)

**Unit:** class_3bb8c_e (round 14, `Node3bb8cE` class). Predicted hardest
this round (5 distinct callee-saved registers). Restored to
`INCLUDE_ASM`.

## What it does

`s32 func_8004E6B8(Node3bb8cE *self, s32 *p1, s32 *p2, s32 *p3)`. Zeroes
`*p2`, then calls `func_8004E77C(self, p1, &localFlag, p3)` once (using a
LOCAL stack variable, not `p2`, for that call's own 3rd argument). If the
result is 0, or `*p1` is nonzero, or `*p3` is zero, retries up to 10 more
times — but every RETRY call uses `p2` itself (not the local) for
`func_8004E77C`'s 3rd argument. On exit, ORs `*p2` with the local flag and
returns the last call's result.

## Where it stands

**Control flow, branch targets, and every computed value are confirmed
correct** against `asm-differ` — this was checked instruction-by-instruction
against the disassembly, not just inferred. The residue is:

1. A missing ONE WORD (48 compiled vs retail's 49), and
2. Register-identity: mine assigns `$s0`=`p2`, `$s1`=`p1`, `$s2`=`p3`,
   `$s3`=retries; retail assigns `$s0`=`p1`, `$s1`=`p3`, `$s2`=retries,
   `$s3`=`p2` (`$s4`=`self` agrees in both).

The missing word traces to WHERE `self` (`$a0`) gets re-established before
the retry call: retail sets `$a1`/`$a2` as two ordinary instructions
inside the retry block, and defers `$a3` to the CALL's own delay slot —
but `$a0` isn't set inside the retry block AT ALL; it's set once, in the
delay slot of the earlier `beqz $a1, <retry>` check, which is shared by
all three "should I retry" tests. My best attempt instead re-establishes
ALL FOUR argument registers (`$a0`-`$a3`) as ordinary instructions
immediately before the retry call, wasting the jal's own delay slot on a
`nop` — functionally identical, one word more expensive in this
particular arrangement (a `nop` where retail has a register move, but
elsewhere retail spends a word my version saves, netting to a persistent
1-word gap I could not close).

## What was tried (9 attempts)

1. A `while ((result==0 || *p1!=0 || *p3==0) && retries--) { call2; }`
   loop with the first call outside it — reached 15/49 in range, but with
   **176KB of drift outside the function**: GCC's cross-jump pass merged
   the two textually-distinct calls to `func_8004E77C` into ONE physical
   call site (computing the 3rd argument differently on each incoming
   path, then jumping to a single shared `jal`), whereas retail keeps two
   separate `jal` instructions. This is the same family as the round-11
   "CROSS-JUMP / tail-merge" lesson, but for two calls that are NOT
   RTL-identical (they differ in one argument) — the merge still happened.
2. Wrapping the retry loop in an outer `if` guard with a `do-while`
   inside (delaying the retry-check CFG shape) — WORSE (185KB drift); GCC
   duplicated the condition test at both the top and bottom of the
   `do-while`, growing the function further.
3. A literal `goto`-based rewrite of the exact jump graph (`goto check;
   retry: ...; check: if (...) goto retry;`) with the SAME combined `||`
   condition as attempt 1 — identical result to attempt 1 (176KB drift,
   same merge). Proves the merge is not sensitive to `while` vs `goto`
   syntax, only to the RTL the condition compiles to.
4. The same `goto` structure but with the combined `||` condition split
   into THREE separate `if (...) goto retry;` statements (matching
   retail's THREE separate branch instructions exactly, rather than one
   fused boolean) — **this is the best attempt**: the cross-jump merge
   disappeared entirely (no more 176KB-scale drift), the compiled
   function is a near-exact structural match to retail (confirmed via
   objdump, instruction-by-instruction), and the residue narrowed to
   exactly the 1-word/register-identity issue described above.
5. Reordering local variable declarations (`retries`/`localFlag`/`result`)
   — no effect on register assignment (consistent with the
   already-established "declaration order doesn't affect allocation"
   rule).

## An important adjacent finding, NOT specific to this function

While deriving this function's needed return-value plumbing, `func_8004E77C`
(matched earlier this round as effectively `void`, since nothing in its
own body used the return value explicitly) had to be given a REAL `s32`
return type so `func_8004E6B8`'s C could read its result. **Adding
explicit `return func_8004E890(...); return 0;` statements to
`func_8004E77C` — changing NOTHING semantically — grew its compiled
length from 21 to 23 words** (confirmed via `objdump`, and it broke the
whole unit's build, cascading a `sha1sum FAILED` even though `make`
reported no compile errors). The fix was to keep `func_8004E77C`'s BODY
exactly as originally written (the bare `if (cond) { func_8004E890(...);
}` with no explicit `return`, letting `v0` carry through unmodified) while
only changing its DECLARED return type to `s32` (compiles with a
"control reaches end of non-void function" warning, which is expected
and harmless here). See `func_8004E77C`'s own report, updated with this
note.

**This refines the project's "a byte match tells you nothing about the
return type" family in the opposite direction of its usual application.**
The established lesson says a caller discarding a return value doesn't
prove the callee is `void`. This case shows the converse hazard: once a
function's own body relies on an IMPLICIT leftover value in `$v0` rather
than an explicit `return`, WRITING that implicit reliance out explicitly
as real `return` statements is not free — it can add real instructions
(here, an extra unconditional jump to skip the "return 0" case cleanly).
**Retype the declaration; do not rewrite an already-matched body to add
explicit returns it does not need.**

### Direction NOT tried, with reason

Did not attempt writing this with `register T v asm("$N")` or any operand
constraint to pin the register numbering — explicitly banned by
CLAUDE.md rule 6, and this is precisely the class of residue (same
values, different register identity) that rule targets. Also did not
attempt splitting the retry-call's four argument setups across
statement boundaries to try to force `$a0` into a shared delay slot
(the way retail does) — ran out of attempt budget (9 used) before
trying this; it is the most promising untried direction, since attempt 4
already reproduces retail's per-check branch STRUCTURE exactly and the
remaining gap is purely about WHERE `$a0` gets (re-)established.

### Proposed learning

**Splitting one fused `||`/`&&` boolean condition into separate `if
(...) goto` statements per sub-condition can eliminate a GCC 2.6.3
cross-jump merge that the fused form triggers**, even when the two call
sites being merged are not RTL-identical (they differ in one argument).
This is a new, more specific lever for the round-11 "cross-jump merges
two source-distinct statements" family: previously documented fixes
changed the STATEMENTS being merged (post-increment vs pre-increment,
distinguishing two calls); this one changes how the SURROUNDING CONTROL
FLOW is expressed, leaving both calls' own text unchanged.


Result: **6/49, WITH massive drift** (176451 bytes outside range) --
far worse than the preserved 1-word-short attempt, and for a structural
reason: this reordering reintroduced something resembling the round-14
attempt-1/attempt-3 cross-jump/merge pathology (the compiled retry block
grew rather than shrank). Reverted immediately; confirmed the reversion
rebuilds green (`build exit=0`, whole-image OK).

**This disproves the hypothesis that retail's post-call instruction
POSITION reflects a source-level statement-order difference.** The
retries-check instructions appearing after the `jal` in retail's own
bytes is itself the SCHEDULER's/delay-slot-filler's output, not evidence
about where the check was written in source -- attempt 4's structure
(retries check BEFORE the call, matching this report's preserved body)
is very likely already the correct source shape; what remains unclosed
is genuinely a cross-basic-block delay-slot-filling decision (GCC's
branch-delay-slot filler hoisting the retry block's `self` argument
setup up into the preceding conditional branch's delay slot, a
machine-dependent scheduling pass operating across basic block
boundaries) rather than anything expressible as a plain source
reordering. Filing unchanged as STALL; the "most promising untried
direction" from round 14 is now tried and ruled out.

### Proposed learning (round 19)

**Not every "instruction X appears after instruction Y in retail's
bytes" implies "statement X comes after statement Y in source."** When
the two instructions in question sit either side of a call/branch (here,
a retry-count check straddling a `jal`), the ORDER in the final binary
can be entirely a delay-slot-filling/scheduling artifact rather than a
reflection of source statement order -- reordering the SOURCE to match
binary instruction order literally made this residue much worse (6/49
with drift, vs. the existing 1-word-short/register-renumbering-only
result). Before reordering statements to "match the asm", check whether
the reordering candidate straddles a branch or call; if it does, the
asm's instruction sequence there is scheduler output, not a source clue.
