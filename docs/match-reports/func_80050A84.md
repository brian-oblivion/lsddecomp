## What it is

An argument-less wrapper around `func_80050948`, the 79-word body in the same
unit. It has no callers anywhere -- no `jal` from any segment and no data
pointer to it -- so it is either dead or an exported entry point.

Retail's delay slot on the call is a bare `nop`, which is the decisive detail:
**no argument register is set up at the call at all**, so the wrapper passes
nothing.

```

addiu sp,sp,0x18
```

## CORRECTION to func_80050B28's report

That report's "next moves" predicted this function would "likely present the
same question" as its own home-slot residue, and recommended attempting the
two together. **The prediction was wrong and the reasoning was bad.** It
generalised from "same call chain, same unit, similar size" -- none of which
bears on the residue. `func_80050B28`'s residue exists because it has an
incoming PARAMETER that must survive a call; `func_80050A84` has no parameter
at all, so the mechanism cannot arise. Its delay-slot `nop` says so on the
face of the disassembly, which is one grep away and was not run before the
prediction was written.

The transferable point: **a residue class is a property of the FUNCTION'S OWN
SHAPE, not of its neighbourhood.** Sharing a call chain, a unit, or a carve
predicts nothing about sharing a residue -- exactly the error
`docs/PARALLEL-RUNS.md` warns about in the other direction when it says a
blocker's scope is measured, not reasoned.

### Proposed learning

**A bare `nop` in a call's delay slot is positive evidence that the caller
passes NO arguments**, and it is worth reading before writing a wrapper's
signature. GCC fills a call delay slot with argument setup whenever there is
any to do, so a `nop` there means there was none. That distinguishes
`return callee();` from `return callee(arg);` at a glance -- and those two
compile to different bytes, unlike the return-type question in the same
position, which compiles to identical bytes and cannot be read off at all.
