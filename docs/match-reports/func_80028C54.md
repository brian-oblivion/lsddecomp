## HEAD ADJUDICATION (round 17) — the fold is NOT unconditional, and NOT the `VabStreamObj__PlayTone` class

Runner echo reproduced `if (call() != 0) return 0; return 1;` compiling to a
branchless `sltiu` and asked whether this is the same underlying GCC 2.6.3
behaviour as `VabStreamObj__PlayTone`'s div/mod fold. It is not, and the fold has a
narrow escape the report did not find.

### What the fold actually keys on

Through the pinned pipeline, four variants:

| source | result |
| --- | --- |
| `if (call()!=0) return 0; return 1;` | `sltiu v0,v0,1` — branchless |
| `r = call(); if (r!=0) return 0; return 1;` | `sltiu v0,v0,1` — identical |
| `if (call()!=0) { a(); return 0; } b(); return 1;` | **real branch** (`bnez`) |
| `if (call()!=0) return 5; return 9;` | **real branch** (`bnez`) |

So the fold is **boolean materialization**, and it fires only when the
function's whole job is to turn a comparison into 0/1 with no other work in
either arm. Two things break it, and both are ordinary C rather than tricks:

- **a side effect in an arm**, and
- **return values that are not 0 and 1.**

### What that means for this function

Retail has a branch here. Retail came out of this compiler. So retail's
source is **not** `if (call() != 0) return 0; return 1;` — it is doing
something else in at least one arm, or returning something other than a bare
0/1 pair. That is where the next attempt should look: read what else retail
does on each path before the return, rather than trying to defeat the fold.

### Why it is not the `VabStreamObj__PlayTone` class

Different pass, different escape. `VabStreamObj__PlayTone` is a strength reduction
(`x - (x>>k)*N` -> `x & (N-1)`) whose escape is narrowing the multiplicand's
TYPE. This one is boolean materialization whose escape is having any work in
an arm. Nothing about narrowing a type touches it, and nothing about adding a
side effect touches the other.

**What the two DO share is the failure mode, not the mechanism** — both were
filed as "unconditional" after probing one axis. That resemblance is what
made them look like one class. It is worth naming precisely because it will
recur: two folds being folds is not evidence they are the same fold.
