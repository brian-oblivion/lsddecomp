## Applying the no-cache idiom: it worked, and it was the right fix

The earlier 24/25 body kept `c1 = *s1;` / `c2 = *(s2 - 1);` in the
mismatch tail -- a genuine RE-cache of values GCC's CSE then optimized
away (since nothing had changed `s1` on that path since the last load),
requiring `volatile` to force back. Per the head's direction, the fix is
to stop caching at that use site entirely: the mismatch tail now
dereferences `*s1` and `*(s2 - 1)` directly in the `return` expression,
with NO local reassignment for GCC to CSE away in the first place. This
eliminated the reload problem AND the `andi $v1,$v1,0xff` mask that
`volatile` had been introducing as a side effect at the LOOP TOP (an
unrelated location) -- confirming the head's read that the mask was
entirely an artifact of the `volatile` qualifier, not something the
un-cached shape needs.

**Important scope note on "stop caching":** a from-scratch attempt that
removed `c1`/`c2` ENTIRELY (comparing `*s1 == *s2` directly at
`loop_start`, `*s1 == 0` directly at `loop_check`) was tried FIRST and
scored much worse (13/25, with the loop's own internal structure
reordered by GCC into a different shape entirely -- `*s1==0` checked
BEFORE the char comparison rather than after, per `func_8002C048`'s own
build log this session). The caching at `loop_check`'s "is this the
matched byte a NUL?" test is NOT the same defect as the tail's redundant
reload -- `c1` there is a genuine cross-statement carry of "the byte the
previous iteration already matched", not a same-value re-read, and
keeping it cached is what reproduces retail's loop shape. **The
documented idiom applies at the specific use site where GCC is proven to
be eliminating a reload, not as a blanket "remove all locals" rule** --
over-applying it regressed the score by 10 words. This is worth recording
because it is the natural next place to over-correct after being told the
"axis never varied" was keeping the locals.

## The remaining single residue (2 of 25 words)

With the no-cache tail in place, the ONLY remaining difference is a pure
INSTRUCTION-ORDER swap of the loop-top's two independent byte loads:

```
retail:  lbu $v1, 0($a0)      (c1, from s1)
         lbu $v0, 0($a1)      (c2, from s2)
mine:    lbu $v0, 0($a1)      (c2, from s2)
         lbu $v1, 0($a0)      (c1, from s1)
```

Both loads are register-identity IDENTICAL to retail (`$v1` ends up
holding `c1`, `$v0` ends up holding `c2`, matching retail exactly) --
only their relative ORDER differs. Per CLAUDE.md's own test ("if removing
it changes WHICH REGISTER holds a value it is banned; if it only changes
instruction ORDER it is allowed"), this is squarely in the ALLOWED
category for a scheduling barrier, and this residue class is exactly what
a bare `__asm__("")` is meant for.

**It did not respond to any lever tried:**
- Source statement order (`c1 = *s1; c2 = *s2;` vs the reverse) -- no
  effect on the compiled order either way, meaning GCC's list scheduler
  is not simply preserving or reversing program order here.
- A bare `__asm__("");` placed before both reads, and again placed
  between the two reads -- no effect in either position.
- Comparison operand order (`c1 == c2` vs `c2 == c1`) -- changed OTHER
  things (regressed to 22/25 and reintroduced the `andi`), no effect on
  the load order itself.
- Restructuring `loop_check`'s guard (`if (c1 != 0) { s1++; goto
  loop_start; } goto return_zero;` instead of the inverse) -- no effect.
- Folding `s2++` differently around the second read (`s2++; c2 = *(s2 -
  1);` instead of `c2 = *s2; s2++;`) -- large regression (12/25, whole
  loop restructured), reverted.

**Classification:** genuine instruction-order residue that resists the
one lever CLAUDE.md sanctions for this exact class. Not a register-pinning
candidate (nothing here would require pinning -- both registers already
match), just a scheduler decision this project's tooling could not steer
from the C source tried. Legitimate permuter candidate at 23/25: the
target is a 2-instruction swap with no semantic difference, about as
narrow a search space as this project is likely to produce.

### Proposed learning

Confirms and narrows `docs/DECOMPILATION_LEARNINGS.md`'s "do not cache a
value across the code that needs a fresh copy" idiom: it is a scalpel, not
a blanket rule. Apply it AT THE SPECIFIC USE SITE where a reload is being
eliminated (proven by comparing a with/without-cache diff), not to every
local in the function -- removing a cache that is carrying a genuine
cross-iteration value (not a redundant re-read) measurably regressed this
function by 10 words. The tell for "this cache is fine, don't remove it":
the cached variable's value differs from what a fresh dereference at that
point would read (here, `loop_check`'s `c1` is the PREVIOUS iteration's
byte, not the current `*s1`).
