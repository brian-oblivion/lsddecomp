## Why this works

The prior stall (see "Revision history" below) had exhausted the manual
levers CLAUDE.md sanctions for a pure instruction-order residue -- a bare
`__asm__("")` in either position around the two loads, comparison operand
order, guard restructuring -- none moved the load order. Materializing the
comparison's RESULT into its own named value, positioned between the reads
and the `s2++` increment, is a different kind of lever: it doesn't reorder
statements, it gives the scheduler an extra independent unit of work (the
`==` itself) to interleave with the two loads, and apparently that changes
which load the scheduler lists first. This is not something a human
reviewer reaches for naturally -- it was the permuter's random
statement-splitting mutation that found it, in well under a hundred
iterations once seeded from a body that already matched everything except
this one swap.

## Revision history on this report

An EARLIER version of this report recorded a 24/25 near-miss body that
used `*(volatile u8 *)s1` casts to force a reload. The head correctly
flagged that as suspect: `volatile` there was fighting a CSE the project
already has a documented idiom for (`docs/DECOMPILATION_LEARNINGS.md`'s
"do not cache a `this->field` across an intervening call -- re-read it at
each use site", generalized here to "don't cache a dereferenced value
across the code that needs a fresh copy of it"), and a body that only
reaches its score via a codegen-lever qualifier is not a body that likely
matches the original source. That guidance was applied and produced a
23/25 body with no `volatile` anywhere and a single clean instruction-order
residue -- see below -- which the permuter pass this round then closed.

## Applying the no-cache idiom: it worked, and it was the right fix

The earlier 24/25 body kept `c1 = *s1;` / `c2 = *(s2 - 1);` in the
mismatch tail -- a genuine RE-cache of values GCC's CSE then optimized
away (since nothing had changed `s1` on that path since the last load),
requiring `volatile` to force back. Per the head's direction, the fix was
to stop caching at that use site entirely: the mismatch tail dereferences
`*s1` and `*(s2 - 1)` directly in the `return` expression, with NO local
reassignment for GCC to CSE away in the first place. This eliminated the
reload problem AND the `andi $v1,$v1,0xff` mask that `volatile` had been
introducing as a side effect at the LOOP TOP (an unrelated location) --
confirming the head's read that the mask was entirely an artifact of the
`volatile` qualifier, not something the un-cached shape needs.

**Important scope note on "stop caching":** a from-scratch attempt that
removed `c1`/`c2` ENTIRELY (comparing `*s1 == *s2` directly at
`loop_start`, `*s1 == 0` directly at `loop_check`) was tried FIRST and
scored much worse (13/25, with the loop's own internal structure
reordered by GCC into a different shape entirely). The caching at
`loop_check`'s "is this the matched byte a NUL?" test is NOT the same
defect as the tail's redundant reload -- `c1` there is a genuine
cross-statement carry of "the byte the previous iteration already
matched", not a same-value re-read, and keeping it cached is what
reproduces retail's loop shape. **The documented idiom applies at the
specific use site where GCC is proven to be eliminating a reload, not as a
blanket "remove all locals" rule** -- over-applying it regressed the score
by 10 words.

## The residue that was closed (2 of 25 words, at the 23/25 stage)

With the no-cache tail in place, the only remaining difference was a pure
INSTRUCTION-ORDER swap of the loop-top's two independent byte loads:

```
retail:  lbu $v1, 0($a0)      (c1, from s1)
         lbu $v0, 0($a1)      (c2, from s2)
was:     lbu $v0, 0($a1)      (c2, from s2)
         lbu $v1, 0($a0)      (c1, from s1)
```

Both loads were already register-identity identical to retail (`$v1` held
`c1`, `$v0` held `c2`) -- only their relative order differed. Manual levers
tried and rejected before the permuter pass: source statement order
(no effect either way), a bare `__asm__("")` before or between the reads
(no effect), comparison operand order (regressed to 22/25, reintroduced
the `andi`), guard restructuring (no effect), folding `s2++` differently
(regressed to 12/25). The permuter closed it via the "materialize the
comparison result between the reads and the increment" lever described
above, which none of those manual attempts happened to try.

### Proposed learning

A pure instruction-order swap of two independent, already register-correct
loads is NOT reliably fixable by a bare `__asm__("")` scheduling barrier --
this function is a confirmed counterexample (barrier tried in both
positions, no effect) where the fix instead came from giving the scheduler
an extra independent computation (the comparison result, materialized into
its own local between the reads and a subsequent increment) to interleave
with. This is squarely the permuter's territory: a 2-instruction swap with
zero semantic difference is about as narrow a search space as this project
produces, and it closed in under 100 iterations here. Confirms
`func_8002C048` as a second data point (after `TaskCore__TickFadeOutCallback` this same
round) that a documented "resists the standard levers" residue is still
worth a bounded permuter pass before being accepted as final -- the
standard levers not working does not mean the class is unfixable, only
that the specific lever tried doesn't reach it.
