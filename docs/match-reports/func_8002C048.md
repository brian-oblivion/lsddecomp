## Three separate residues found and fixed, in order

1. **Branch polarity from literal control-flow transcription.** The
   preamble's three checks (`s1==NULL`? `s2!=NULL`? `s1==s2`?) are NOT
   nested the way a naive reading suggests (`if (s1==NULL) { if
   (s2!=NULL) goto loop; }`) -- retail's actual shape is SEQUENTIAL: `if
   (s1==NULL) goto check_eq;` (skipping the `s2` check entirely when
   `s1==NULL`) `if (s2!=NULL) goto loop_start;` (only reached when
   `s1!=NULL`). Fixed by transcribing the literal `.s` branch targets with
   `goto`, exactly the discipline `func_80052D10`'s report (this unit's
   sibling `class_3bb8c_k`, this round) already documents for 3-way
   dispatches: read the actual branch graph, not the textual nesting a
   quick read suggests.
2. **A shared 2-instruction tail block** (`return 0`, reached both by
   falling through from the `s1==s2` check AND by an explicit `goto` from
   deep in the loop) **needs the right polarity on ITS OWN guard to get
   reused rather than duplicated.** `if (s1 == s2) goto return_zero;`
   compiled the shared block fine but scrambled a LATER, unrelated branch's
   sense; `if (s1 != s2) goto not_equal; return_zero: return 0;` (goto the
   FAILURE case, fall through to the shared success block) is what
   actually let GCC reuse the same two words for both the fallthrough and
   the backward `goto`. Devising which of two logically-equivalent
   guards produces sharing rather than duplication took several attempts;
   there is no static rule found for predicting it other than trying both.
3. **A CSE'd-away reload, fixed by a targeted `volatile` cast -- but with
   a side effect.** After (1) and (2), 17/25 words matched with one
   remaining defect: retail reloads `c1` from `*s1` a second time in the
   mismatch tail (`lbu $v1, 0($a0)` at `.s` offset `0x1C894`) even though
   nothing changed `s1` since the earlier load on that specific path, so
   plain `c1 = *s1;` there got optimized away by GCC's own CSE (the
   register still holds the right value). Casting through `*(volatile u8
   *)s1` at BOTH the loop-top read and the tail-mismatch read (one alone
   was insufficient -- tried each individually, see attempts log below)
   forced the reload AND, as an apparent side effect, fixed a register-
   order swap in the loop-top's two `lbu`s that had been present since
   before the `volatile` was added. This got to **24/25**.

## The remaining single-word residue

With the `volatile` cast in place, GCC additionally emits `andi $v1,
$v1, 0xff` immediately after the loop-top's two byte loads (`.s` offset
approximately `0x1C888`) -- retail has a plain `nop` there instead. This
reads as a defensive re-mask GCC inserts specifically because a
`volatile`-qualified load's value is not trusted to already be
zero-extended for the immediately following comparison, even though a
plain (non-volatile) `lbu` demonstrably would be trusted (as shown by
every OTHER byte load in this same function, none of which get an `andi`).

**Attempts to eliminate the `andi` without losing the reload fix, all
unsuccessful:**
- `u8` instead of `char` for `c1`/`c2`'s declared type -- byte-identical
  result (expected: `char` already means `u8` under `-funsigned-char`).
- Marking `c1` itself `volatile` (rather than casting the pointer at each
  read site) -- catastrophic regression (13+ extra loads/stores, `c1`
  spilled to memory throughout the whole function, score collapsed).
- Casting `s2`'s loop-top read through the same `volatile u8 *` pattern
  (symmetry with `c1`) -- no change to the `andi`.
- Swapping the comparison operand order (`c2 == c1` instead of `c1 ==
  c2`) -- large regression, unrelated control flow scrambled again.
- Explicit `(s32)c1 == (s32)c2` cast in the comparison -- no change.

**Classification:** this is a genuine register-IDENTITY-adjacent residue
in the sense CLAUDE.md's rule is about (removing something changes what's
in a register / what gets masked), not a pure instruction-order one -- so
per the project's own test ("if removing it changes WHICH REGISTER holds
a value, it is banned"), reaching for `register T v asm("$N")` or an
operand constraint to force the exact retail shape here would cross the
line explicitly forbidden by CLAUDE.md, and was correctly not attempted.
The `volatile` qualifier itself is legitimate C (explicitly endorsed as a
lever in `docs/MATCHING-GUIDE.md`'s residue list -- "frequently a missing
volatile"), but its side effects here are a package deal: it buys the
reload and the register-order fix together with an unwanted extra `andi`,
and no combination of placement tried separates the wanted effects from
the unwanted one.

### Proposed learning

A `volatile` cast at ONE specific dereference can simultaneously fix a
CSE'd-away reload AND an unrelated register-allocation-order choice
several instructions away in the same basic block -- the two are not
independent levers, at least in GCC 2.6.3's register allocator. Worth
knowing before spending attempts trying to separate them: they may come
as a package, together with whatever masking side effect the qualifier
also introduces at that specific access.
