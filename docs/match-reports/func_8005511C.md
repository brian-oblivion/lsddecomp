## What the function does (recovered from the magic-number division idioms)

Three GCC constant-division sequences, in order:

1. `(u32) rand() % 3` (unsigned reciprocal `0xAAAAAAAB` + `multu`/`srl 1`) --
   indexes a 3-byte-stride table `D_80087228`, storing the computed address
   into `D_8008E0C0[0]`.
2. `D_8008AC74 % 20 == 0` (signed reciprocal `0x66666667` + `mult`/`sra 3` --
   the extra 2 shift bits beyond the standard `/5` shift fold in an implicit
   `/4`, giving `/20` directly) -- ternary-shaped default/override (this
   round's ternary-order lever already applied: explicit `if`/`else`, not a
   `?:`), storing `0` or `D_80087430`'s value into `D_8008E0C0[1]`.
3. A second, independent `rand()` call, divided by 3 with the SIGNED
   reciprocal `0x2AAAAAAB` (`mult`, no extra shift), then `rand_val -
   (rand_val/3)*6` stored into `D_8008E0BC` -- not a plain `% 6`, a
   literal "quotient of `/3`, times 6" expression.

`D_8008E0B0` (a global pointer) is set to `D_80087174`'s address; the
address of `D_8008E0B0` ITSELF, minus `0xC`, is passed as
`func_80056320`'s second argument -- this is genuinely `D_8008E0A4`'s
address (the same symbol `func_80054F30` references directly by name
elsewhere in this unit), but retail computes it here via `&D_8008E0B0 - 0xC`
pointer arithmetic on an already-loaded register rather than an independent
`%hi`/`%lo(D_8008E0A4)` pair -- confirmed as a genuine, function-local
choice (this function's OWN 79 retail words show the subtraction form, and
`func_80054F30`'s OWN retail words show the direct-symbol form; both are
correct readings of the same underlying address, per the multiple-
independent-local-views convention -- neither should be "corrected" to
match the other).

## What is fixed vs still open

**Fixed, all three magic-number divisions reproduce byte-exact in
isolation** (verified via a focused rebuild of just those instruction
groups) -- the two `rand() % 3`/`% 20`/quotient-times-6 idioms are not
inherently the residue.

**Still open, two intertwined issues:**

1. **`arg1` capture timing.** Retail moves `arg1` into a dedicated saved
   register (`$s2`) as an explicit, separate instruction BEFORE the first
   `rand()` call. Every version tried here instead let GCC fold the capture
   into the first call's own delay slot (`move $s0,$a1` in the `jal rand`
   delay slot) -- functionally identical, cheaper, but ONE FEWER
   instruction than retail's explicit early move, which is the seed of the
   1-word gap.
2. **Instruction-scheduling interleave order between the two magic-number
   setups.** Retail interleaves the SECOND division's magic constant
   (`0x66666667`) and the `D_8008E0C0` base-address computation into the
   latency gap of the FIRST division's `multu`, before finishing the first
   division's own `mfhi`/`srl`. Three different C statement orderings were
   tried (idx-then-address, address-then-idx, /20-check-computed-first) and
   each produced a DIFFERENT interleave, none matching retail's exact
   choice, and two of the three also reintroduced length drift.

4. Reordered to compute the `/20` check BEFORE the `rand()%3`/index

5. Reordered to compute `slot = D_8008E0C0;` BEFORE `idx = ...`: 16/79 but

### Proposed learning

**A function combining multiple GCC constant-division idioms with several
subsequent calls is dominated by INSTRUCTION-SCHEDULING interleave order
during the multiply latency window, not by which arithmetic expression you
write.** All three divisions here reproduce their own instruction sequences
correctly in isolation; the residue is entirely about which INDEPENDENT
work (a second magic constant, a base-address computation, a parameter
capture) the compiler chooses to hoist into the gap before the first
`multu`/`mult`'s `mfhi` becomes available, and that choice tracks the
source's STATEMENT order in ways that are expensive to reverse-engineer by
trial reordering. A permuter search over statement/expression order (not
manual reordering) is the more promising next step, if this is picked back
up -- flagging it as a good permuter candidate rather than continuing hand
attempts, per this round's guidance to prefer breadth.
