## What it does

`s32 func_80032148(s16 a0, s16 a1)`. Signature confirmed from a caller in
the sibling unit `code_179d8_i.c` (`func_800334F0`, line ~123: `extern s32
func_80032148(s16 a0, s16 a1);`, called as `func_80032148(a0, idx)`).

This is the "activate a slot" half of the VAB-channel machinery
`code_179d8_i.c` documents elsewhere (`SsUtGetVabHdr`, `D_8008EA2C` as a
per-channel state byte, `D_8008E968` as a "current" `Entry8E968 *`
pointer). Given `chan` (0-15) and `idx`:

1. Bounds-check `chan` (`(u16)chan < 0x10`) and `D_8008EA2C[chan] == 1`
   (channel must be in the "loaded" state) and `idx < D_8008E938` (a
   signed halfword limit). Any failure returns `-1`, doing nothing else.
2. On success: caches `D_8008E80C[chan]` into `D_8008E970`, caches
   `D_8008E7A4[chan]` (an `Entry8E968 *` -- the per-channel slot array
   base, matching `code_179d8_i.c`'s own `SlotE968`/`Entry8E968` reduced
   view of the SAME global at offset 0x10-stride) into `D_8008E968`,
   stores `chan`/`idx` into byte globals `D_8008EA0D`/`D_8008EA12`, copies
   `D_8008E850[chan]` into `D_8008E978`, and finally reads
   `D_8008E968[idx].unk8` (`arr[idx]` where `arr = D_8008E7A4[chan]`) into
   `D_8008EA13`. Returns 0.

## Residue: CFG and every value are exactly right; two registers are swapped

### Getting the CFG right (48/53) took a real structural fix, not a stall from the start

First attempt (three flat `if (cond) return -1;` guards) built clean but
scored **9/14 -- wrong function, sorry, this was actually 9/53** with a
huge "differs outside range" warning: the compiler tail-merged all three
guard clauses into ONE 3-instruction shared exit, while retail's CFG has
THREE different shapes for its three guards (see below), so the branch
*targets* didn't line up at all past the first guard.

Reading the `.s` closely: retail's third check (`idx < D_8008E938`) uses
`bnez` (branch-if-true-to-success), not the `beqz`-skip-if-false pattern a
plain `if (cond) { success } ` naturally compiles to. That only comes out
of GCC 2.6.3 when the THIRD check is phrased as a positive "goto success"
with the fallthrough being the shared failure path, and the first two
checks are phrased as ordinary early-exit guards whose common failure
label sits physically **right after the third check**, not at the
function's end:

```c
if ((u16)chan >= 0x10) {
    goto fail;
}
if (D_8008EA2C[chan] != 1) {
    return -1;
}
if (idx < D_8008E938) {
    goto success;
}
fail:
    return -1;
success:
    /* ... body ... */
```

This one change took the function from a structurally-wrong 9/53 (CFG
mismatched from word 4 on) to a clean **48/53** with every branch target,
polarity, load, and store correct except a two-register swap in the
success body. Load/store ORDER (`D_8008E80C[chan]` before
`D_8008E7A4[chan]` before `D_8008E850[chan]`, matching retail exactly)
also had to be preserved -- swapping statement order to load `arr` before
`hdr` changed the LOAD order too (regressed to 49/53 with the mismatch
now including which global loads first, worse in a different way).

### The remaining residue: `hdr` and `arr` land in the opposite registers from retail

Retail: `D_8008E80C[chan]` (`hdr`) -> `$v1`, `D_8008E7A4[chan]` (`arr`)
-> `$a0`. Ours: `hdr` -> `$a0`, `arr` -> `$v1`. Every subsequent
instruction that reads these values is correspondingly swapped (the
`addu` building `arr + idx*16`, and the two stores to `D_8008E970` /
`D_8008E968`), so the diff is exactly these two temporaries' hard-register
assignment, propagated through their remaining uses -- semantically
identical code, different registers.

Confirmed **inert per this project's own established finding**
(DECOMPILATION_LEARNINGS.md, "declaration and introduction order... 3
functions, 9 attempts, byte-identical every time") and reproduced here
independently:

- Swapping the LOCAL VARIABLE DECLARATION order (`Entry8E968 *arr; void
  *hdr;` vs `void *hdr; Entry8E968 *arr;`): no change.
- Retyping `hdr` to `Entry8E968 *` (matching `arr`'s type) instead of
  `void *`: no change.
- Moving the `val = D_8008E850[chan];` assignment earlier/later relative
  to the two byte stores (`D_8008EA0D`/`D_8008EA12`): no change to the
  registers, though it does keep the load-order match as long as `hdr`
  then `arr` then `val` stays the relative order of the three loads.
- Swapping STATEMENT order of the `hdr =` / `arr =` assignments: DOES
  change the LOAD order (regresses, see above) but does not flip the
  register assignment the way that would be needed -- the swap makes both
  the order AND the registers wrong simultaneously in a way that doesn't
  net out to a fix.

## Proposed learning

**A three-guard-clause chain where the LAST guard is phrased positively
("goto success" on success) while the earlier guards are phrased as plain
early-return failures reproduces a real, observed retail shape**: the
early guards' failure code and the last guard's failure fallthrough
physically share ONE small stub positioned right after the last guard
(before the success body), while the last guard's SUCCESS branch jumps
forward past that stub to the success body at the end. Getting this exact
mix of goto-forward / early-return / goto-success right (not just "these
three conditions all `return -1`") was the difference between a
structurally-wrong CFG (9/53, all branch targets off) and a correct one
(48/53, register swap only). Worth checking on any guard-clause chain that
looks like it should be trivial early-returns but scores far worse than
its instruction count would suggest.
