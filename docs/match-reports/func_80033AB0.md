## Reading the disassembly

A per-(screen,slot) "value approaches target" tick, called once per frame
from `func_80033738` when bit `0x40` or `0x80` of `unk90` is set:

- `unkA0` is a countdown; when it hits a multiple of `unk44` (a step-rate,
  checked via unsigned modulo — hence the `divu`/`break 7` zero-check pair
  that C's runtime `%` always emits for a non-constant divisor), `unk8C`
  nudges by exactly 1 toward `unkA4`.
- If `unk44` is `<= 0` instead, `unk8C` steps by `unk44` itself (not fixed
  at 1) every call, clamped so it cannot overshoot past `unkA4`.
- `unk70` is `unk4A * unk8C * 10 / (gSeqTickRate * 60)`, clamped to a minimum
  of 1 — reads like a percentage/ratio derived from the current value.
  `gSeqTickRate` is unsigned (forces the observed `divu`, even though the
  numerator is built by a signed `mult`+shift-multiply sequence) — a
  `(s32)` cast on the `unk8C` operand of the multiply was needed to keep
  that multiply signed once `unk8C` itself became `u32` for the comparisons
  below.
- Once `unk8C` reaches `unkA4` (or the countdown hit zero), bits `0x40` and
  `0x80` of `unk90` are cleared — using fresh `D_800902E8[a0][a1]` array
  indexing rather than the already-live `e` pointer, matching retail's own
  redundant from-scratch address recomputation there (two separate
  load-modify-store sequences, not a combined `&= ~0xC0`).

## Attempts 1-3 (residues, corrected)

**Attempt 1** declared a local `s16 speed = e->unk44;` and used `s32 a0, s32
a1` parameters with explicit `(s16)` truncation into local `sa0`/`sa1`.
Scored 15/120 with heavy drift (273779 bytes outside range — a real length
mismatch, not just reordering). Two defects stacked:
- The named `speed` local caused GCC to load `unk44` via `lhu` (unsigned)
  and separately re-sign-extend for the signed comparison, instead of a
  single sign-extending `lh` — two extra instructions. Reading `e->unk44`
  directly at each use site (no named local) restored the plain `lh`.
- `s32 a0, s32 a1` parameters plus explicit `(s16)` casts into new locals
  produced a different instruction ORDER around the address computation
  than retail's, because retail's own reuse of the raw parameter register
  for a *second*, independent re-derivation of the screen offset later in
  the function (before the trailing flag clears) only reproduces byte-exact
  when the parameters are declared `s16` themselves — retyping them (and
  the file's pre-existing forward declaration) to match fixed this file.

**Attempt 2** (after the `lh`/parameter fixes): 33-34/120, with the
remaining drift isolated to one spot: retail's two `sltu` (unsigned)
comparisons between `unk8C` and `unkA4` were compiling as `slt` (signed).
Retyping both fields `u32` fixed the opcode choice, but then required an
explicit `(s32)` cast on `unk8C` at the `unk70` multiply site to keep that
multiply's opcode `mult` (signed) rather than `multu`.

**Attempt 3**: 116/120, no drift (compiled length now exact). The
remaining four words were two swapped-order register PAIRS — retail loads
`unk8C` before `unkA4` at the top of each converge branch; my
`if (e->unkA4 < e->unk8C)` phrasing evaluated the operands in the opposite
(written) order. Flipping both conditions to `if (e->unk8C > e->unkA4)`
(same logic, `unk8C` written first) matched the load order and closed the
last four words.

**A genuine tail-merge required a `goto`, and no non-`goto` phrasing found
it.** The `if (unkA4<unk8C) {...} else if (unk8C<unkA4) {...}` convergent

form reproduces that exact shape and was needed only for the `unk44>0`

already tail-merged on its own without any restructuring.

### Proposed learning

**A named local can change load SIGNEDNESS, not just register identity.**
`s16 speed = e->unk44;` versus using `e->unk44` directly at each use site
changed `lh` to `lhu`+re-extend — a new instance of the
"register-shaped-symptom is often a type/declaration artifact" family
already documented, but the artifact here is an EXTRA UNSIGNED LOAD plus a
separate sign-extend, not a register swap.

**A parameter's declared width can change instruction ORDER even when both
widths produce the "same" truncated value at every use site.** `s32` params
with explicit `(s16)` casts into new locals vs `s16` params used directly
differ in when/whether the compiler re-derives a raw-register-based
computation later in the function. When retail's disassembly shows a
parameter register being copied and REUSED via a full recomputation
(shift-sign-extend-multiply) far from its first use, try declaring the
parameter at its true narrow width before introducing intermediate locals.

**Comparison operand ORDER (not just polarity) affects which side loads
first**, and it is invisible until you check `funcdiff`'s raw diff rather
than trust "same logic, so it must compile the same." Two register loads
in the same statement can come out in either order depending on which
operand is written first, with no reordering of the comparison's semantics.
