stall this round). Retail: `$s0 = arg0`, `$s1 = arg1` (parameter order,

not re-attempted with fresh rephrasings here, given `func_800558F0`

**2. `D_8008E0AC`'s address is recomputed fresh at each of 3 accesses
instead of cached.** Retail loads `&D_8008E0AC` ONCE into `$v1` and reuses
it for `lw`/`negu`/`sw`/`lw`/`slti`/`sw` across the clamp block (3
load-or-store operations, 1 address computation). My build recomputes a
fresh `lui`/`addiu` pair for `$at` before each of the 3 accesses --
functionally identical, 4 extra words. Tried caching the address explicitly
(`s32 *p = &D_8008E0AC; if (*p>0) *p=-*p; if (*p<-0x7800) *p=-0x7800;`):
this made things WORSE (16/81 with 106238 bytes of drift), not better --
reverted. Unlike `func_80054F30`'s successful "hoist a global read across a
call boundary" lever and `func_8005511C`'s successful `s32 *slot` walk for
`D_8008E0C0`, this specific block has NO call between the repeated
accesses, and forcing an explicit local pointer here disturbed something
else (plausibly overall register pressure, given the swap above is already
consuming the function's register budget differently than retail).

### Proposed learning

**The "cache a global's address in a local pointer" lever is NOT uniformly
positive -- it depends on whether a CALL sits between the repeated
accesses.** `func_80054F30`'s and `func_8005511C`'s wins both cached a
value/address across a boundary the compiler otherwise couldn't prove safe
(a function call). Here, with no call between the three `D_8008E0AC`
accesses, introducing the same pattern made the build WORSE, not better --
suggesting GCC's own CSE should handle purely call-free repeated-global
access on its own, and when it visibly doesn't (as here), forcing it by
hand is fighting register-allocation pressure elsewhere in the function
rather than filling a gap the compiler couldn't see. Treat this as the
negative half of round 46's `func_80054F30` lever: scope it to values that
cross a CALL, not to same-block repeated access.
