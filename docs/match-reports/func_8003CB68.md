# func_8003CB68 — STALL

**Unit:** code_2cc8c · **Size:** 20 instructions · **Best reached:** 15/20 words

## What it does

A setter copying three 3-byte groups from three pointers into
`self->unk90[3]`/`unk93[3]`/`unk96[3]`:

```c
void func_8003CB68(Obj86B60 *self, s8 *a1, s8 *a2, s8 *a3)
{
    self->unk90[0] = a1[0];
    self->unk90[1] = a1[1];
    self->unk90[2] = a1[2];
    self->unk93[0] = a2[0];
    self->unk93[1] = a2[1];
    self->unk93[2] = a2[2];
    self->unk96[0] = a3[0];
    self->unk96[1] = a3[1];
    self->unk96[2] = a3[2];
}
```

Retail reads each byte with `lb` (SIGN-extending) even though the source
pointers are conceptually raw bytes and the destination fields
(`self->unk90` etc.) are read UNSIGNED (`lbu`) by `func_8003CC2C`.

## Residues found, and what closed each one

**Residue 1 (closed): `lbu` where retail has `lb`.** The naive
`self->unk90[i] = a1[i];` (whatever the signedness of the array types)
ALWAYS compiles to `lbu` under this toolchain's `-funsigned-char` --
confirmed with an isolated reproducer (`tools/gcc263/cc1 ... -funsigned-char`
on a minimal repro `struct { u8 arr[3]; }` / `s8 *a1`, both
`self->arr[i]=a1[i]` directly and via a `struct { s8 r,g,b; }` member-access
form): the LOADED value's own C type does not matter when it flows straight
into a byte STORE with no other use -- GCC always picks the "extension
doesn't matter, use the -funsigned-char default" form (`lbu`). **Fix:**
assign each byte into an `s32` local FIRST (`s32 v = a1[i]; self->arr[i] =
v;`), forcing the compiler to sign-extend at the load (since the value is
now promoted to `int` and its subsequent truncation back to a byte isn't
provably safe to elide at that point in cc1's pipeline) -- confirmed with
the same reproducer harness, `lb` appears as soon as the intermediate is
`s32`. This closed 2 of the unit's 3 groups completely (words for `a2`'s
and `a3`'s triplets all matched byte-for-byte) and got the whole function
from 0/20 (wrong opcode throughout, plus interleaved load/store instead of
retail's load-load-load/store-store-store batching, which the `s32`-local
rewrite also fixed for free) up to 15/20.

**Residue 2 (NOT closed): register identity on group 1's third byte, plus a
consequent scheduling difference at the function's very end.**

- Retail's group-1 loads are `lb v0,0(a1)` / `lb v1,1(a1)` / `lb t0,2(a1)`
  -- the third value goes to `t0`. Groups 2 and 3 (bases `a2`/`a3`) instead
  reuse the now-free `a1` register for their own third value (`lb
  a1,2(a2)`, `lb a1,2(a3)`). Every C shape tried (a single reused
  `s32 b0,b1,b2` triple across all three groups; nine distinct
  `r0..b2` locals; each group wrapped in its own nested `{ }` scope to
  shrink live ranges) put GROUP 1's third value in `a1` too -- matching
  retail for groups 2/3 but NOT for group 1, every time.
- Retail's function ends `sb a1,0x98(a0)` / `jr ra` / `nop` (the last
  store BEFORE the branch, ordinary `nop` delay slot). Every C shape tried
  instead scheduled that final store INTO the `jr`'s delay slot (`jr ra` /
  `sb a1,0x98(a0)`, no trailing `nop`) -- one word shorter, hence the
  "differs outside this range" drift warning every attempt produced.
- **Isolated reproducer confirms this is NOT a project-specific quirk of
  the real header/struct** -- a minimal repro (`struct { u8 pad[0x90]; u8
  arr[9]; }`, three `s8*` params, `s32` locals, `arr[0..8]` output, even
  with an explicit trailing `return;`) reproduces BOTH residues exactly
  (`a1` reused for group 1's third value, final store in the delay slot)
  under the same pinned pipeline. This means the naive/obvious C shape for
  this exact operation compiles to something structurally close but not
  identical to retail on THIS toolchain, and the true source almost
  certainly differs in some detail not yet found (an unrolled-with-index
  loop? a different parameter order? a struct-typed argument copied as a
  whole rather than three separate pointers?) -- not a scheduler quirk
  reachable by reshaping the obvious per-byte-assignment C.

Per CLAUDE.md rule 6, a register-identity mismatch (which residue 2 is) is
a STALL by definition -- `register T v asm("$N")` or an operand constraint
are banned, and a bare `__asm__("")` barrier only helps when it is pure
instruction ORDER, not WHICH register holds a value, so it does not apply
here either.

### Proposed learning

A plain `dst[i] = src[i];` byte copy under this toolchain's
`-funsigned-char` ALWAYS assembles as `lbu`, regardless of the C-level
signedness of either side (`s8`/`u8`/explicit `signed char`) -- confirmed
with an isolated reproducer. If retail shows `lb` for a byte copy, promote
the loaded value through an `s32` (or other >8-bit) local before storing it
back down; this is a load-bearing, general, and now project-confirmed
lever (not specific to this function), distinct from and worth recording
alongside the existing `-funsigned-char` note in CLAUDE.md's "Key technical
facts".

## Plain conclusion

**This is a confident negative, not an open lever.** Both remaining
residues (group-1's `t0`-vs-`a1` register choice, and the trailing
store-scheduled-into-the-delay-slot) were confirmed reproducible in an
isolated single-function reproducer independent of the rest of the unit,
survived every C-level reshape tried (single/triple named locals, nested
per-group scoping, `s32`-promoted locals in every combination), and the
permuter found no improvement in ~13.5k iterations. Per CLAUDE.md rule 6 a
register-identity mismatch is a stall by definition, not something to keep
reshaping toward. Recommend NOT re-staffing this function without a new
idea that changes the SOURCE'S shape in a way not yet tried here (e.g. a
totally different parameter-passing convention -- a struct-typed RGB
argument instead of three raw `s8*` pointers -- which was suspected but
never attempted due to no positive evidence for it beyond "everything else
has been tried").
