## What it does

Bisects the segment `[near, far]` against an axis-aligned bounding box
(`box`) until the running midpoint exactly equals one of the two endpoints.
The midpoint is written into `*out` every iteration — the caller's actual
result is whatever `*out` holds when the function returns, not a return
value.

```c
void func_8001E2E8(Vec3S16_d294 *out, BoundsBox_d294 *box, Vec3S16_d294 *near, Vec3S16_d294 *far) {
    Vec3S16_d294 buf0;
    Vec3S16_d294 buf1;
    Vec3S16_d294 *dst;
    u8 flags;

    for (;;) {
        out->x = (near->x + far->x) >> 1;
        out->y = (near->y + far->y) >> 1;
        out->z = (near->z + far->z) >> 1;

        if (out->x == near->x && out->y == near->y && out->z == near->z) {
            return;
        }
        if (out->x == far->x && out->y == far->y && out->z == far->z) {
            return;
        }

        flags = 0;
        if (box->hi.x < out->x) {
            flags = 8;
        } else if (out->x < box->lo.x) {
            flags = 4;
        }
        if (box->hi.y < out->y) {
            flags |= 2;
        } else if (out->y < box->lo.y) {
            flags |= 1;
        }
        if (box->hi.z < out->z) {
            flags |= 0x20;
        } else if (out->z < box->lo.z) {
            flags |= 0x10;
        }

        if (flags != 0) {
            dst = &buf1;
            far = dst;
        } else {
            dst = &buf0;
            near = dst;
        }
        *dst = *out;
    }
}
```

Each iteration computes a 6-bit Cohen-Sutherland-style outcode (`flags`)
from `box` against the midpoint: bit `0x08`/`0x04` for X above/below the
box, `0x02`/`0x01` for Y, `0x20`/`0x10` for Z. A non-zero outcode means the
midpoint overshot the box, so it becomes the new `far`; a zero outcode
means it's still inside, so it becomes the new `near`. Each new endpoint is
written into one of two fixed on-stack scratch buffers (`buf0` for `near`,
`buf1` for `far`) rather than a single shared temp, so the OTHER endpoint's
backing storage is never disturbed while it's still being read next
iteration — this is why there are two 6-byte stack slots (`sp+0x0`,
`sp+0x8`), not one reused in place.

## Two things read straight off the disassembly, not guessed

- **`flags` is `u8`, not `s32`.** Retail inserts an explicit `andi
  $v0,$v1,0xFF` every time the accumulated flags value is read back (once
  mid-computation for the early-exit check between the Y and Z axis blocks,
  once before the final `if (flags != 0)`), even though the value never
  exceeds `0x2A` and an `s32` would need no such re-mask. This is the same
  "the compiler re-truncates a byte-typed value after arithmetic" tell as
  elsewhere in this project — declaring the accumulator `s32` would drop
  the `andi` and mismatch.
- **`Vec3S16_d294` (all-`s16` fields, alignment 2) is what makes `*dst =
  *out;` compile to unaligned `lwl`/`lwr` + `swl`/`swr`** instead of a
  plain `lw`/`sw`, matching retail's own loop-tail struct copy exactly —
  same confirmed idiom as `S16Quad_d294` (`func_8001D4DC`, this unit,
  earlier this round) and `FlashbackRotation` (DECOMPILATION_LEARNINGS).
