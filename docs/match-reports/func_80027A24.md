## What it took, and where it stopped

**Four real levers, each closing a distinct, confirmed residue, before the
final one:**

1. **`node->unk8` must be read as a SHARED variable ONCE before branching,
   not re-read separately inside each of the two switches.** Storing it
   into one local (`code`) reused across both mutually-exclusive branches
   matches retail's single `lw a0,8(s1)` read (before either branch), unlike
   inlining `node->unk8` directly into each `switch (...)`, which produced
   two separate loads (1 word longer, one load on a dead path).

2. **The register for `code` (a0 vs a1) is sensitive to the presence of the
   SECOND switch/branch, not to source statement order.** Isolated through
   the pinned pipeline: `self`/`code` assigned in either order, alone,
   always landed `code` in `$a0` (matching retail) when the function had
   ONLY the first branch; adding the second `else if` branch back in
   pushed `code` to `$a1` regardless of statement or declaration order.
   This resolved itself as a SIDE EFFECT of lever 4 below (the `volatile`
   fix for `unk24`), not from anything done to `code` directly -- worth
   knowing before spending time on register-order experiments for a
   symptom that traces to a different statement entirely.

3. **`self->unk24 |= N;` written twice in a row (once unconditional, once
   inside an `if`) gets CACHED into one register and the two immediate
   constants get CONSTANT-FOLDED TOGETHER (`|= 2` then `|= 4` becomes one
   `|= 6`) -- retail re-reads the field fresh for BOTH occurrences,
   never combining them.** This is the round-44 "retail recomputes/rereads
   something our GCC CSEs away" class, but for a STRUCT FIELD across two
   back-to-back read-modify-write STATEMENTS rather than a global read
   inside one expression. A plain `__asm__("" ::: "memory")` barrier
   between the two statements fixed the SECOND occurrence's caching but
   also pulled the FIRST occurrence's load/store earlier than retail
   schedules it (a new, different residue) -- the barrier is too blunt an
   instrument here.

4. **The lever that actually worked for #3: read through a `volatile`
   pointer cast for BOTH occurrences, but keep the STORE through the
   ordinary (non-volatile) field.** `self->unk24 = *(volatile s32
   *)&self->unk24 | 2;` (and the same shape for `|= 4`) forces a fresh load
   each time (defeating the CSE) while leaving the store schedulable
   normally (so it can still land in whatever delay slot retail's build
   puts it in). A pure `*(volatile s32*)&self->unk24 |= 2;` (volatile
   read-modify-WRITE) was tried first and got extremely close (matched
   every register) but cost 1 extra word: it forces the STORE to happen
   strictly before the following branch instead of inside its delay slot,
   since a volatile store's position relative to a branch cannot be
   reordered. Splitting the load (volatile) from the store (plain) keeps
   both properties retail wants: fresh read, freely-schedulable write.
   Isolated and confirmed byte-exact in a **12-line standalone
   reproduction** through the pinned pipeline before touching the unit.

**After levers 1-4, the function was 150/151 words, single differing
instruction at file offset 0x018268 (vram 0x80027A68):** the bounds-check
failure branch for the FIRST switch (`sltiu`/`beqz`, out-of-range or value-6
dispatch) targets the wrong address. Retail's target (`.L80027B40`) is
`case 7`'s own natural fall-through tail (case 7 has no `break`, so its
`self->unk28 = 0; j <shared-exit>` sits physically right after case 7's
unique code, and BOTH the jump-table slot for value 6 and the bounds-check
failure branch point there). My build's same branch instead targets
**`case 2`'s** tail -- a BYTE-IDENTICAL two-instruction sequence
(`sh zero,0x28(s0); j <shared-exit>`) that legitimately also exists,
earlier in the function. GCC's own cross-jump/tail-merging pass is treating
the two occurrences as interchangeable and redirecting the fallback branch
(and the jump-table slot) to the earlier one -- correctness-preserving
(both do the same thing) but not what retail's build did.

**What this implies, and what was NOT tried:** the residue appears to depend
on the OVERALL compilation unit's contents -- specifically, something about
compiling `func_80027A24` alongside the five EARLIER, already-matched
functions in `code_179d8_s.c` changes whether GCC 2.6.3's cross-jump/tail-
merge pass fires for this one pair of identical blocks. Nothing about this
function's OWN source controls that pass's decision (four independent
switch-restructuring attempts -- explicit `case 6:`, a non-fallthrough
`case 7` with its own literal `self->unk28 = 0; break;`, and reordering --
all left the merge target unchanged, always case 2). Reordering or editing
the PRECEDING, already-matched functions to test this theory was not
attempted: they are correct and verified, and perturbing them to chase a
different function's residue is exactly the risk CLAUDE.md's shared-struct
warnings are about, scaled up to whole functions.

## Proposed learning

**A permuter scaffold can disagree with the real build in BOTH directions,
and the direction matters for what it tells you.** Round 45 documented
"scaffold worse than real" (search finds nothing because the isolated
build's own register allocation differs). This is the mirror: "scaffold
BETTER than real" -- a residue that is invisible in isolation because it
depends on the function's neighbors in the same translation unit. The
existing check-3 discipline (rebuild the scaffold, compare its base score to
the real build) catches this shape too, and the correct response is the
same as round 45's: don't run the search, because the object under test
already has the byte-exact answer and is not the object the search would
optimize. Worth naming as its own signature: **base score 0 on a scaffold
whose real-build sibling is NOT byte-exact is itself the finding**, not a
green light to skip searching -- it means the gap is a whole-file artifact,
and the fix (if one exists within project rules) is not in this function's
own text.
