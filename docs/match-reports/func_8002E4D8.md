## Two loads, not one: a genuine correctness finding, kept even though it did not close the function

`D_8008D9A6[a0]` is read from the SAME address TWICE by retail — once
`lhu` (for the unsigned add into the accumulator) and once `lh`
(for the signed sign-test that selects which clamp branch runs). **A single
C expression typed either way and reused for both purposes folds to ONE
load** (the compiler CSEs identical-typed reads of the same lvalue), which
undercounts against retail's two. The fix, applying the SAME idiom this
unit already uses everywhere else for a symbol needing both widths: an
UNSIGNED cast view (`Rec34HalfU`, `u16 unk0`) for the accumulator add, kept
textually SEPARATE from the plain signed `Rec34Half` read for the sign
test. `D_8008D9AC[a0]` needs the analogous unsigned view for ITS one read
here too (`lhu`, confirmed against the disassembly), and its LATER,
separate re-read for the percentage chain (`accum = D_8008D9AC[idxCopy]`)
is ALSO `lhu` in retail and needs the same unsigned cast.

**Applying this fix alone moved the function from 233 to 236 words — in the
WRONG direction** (retail is 231), because it exposed a SECOND, distinct
problem: comparing the newly-`u16`-typed accumulator sum against a `s16`
limit (`(s16) accumU >= limit`) forces a REDUNDANT sign-extension
(`sll`/`sra` pair) at EACH of the two comparison sites (the `incS > 0` and
`incS < 0` branches), where retail computes the sign-extension only ONCE
and reuses it. Introducing a separate `s16 accumS = accumU;` local
computed once and read at both comparison sites did NOT remove the
duplication (rebuilt: still 236 words, unchanged) — the compiler still
re-extends at each use site rather than caching the local's sign-extended
form across the two `if`/`else if` branches. This second problem was not
resolved within this round's budget.

## The same "split scaled index" residue documented for func_8002EA44 and func_8002EDD4

Exactly as in both siblings: retail computes `sll t0,v1,0x3` (`idx*8`) as
the SECOND instruction of the function (right after sign-extending the
parameter, BEFORE even the countdown-gate check), keeps `t0` alive across
the ENTIRE function body untouched, and consumes it only at the very end
(`sra a0,t0,0xF` after an `sll #16`, algebraically `t0*2 = idx*16`) as the
byte offset for the final `D_8008D7F2`/`D_8008D7F0` stores. This attempt's
C computes that same `idx*16` offset via ordinary `array[idxCopy]` struct
indexing at the point of use, which folds to a single `sll #4` rather than
retail's early-split `sll #3` / late-`sll #1` pair — the identical gap
`func_8002EA44`'s report already documents as unresolved, and the identical
gap `func_8002EDD4`'s report (this same round) also hit and equally failed
to close via an explicit early-hoisted local. **Do not re-attempt the
"declare an early local for the split product" lever a fourth time without
new evidence** — it has now failed on three independent functions sharing
this shape. `func_8002EDD4`'s report proposes the next concrete lever: look
for a genuinely separate, not-yet-identified THIRD statement that uses
`idx*8` directly (not `idx*16`), rather than continuing to treat this as a
scheduling artifact of a single index expression.

### Proposed learning

**A symbol needing BOTH a signed and an unsigned read at DIFFERENT sites in
the SAME function needs the unsigned view applied INDEPENDENTLY at every
site that reads it unsigned in the disassembly — including a value that is
itself DERIVED from an unsigned read (e.g. an accumulator sum stored back
through the unsigned view).** Fixing only the OBVIOUS site (the raw
increment read) and leaving a DERIVED value (the sum, or a later re-read of
the same accumulator) typed signed produces a spurious sign-extension at
every point that derived value is later compared against a limit — visible
as a repeated `sll`/`sra` pair the retail disassembly does not have. This
is now a confirmed, reproducible pattern (not fixed by introducing an
intermediate named local either) worth checking on ANY stalled function in
this record family carrying an accumulate-then-clamp shape.
