Called from `func_80049CA8` (this unit, `ClassA`'s +0x054 slot -- not
attempted this round). Builds a sub-object from four instance fields,
notifies it through the inherited slot10, dispatches the sub-object's own
+0x044 slot, then marks `state` active (2):

```c
void func_80049E20(ClassA *self, s32 arg1) {
    Dispatch4C *d;

    d = func_80052B70(self->unk34, self->unk40, self->unk44, self->unk48);
    self->unk4C = d;
    self->methods->slot10(self, d);
    self->unk4C->methods->slot44(self->unk4C, self->unk0C, self->unk38);
    self->state = 2;

```

This reproduces every one of retail's 33 words **except one**: retail's
prologue includes `sw $a1, 0x10($sp)` (spilling the second parameter to a
stack slot that is never read again anywhere in the function), and my
build's prologue omits it, shrinking the frame from 0x20 to 0x18 bytes and
shifting everything after by one word. Confirmed with `asm-differ`: every
other instruction, including all four field loads, both indirect calls,
and the epilogue, lines up exactly once the frame-size offset is accounted
for.

## What was ruled out

Isolated the residue in a standalone reproducer through the pinned
toolchain (`tools/gcc263/cpp | cc1 -O2 | maspsx | as`), independent of this
unit's build:

- A **plain unused second parameter** (`s32 arg1` never referenced) does
  NOT get spilled by this compiler at this optimisation level -- confirmed
  with a minimal struct/function reproducer matching this function's shape
  (one call, unused 2nd param): no spill emitted.
- An **explicit dead local** (`s32 unused = arg1;`, never read again) also
  does not survive to codegen -- GCC 2.6.3 eliminates it entirely, no store
  at all, not even a spilled-then-unused one.
- **K&R-style (non-prototyped) function definition** for the same body:
  identical codegen, same frame size, no spill.
- Compiled the **exact real header + body** (`include/class_39e08.h` +
  this function, verbatim) through the standalone pipeline outside the
  unit's own build: reproduces the same 32/33-word result byte-for-byte,
  ruling out anything specific to this unit's other translation-unit state
  (declaration order, other functions, etc.) as the cause.

None of the three reshaping attempts reproduce retail's spill. The pattern
doesn't match any of the documented residue classes in
docs/MATCHING-GUIDE.md either (it isn't a register-identity swap, an
instruction-order-only difference, a missing `nop`, a `div` macro
difference, a gp-relative or addiu_at hit -- grepped for both, neither
present in this function's `.s` -- or a redundant `move`). It presents as a
genuinely unmotivated register-argument spill: the value is provably dead
in every observable sense, yet retail's compiler chose to materialise it to
memory anyway.
