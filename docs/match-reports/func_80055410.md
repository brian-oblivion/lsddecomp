## One value initially transcribed WRONG, costing exactly 1 word

First attempt wrote `D_8008E0AC = -0x6000;` for the `mod3 == 1` branch,
misreading the comment `(0xFFFF6000 & 0xFFFF)` as `0x6000` directly rather
than computing `0xFFFF6000` as a signed 32-bit value. `0xFFFF6000` as
signed is `-0xA000` (`-40960`), NOT `-0x6000` (`-24576`) -- and the two
differ in more than value: `-0x6000` fits a 16-bit signed immediate
(compiles to one `addiu`/`li`), while `-0xA000` does not (needs `lui`+`ori`,
two words), so the wrong constant was ALSO the wrong instruction count.
Fixing the literal to `-0xA000` immediately fixed that entire region to a
pure register-rename match (confirmed via `asm-differ`, the branch/store
block from the `mod3` check through the `else if` is byte-identical modulo
`$v0`/`$v1` colour after the fix).

### Proposed learning

**A `lui`/`ori` pair's operand comment written as `(CONST >> 16)` /
`(CONST & 0xFFFF)` must be evaluated as the FULL 32-bit `CONST`, signed, not
read as "the low half is the literal" -- doing so both gets the value wrong
AND silently picks the wrong instruction count (a value that fits 16 bits
signed collapses from 2 words to 1).** Always compute the full 32-bit
value (a one-line Python check) before transcribing a `lui`+`ori` pair as a
C constant, especially when the compiler could plausibly use either `li`
(1 word) or `lui`+`ori` (2 words) depending on which one you pick.
