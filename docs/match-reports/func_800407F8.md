# func_800407F8 — STALL (one word short + register-identity, best 0/11 at wrong length)

Unit: `src/code_2cc8c_f.c`. Blocker screen clean. Retail's own
callee-saved count is 0 -- not the saturated-register-file class.

```c
void func_800407F8(Obj6EAC0 *self, s32 *a1) {
    if (self->unkC != 0) {
        s32 x, y;
        x = a1[0];
        y = a1[1];
        self->unk50 = x;
        self->unk54 = y;
    }
}
```

## The residue, measured precisely (not just from the funcdiff score)

Retail is **11 words** (`0x2C` bytes, from the `.s` file's own
`nonmatching func_800407F8, 0x2C`). Cross-checking the REAL compiled
length via `objdump -d build/src/code_2cc8c_f.c.o` (per
`docs/DECOMPILATION_LEARNINGS.md`'s "funcdiff's byte range is not a
stalled function's true length") rather than trusting the word count
funcdiff prints:

- The body shown above (two named temps `x`/`y`, needed to avoid a
  load-delay-hazard nop between the two loads -- see `func_80040790`'s
  report for the same fix) compiles to exactly **10 words** -- a true
  bare minimum, with the branch's own delay slot as a plain `nop`.
- Retail's extra 11th word is an UNCONDITIONAL `addu $a2, $a0, $zero`
  (self cached into `$a2`) sitting BEFORE even the guard load, with a
  SECOND cache (`addu $a3, $a1, $zero`) filling the branch's delay slot
  (replacing what would otherwise be a wasted `nop`, which is why
  retail is only +1 word despite caching two values, not +2).
- So this is `docs/MATCHING-GUIDE.md`'s "one instruction short, and
  everything after it shifted" family, NOT a same-length pure register
  swap -- the `funcdiff` word-count line by itself does not show this;
  it required the explicit `objdump` cross-check to see the true 10-vs-11
  gap once the load-hazard issue was fixed.

## Attempts (4)

1. Direct body, no temps: `self->unk50 = a1[0]; self->unk54 = a1[1];`
   -- compiled to **12** words (2 too many): reusing `$v0` for both
   loads serialises them behind a load-delay nop each time, same
   mechanism as `func_80040790`'s attempt 1.
2. Split into named `x`,`y` temps (shown above) -- compiles to the true
   bare-minimum **10** words. Confirms the load-hazard fix from
   attempt 1 without yet reproducing retail's two extra caches.
3. `Obj6EAC0 *q = self; s32 *p = a1;` declared unconditionally before
   the `if`, guard and body rewritten through `q`/`p` (matching
   retail's apparent shape -- even its GUARD TEST reads through the
   cached `$a2`) -- **no change**: still 10 words, GCC 2.6.3
   copy-propagates both aliases away completely regardless of temp
   placement.
4. Combined attempt 2 + attempt 3 (temps for the loads AND the q/p
   aliases) -- still exactly 10 words, identical object code to
   attempt 3. Confirms the two fixes are independent and neither
   subsumes the missing-cache problem.

This is the SAME class as `func_80040790`'s stall in this unit (see
that report) -- a value whose lifetime crosses a branch gets an extra
unconditional cache into a fresh caller-saved register in retail, and
no source reshaping tried reproduces it. Here it additionally shows up
as a genuine missing INSTRUCTION (not just a same-length rename),
which sharpens the class: it is not merely "GCC picked a different
register for an existing move" but "GCC did not materialise the move
at all".

register-identity framings are the SAME underlying defect, not two

branch into an unconditional fresh register, and this project's GCC
2.6.3 will not materialise that cache from any C shape tried
