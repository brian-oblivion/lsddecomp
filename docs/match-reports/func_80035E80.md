## What it is

The shared "advance the sequencer cursor" helper every other function in
this unit's family calls and caches the return value from. It decodes ONE
MIDI-style big-endian 7-bit-per-byte variable-length quantity from
`rec->unk4` (a byte cursor into a per-voice event stream, advanced as it
reads), scales the decoded magnitude by 10, adds that to `rec->unk80` (a
running tick position), and returns the scaled delta. A first byte of `0`
is a sentinel for "no delta due" -- it returns `0` immediately without
touching `rec->unk80` at all (retail explicitly sets `$v0=0` and jumps
past the accumulate-and-store code entirely; this is not merely "the
value happened to be zero").

```c
s32 func_80035E80(s16 a0, s16 a1)
{
    Entry90902E8 *rec = &D_800902E8[a0][a1];
    u8 *cursor = rec->unk4;
    s32 acc;
    s32 val;
    s32 result;
    u8 nb;

    rec->unk4 = cursor + 1;
    acc = *cursor;
    if (acc == 0) {
        return 0;
    }
    val = acc * 4;
    if (acc & 0x80) {
        acc &= 0x7F;
        do {
            cursor = rec->unk4;
            rec->unk4 = cursor + 1;
            nb = *cursor;
            acc = (acc << 7) + (nb & 0x7F);
        } while (nb & 0x80);
        val = acc * 4;
    }
    result = (val + acc) * 2;
    rec->unk80 += result;
    return result;
}
```

## Levers that closed most of the gap (kept, all load-bearing)

Starting point after a literal transcription was 17/47 with the compiled
body 3 WORDS LONGER than retail (50 vs 47), i.e. this began as a length
mismatch, not a word-for-word residue -- funcdiff's own drift warning
(`differs OUTSIDE this range`) was the tell.

1. **`s32`, not `u8`, for the running accumulator.** A `u8`-typed
   accumulator (whether split into separate "byte just read" / "running
   value" variables, or merged into one) produced a spurious
   `andi reg,reg,0xff` on every comparison and arithmetic use, because
   GCC 2.6.3 re-widens a *named* QImode variable on every use rather than
   trusting that an `lbu` already zero-extended it -- even though the
   hardware guarantee is real. Declaring the accumulator `s32` from the
   point it is assigned (`acc = *cursor;` into an `s32`, not a `u8`) let
   the value stay a clean SImode value with no re-masking, closing the
   extra instructions this caused (3 separate attempts, u8-both,
   u8-nb-only, u8-b-merged, all reproduced the mask; s32 removed it in
   one rebuild). This is a NEW, narrower case of the project's existing
   "a wrong TYPE produces register-shaped symptoms" finding
   (`DECOMPILATION_LEARNINGS.md`) -- here the type was wrong not because
   it changed which register held the value, but because it changed
   whether GCC believed the value needed re-widening at all, which
   shows up as extra INSTRUCTIONS rather than a swapped register.
2. **Recompute the scaled value into a THIRD variable at the tail,
   rather than reassigning the same one used for the two speculative
   `*4` candidates.** `val = acc*4;` speculatively before the branch,
   recomputed the same way after the loop, matches retail's own
   redundant-recompute shape (retail computes `sll v0,a0,2` at BOTH the
   single-byte branch delay slot and the loop-exit fallthrough, rather
   than merging the two paths). But writing `val = (val+acc)*2;
   return val;` forced `val`'s ONE storage location (already pinned to a
   non-`$v0` register by the two earlier `*4` assignments) to also hold
   the return value, producing a spurious `move $v0,<val's register>`
   right before `jr $ra` that retail does not have. Introducing a THIRD
   variable (`result`) for the final combine let GCC allocate it fresh
   -- to `$v0`, matching retail -- with no bridging move (50 -> 48
   words, one rebuild).
3. **Statement order matching retail's own load-then-store-then-load
   sequence removed a spurious load-delay NOP.** Retail computes
   `cursor+1` and stores it back to `rec->unk4` BEFORE reading the byte
   at the old cursor; an intervening `nop` at that point is a genuine
   MIPS-I load-delay hazard (nothing else is available to fill the slot
   between the pointer's own `lbu`-adjacent load and the next use).
   Writing the C in the OPPOSITE order (read byte first, store back
   second -- the more "obvious" reading order) let GCC fill that gap
   with the `addiu` instead, one instruction short of retail (48 -> 46
   -> matching-length-once-combined-with-#2, see below). Restoring
   retail's own read/store order (`rec->unk4 = cursor + 1;` textually
   BEFORE `acc = *cursor;`) reintroduced the nop naturally and brought
   the compiled length to the exact 47 retail has.

Combining all three took the function from 17/47 (wrong length, 3 words
over) to 44/47 at the CORRECT length, in that order.

## The residue that did not close (4 words, all one class)

```
26680: TARGET addu a1,v0,v1        CURRENT addu a1,v1,v0        (word 15, operand order only)
266ec: TARGET sll  v0,a0,0x2       CURRENT sll  v1,a0,0x2        (word 27, first real diff)
2671c: TARGET sll  v0,a0,0x2       CURRENT sll  v1,a0,0x2        (word 39)
26720: TARGET addu v0,v0,a0        CURRENT addu v0,v1,a0         (word 40, downstream of the sll above)
```

Word 15 is the project's already-SETTLED "commutative-operand-order
canonicalization" class (`DECOMPILATION_LEARNINGS.md`, round 20): same
opcode, same two operands, order swapped, and BOTH C orderings of the
underlying pointer addition (`&D_800902E8[a0][a1]` vs `a1 + tbl` written
out explicitly) produced the identical wrong order -- which is the
project's own decisive test for ruling out source control. Not
re-attempted further per that entry's explicit guidance.

Words 27/39/40 are a SINGLE register-identity choice, not three
independent residues: `val` (the speculative `acc*4`, computed at BOTH
the single-byte-path delay slot and the loop-exit fallthrough) lands in
`$v1` here against retail's `$v0`, and that one choice produces the same
wrong register at both computation sites plus the one place it is
consumed (word 40). Tried and inert: swapping `* 4` for `<< 2` in both
places (no change, same three words wrong); this is presented as one
axis, not evidence the residue is unreachable -- only that this
particular axis does not touch it.

**Proposed learning:** the settled commutative-canonicalization entry
should be read as covering more than the operand-order symptom itself --
here it also determined which of two symmetric temporaries (`$v0` vs
`$v1`) absorbed a value used identically on both branches of an
`if`/loop-exit pair, one register hop downstream of the actual swapped
`addu`. Whether that's the SAME mechanism or a sibling one worth its own
entry is for the head to adjudicate against other instances; flagging
rather than asserting.
