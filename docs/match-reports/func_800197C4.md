## HEAD PASS, round 13 (2026-09-03): the residue is NOT register identity, and this family is not exhausted

**This report's classification is superseded.** It concluded the residue was a
register-identity choice on the mask constants plus a dead `addiu`, "confirmed
not reachable from C after 6 attempts", and that conclusion was applied to
seven sibling functions. The head re-derived it and reached the **correct
instruction count and length** — asm-differ shows zero inserted and zero

Two changes got it there, and **both generalise to all seven siblings**:

### 1. The OT splice is a 24-bit BITFIELD write, not hand-written masking

Every attempt in the log below wrote the masks by hand:

```c
*(u32 *)arg0 = (*(u32 *)arg0 & 0xFF000000) | (*head & 0xFFFFFF);
```

Retail's source wrote a **24-bit bitfield**. This is Psy-Q's GPU primitive tag
(`P_TAG` in `include/psyq/LIBGPU.H`, whose first member is
`unsigned addr : 24`), reached through `setaddr`/`getaddr`/`addPrim`. On
little-endian MIPS `addr` occupies bits 0..23, so assigning it is a
read-modify-write that GCC 2.6.3 emits as `& 0xFF000000` on the old word,
`& 0x00FFFFFF` on the new value, and an `or` — **the same value as the
hand-written form, with different register allocation.** That is the whole
reason the residue looked like an unreachable register choice.

`include/psyq/LIBGPU.H` does **not** compile standalone under this toolchain
(it needs the `LIBGTE`/`RECT` chain, and no unit includes it yet), so this
unit carries a minimal local view instead, in the project's usual
local-minimal-view style:

```c
typedef struct OtTag {
    u32 addr : 24;
    u32 len  : 8;
} OtTag;
```

### 2. The OT expression must be RE-EVALUATED, not cached

With the bitfield in place but the OT pointer cached in a local, the body came
out **two instructions short**: retail re-reads `arg1->unk30` before the second
store, where a cached local reuses the register. That is ordinary macro
argument semantics — `addPrim(ot, p)` is
`setaddr(p, getaddr(ot)), setaddr(ot, p)`, so `ot` is expanded twice and
evaluated twice. Writing the expression out twice restores both loads:

```c
((OtTag *)arg0)->addr = (*(OtTag **)((u8 *)arg1 + 0x30))->addr;
(*(OtTag **)((u8 *)arg1 + 0x30))->addr = (u32)arg0;
```

This is the same shape as the existing learning *"Do not cache a
`this->field` across an intervening vtable call — re-read it at each use
site"*, one step further out: here there is no call at all, just a macro that
happens to evaluate its argument twice.

### What is left

- `lui $a2, 0xff00` where this body gets `lui $a1, 0xff00`, plus the renames
  that follow from it.
- Retail fills a load-delay slot with **`addiu $v0, $s1, 0x14`** — it computes

## HEAD NOTE, round 13: the filler is CODE MOTION, not an arithmetic formula

The runner pass derived `N = align_up_4(last arg0-relative offset touched by
the calls branch + the access width there)` and confirmed it on all eight
siblings. **The head verified it on this root case and it holds** — the calls
branch touches `$s1+0x4`, `+0x8`, `+0xC`, `+0x10`, and
`align_up_4(0x10 + 4) = 0x14`, which is the filler.

But the same grep shows something the formula obscures, and it is a stronger
lead: **`$s1 + 0x14` is a value the OTHER branch genuinely computes.** The
calls branch's own offset list includes `0x14`, and this function has TWO
fillers, `addiu $v0, $s1, 0x14` and `addiu $v0, $s1, 0x10` — both of them
addresses the calls branch really uses.

So this is not GCC materialising an arithmetic result derived from the
function's shape. It is **code motion of a real computation across the
branch**: the address exists in the source, and GCC 2.6.3 has it available in
the splice branch and spends it filling a load-delay slot. That is consistent
with the general rule that 2.6.3 hoists an EXISTING instruction into a
load-delay slot and never invents one.

Why this matters for the next attempt: the formula invites reconstructing a
number, which is a dead end. The thing to reconstruct is a source expression
that makes `arg0 + 0x14` (and `arg0 + 0x10`) live at the branch. The runner
already ruled out the two obvious spellings — a cross-branch-live local

## RUNNER PASS, round 19 second head-directed pass (delta): the aggregate-assignment lever, checked directly against this residue -- clean negative, mechanism identified

The head staffed this cluster this round on the strength of the

alpha's own sibling closures) -- both cases where writing several

batch loads-then-stores instead of interleaving load/nop/store per field,
closing a word-count gap. Checked whether that SAME mechanism could
plausibly produce this family's missing `addiu $v0,$s1,N` filler. It
cannot, and the reason is mechanical, not a re-run of an already-tried
variant:

**The filler's mechanism is a load-delay-slot fill, confirmed instruction-
by-instruction on `func_800199EC`'s own raw disassembly** (re-derived
independently, not read from this report first, then cross-checked
against it): the missing `addiu $v0,$s1,0x20` sits IMMEDIATELY after
`lw $a1,0x30($s2)` (the SECOND OT-pointer reload) and immediately BEFORE
`lw $v1,0(a1)` (the load that consumes it) -- i.e. it fills the one-
instruction gap MIPS I's load-delay-slot rule requires between a load and
the first use of its result. This is not new information about WHERE the
value sits (the "code motion" head note already placed it in the splice
branch's own basic block), but it is a precise confirmation of WHICH load
it is filling for, on a second sibling, independent of the root case.

**Why the aggregate-assignment lever cannot reach it: the value is a
compile-time-constant offset (`self + literal`), and every closing use of
the lever elsewhere this round involved a RUNTIME-variable address (a
loop index, or copying between two already-computed pointers) that
resists constant folding.** `DreamSys`'s closing fix worked because
`*(DreamSysVec3 *)out = *(DreamSysVec3 *)local;` is a copy between two
POINTER VALUES only known at runtime -- there is no compile-time constant
to fold, so GCC must emit real load/store instructions for the batch, and
choosing to batch-then-store instead of interleaving is what closed the
gap. Here, `self + N` for any FIXED, compile-time `N` is exactly the kind
of expression GCC 2.6.3's constant folding collapses into a single
`addiu reg, self, N` at the point of use, REGARDLESS of how many
intermediate C-level names or array-index expressions are used to spell
it -- `self + 8 + 3*8 - 2`, `&arr[3] - 1` where `arr` is a local array
type, `(SomeStruct *)(self+8))[2].field` -- all of these fold to the
identical single-instruction address computation the CURRENT body already
produces at its point of use, because every operand is a compile-time
constant. **There is no C-level spelling of a constant offset that
survives as a separate, schedulable, non-folded intermediate value** --
folding happens before scheduling, so by the time GCC's delay-slot filler
pass runs, there is nothing left to hoist except the single instruction
that's already there.

**This also explains why turning the tail copies into a real loop is not
a live option, independent of whether it would help.** The calls branch's
own tail copies are ALREADY byte-exact as manually-unrolled, branch-free
straight-line code (confirmed on every sibling's own report). A genuine
`for`-loop over the 3 (or 4) vertex records would need to survive as a
real loop with a real induction variable and a real comparison against an
`end` pointer for the "one past the end" value to be a non-folded runtime
computation at all -- but nothing in this toolchain's behavior anywhere
else in this project shows GCC 2.6.3 unrolling a 3-4 iteration loop into
straight-line code at `-O2`, and retail's OWN disassembly for the tail
copies has no loop structure (no backward branch) in ANY sibling. Writing
a real loop to manufacture a non-folded `self+N` would first have to
survive NOT being what retail's calls branch shows, and would risk
regressing code that already matches. This is not "untried because
nobody thought of it" -- it is untried because the two possible forms
(constant-folded expression, or a real loop) each fail for a different,
identifiable reason before either reaches the oracle.

**What remains genuinely open, restated precisely now that the mechanism
is pinned down:** a value equal to `self + N` that is (a) a REAL,
non-constant-foldable runtime computation, (b) alive in a register at the
exact point in the SPLICE branch's own basic block between the second
OT-pointer reload and its first use, and (c) does not require a 4th
callee-saved register carrying it across the branch split (which drifts).
No hypothesis meeting all three constraints has been proposed by any pass
on this family, including this one. If one exists, it most likely comes
from `self`'s TRUE type having some property (a trailing member whose
address is computed via a non-constant expression, e.g. indexed by a
runtime flag already read earlier in this SAME function) rather than from
any reshaping of the C already written -- and nothing in `code_8220_c`
alone currently suggests such a property exists.

### Proposed learning

**The aggregate-assignment/whole-struct-copy lever closes a residue by
letting the compiler batch REAL, runtime-only load/store operations
differently -- it has no purchase on a residue whose extra instruction is
a compile-time-constant address computation, because constant folding
happens upstream of instruction scheduling and collapses any C-level
spelling of `ptr + constant` to the identical single instruction
regardless of how many named intermediates or array/struct accesses are
used to reach it.** Before applying this lever to a "missing instruction"
residue, check whether the missing instruction's OPERANDS are all
compile-time constants (a literal offset from a pointer already in scope)
or involve at least one genuinely runtime value (an index, a second
pointer, a loop bound) -- only the latter is a candidate for the lever;
the former needs a different mechanism, most likely a real property of a
not-yet-modelled type rather than a reshaping of existing C.

### Proposed learning

**A "same residue, same position" claim across a sibling family is worth
checking by grepping every sibling's own disassembly side by side in one pass,
not by trusting pairwise analogy across reports written in different rounds.**

recording even when — especially when — the experiment is not actually run,
because it forecloses the next runner re-deriving the same negative from
scratch.
