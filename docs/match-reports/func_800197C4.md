## Attempts (6, well under the cap)

1. First cut, `if (cond != 0) { calls } else { list }` (natural reading
   order) — 16/54, badly wrong. Root cause: retail places the SMALL block
   (list splice, ~13 instructions) as the fallthrough/branch-NOT-taken path
   and the LARGE block (calls, ~20 instructions including 3 `jal`s) as the
   branch target — i.e. the opposite of what a literal `if (flag) {calls}`
   reading produces. This is the "write a small early exit/branch as an
   inverted guard, not as the `else` of a big `if`" idiom from
   `docs/DECOMPILATION_LEARNINGS.md`, confirmed on a THIRD shape here (an
   `if`/`else` where NEITHER side is an early exit, both converge to the
   same return — the size asymmetry alone, not exit-vs-continue, decided
   the layout).
2. Inverted the condition (`if (cond == 0) { list } else { calls }`),
   matching physical block order — 44/54. The `else` branch (calls) went
   byte-exact immediately; all remaining diffs moved into the `if` branch.
3. Traced the `if` branch precisely against the disassembly: two "combine"
   operations, `*arg0 = (*arg0 & top) | (*head & low)` then
   `*head = (*head & top) | (arg0_as_int & low)`, where `head` is loaded
   TWICE from `arg1->0x30` (a genuine reload each time, not a cache) — a
   THIRD instance of the reload-not-cache idiom already confirmed twice in
   `code_8220_b`. First attempt at this shape used one shared `head`/
   `headPtr` local reused for both reads — 44/54 still, both reloads landed
   in the SAME hardware register (`$a2` in the build), where retail uses
   TWO DIFFERENT registers (`$v0` then `$a1`) for its two reloads.
4. Split into two independently-scoped locals (`head0`, `head1`, one per
   reload) so each gets its own live range — 46/54. Retail's TWO registers
   became MY two registers too, but the wrong PAIR (`$v0`/`$v1` instead of
   `$v0`/`$a1`).
5. Removed the `head0` local entirely (inlined the double-dereference
   directly into the first combine expression, since it's used exactly
   once) — no change, still 46/54, identical diffs.
6. Named the two mask constants (`lowMask`/`topMask` locals) instead of
   repeating the literals, on the theory that explicit naming might steer
   which register the allocator picked for each — no change whatsoever,
   byte-identical diff to attempt 4/5. This is strong evidence the residue
   is NOT reachable by varying how the C mentions these values.

## Remaining residue: register identity in the `if` branch, not order or reload count

Every remaining mismatch is which SPECIFIC register holds an already-
correctly-reloaded or already-correctly-masked value, never a missing/
extra instruction and never a wrong branch target:

- The "top byte" mask constant (`0xFF000000`) lands in `$a1` in every
  attempt; retail uses `$a2`, leaving `$a1` unused entirely in this
  function (retail's constant-loading order is low-mask into `$a0` THEN
  top-mask into `$a2`, skipping `$a1` — plausibly because the register
  allocator reserves `$a1` against the OTHER branch's call-argument use of
  it, something no amount of reordering the `if`-branch's own C moved).
- The second `head` reload lands in `$v1` (attempt 4) or stays `$v0`+fresh-
  temp (attempts 5/6); retail uses `$a1` specifically.
- One instruction retail has and every attempt lacks: `addiu $v0,$s1,0x14`
  between the first combine's store and the second reload — computed and
  then genuinely never read again by anything in this function. No source
  shape tried (including a deliberately unused local at that exact point,
  which -O2 simply eliminated) reproduced it; it may be a scheduler
  artifact of filling an otherwise-idle `$v0` slot with a "free" address
  computation from a different part of the same expression tree that
  ended up not needed after all, rather than something a straightforward
  C statement can mention.

This is a register-identity residue per CLAUDE.md's own test (removing/
changing the C changes WHICH REGISTER holds a value, not just instruction
order), so per HARD RULE 6 it is a stall, not a target for
`register T v asm("$N")` or an operand-constraint fix.

### Proposed learning

**A third confirmed instance of "write a small block as the branch-not-
taken fallthrough and a large block as the branch target," extending the
existing early-exit-guard-clause entry to plain `if`/`else` pairs where
BOTH sides converge to the same return (not just early exits).** The
decisive factor is relative SIZE of the two blocks, not which one exits
early. (`func_800197C4`, 16/54 -> 44/54 from inverting the condition
alone.)

Also: when a residue survives (a) fixing block layout, (b) fixing an
under-reload into an over-cached value, and (c) splitting shared locals so
each reload gets its own live range — and NAMING the remaining constants
differently produces a byte-identical diff to not naming them — that last
result is itself useful evidence, not just a wasted attempt: it means the
allocator's choice for that specific register is being driven by something
outside the immediate expression (here, plausibly cross-branch register
pressure from the OTHER arm's call arguments), which no local rephrasing
of the branch under examination will reach.

## HEAD PASS, round 13 (2026-09-03): the residue is NOT register identity, and this family is not exhausted

**This report's classification is superseded.** It concluded the residue was a
register-identity choice on the mask constants plus a dead `addiu`, "confirmed
not reachable from C after 6 attempts", and that conclusion was applied to
seven sibling functions. The head re-derived it and reached the **correct
instruction count and length** — asm-differ shows zero inserted and zero
deleted instructions across the whole function — with only two
register-identity choices and one delay-slot filler left.

Two changes got it there, and **both generalise to all seven siblings**:

### 1. The OT splice is a 24-bit BITFIELD write, not hand-written masking

Every attempt in the log below wrote the masks by hand:

```c
*(u32 *)arg0 = (*(u32 *)arg0 & 0xFF000000) | (*head & 0xFFFFFF);
```

Retail's source wrote a **24-bit bitfield**. This is Psy-Q's GPU primitive tag
(`P_TAG` in `include/psyq/LIBGPU.H`, whose first member is
`unsigned addr : 24`), reached through `setaddr`/`getaddr`/`addPrim`. On
little-endian MIPS `addr` occupies bits 0..23, so assigning it is a
read-modify-write that GCC 2.6.3 emits as `& 0xFF000000` on the old word,
`& 0x00FFFFFF` on the new value, and an `or` — **the same value as the
hand-written form, with different register allocation.** That is the whole
reason the residue looked like an unreachable register choice.

`include/psyq/LIBGPU.H` does **not** compile standalone under this toolchain
(it needs the `LIBGTE`/`RECT` chain, and no unit includes it yet), so this
unit carries a minimal local view instead, in the project's usual
local-minimal-view style:

```c
typedef struct OtTag {
    u32 addr : 24;
    u32 len  : 8;
} OtTag;
```

### 2. The OT expression must be RE-EVALUATED, not cached

With the bitfield in place but the OT pointer cached in a local, the body came
out **two instructions short**: retail re-reads `arg1->unk30` before the second
store, where a cached local reuses the register. That is ordinary macro
argument semantics — `addPrim(ot, p)` is
`setaddr(p, getaddr(ot)), setaddr(ot, p)`, so `ot` is expanded twice and
evaluated twice. Writing the expression out twice restores both loads:

```c
((OtTag *)arg0)->addr = (*(OtTag **)((u8 *)arg1 + 0x30))->addr;
(*(OtTag **)((u8 *)arg1 + 0x30))->addr = (u32)arg0;
```

This is the same shape as the existing learning *"Do not cache a
`this->field` across an intervening vtable call — re-read it at each use
site"*, one step further out: here there is no call at all, just a macro that
happens to evaluate its argument twice.

### What is left

- `lui $a2, 0xff00` where this body gets `lui $a1, 0xff00`, plus the renames
  that follow from it.
- Retail fills a load-delay slot with **`addiu $v0, $s1, 0x14`** — it computes
  `arg0 + 0x14` somewhere in this branch — where this body has nothing to
  schedule and GCC emits a `nop`. That instruction is the remaining lead, and
  it is NOT dead: GCC 2.6.3 hoists an existing independent instruction into a
  load-delay slot, it does not invent one. Something in the real source reads
  or forms `arg0 + 0x14`. Whoever holds this unit knows what lives at `+0x14`
  in this object from the seven siblings and the `func_8001A380`/
  `func_8001A3EC` call sites, and is far better placed to name it than a
  cold re-derivation.

### Why the original conclusion read as exhaustive

Worth recording, because it is the failure mode MATCHING-GUIDE warns about:
all six attempts varied *how the masking was expressed* while holding fixed
the assumption that the masking was **written in the source at all**. Six
attempts along one axis reads exactly like a search of the whole space. The
axis nobody varied was the type of the thing being assigned.

**Consequence for this family: the seven siblings' reports inherit a
superseded cause.** They were classified by analogy to this function, and the
analogy held for the residue's SHAPE but not for its reachability. None of
them is known to be unreachable.

## RUNNER PASS, round 13 continued: verified the delay-slot filler's formula, still not cracked

Reproduced the head's instruction-exact body exactly (46/54, same two register
choices, same missing `addiu $v0,$s1,0x14`) and confirmed via `asm-differ`
that it is genuinely zero-inserted/zero-deleted, matching the head's own
report.

**New, verified finding: the filler's offset is not arbitrary.** Checked all
eight siblings' own retail disassembly directly (not by analogy) and found
the missing `addiu $v0,$s1,N` in every one of them satisfies:

```
N = (highest arg0-relative offset read anywhere in that function's CALLS
     branch) + (the access width at that offset)
```

i.e. it is the address one byte past the LAST field of `arg0` (self) the
function ever touches — the exact size of whatever `self` "is" from this
function's point of view. Confirmed by direct measurement, not inference:

| function | last touched `self` field | width | sum | actual filler |
|---|---|---|---|---|
| `func_800197C4` | `+0x10` (uv2, `PolyUV4`) | 4 | 0x14 | 0x14 |
| `func_80019B24` | `+0x14` (uv3, `PolyUV4`) | 4 | 0x18 | 0x18 |
| `func_8001989C` | `+0x18` (uv2, `PolyUV4`) | 4 | 0x1C | 0x1C |
| `func_800199EC` | `+0x1E` (`u16` read) | 2 | 0x20 | 0x20 |
| (`func_80019C04`/`func_80019D84`/`func_80019EE4`/`func_8001A064` not
  individually re-derived this pass, but each carries the identical
  shape and an analogous filler — see their own reports) | | | | |

This is too regular to be coincidence, and it rules out one attractive
theory outright: it cannot be `sizeof(some fixed struct)`, because the value
scales per-sibling with exactly how much of `self` that PARTICULAR variant
touches, not with a constant type size.

**What this doesn't answer: why GCC computes it, or why the value survives
optimization to be schedulable in the LIST branch specifically.** Two
concrete hypotheses tried and rejected:

1. Compute the "one past last field" pointer as a local live across the
   whole function (so it would legitimately be available in either branch)
   — regresses badly: retail uses only 3 callee-saved registers (`$s0`-
   `$s2`) for this whole function, and giving this pointer its own
   cross-branch lifetime forces a 4th (`$s3`), which drifts the function's
   own length. 0/54, WARNING: drift.
2. Compute it as a purely local, `(void)`-cast, unused expression scoped
   inside the `if` branch only — eliminated entirely by `-O2`, reproducing
   exactly what `func_8001A268`'s report already found for a genuinely
   unused local: GCC 2.6.3 does perform basic dead-store/dead-expression
   elimination for a value with no read whatsoever, so a plain "mention the
   address and do nothing with it" does not survive to be schedulable.

The load-delay-slot mechanics (MIPS I: the instruction immediately following
a load cannot use the loaded register, and the reorg pass fills that slot
from the SAME basic block, not by reaching into the other arm of a branch)
means whatever computes this address must be a genuine, non-eliminated
value local to the list-splice branch's own basic block — which contradicts
every "it's really an artifact of the calls branch" theory tried so far,
including this pass's.

**Left for whoever picks this up next:** given the value equals exactly
"one past the last field of `self` the CALLS branch reads," and the
calls-branch's own field layout is not shared code with the list-splice
branch, the most promising remaining direction is a construct that is
genuinely LOCAL to the list-splice arm but happens to numerically equal that
address without referencing the calls-branch's fields directly — for
example, if `self`'s own declared TYPE (whatever struct it actually is, as
opposed to the local `OtTag` view used only for the splice) has a member or
`sizeof` that independently equals this same value. That would require
identifying `self`'s real type from a caller of this function (most likely
`func_800193C0`/`func_800194A4`-style code elsewhere, since this family's
signature and its `arg1`/`arg0` roles match those functions' own `(self,
prim)` calling convention closely enough to suspect these ARE
`func_800193C0`'s `callback` argument) rather than from anything visible
within `code_8220_c` alone.
