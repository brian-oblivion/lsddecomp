### Why this differs from round 20's attempt 8

Attempt 8 held the POINTER-WALK SHAPE fixed and only varied how the
pointer's address expression was spelled (`&D_8009025C[i]` vs
`D_8009025C + i` vs explicit byte arithmetic) or which of `p`/`node`
was declared first. All of those preserve two live pointer values
across the loop body (`p` itself, and `*p`/`node` derived from it) --
GCC 2.6.3 evidently colors THAT pair of pseudo-registers into `$v0`/`$v1`
in the opposite order from retail regardless of spelling. Indexing
`D_8009025C[i]` directly removes the DECREMENTING POINTER as a live
value across iterations entirely -- only the loop index `i` (already
correctly in `$s1`, matching retail throughout every prior attempt) and
the per-iteration temporary address computed from it remain, and that
narrower live-range set is what retail's own compile also produced. The
fix was not a different spelling of the same expression; it was
removing a variable whose live range spanned iterations at all.

### Proposed learning

**A register-pair-swap residue survives every operand-order and
declaration-order rewrite of the OFFENDING expression, but can still
close by removing a REDUNDANT POINTER LOCAL whose live range spans
loop iterations, replacing it with direct index-into-array access.**
This is a distinct lever from the "declaration order decides
register/stack layout" family already documented elsewhere in this
project (`func_8004042C.md`, `func_80040154.md`): those cases kept the
same set of live variables and only varied ORDER; here the fix was
reducing the set of live-across-iterations values from two (pointer +
its dereference) to one (the index alone). Worth trying "eliminate the
pointer, index directly" as its own axis on any register-identity
residue inside a loop that walks a pointer derived from `&array[i]`,
before concluding operand-order/declaration-order exhausts the space.

## Shape (confirmed by full derivation + build)

`self` (`$a0`) is walked as a `HistoryNode *` up its own `parent` chain
(`+0x048`), recording each node visited into a fixed 100-entry global
trail table `D_80090260[0x64]` (indexed by walk depth). Each node holds
an "owner" tag at `+0x000` (compared against 0, and against a global
sentinel `D_80090B74`) plus two 8-word (0x20-byte) chunks: a "live"
snapshot at `+0x004` and a "finalized/backup" snapshot at `+0x024`.

The walk looks for the first of three stopping conditions per node,
starting from `self` and climbing toward the root:

1. **A node whose own tag is already the sentinel** (already finalized
   by a previous call to this same function): use its own backup chunk
   as the output, stop immediately.
2. **The root itself (no parent), tag is 0 or the sentinel**: this is
   the "nothing owns any of this yet" case -- copy the root's OWN live
   chunk into its own backup chunk (finalizing it in place), copy that
   into `*out`, latch the tag to the sentinel, stop.
3. **The root itself, tag is some other real value**: fall back to
   whichever ancestor along the just-completed walk was the deepest one
   found with tag `== 0` (tracked in a local, `lastFree`, as a "depth
   index" recorded each time such a node is passed over while climbing);
   if none was ever found (`lastFree` stays at its `0x64` sentinel
   value), use the ORIGINAL `self` (trail index 0) as the fallback
   source instead. Either way, copy that node's *own* backup chunk into
   `*out`.
4. **A non-root node with a real (non-zero, non-sentinel) tag**:
   remember this depth as `lastFree` if the tag is 0 specifically
   (separate flag from the stopping condition), then continue climbing
   to `cur->parent`.

After the walk breaks out (any of the three stop conditions), a second,
independent loop runs IF the walk depth (`i`, the loop-exit value) is
positive: it walks a SEPARATE, adjacent global array `D_8009025C[]`
(splat's own label at `D_80090260 - 4` -- a different address, so a
different symbol seen from C; NOT modeled here as an alias of
`D_80090260`, since nothing forces that relationship and touching
`config/` is off-limits) from index `i` down to `1`, and for EACH entry
calls a Psy-Q helper (`func_80012AF8`, `asm/psyq_2258.s`, an
accumulator-shaped routine that reads/writes an `out`-shaped struct and
a second struct pointer -- not derived further, out of this unit's
scope) with `(out, &node->cur)`, then writes `*out` back into that
node's OWN backup chunk and latches its tag to the sentinel too. This is
the "apply accumulated deltas back down the chain, finalizing every
node walked past" phase. **The call genuinely executes once per
iteration** -- confirmed by the disassembly's own backward branch target
(`bgtz $s1,.L8003FA80`) reaching back far enough to include the `jal`,
which matters below (attempt 7 got this wrong).

## Residue -- confirmed, isolated to ONE address computation (4 words)

`tools/asm-differ/diff.py func_8003F848` shows the ENTIRE function

computing `p = &D_8009025C[i]`):

```
retail:  sll v0,s1,0x2 / lui v1,hi(D_8009025C) / addiu v1,v1,lo / addu s0,v0,v1
built :  sll v1,s1,0x2 / lui v0,hi(D_8009025C) / addiu v0,v0,lo / addu s0,v1,v0
```

Same four instructions, same operands conceptually (`i*4` and

register-identity residue: same instruction count, same total length, no

## How this was reached this round (62/177 -> 173/177)

The FIRST body written this round scored 62/177 raw (with an address
drift warning), but `asm-differ` showed the true shape immediately: the
first 63 words were byte-exact, and past one point every remaining word
was the SAME instruction at a CONSTANT 4-byte offset, just a different
register -- the signature of one missing/extra instruction upstream, not
a spread-out defect (see CLAUDE.md's `func_8004BB3C`/`func_8003D73C`
precedent for reading a low raw score this way).

That one point was `D_80090260[0]` (the "`lastFree==0x64`, use the
original `self`" fallback): retail recomputes its address fresh via
`lui`/`lw` even though `$a3` (already `&D_80090260`, live from the walk
loop) could serve as the base for a one-instruction `lw`. My C initially
CSE'd this the "efficient" way (reusing `$a3`), one instruction shorter
than retail. Four hand levers failed to change this (`__asm__("")`
barrier, variable-index vs literal, a `volatile` pointer cast, inlining
vs naming a temp for the SIBLING arm) -- all produced byte-identical
output to each other. An unguided permuter search (seeded from the
62/177 body, `-j 6 --stack-diffs`, `timeout 500`) found a candidate
scoring 140 that, when applied through the REAL oracle, changed nothing
(same 62/177, same divergence point) -- a confirmed instance of
`docs/MATCHING-GUIDE.md`'s "permuter score is not the oracle" caution.

**What actually closed the 4-word gap was re-examining which of the TWO
sibling arms used a named `src` local vs an inlined expression.** Attempt
5 (see below) had already shown GCC compiles
`src = D_80090260[i]; *out = src->backup;` and
`*out = D_80090260[i]->backup;` IDENTICALLY for the "found via lastFree"
arm. Applying the SAME choice to the OTHER arm -- inlining
`*out = D_80090260[0]->backup;` there instead of naming `src` -- was
untried; doing so, in combination with keeping `src` NAMED in the
sibling arm (the exact opposite pairing from the body originally
written), jumped the score straight from 62/177 to 173/177 with NO
drift warning. **Which of the two structurally-parallel arms gets the
named-temp treatment, independent of what either arm's OWN codegen looks
like in isolation, decided the `$a3`-reuse question for the whole
function** -- confirmed by testing the swap in isolation (see attempt 8).

   `D_80090260[0]` read: no change from the 62/177 baseline -- a barrier
   does not defeat cross-block address CSE in GCC 2.6.3's front end; it
   only pins instruction order.
2. **Variable-index rewrite** (`i = 0; src = D_80090260[i];` instead of
   the literal `D_80090260[0]`): no change -- GCC constant-propagates `i`

   original `.s` label, matching the disassembly's block boundaries 1:1
   instead of nested `if`/`else`/`break`): regressed SHARPLY to 6/177 --
   restructuring control flow this way perturbs register allocation for
   the ENTIRE function. Reverted immediately; not a viable direction.
4. **Surgical `volatile` cast** at just this access

   GCC 2.6.3 does not treat a `volatile`-qualified POINTER CAST on an

   though the runtime behavior differs completely. **A second, sharper
   instance of the "permuter score is not the oracle" trap**: this one
   very nearly reads as a genuine zero-adjacent match while being
   outright incorrect C, not just a different valid compilation. Not
   used, not carried forward.

## Proposed learning

**Two structurally-parallel `if`/`else` arms that each independently
compile identically whether a temp is named or inlined can still
DIFFER, as a PAIR, in which arm should get which treatment** -- the fix
here was not "inline both" or "name both," it was inlining ONE arm while
keeping the OTHER named, discovered only by testing the swap
combination rather than trusting each arm's own isolated no-op result.
Worth checking on other multi-arm residues before concluding a
transformation is neutral just because it is neutral in ONE arm tested
alone.

**The permuter can produce a candidate that is SEMANTICALLY WRONG (here:
moves a call out of a loop, changing how many times it runs) yet scores
almost exactly like a correct match** -- because moving code across a
loop's back-edge changes only the branch-target immediate, not the
static instruction count, a call-hoisting bug and a genuine near-miss
can look identical to the permuter's own scorer and very close even to
`funcdiff.py`'s per-word count (176/177 here, ONE word short). This is a
sharper version of `docs/MATCHING-GUIDE.md`'s existing "permuter score
is not the oracle" caution: it is not enough to reject a false lead by
score alone when the score is this close -- the candidate's CONTROL FLOW
must be checked against the original disassembly's own branch targets
before ever considering committing it, exactly per this project's own
"branch targets disagree = outranks everything" rule
(`docs/MATCHING-GUIDE.md`, "Reading a residue").

**Read a low raw funcdiff score's SHAPE before triaging it as "far
off"**: a constant-offset, same-mnemonic-different-register pattern for
the entire remainder of a function, after one clean initial stretch, is
the same "one-defect-explains-the-whole-gap" signature CLAUDE.md
documents for `func_8004BB3C`/`func_8003D73C` -- the 62/177 intermediate
state here was actually 173/177-equivalent in structure the whole time.
