## The residue

Best in-window score 69/98, but `objdump -d build/src/Entity_g.c.o` shows
the actual compiled body is ~94 instructions against retail's 98 -- roughly
4 words SHORT, which is why `funcdiff`'s "differs outside this range"
warning fires (96753 bytes) and the raw word-match count is not
trustworthy on its own.

`tools/asm-differ/diff.py` shows retail materialises the literal `-0x3C`
(the final call's `arg4`) into `$v0` MUCH earlier than the call site --
right after the `this->unk44 == 0` branch decision, before even testing
`this->unkFC >= 0x870` -- and keeps re-materialising the same literal at
several later branch points (at least 3 separate `li v0,-0x3c` sites),
rather than computing it once at the point of use. My rewrite, which passes
`-0x3C` as a plain literal argument at the single call site, lets GCC
compute it exactly once, there -- fewer instructions than retail, not more,
which is the direction one would normally read as "correct, just
differently scheduled." It is not: retail's OWN choice to redundantly
rematerialize a constant across branches is the actual byte count, and my
leaner version is short by the difference.

## Why this reads as an under-explored residue, not a dead end

The specific SHAPE needed -- re-materialize the same literal on 3+
independent branches that each reach the shared tail call, without
widening its live range across any call -- is not something a `goto`
restructuring or a single hoisted local can express (attempt 2 shows the
local approach fails specifically because it makes the value survive across
calls it should not). A per-branch LOCAL literal restatement (repeating
`-0x3C` as the LAST computed value on each of the 2-3 paths that fall
through to the call, rather than the single point where I wrote it) is the
untried lever -- not attempted here due to the combinatorial number of
branch points and this round's remaining queue size.

### Proposed learning

A negative outside-range `funcdiff` warning is not always "my function is
too LONG" -- here it is 4 words too SHORT, the opposite of every other
drift case this project has documented so far. Always cross-check with
`objdump -d build/src/<unit>.c.o` before assuming the direction of a
length mismatch; guessing wrong wastes a whole attempt cycle (attempt 2
above chased the "keep it alive longer" theory and made things worse
because the real fix needed the OPPOSITE -- MORE independent re-computation
sites, not one canonical one).

register across the intervening `jalr`s. This is a scheduler-level
decision (which delay slots to fill with an unrelated-but-needed-later

simple hoist/no-hoist question. Not attempting to hand-derive a source
