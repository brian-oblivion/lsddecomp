**The lever: retail has TWO calls to `func_80064FBC`, one per arm of the
`unk44 != 0 && unkFC >= 0x870` test, not one call fed by `arg3`.** The tell
was in the asm the whole time: two separate argument set-up blocks
(`.L80064F70` with `a3 = 0xFA0`, `.L80064F88` with `a3 = 0x884`), each
starting with `sw v0,0x10(sp)`, joined only at the `jal` by a `j` whose delay
slot holds the arm's own `ori a3` — that is cross-jumping merging two call
statements' shared tail, not a phi. The four `li v0,-0x3C` sites are not
redundant rematerialisation either: each call block begins with
`li v0,-0x3C` (the 5th argument, stored to the stack), and reorg's
fill-from-target steals that first instruction into the delay slot of every
branch that jumps to the block (three of them) while the fall-through after
`slotCC` keeps its own copy. With one call and a merged `arg3` variable
there is only one such block, hence 7 words short.

**Why round 20's "two call sites" variant (104 words) missed:** it also

### Proposed learning

**Several `li` of the same constant in branch delay slots, each landing on
a block that begins with that same `li`, is reorg's fill-from-target, not
redundant rematerialisation.** Count the argument set-up blocks before a
shared `jal`: two blocks joined by a `j` whose delay slot sets the one
differing argument means two call statements that cross-jumping merged.
Write one call per arm. The "no C spelling for independent transient
lifetimes" reading (LEARNINGS 3d as cited by this report) was an
explanation for a shape that was really one call statement too few.

## ROUND 20 (runner echo): six fresh structural variants, bracketing retail's length from both sides -- sharper diagnosis, still not closed

Per the coordinator's explicit ask for a real attempt (best ratio in the
family). Traced every one of retail's FOUR `li v0,-0x3c` sites precisely
against the raw disassembly (not just re-reading this report's prose):
two feed the `unk44==0`-or-`unkFC<0x870` merge point (`.L80064F88`,

computed `-0x3c`, in a delay slot or immediately after a call, never
shared with its neighbor even within the same merge group.

**Six structural variants tried, spanning both directions of the size
gap:**

1. **Four fully independent `func_80064FBC(...)` call statements**, one
   per branch, no shared `arg3` variable at all (on the theory retail's
   source might genuinely repeat the whole call four times and let
   cross-jump find its own merge, mirroring `Entity__MoodCue115`'s nested-merge
   pattern from earlier this round). **Compiled to 110 words -- 12 words
   too LONG**, the opposite direction from the documented 94-word/4-short
   result. GCC did not reproduce retail's partial 2-level merge for this
   shape at all.
2. **Two call sites** (one shared call per `arg3` group, matching retail's
   two `jal` instructions, but with the first group written as two
   textually separate early-return statements rather than an `||`-combined
   guard) -- **104 words, 6 too long.**
3. **A combined `if (a == 0 || b) {...}` guard** for the first group instead
   of two separate `if`s -- **also regressed** (26/98 in-range, real
   drift; short-circuit `||` compiles to a different branch shape than two
   independent tests reaching the same target).
4. **One shared call (matching the original 94-word structure) plus a
   named `arg4` local reassigned redundantly at each of the four real
   sites, with an extra unconditional top-level assignment** -- **97
   words, 1 word SHORT.** Closest yet, but introduces an extra
   callee-saved register (`$s2`) in the prologue: confirmed via
   `asm-differ`, word 3 onward diverges because `arg4`'s live range (as a
   single C-level variable assigned before `slotCC`'s call and read after
   the shared call) forces GCC to keep it in a permanent register across
   that call boundary.
5. **Same shape, `arg4` reassigned at the four real sites with NO spurious
   top-level assignment** -- **99 words, 1 word LONG**, same
   extra-callee-saved-register defect, confirmed via `asm-differ` at the
   identical prologue location.
6. **A `goto` to one shared call label, with `arg3`/`arg4` set immediately
   before each jump** (on the theory that a short, jump-adjacent
   assignment might stay in a scratch register rather than needing a
   permanent one) -- **92 words, 6 words SHORT.** GCC recognized all four
   `goto`-to-the-same-label sites as one genuine merge point and used PHI-
   like reasoning to eliminate the redundant computation entirely (even
   more aggressively than the single-call literal form), rather than
   preserving four separate scratch-register rematerializations.

**What this establishes, precisely, that the existing report's diagnosis
did not yet pin down: the moment `-0x3c`/`arg3` is named as a persistent
C-level variable (even one reassigned at every branch, even one whose
assignments are textually adjacent to their own `goto`), GCC 2.6.3's
non-SSA register allocator assigns it ONE fixed storage location for its
entire scope -- and if ANY reachable path requires that location to
survive a call (here, the `slotCC` call on one branch), the whole
variable gets promoted to a callee-saved register, regardless of how
many redundant assignment sites exist elsewhere. There is no C-level way
tried (redundant reassignment, `goto`, per-path fully independent
locals) that reproduces retail's actual shape: four SEPARATE, transient,
scratch-register recomputations of the same literal, each local to one
predecessor edge, that a shared merge point simply reads without ever
treating as one persistent variable. This is a register-allocation-level
property (liveness is a per-symbol, whole-function fact in this
compiler, not a per-edge one), not a source-shape property -- consistent
with, and considerably sharper than, this report's own prior "scheduler
filler pattern, not a reasoning problem" conclusion and the round-19
permuter run's failure to find a legitimate translation.

**Disposition unchanged: STALL, best 69/98 in-window (94 real compiled
words vs retail's 98, confirmed via `objdump`).** `INCLUDE_ASM` restored.
Not re-run through the permuter this round (already run for 33161
iterations in round 19, floor 500, no zero; the coordinator's guidance
this round was hand work over another search, and none of this round's
six structural leads produced a smaller, more-targeted seed worth a fresh
bounded run).

### Proposed learning

**A residue characterized as "redundant constant rematerialization across
multiple delay slots" should be tested against BOTH directions of a
size-changing restructuring, not just the "make it one canonical value"
direction** -- this function brackets retail's word count from both
sides (92-99 range tried, retail sits at 98) purely by varying how many
independent call/goto sites exist and whether the repeated literal is
named. The single unifying fact across all six failures: GCC 2.6.3 does
not have a way, reachable from this project's C, to give one value
several INDEPENDENT, transient (non-callee-saved) lifetimes converging on
one physical merge point -- a named variable gets ONE lifetime for the
whole function; unnamed literals at genuinely separate call sites get
merged by cross-jump into fewer physical sites than retail keeps. Retail's
actual shape sits in the gap between what a persistent variable and a
literal-per-call-site can each express in this toolchain.

### 2. Testing the mechanism claim in isolation (pinned pipeline, per CLAUDE.md "Escalate, do not experiment")

The report's claim, as stated by round 20 and promoted into
`docs/DECOMPILATION_LEARNINGS.md` section 3d ("it is also why retail's
transient rematerialization shape has no C spelling"), is broad: **GCC 2.6.3
has no way, reachable from this project's C, to give one value several
independent transient lifetimes converging on one merge point.**

Rather than assume it, built two ~15-line reproducers through the exact
pinned pipeline (flags read live from the Makefile, not retyped):

```
tools/gcc263/cpp -Iinclude -Iinclude/psyq -undef -lang-c -nostdinc -Dmips -D__GNUC__=2 t.c \
  | tools/gcc263/cc1 -mips1 -mcpu=3000 -quiet -G0 -O2 \
  | .venv/bin/python3 tools/maspsx/maspsx.py --aspsx-version=2.34 --dont-force-G0 \
      --expand-div --addiu-at --gp-symbols=config/gp-symbols.txt --no-nop-mflo-mfhi \
  | tools/binutils/bin/mipsel-linux-gnu-as -march=r3000 -EL -no-pad-sections -G0 -o t.o
```

**Reproducer A** (`t_withcall.c`, mirrors the shape: two branches merge on a
value, one path has an intervening call before the merge):

```c
extern void use(int, int);
extern void maybe_call(void);

void f(int a, int b) {
    int c;
    if (a) {
        if (b) { maybe_call(); }
        c = 1;
    } else {
        c = 2;
    }
    use(a, c);
}
```

Compiled output shows `li a1,0x1` **TWICE**: once in the delay slot of
`beqz a1,<merge>` (the `if (b)` test) — filling that branch's
otherwise-empty delay slot speculatively, serving the `b==0` path directly —
and a SECOND time, redundantly, right after the `maybe_call()` call
returns, before the `j <merge>`. `a1` is a caller-saved argument register;
the delay-slot filler materialized `c=1` early as free filler, but the
intervening call invalidates it, forcing a second materialization on the
path that took the call. **No named `s`-register promotion at all** — `c`
never leaves a scratch/argument register.

**Reproducer B** (`t_nocall.c`, identical shape with the inner call replaced
by a side-effect-free ALU op, `a = a + b;`) — control for the same
structure with NO intervening call: `li a1,0x1` appears **exactly once**,
in the natural delay slot before the merge. No duplication.

**Verdict: the mechanism is REAL and reproduces cleanly outside this
project, in ~15 lines, on the pinned toolchain — confirming it is a genuine
GCC 2.6.3 MIPS backend behavior (delay-slot filler opportunistically fills
an otherwise-empty delay slot with a value it can prove is needed on a
successor path; an intervening CALL invalidates a caller-saved
materialization and forces a second one), not a fabricated or
misremembered diagnosis.** This is a positive isolation result, exactly the
kind CLAUDE.md asks to attempt before trusting a report's own claim.

**But it sharpens the claim rather than confirming it as stated.** The
promoted `DECOMPILATION_LEARNINGS.md` framing ("no C spelling for
independent transient lifetimes... a named variable gets ONE lifetime for
the whole function") is the round-20 read; this round's reproducer shows
the actual trigger is narrower and does not require naming anything:

- Duplication happens when the constant's *one* textual computation point
  in the source sits CLOSE (in the pre-reorg RTL, which tracks source
  control-flow structure) to a branch whose delay slot is otherwise empty
  AND which is followed, on at least one outgoing edge, by a call that can
  clobber the register before the value's real use.
- It is proximity-dependent, not identity-dependent: Reproducer B shows the
  SAME two-branches-merge shape produces exactly ONE materialization when
  no call intervenes — the redundancy is not automatic from "two paths
  converge," it needs the call in the middle.
- Retail's actual four `-0x3C` sites split into two different sub-cases:
  the FIRST TWO (feeding `.L80064F88`/merge A) have **no call between
  either branch and the merge** — that duplication is the "free filler,
  needed downstream" case, not the call-invalidation case Reproducer A
  isolates. The LAST TWO (feeding `.L80064F70`/merge B) each follow a
  `jalr` (`slot12C`/`slotCC`) — that pair IS the call-invalidation case.
  **This report's residue is two distinct instances of the mechanism
  stacked, not one uniform pattern** — consistent with
  `DECOMPILATION_LEARNINGS.md`'s standing "is this one defect or several
  whose scores do not add?" question, here answered: two, of two different
  sub-kinds of the same family.
- Neither sub-case is reachable by NAMING `arg3`/`arg4` (round 20 variants
  4/5, confirmed again by this round's isolated reproducers never needing a
  name) — naming only changes whether the eventual value survives in a
  scratch or callee-saved register, which is a different, ALREADY-explored
  axis. The unreached lever is **structural/textual proximity of the
  constant's computation to specific branches, without naming it** — and no
  C source shape was found (this round included) that reproduces retail's
  own choice of which branches host which materialization, because C has no
  construct for "compute this literal argument early, opportunistically, in
  a way visible to the delay-slot filler, without writing a second copy of
  the call or naming a variable."

Did not attempt to hand-craft a proximity-matching restructure of the full
