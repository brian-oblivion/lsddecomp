## Two real fixes, one still-open header claim corrected

**1. The base-prefix dispatch is a `switch`, not an if/else-if/else chain
-- the header's own pseudocode shape was WRONG here, exactly the kind of
error the assignment asked to flag rather than work around.** A direct
transliteration of the header's
`if (*p=='X'||*p=='x') {...} else if (*p=='B'||*p=='b') {...} else {...}`
compiles to a linear OR-chain of compares and was 4 words short (75/79).
Retail's actual compare tree splits FIRST on `*p < 'Y'` (0x59) -- grouping
uppercase `'B'`(0x42)/`'X'`(0x58) against lowercase `'b'`(0x62)/`'x'`(0x78)
-- which is the compare-tree a `switch` over four sparse case values lowers
to, not what an if/else-if chain over two `||` conditions produces.
Rewriting as
```c
switch (*p) {
case 'X': case 'x': p++; base = 16; break;
case 'B': case 'b': p++; base = 2; break;
default: base = 8; break;
}
```
reproduced retail's exact compare tree (the `slti v0,v1,0x59` / `beqz`
split) immediately, closing all 4 words in one change (75/79 -> 78/79).
This is the header's shape being a correct BEHAVIORAL description but the
wrong SOURCE FORM to transcribe literally -- worth recording since the
assignment specifically anticipated "if you find the decode wrong, say so
plainly." The decode of WHAT the code does was right; the suggested C
shape for HOW to write it was not.

**2. `acc = acc * base + d;` (one combined statement) put the `mflo`
result in `$v0` with a following `addu $s2,$v0,$v1`; splitting into
`acc *= base; acc += d;` (two statements) put it directly in `$s2` via
`mflo $s2` / `addu $s2,$s2,$v1`, matching retail exactly.** Same
instruction count either way (not a length residue), but a genuine
register-identity difference the split statement fixed outright.

## Signature note: the argument-less caller

`func_80050A84` (already matched, unchanged) calls this function with
**zero arguments** -- retail's own call site has a bare `nop` in the delay
slot, no `a0` setup at all. An ordinary ANSI-prototype definition
(`s32 func_80050948(const char *p) { ... }`) makes cc1 correctly reject
that call as "too few arguments" once both are visible in the same
translation unit (confirmed by hitting exactly that error first). Using an
**old-style (K&R) function definition** --
```c
s32 func_80050948(p)
const char *p;
{ ... }
```
-- does not establish a full prototype, so `func_80050A84`'s zero-argument
call compiles unchanged. This almost certainly reflects the two having been
separate translation units in the original 1998 source (a cross-TU call is
never checked against the callee's real definition), not an intentional
mismatch; K&R syntax here is a decomp-C accommodation for that, not a claim
about the original source's own style.

## The residue that did not close (1 word: a delay-slot scheduling choice)

Confirmed via `tools/asm-differ/diff.py func_80050948` (which realigns) that
this is the **entire** gap -- every instruction before and after it is
byte-identical once the 1-word offset is accounted for, all the way through
the epilogue:

```
4117c: TARGET lbu v0,0(s0)         CURRENT lbu v0,0(s0)      (identical)
41180: TARGET nop                  CURRENT (missing)          <- the whole residue
41184: TARGET lui at,0x8006        CURRENT lui at,0x8006 (at 41180, i.e. shifted -4)
...                                (everything after ripples by exactly
                                    -4 bytes, content-identical throughout)
```

After loading `*p` (the whitespace-skip loop's first instruction, itself a
branch target reached both on entry and on the loop backedge), retail
schedules a genuine `nop` before computing `D_80066841`'s address
(`lui`/`addiu`). This build's scheduler instead hoists the `lui` (which has
no data dependency on the just-loaded byte) into that same delay-slot-
adjacent position immediately, one instruction earlier than retail. Both
schedules are valid MIPS -- the loaded value isn't consumed until the
`addu $at,$at,v0` two instructions later either way -- so this is a pure
instruction-scheduling preference, not a logic or register-identity
difference. This is the SAME residue CLASS already documented at length in
`code_179d8_k` (`func_80034F90.md`: "an independent instruction the
compiler hoists into a branch delay slot one branch earlier than retail
places it"), now confirmed in a second, unrelated unit.

**Six reshapes tried, all inert (byte-identical output, same missing nop):**
1. `p += 1;` instead of `p++;` for the loop increment.
2. Splitting into an explicit `u8 c = *p;` local plus a bare `__asm__("")`
   scheduling barrier immediately after it, before the array index --
   inert, because the `lui` being hoisted doesn't depend on `c` at all, so
   a barrier protecting `c`'s value doesn't block it from moving before
   the barrier too.
3. `D_80066841[*(const u8 *)p]` (pointer cast) instead of `(u8)*p` (value
   cast).
4. `8 & D_80066841[(u8)*p]` (swapped `&` operand order).
5. `for (; D_80066841[(u8)*p] & 8; p++) { }` instead of a `while` loop.
6. A bare `__asm__("")` was the only CLAUDE.md-sanctioned lever tried; no
   operand-constrained or whole-function `__asm__` was attempted (banned
   outside the documented COP2 exception, which does not apply here).

Per CLAUDE.md's register-identity/scheduling STALL guidance: reshaping did
not move it, so this is a stall to report, not banned-fix territory to keep
pulling on.
