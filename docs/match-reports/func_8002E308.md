## What it computes, and the sibling relationship

**This is the register-pressure / `s16`-argument-narrowing shape flagged in
the unit's carve-time header comment**, not a BIOS trampoline: the opening
`addu $t3,$a0,$zero` / `addu $t0,$a1,$zero` / `addu $t1,$a2,$zero` preserves
each of three incoming parameters in a raw (un-narrowed) register BEFORE the
same three registers get narrowed to `s16` in place (`sll..16`/`sra..16`).
Confirmed by hand, matching the header's note that `func_8002E874` in
`code_179d8_m` (this round's runner bravo) opens with the identical
three-register preserve-then-narrow prologue and the same early-out branch
comparing two of the narrowed arguments — **this is the same shape as that
sibling, derived independently from this side**, exactly as the carve note
anticipated.

Semantically: 4 params (call them `start`, `a1`, `a2`, `duration`, matching
`t3`/`t0`/`t1`/`t2`). If the narrowed `a1==a2`, return immediately (nothing
to interpolate). Otherwise this looks like ramp/tween setup: it writes
`1` / `a1` / `a2` into three per-channel 52-byte-stride tables
(`D_8008D9A4`/`D_8008D9AC`/`D_8008D9AE`, same stride-52 "channel record"
convention seen in `func_8002DDBC` and `func_8002E138` this round — index
`chan*52` where `chan` is the narrowed `start` param) marking the channel
"active" with its start/end values, then picks a numerator/denominator pair
depending on whether `a1-a2` (or its negation) is closer to zero than
`duration`, divides, and writes the quotient (plus a second `1`-flag and a
duplicate) into three MORE stride-52 tables
(`D_8008D9A6`/`D_8008D9A8`/`D_8008D9AA`). The two branches (`diff<0` vs
`diff>=0`, and within each, "close" vs "far") are NOT symmetric in their
final formula — transcribed faithfully from the `.s`, not simplified, since
the byte-match depends on which exact subtraction/division retail performs
in each arm.

## The residue: same pattern as `func_8002DDBC` and `func_8002E138`, worse

**All three stall reports filed in this unit this round hit some variant of
"GCC 2.6.3 proves a preserved raw copy is bit-identical to a value already
computed elsewhere and elides the copy, where retail keeps a genuinely
separate register."** This is the clearest instance yet: retail's `t0`/`t1`
hold `a1`/`a2` UN-narrowed specifically so their full 32-bit bit pattern is
available for later 16-bit stores — but since a 16-bit store only reads the
low half regardless, and the narrowed `s16` value is bit-identical in that
half for any value that actually fits 16 bits, the compiler correctly
deduces it doesn't need both and keeps only one.

A scheduling barrier (`__asm__("")` right after the three raw-copy
assignments, before narrowing starts) **was tried and confirmed to work in
an isolated 3-argument reduction of this exact shape** — it forced GCC to
keep genuinely separate registers there. Applied verbatim to the real
function, in the same source position, it made no difference at all — the
compiled output was byte-identical with and without it. This means whatever
defeats the copy in the full function is NOT simply "the compiler proved
equivalence early and folded it before the barrier could matter" (the
isolated case proves a barrier CAN stop that fold) but something about the
REST of the function's register pressure (four preserved values, not two;
several later uses in different branches) changes which optimization pass
fires or in what order. Not resolved — flagged as the concrete case to
re-attempt first, since a working technique exists for a smaller version of
the same shape and only stopped working when scaled up.

### Proposed learning

Promote the "spurious/missing register copy under provable value equivalence"
observation from the other two reports in this round from "pattern" to
"standing lever, still unsolved at scale": a scheduling barrier
(`__asm__("")`) demonstrably works on a small isolated reproduction of the
"preserve raw copy, then narrow in place" idiom, but the SAME barrier at the
SAME source position in the real function (this one) made zero difference.
Whatever governs it depends on the function's overall register pressure,
not just local instruction adjacency — a lead for whoever investigates this
class next: try adding MORE `__asm__("")` barriers between successive
preserve/narrow pairs (one per parameter, not one for the whole group), or
try reordering which parameter is preserved/narrowed first.

## Round 33 follow-up (runner alpha): the residue is NOT the copy-elision class this report names — it is value hoisting

Re-verified the inherited 118/116-word body first (per the round-33 "check
inherited bodies" instruction): it reproduces exactly as claimed — compiled
length 0x1D8 (118 words), confirmed via
`mipsel-linux-gnu-objdump -t build/src/code_179d8_l.c.o` on the size column,
not via `funcdiff.py`'s raw score (which is meaningless here: the 8-byte
size mismatch shifts every downstream absolute address in the whole image,
producing a 230400-byte "outside range" warning — an expected consequence
of the drift CLAUDE.md describes, not a sign anything is newly broken).

**`tools/asm-differ/diff.py` shows the real mechanism is a GLOBAL
value-availability hoist, not a copy-elision decision at the top of the
function.** Both branches of the near/far split (`common:` and the
fallthrough "far" path) compute the identical value `(s16)t0 - (s16)t1` —
retail recomputes it fresh, separately, in EACH arm (confirmed
instruction-for-instruction: `.L8002E3B0`'s own `subu v1,v1,v0` at
`0x1EBC4`, and the far path's own independent `subu a0,a0,v0` at `0x1EC5C`,
using different registers, no sharing). GCC recognizes that this exact
subtraction is needed on EVERY path out of the `if (na1!=na2)` block
(whichever arm is taken) and hoists it to before the ENTIRE near/far
decision tree — visible as a `subu v1,t1,t0` inserted right after the third
table store, before any of the `bltz`/`slt`/`bnez` sequence that decides
which arm to take at all. This is despite the C writing the two
computations as textually separate statements in textually separate
branches (goto-target `common:` vs. the straight-through "far" code) — the
per-branch-duplication idiom documented for `func_8002D6A4` (share nothing
after the `if`) does NOT defeat this, because the mechanism here is a true
cross-branch redundancy/availability analysis, not a same-block CSE of a
shared tail statement.

**Two new levers tried this round, both negative, both worth recording:**

1. **`volatile s32 t0, t1`** (lever 1 from the runner brief, on the theory
   that a narrower "fence one access" instrument might stop the hoist where
   a scheduling barrier couldn't). Result: **regressed to 126/116** (0x1F8).
   `volatile` on a plain local here does not merely fence access order — it
   forces GCC to materialize the values in actual memory (an
   `addiu $sp,$sp,-8` frame appears, `sw`/`lw` pairs replace what were
   register-to-register copies), because `volatile` semantics require a
   real load/store at every access and GCC has no register-only way to
   honor that for a local whose address is never taken. This is a strictly
   worse mechanism for THIS class than for the order-only cases lever 1 is
   documented to help — record as a fourth data point alongside round 33's
   three (callee-save store order, magic-multiply constant): **`volatile`
   has no purchase on cross-branch value-hoisting either, and can actively
   regress by forcing a spill.**
2. **A bare `__asm__("")` placed at the entry of BOTH divergent blocks**
   (right after the `far`-path's `numer = (s16)t0;` line and right after the
   `common:` label, i.e. bracketing each independent computation of the
   supposedly-common subtraction). Result: **still regressed, to 120/116**
   (0x1E0) — better than the `volatile` attempt but still worse than the
   118/116 baseline. The hoist was not eliminated, only relocated one
   instruction later in program order (the `subu` still appears before the
   `bltz`/`slt`/`bnez` decision, just after a different preceding
   instruction) — confirming CLAUDE.md's documented scope for this idiom:
   a barrier fences instruction SCHEDULING/ordering, not a global
   redundancy-elimination decision with no side effects to protect against
   reordering past. GCC is free to hoist a side-effect-free arithmetic
   expression across an empty `asm("")` because the barrier has nothing
   for it to conflict with.

**Disposition: restored to the original 118/116 body (both new experiments
reverted, `git diff --stat` clean against the pre-session state).** Neither
lever from the runner brief applies to this residue's real mechanism.
**Not tried, and the most likely next lever given the mechanism now
correctly identified:** break the SYNTACTIC/value-numbering equivalence
between the two `t0-t1` computations rather than trying to fence them —
e.g. compute one arm's dividend as `-(( s16)t1 - (s16)t0)` (algebraically
identical, but a different RTL pattern that old GCC's value-numbering may
not unify with the other arm's direct `t0-t1`), adjusting the
surrounding sign/quotient use accordingly. This is a real structural
rewrite, not a qualifier or barrier, and was not attempted this round for
lack of remaining budget on this one function relative to the unit's other
four queued functions.

## Round 35 update (runner bravo): the algebraic value-numbering lever, tried and negative

Re-verified the inherited 118/116-word body first: `objdump -t` on
`build/src/code_179d8_l.c.o` confirms `func_8002E308` compiles to `0x1d8`
bytes = 118 words, matching round 33's figure exactly.

**Tried round 33's own proposed next lever — rewriting the "far" arm's
dividend as `-((s16)t1 - numer)` instead of `numer - (s16)t1`, to break the
syntactic/value-numbering equivalence GCC uses to unify it with the
`common:` arm's `(s16)t0 - (s16)t1`.** Result: **no change, still
118/116**, and the realigned diff shows the hoisted `subu` is still
present in the identical position — GCC 2.6.3 normalizes `-(b-a)` to `a-b`
at the tree/RTL level before the availability analysis that does the
hoisting runs, so the two expressions remain value-identical to the
optimizer despite reading differently in the C source. Reverted (`git
diff --stat` clean).

**A second, more aggressive attempt: routing the far arm's subtraction
through a `volatile s32` temporary** (`vtmp = numer - (s16)t1; dividend =
vtmp;`, forcing a real store+load rather than a register-to-register
value) — **regressed to 122/116** (0x1e8), four words worse than the
118/116 baseline. Consistent with this report's existing finding that
`volatile` on a value in this function's hot path costs more than it buys
(the earlier whole-variable `volatile s32 t0, t1` attempt regressed to
126/116 for the same reason — forcing a spill where GCC would otherwise
keep the value in a register is never free here). Reverted.

**Disposition: still stalled at 118/116, unchanged from round 33.** Both
levers this report's own text flagged as the natural next move (algebraic
rewrite, and — implicitly, by analogy with the barrier finding — a
memory-forcing qualifier) are now tried and confirmed negative. The
remaining candidate is a genuinely different SOURCE SHAPE for the
`if`/`goto common` control flow (e.g. restructuring away from `goto`
entirely into nested `if`/`else`, or duplicating the whole trailing
divide-and-store block instead of merging at `common:`) — untried this
round for lack of budget relative to this unit's other four queued
functions, and not obviously more promising than the two negative results
above given GCC's value-numbering operates on the RTL these all lower to,
not the surface `goto` structure.

### Proposed learning (round 35)

**GCC 2.6.3 recognizes `-(b - a)` and `a - b` as the same value even
though they are different C token sequences** — an algebraic-identity
rewrite is not a working lever against this project's "immune to
scheduling barriers" CSE/value-hoisting residue class (already named in
`func_8002CF18`'s and this function's own round-33 sections). Combined
with the `volatile`-regresses-further finding (now confirmed twice, in two
different functions), the working hypothesis for this residue class should
move from "try qualifiers and rewrites" to "look for a source restructuring
that changes the CONTROL-FLOW GRAPH shape itself, not the expression tree
feeding it" — the next runner should not re-try either qualifier or
algebraic-identity variants without a new idea for why they'd differ from
what's now confirmed twice each.
