# func_80032588 -- STALL (structural ~90/96 words, register/CFG confirmed)

Unit: `code_179d8_c`. Round 23, runner bravo. Owns `jtbl_80010CD8`
(attached rodata, do not touch).

## What it does

`void func_80032588(s32 a0)`. Two parts:

1. Splits `a0` into a "cmd" value stored in `D_8006DCA4` and a flag in
   `D_8006DCA8`: if `a0 & 0x1000`, `D_8006DCA8 = 1` and `D_8006DCA4 = a0 &
   0xFFF`; else `D_8006DCA8 = 0` and `D_8006DCA4 = a0` (the raw value).
2. Reloads `cmd = D_8006DCA4` and dispatches:
   - `cmd >= 6` (signed): `D_8009024C = cmd` (raw passthrough).
   - `cmd < 0` (falls out of the unsigned `cmd < 6` recheck): `D_8009024C
     = 0x3c`.
   - `0 <= cmd < 6`: a genuine `switch` over `jtbl_80010CD8` (6 dense
     cases), each setting `D_8009024C` to a per-case tempo/rate constant,
     and cases 1 and 4 additionally rewriting `D_8006DCA4` based on
     `D_8006DC98` (looks like a play-state flag: 0/1/other).

Full derived case semantics (verified against the `.s` instruction by
instruction, believed correct even though the byte match is not there yet):

| case | D_8009024C | D_8006DCA4 side effect |
| --- | --- | --- |
| 0 | `(D_8006DC98==1) ? 0x32 : 0x3c` | none |
| 1 | `0x3c` (always) | `(D_8006DC98==0) ? 5 : 0x3c` |
| 2 | `0xf0` | none |
| 3 | `0x78` | none |
| 4 | `0x32` (always) | `(D_8006DC98==1) ? 5 : 0x32` |
| 5 | `(D_8006DC98==1) ? 0x32 : 0x3c` | none |

## Key structural finding: case bodies are laid out 4,1,3,2,5,0, not 0..5

`jtbl_80010CD8`'s slots point at `.L800326B4`(0) `.L8003262C`(1)
`.L8003267C`(2) `.L80032668`(3) `.L800325FC`(4) `.L80032690`(5) -- i.e. the
table is indexed by case value as always, but the PHYSICAL code for the
cases is laid out in source order **4, 1, 3, 2, 5, 0**, not ascending. This
only becomes visible by reading which label falls immediately after which
in the `.s`, and it matters: writing the `switch` with cases in numeric
order (0,1,2,3,4,5) produced a function with the right per-case LOGIC but
wrong physical layout and cost the first ~10 words of match immediately
(confirmed structurally, not just by intuition -- rewriting the switch's
case order to `4,1,3,2,5,0` reproduced retail's exact block sequence,
branch polarities and branch-target relationships for the two-part bound
check and every case up through the point described below).

## Residue: GCC's own tail-merge collapses identical case endings that retail keeps duplicated

With cases in the right order, the CFG (branch targets, polarities, the
signed-then-unsigned double bound check, the shared `D_6DC98==0` default
label reused by cases 0/5) all line up with retail's `.s`. The residue is
size: our build compiles to **86-90 words against retail's 96** (word count
varied 86 -> 90 across attempts below), because our `-O2` build recognizes
that cases 2, 3, and the "cmd<0" default all reduce to the identical
tail `lui $at,%hi(D_9024C) / sw $v0,%lo(D_9024C)($at) / j <epilogue>` and
merges them into ONE shared block that the others jump into (paying only a
`j` + the case's own `li`). **Retail does not merge this at all** -- every
one of those cases carries its own full `lui/sw/j/nop` copy, verified
directly in the `.s` (e.g. `L80032668` and `L8003267C`, cases 3 and 2, are
byte-identical 5-word blocks in retail, positioned back to back, and
retail still did not fold them into each other).

Things tried, in order, all against the pinned toolchain:

1. **Baseline switch, cases in numeric order.** Wrong physical layout
   entirely (CFG target offsets didn't line up at all) -- not just a size
   issue.
2. **Cases reordered to `4,1,3,2,5,0`.** CFG lines up exactly (branch
   polarities, shared-default reuse for cases 0/5, the double bound check)
   through the dispatch and into the case bodies. Structural word count:
   86/96. The gap is entirely the merged-tail residue above.
3. **Declaration order / statement order permutations** inside cases 0 vs
   5 (which are logically identical): CONFIRMED INERT for the tail-merge
   question, as expected from the project's existing finding on this axis.
   It DID matter for something else: see the branch-polarity note below.
4. **Bare `__asm("")` scheduling barrier** after the store in cases 2 and
   3 (before `return;`). This is the permitted instruction-order-only
   barrier, not a register pin. Effect: case 3 stopped merging with the
   FAR shared tail, but merged instead with the now-adjacent case 2 body
   (which still had its own `lui/sw/j`) -- net gain of 4 words (86 -> 90).
   It narrows the gap but does not close it, and a bare empty asm barrier
   generates zero bytes of its own, so it cannot by itself force retail's
   full duplication; whatever changes GCC 2.6.3's tail-merge decision here
   is a genuine RTL-level threshold, not something reachable by inserting
   a real barrier instruction (that would add bytes retail doesn't have).
5. **`volatile u32 D_8009024C`.** No effect on the merge (tested and
   reverted -- there's no positive evidence this global is memory-mapped
   I/O, unlike the IRQ mask pair in `func_80032BF0`'s report).
6. **Branch-polarity mismatch between case 0 and case 5, found but not
   closed.** Retail's case 0 and case 5 implement the IDENTICAL 3-way logic
   (`D_8006DC98==0 -> 0x3c`, `==1 -> 0x32`, else `-> 0x3c`) but compile to
   DIFFERENT instruction sequences: case 0 uses `bne` (the `==1` success
   path is the fallthrough, physically adjacent to the store), case 5 uses
   `beq` (the `==1` success path is reached by an explicit branch AWAY, and
   the `!=1` path is the local fallthrough). Writing case 5's C with the
   condition polarity inverted (`if (x!=1) {0x3c} else {0x32}`, and other
   phrasings) reproduced the SAME `bne` pattern as case 0 every time --
   GCC 2.6.3 appears to canonicalize this specific 3-way shape to one
   normal form regardless of how the middle condition is spelled in C, so
   this specific one-of-two-identical-cases divergence looks like it needs
   a different lever entirely (possibly a nested `switch(D_8006DC98){case
   0: case 1: default:}` for one of the two, not yet tried).

extern s32 D_8006DCA4;

void func_80032588(s32 a0)

    if (a0 & 0x1000) {
        D_8006DCA8 = 1;
        D_8006DCA4 = a0 & 0xFFF;

        D_8006DCA8 = 0;
        D_8006DCA4 = a0;

            D_8006DCA4 = 5;

            D_8006DCA4 = 0x3c;

        D_8009024C = 0x78;

        return;

        D_8009024C = 0xf0;

        return;
    case 5:

            D_8009024C = 0x3c;

            D_8009024C = 0x32;

## Proposed learning

**A dense `switch`'s case bodies are laid out in the ORDER THEY APPEAR IN
THE SOURCE, not in case-value order, and the jump table's slot order is
unaffected by that choice** (the table is always indexed by case value; it
just points at wherever the compiler put each case's code). When a
retail `.s` shows a switch's labels chaining together in a non-ascending
order (check which label immediately precedes which, not just the table's
own slot order), reorder the C source's case labels to match BEFORE
tackling anything else -- this fixed our function's branch targets and
polarities completely, in one step, for every part of the function except
the specific tail-duplication residue described above.

Separately: **`-O2`'s tail/cross-jump merge of a switch's case endings
looks like a real per-instance threshold, not something under source
control here.** Multiple structurally-identical case bodies (same three
trailing instructions, same semantics, reached only via a jump-table
target) got merged by our build into shared code that retail keeps
duplicated. A bare `__asm("")` barrier shifted WHICH neighbour a case
merged with but did not stop the merge outright, and it cannot (an empty
barrier contributes zero bytes, so it cannot force retail's literal
duplication into existence). This may be a good permuter target for a
future round, since the "right" source form is apparently very sensitive
to something not yet identified (case 0 vs case 5 above is the sharpest
example: byte-identical LOGIC, different retail bytes, and no C-level
condition-polarity rewrite reproduced the second one).
