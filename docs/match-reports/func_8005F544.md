## Residue

Retail materializes the literal `0x6E` into `$v1` **twice**:

1. Unconditionally, in the delay slot of the `bnez $v1, .L8005F5C8` that
   tests the div remainder (`ori $v1, $zero, 0x6E` at `0x8005F59C`) -- this
   value is needed by BOTH paths at the shared merge point below.
2. **Redundantly**, at `0x8005F5C4`, right after the `slot148` vtable call
   inside the `remainder == 0` branch -- because `$v1` is caller-saved and
   the intervening `jalr` through `slot148` clobbers it, so the same literal
   has to be re-established before falling into the shared
   `this->unkFC == 0x6E` comparison.

Every C form tried produces the comparison-time load only ONCE, at the
single point of use, and comes up exactly one instruction short in the
`remainder == 0` path -- which shifts everything after it (funcdiff's
"differs outside this range" guard fires at ~73KB once the function's own
size is wrong).

## Classification

**Constant-rematerialization / delay-slot-fill residue** -- the same family
as the already-documented "Magic-multiply constant load POSITION" and "Pure
instruction-scheduling residue" open classes in DECOMPILATION_LEARNINGS. The
value in question here is a plain immediate needed at a shared merge point
across two predecessors, one of which contains an intervening indirect call
that clobbers the caller-saved register holding it; retail's compiler
re-materializes the constant in that predecessor rather than promoting it to
a callee-saved register or leaving a single shared load at the merge point.
No source form tried reproduces this without either (a) landing exactly one
instruction short (flat form) or (b) forcing a wrong-shaped frame growth
(any form that makes the value live-across-call via a named local).

Per HEAD BROADCAST #1/#2 (received while working this function): this is
NOT the "redundant move because a value is already resident" lever (that is
about `$v0`/return-value restatement) and NOT the "missing move because a
variable should replace a literal" lever either -- I tried the direct analog
of the latter (a named local carrying the same value across the call,
attempts #2 and #4 above) and it produced a WORSE, differently-wrong result
(frame growth) rather than the hoped-for redundant `li`. The broadcasts'
"count mentions" test does not resolve this residue; recording that
negative result here so the next attempt does not re-spend budget on the
same named-local idea.

Clean of both open toolchain blockers (`gp_rel`, `addiu_at`).

## Proposed learning

A value that is genuinely needed at a CFG merge point, where one incoming
path contains an intervening call through a function pointer that clobbers
the register holding it, is NOT reliably reproduced by naming it as a C
local -- GCC 2.6.3 promotes a real local that must survive an indirect call
to a callee-saved register (frame growth), where retail instead
re-materializes a cheap immediate in caller-saved space after the call. This
is the opposite failure mode from the project's other confirmed
"value reused after an intervening indirect call needs an explicit local"
lever (which is about STRUCT FIELD reads, not compile-time constants) --
worth flagging as the boundary of that lever: it applies to field reads,
not to literals, and forcing a literal into a named local can make an
otherwise-close near-miss (30/49) much worse (6/49) rather than better.
