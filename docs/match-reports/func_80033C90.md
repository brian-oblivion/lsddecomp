None of the three axes tried (indexing style, pre-naming the truncated
index locals, explicitly caching the row address) reproduces retail's
combination of "6 registers saved AND exactly 0x40 of frame AND `s2`
holds `&D_800902E8[a0]` reused after the call for `negHandler` only, not
for the two other identical-looking `unk90` clears at `viaE64`/
`tailCheck`". That last asymmetry (one of three textually-identical
`D_800902E8[a0][a1].unk90 &= ~0x20;` clears gets the cheap `s2`+`s1`-reuse
codegen, the other two get a full from-scratch address recompute via
`lui/addiu`+the 5-instruction ×172 multiply) is explained by `s1`'s
register lifetime — `s1` holds the byte offset `(s16)a1 * sizeof(Entry

pattern from C, rather than a fresh recompute at all three, did not fall
out of any variant tried. This reads as sensitive to GCC 2.6.3's
extended-basic-block CSE scope in a way that (unlike the block-order
lever) responds to source SHAPE in a way not yet identified in 3
attempts; a 4th+ structural axis (e.g. splitting the function into an
explicit two-phase helper, or trying `u32`/plain `int` for `c42`/`newCnt`

inside the time budget for this round.

## Proposed learning

When a function's `.s` shows one of several textually-identical array-
index expressions getting cheap register-reuse codegen while sibling
occurrences of the SAME expression get a full recompute, the asymmetry is
about a REGISTER'S LIFETIME (what it was still holding at that program
point), not about the source needing different phrasing at each site —
but confirming this by getting GCC 2.6.3 to reproduce it via source
restructuring alone, without also perturbing the overall stack frame
size, was not achieved here in the 3 variants tried. Future attempts:
try shrinking live-range pressure by splitting the "compute pk, call
0584, check thresholds, call 0404" sequence into its own `static` helper
taking `(s16 pk, s16 threshold, ...)`, so the compiler allocates its
registers independently of the caller's `s0`-`s4` set.
