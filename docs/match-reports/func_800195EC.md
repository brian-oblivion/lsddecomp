# func_800195EC — MATCHED (58/58 words)

Unit: `src/code_8220_b.c`. Flagged `/* Handwritten function */` by splat's own
extraction (asm/nonmatchings/code_8220_b/func_800195EC.s) — one of only two
non-`psyq_*` functions in the whole executable carrying that tag (the other,
`func_80018464`, is this unit's deprioritized ~1000-instruction body). GTE
transform/clip/OT-bucket routine: runs `rtpt` (triple perspective transform,
consuming vertices the caller already loaded into GTE data regs 0-5 before
the `jal`), checks a GTE flag-register overflow bit, runs `nclip` (backface
cull) and `avsz3` (Z average for the ordering table), and on success computes
`&ot_table[(otz >> shift)]` and stores it into the context struct, returning
`0`. Any of the three checks failing returns `1` (culled/degenerate).

`rtpt`/`nclip`/`avsz3` have no assembler mnemonic in this pinned binutils
build (it recognizes `cfc2`/`swc2`/`lwc2` generically as COP2 transfers but
has no PSX-GTE opcode table for the "cofun" execute instructions — confirmed
by hand-assembling a standalone `.s` with these mnemonics: `as` errors
`unrecognized opcode`, and `objdump` disassembles retail's own encoded bytes
for them generically as `c2 0x...` rather than by name). They are emitted as
raw `.word` values, taken directly from retail's own instruction bytes
(`rtpt`=`0x4A280030`, `nclip`=`0x4B400006`, `avsz3`=`0x4B58002D`).

## How it was built

1. Traced every instruction by hand against register semantics (GTE data
   register map: `d24`=MAC0 written by `nclip`, `d8`=IR0 written after the
   IR0-saturation guard, `d7`=OTZ written by `avsz3`, `d12`-`d14`=SXY0-2). No
   C form is possible for `rtpt`/`nclip`/`avsz3`/`cfc2` (control-register
   read) at all — this is the established GTE-store-leaf precedent
   (`func_800196D4` etc., same unit) scaled up to include real branches.
2. Attempted the WHOLE function body as one `__asm__ volatile` block with
   empty operand lists, referencing `$a0`(`$4`)/`$a1`(`$5`) by their natural
   calling-convention registers (this is the function's only statement, so
   nothing has moved them yet) and letting GCC's own implicit function
   epilogue generate the trailing `jr $ra`/`nop` rather than including it in
   the asm text — proven first with an isolated two-line reproducer through
   the pinned pipeline: embedding a function's own `jr $ra` inside the asm
   text and leaving the C function to fall off the end produces a SECOND,
   dead `jr $ra`/`nop` pair (GCC does not know the asm exited), so the asm
   must stop just short of the return and let GCC supply it.
3. First real build: 17/58 words matched, then drift starting exactly at the
   first `bne` in the block. Root cause, found by instrumenting `maspsx.py`
   directly (`tools/maspsx/maspsx/__init__.py`): `elif op in branch_mnemonics
   or op in jump_mnemonics: res.append(line); if self.is_reorder: res.append
   ("nop  # DEBUG: branch/jump")` — maspsx defensively inserts a REAL nop
   after any `bne`/`beq`/`blez`/`bgez`/`bgtz`/`bltz`/`j`/`jal` it sees, and
   this pushed my own explicit delay-slot instruction OUT of the delay slot
   entirely (into a separate following instruction, changing the actual
   control-flow semantics: it would then only run on the fallthrough path,
   not unconditionally as delay slots do). `beqz` was untouched only because
   it's a pseudo-mnemonic *not itself* in `branch_mnemonics` (only real
   `beq` is listed) — not because of anything about our code.

   The check for whether to insert the nop is `self.is_reorder`, which
   maspsx tracks by literally matching `line.startswith(".set\t")` and
   `line.endswith("\tnoreorder"/"\treorder")` against each processed line —
   a real *tab*, not a space, on both sides. `.ent` handling in maspsx
   injects its own `.set\tnoreorder` text into the OUTPUT for gas's benefit,
   but does not re-run it through `process_line`, so it never updates
   `self.is_reorder` — meaning is_reorder is left at its default `True` for
   the whole of a hand-written asm block unless the block asserts its own
   tab-formatted `.set\tnoreorder` line (verified against a standalone
   `maspsx.py` invocation on a two-instruction reproducer before touching
   the real function).
4. Added `".set\tnoreorder\n\t"` as the asm block's first line (matching
   maspsx's exact tab-delimited string match) — 57/58, one word short at the
   very end this time.
5. The `noreorder` state set in step 4 persists (maspsx has no scope, only a
   flat flag) past the end of the asm block, so when cc1 emits ITS OWN
   trailing `j $31` epilogue instruction (with no nop of its own — cc1 relies
   on assembler/maspsx "reorder mode" to supply one), maspsx now sees
   `is_reorder == False` and skips the customary nop insertion there too.
   Confirmed by objdump: the built function ended in a bare `jr ra` with the
   very next function's first word occupying what should have been the
   delay-slot nop. Fix: end the asm block with `".set\treorder\n\t"`,
   restoring the state cc1's own generated epilogue code depends on. 58/58.

### Proposed learning

**A hand-written `__asm__` block containing ANY branch/jump mnemonic from
maspsx's list (`beq`, `bgez`, `bgtz`, `blez`, `bltz`, `bne`, `j`, `jal` —
note NOT the `beqz`/`bnez`/`b` pseudo-forms, which aren't in the list and
pass through untouched) needs an explicit, TAB-delimited
`".set\tnoreorder\n\t"` as its first line, and a matching `".set\treorder\n
\t"` as its last line, or two separate defects appear:**

1. **Without the opening `noreorder`:** maspsx inserts a genuine extra `nop`
   immediately after the branch/jump and pushes YOUR intended delay-slot
   instruction to become an ordinary post-branch instruction — this is not
   just a size/scheduling bug, it changes semantics (an instruction meant to
   execute unconditionally, branch taken or not, now only runs on the
   fallthrough path).
2. **Without the closing `reorder`:** the `noreorder` state leaks past the
   end of your asm block (maspsx's tracking is a single flat flag, not
   scoped to the asm text), so cc1's own subsequent auto-generated code —
   most commonly the function's own trailing `j $31` return — loses its
   customary auto-inserted nop too, silently shortening the function by one
   word and drifting everything after it.

Both directives are assembler-only (`.set` never emits bytes) so they add
zero risk to the byte-exact goal; they only correct maspsx's own bookkeeping.
This generalizes past this one function: ANY hand-written multi-instruction
`__asm__` block with internal branches in this codebase needs this bracket.
(`func_800195EC`, 17/58 -> 57/58 -> 58/58, and the technique is otherwise
unprecedented in this project's match reports — the six prior GTE inline-asm
functions, `func_800196D4` etc., are all straight-line store leaves with no
branches, so they never triggered this.)

**Separately, useful mechanical notes for reproducing this class of
function:**
- The pinned binutils genuinely does not know `rtpt`/`nclip`/`avsz3`/etc as
  mnemonics (verified: `as` errors `unrecognized opcode`, and `objdump`
  disassembles their raw retail bytes generically as `c2 0x...`, not by
  name) — `.word` with the literal bytes (reinterpreted as a little-endian
  32-bit value) is required. `cfc2`/`swc2`/`lwc2` and ordinary `addi` ARE
  supported mnemonics and need no such workaround.
- To let GCC's own implicit function epilogue supply the final `jr $ra`/
  `nop` byte-identically (rather than emitting your own inside the asm,
  which produces a dead SECOND copy since GCC has no way to know your asm
  already returned): write the asm block ending right where the return
  value sits in `$v0`, add no C-level `return` statement, and accept the
  "control reaches end of non-void function" warning — it is a warning, not
  an error, and adds no instructions.
- Parameters not referenced as C-level operands (used via their natural
  calling-convention registers `$4`/`$5` instead of `%0`/`%1`) remain valid
  IF the asm block is the function's only statement — nothing has moved them
  out of `$a0`/`$a1` yet. This is the same trick already used by this unit's
  simpler `swc2` leaves, just without the `"r"(ptr)` operand indirection,
  because here the same register (`$a0`) gets legitimately reused as scratch
  partway through and needs to keep its LITERAL identity for byte-matching,
  which an operand-bound `%0` cannot guarantee.
