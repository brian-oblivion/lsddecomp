## What this function does

The same retry-loop driver shape as `func_80028DF0`/`func_80028F38` (see
`func_80028DF0`'s report for the tag/flag/save-restore/array-probe
derivation, unchanged here), but WITHOUT the `errorCode`-style
status-value residue that stalled the other two — this function's tail is
structurally different and simpler:

- On the shared call's SUCCESS (`func_80029F10(...) == 0`), the function
  makes ONE MORE call, `func_800299BC(0, arg2)`, and returns
  `(that result ^ 2) == 0` — i.e. "did it return exactly 2".
- On loop exhaustion (all 4 retries failed) OR the special-case early
  exit, it returns `0` directly, with no extra call.

Both of retail's two ways of reaching the shared merge point
(`.L8002917C`) arrive with `$v0` already holding the value that decides
which of the two paths above to take (`0` for success, `-1` — the SAME
register the loop-continuation check itself needs — for exhaustion), so no
dedicated extra register is needed the way `func_80028DF0`/`func_80028F38`
need one for `errorCode`. **This is why the byte total already matches
retail's exactly** despite the function still not being byte-identical:
the residue here is PURELY which named C local lands in which physical
register, not a missing/extra instruction.

## The register-mapping puzzle, isolated and fully mapped

Retail's prologue: `$s1`=`arg1`, `$s3`=`arg2`, `$s4`=`arg0`, `$s2`=`tag`
(`arg0 & 0xFF`). Note `arg1` — NOT `arg0` — lands in the lowest-numbered
persistent register, despite `arg0` being referenced first in every
natural C reading (it's needed to compute `tag`, the loop's own
comparison variable). This exact pattern (`arg1` prologue-first) recurs
identically in `func_80028DF0` and `func_80028F38`, so it's a genuine
property of this driver's source, not noise.

**Six source variable-ordering experiments run** (via a fast raw-toolchain
reproducer — `tools/gcc263/cpp | cc1 | maspsx | as`, sub-second per
iteration — reproduced identically against the full project build for the
baseline case, confirming the reproducer is faithful):

| variant | resulting mapping (`$s1,$s2,$s3,$s4`) |
| --- | --- |
| unordered (arg0/arg1/arg2 used directly, `tag` computed first) | `arg0, tag, arg2, arg1`(1) |
| `saved = D_8006D5FC;` moved before `tag=...` | `tag, arg0, arg1, arg2` |
| `savedArg1 = arg1;` as first statement only | `tag, arg1, arg0, arg2` |
| `savedArg1`+`savedArg2` as first two statements | `tag, arg0, arg1, arg2` |
| `savedArg0 = arg0;` as first statement only | `tag, arg1, arg0, arg2` |
| `tag` computation moved to LAST prologue statement | `arg0, arg1, arg2, tag` |
| all three (`savedArg1, savedArg2, savedArg0`, in that order) | `tag, arg0, arg1, arg2`(2) |
| **retail (target)** | `arg1, tag, arg2, arg0` |

(1) actual measured order was `$s1`=`arg0`,`$s2`=`arg1`,`$s3`=`tag`,`$s4`=`arg2`;
(2) actual measured order was `$s1`=`tag`,`$s2`=`arg0`,`$s3`=`arg1`,`$s4`=`arg2`.
Table cells above list roles in `$s1..$s4` reading order for quick
scanning; see the raw sequence noted parenthetically where it doesn't
collapse cleanly to the table's left-to-right convention.

**None of the six reproduced retail's mapping.** `tag` consistently
grabs one of the two lowest-available registers regardless of where its
computation is textually placed — including when moved to be the LAST
prologue statement, where it still displaced `arg2` rather than settling
at `$s4`. This is consistent with a PRIORITY- or DEGREE-based allocator
tie-break (`tag` has the highest reference count / tightest live range
inside the loop) overriding simple definition-order, which retail's
compile evidently does NOT hit in the same way — meaning either retail's
real source structures the comparisons differently enough to change
`tag`'s effective priority, or there is a lever not yet tried (candidates
not yet attempted: splitting the two `tag` comparisons into differently-
named locals rather than one reused `tag`; expressing the loop as a
genuine `for`/`do-while` rather than `goto`, which changes how GCC's
loop-invariant/strength-reduction passes see the comparison).

### Proposed learning

**This is the cleanest evidence yet that this project's "redundant move"
residue family (DECOMPILATION_LEARNINGS) has a sibling class that's
harder to fix: WHICH callee-saved register a value lands in, independent
of instruction count or scheduling.** Every source-level lever tried here
(statement order, explicit copy-locals, moving a computation earlier or
later) changed the mapping, but never landed on the specific one retail's
real compile produced — reordering finds A DIFFERENT wrong answer, not
progressively closer ones, which suggests the allocator's tie-break is
sensitive to something not exposed by these particular levers (candidate
for the next attempt: express the retry loop as `for`/`do-while` instead
of `goto`-and-labels, since GCC 2.6.3's loop-specific passes run before
final register allocation and may assign `tag` a different priority when
recognised as a genuine loop-invariant condition rather than an opaque
`goto` target).
