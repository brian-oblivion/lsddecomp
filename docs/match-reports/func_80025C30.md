## Residue — and why it is the same bug as code_171e0's eight stalls

The first instruction is the whole story:

```
retail:  8f824000   lw   $v0, 0x40($gp)      <- gp-relative, ONE instruction
built:   3c020809   lui  $v0, 0x0809         <- absolute, TWO instructions
         8c42a850   lw   $v0, -0x57b0($v0)
```

`$gp` is `0x8008A808` and this global is `D_8008A848`. `0x8008A848 -
0x8008A808 = 0x40`, which is exactly retail's displacement. So retail reached
this global gp-relatively and the build cannot.

The extra `lui` shifts every subsequent instruction by one word, which is why
the raw in-range figure (2/21) understates how close the body is: the C is
plausibly correct and only the addressing mode is wrong.

**This is the same root cause runner/delta hit eight times in `code_171e0`,
found independently, in a different unit, by a different runner.** Neither
runner could see the other's evidence. See
`docs/research/gp-relative-blocker.md` for the isolated reproducer and the
flag matrix.

## Do not "fix" this locally

There is no source-level workaround. The addressing mode is chosen by the
toolchain's `-G` value, not by how the C is written, so no reshaping of this
body will move it. It is blocked pending the operator's decision on the
escalation.
