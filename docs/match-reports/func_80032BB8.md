# func_80032BB8 -- STALL (register identity, not fixable by reshaping)

Unit `code_179d8_c`, carved round 16 (2026-09-04). **Attempted, restored
to `INCLUDE_ASM`.**

## What it does

Getter for the `count` field (offset `0x0`) of the root-counter shadow
table entry `D_8006DCB0[idx]` (see `SetRCnt.md` for the table layout),
where `idx = (u16)n`. Returns `0` if `idx >= 3`.

## Best C reached (content-correct, register allocation differs)

```c
#if 0
s32 func_80032BB8(s32 n)
{
    s32 idx = (u16)n;

    if (idx >= 3) {
        return 0;
    }
    return D_8006DCB0[idx].count;
}
#endif
```

## Residue: pure register identity, confirmed resistant to reshaping

Every instruction present matches retail's opcode and operand structure
one-for-one (14/14 in content, ignoring the two words affected by
whole-unit address drift while `func_80032C60` was also mid-fix). The
only disagreement: retail allocates the masked index to `$v1` from the
very first instruction (`andi $v1,$a0,0xffff`) and keeps `$v0` free for
the eventual `lhu`; this build allocates the index to `$a0` (coalesced
with the incoming parameter register) and uses `$v0`/other regs
differently downstream. Every subsequent instruction in the "valid"
branch is the same operation on the swapped register pair.

This is CLAUDE.md's named register-identity class: same instructions,
different registers, and the ban on `register T v asm("$N")` / operand
constraints applies squarely -- there is a plain C form (the one above),
this is not a GTE/COP2 case.

**Seven distinct C reshapes were tried, all producing the identical
register swap:**

1. `s32 idx = (u16)n;` inline, direct `return D_8006DCB0[idx].count;`
2. Same, with an explicit `RCntEntry *rc = &D_8006DCB0[idx];` pointer
   temp before the return
3. Declaration split from initialization (`s32 idx; idx = (u16)n;`)
4. `rc = D_8006DCB0 + idx;` (pointer arithmetic instead of array index)
5. `u16 *p = &D_8006DCB0[idx].count; return *p;`
6. Fully inlined, no named `idx` at all (`(u16)n` recomputed at both use
   sites) -- this additionally regressed the `idx>=3` comparison from
   `slti` back to `sltiu` (see `SetRCnt.md`'s signedness note), so it is
   strictly worse, not just equally stuck
7. Parameter declared `u16 n` directly (hoping the calling-convention
   copy-in would land in `$v1` the way `SetRCnt`'s masked index lands in
   `$t0`) -- no change at all

Notably, the ~identical-shaped sibling `func_80032C60` (write instead of
read, same guard, same table) allocates registers CORRECTLY as `$v1` with
no special handling once its statement order was fixed (see that
function's own report) -- so the difference is not "this whole pattern is
unreachable," it is specific to this exact function, likely an artifact
of `func_80032C60` having one more live value (the `1`/`0` return
constant) that perturbs GCC 2.6.3's simple pseudo-to-hardreg assignment
enough to avoid the coalescing that happens here. Not chased further; see
"Proposed learning" below.

**Attempt 8 (round 2, head-directed): flip the guard from
negative-first (`if (idx >= 3) return 0; return field;`) to
positive-first (`if (idx < 3) { return field; } return 0;`), the same
lever that fixed `func_80032AD0`'s block-order mismatch.** This is a
CONTROL-FLOW change, not an expression reshape -- the one axis all seven
prior attempts left untouched. Checked negative, and it does not produce
a partial improvement, it actively regresses:

```
retail (unchanged)                        positive-first guard (attempt 8)
andi v1,a0,0xffff                         andi a0,a0,0xffff   (register swap: still present)
slti v0,v1,3                              slti v0,a0,3
beqz v0,233e4  (-> shared "return 0")     bnez v0,233d0  (-> jumps to the valid-path body)
sll  v1,v1,0x4  (delay slot)              sll  v0,a0,0x4  (delay slot)
                                           j    32be4          <- NEW: retail has no such jump here
                                           move v0,zero        <- NEW: retail's "return 0" lives at
                                                                   the END, not inlined here
lui v0,...  / lw v0,...                   lui v1,... / lw v1,...  (register swap: still present)
...
```

Positive-first guards produce the SAME register swap as before, PLUS an
extra inline `j`/`move` pair that retail does not have (retail's
`return 0` path lives once, at the shared exit; the positive-first shape
duplicates the early-return code inline before jumping over it to reach
the valid body). Net: 0/14 words vs. the negative-first form's 14/14
content match modulo the register swap. **The `func_80032AD0` lever does
not generalise to this guard-and-return shape** -- see `func_80032C60.md`
for the identical finding on its sibling, and `SetRCnt.md`'s own
guard (`if (idx >= 3) return 0;`), which already independently agreed
with negative-first as the byte-exact-reproducing shape (`SetRCnt`
matched clean with it, no flip needed). Reverted; no change kept in
`src/`.

### Proposed learning

1. Register-identity residues in short leaf functions (no calls, one
   parameter, one comparison) may be sensitive to whether the function has
   an "extra" live value competing for registers -- a sibling function one
   instruction more complex allocated correctly with no changes. Not a fix,
   but worth trying as a NEXT experiment before stalling: does adding a
   genuinely-needed second live temporary (not a dummy) change the
   allocation? Untested here for lack of a non-contrived way to add one to
   this specific function.
2. **Boundary on the `func_80032AD0` block-order finding:** it applies to
   a raw truthy/flag test feeding `beqz`/`bnez` directly. It does NOT
   generalise to a "guard clause + range comparison" shape (`slti`/`sltiu`
   against a small constant) -- there, negative-first (`if (x >= N) return
   fail;`) is what retail actually compiles to, confirmed independently on
   two sibling functions (`func_80032BB8` here, `func_80032C60`) plus
   `SetRCnt`'s own un-flipped guard. Positive-first on a guard clause is a
   regression, not a neutral alternate phrasing.

## Round 19 re-examination (runner charlie)

Round 19's brief was to treat "register identity" as a hypothesis, not a
verdict, and specifically try (1) retyping a parameter/return to its real
width, and (2) whole-struct/pointer-split reshaping, before accepting the
stall. Both were tried here and both are negative; **note for the record:
this function's residue was, and still is, a clean 7/14 content-correct
register swap, not the "0/14" figure quoted in the round-19 work-list
table** -- no attempt in this function's history (round 16 or round 19)
has ever produced a genuine 0/14 except when a reshape also broke control
flow (see below), which is a different failure mode, not the steady-state
residue. If "0/14" was read from a live build, it was almost certainly
mid-edit by one of the control-flow variants, not this function's settled
state.

Four more attempts (9-12 overall), all reverted, none kept in `src/`:

9. **Return-type retype, `u16 func_80032BB8(s32 n)`.** CLAUDE.md's own
   round-19 axis 1 (retype to real width) applied to the return side
   instead of the parameter side, since the loaded value is a `u16`
   (`lhu`). No change: still 7/14, identical register swap
   (`andi $a0,...` where retail has `andi $v1,...`).
10. **Parameter retype, `s32 func_80032BB8(s16 n)`.** Axis 1 applied to
    the parameter. No change: 7/14, identical swap.
11. **Pointer-split reorder**, `RCntEntry *base = D_8006DCB0;` declared
    BEFORE the guard (rather than after it, which is what
    `func_80032C60.md` says was already tried with no effect) --
    `return base[idx].count;` after the guard. This is axis 2
    (whole-struct/pointer-split) with a different declaration position
    than the prior attempt. Result: WORSE, not neutral -- GCC hoisted the
    `lui`/`lw` table-base load above the guard entirely, which is a
    genuine control-flow-adjacent reordering (the load now happens on
    both the valid and invalid paths), producing 0/14 in-range plus
    268592 bytes of outside-range drift (a real size change, this is the
    likely source of a stray "0/14" reading if one was taken from an
    in-progress experiment rather than the settled stall).
12. **`volatile s32 idx`** to defeat parameter-coalescing outright. Far
    worse: forces `idx` to a stack slot, changes the prologue/epilogue
    entirely (frame allocated where retail has none), 0/14 in-range, large
    outside-range drift. Confirms the coalescing is not something a
    barrier-style tool can suppress without wrecking the frame shape.

Also re-tried, as a single-`result`-variable if/else (structurally closer
to retail's actual single-exit shape than the two-`return` form): produces
an inverted branch structure (`bnez` into the valid path, explicit `j`
over an inlined `move $v0,$zero`) that does not match retail's `beqz`-to-
shared-tail shape at all -- 0/14, worse than the two-return form, and
consistent with the already-documented finding that positive-first/single-
exit reshaping regresses this guard-clause shape (see attempt 8 above and
`func_80032C60.md` attempt 6).

**None of the four round-19 axes closes this function.** The retype axis
(1) and the whole-struct axis (2) were the two most promising per the
round-19 brief and both are now confirmed negative here, on top of the
round-16 finding that expression reshaping alone doesn't move it either.
Split-statement (axis 3) and wrong-void-return (axis 4) do not apply --
there is only one expression to split (already tried, see attempt 3 in

function's own callers, unconfirmed but consistent with the value being
consumed as a count, expect a real value back). This remains the
project's cleanest example of a register-identity stall that resists

## ROUND 20 (runner echo): re-derived from scratch, skeptical of "not fixable" -- real progress, still not closed (12/14, was 7/14)

The coordinator specifically named this function as one of the two
cheapest in the executable and asked for a from-scratch, skeptical
re-derivation, on the strength of `func_8001A4C0` (a different unit,
`code_8220_c`) turning out to be ordinary C after being filed as an
unreachable-from-C residue. Re-read the disassembly fresh rather than
resuming any preserved body.

**New technique tried: split the pointer computation into TWO separate
locals (`base = D_8006DCB0;` then a SEPARATE `entry = &base[idx];`)
rather than one (`base = D_8006DCB0; return base[idx].count;`, already
tried and negative per the "Provenance" section above).** This is
subtly different from every previously-tried variant: attempts 2 and 4
in the original list combine the pointer-index computation into ONE
expression (`rc = &D_8006DCB0[idx];` or `rc = D_8006DCB0 + idx;`); this
one keeps the array base and the indexed pointer as two INDEPENDENT
locals, giving the register allocator one more live pseudo to work
with -- the same shape that (per this function's own report) helped its
sibling `func_80032C60` (a real assignment, not just a read) reach
correct register allocation.

Found via a bounded, blind decomp-permuter search (seeded with the
existing `base = D_8006DCB0; return D_8006DCB0[idx].count` idiom,
`-j 6`, `--stack-diffs`, no PERM macros; base score confirmed **55** =
11 register diffs x 5, matching this report's own "pure register swap"
characterization exactly): iteration found a **genuine sub-baseline
candidate, score 20** (`permuter-work/func_80032BB8/output-20-1/`),
reproducible (7 of ~16000 iterations landed there independently before
the process was stopped for the next test). Translated to idiomatic
C and verified against the REAL oracle (not the permuter's own score):

```c
s32 func_80032BB8(s32 n)
{
    s32 idx = (u16)n;
    RCntEntry *base;
    RCntEntry *entry;

    if (idx >= 3) {
        return 0;
    }
    base = D_8006DCB0;
    entry = &base[idx];
    return entry->count;
}
```

`build exit=0`, `funcdiff.py func_80032BB8` reports **12/14 words, no
drift warning** -- a real, oracle-verified improvement from the
long-standing 7/14, achieved by adding exactly the "genuinely-needed
second live temporary" this report's own round-16 "Proposed learning
#1" speculated about but called "untried here for lack of a non-contrived
way to add one." The permuter found the non-contrived way: the SAME
struct-indexing computation this function already needed, just written
as two statements instead of one.

**What's left (asm-differ, aligned view): a single commutative-add
operand/destination-register choice.**

```
retail                    built (12/14 body)
addu v1,v1,v0     ->      addu v0,v0,v1
lhu  v0,0(v1)     ->      lhu  v0,0(v0)
```

Same two registers (`v1`=idx<<4, `v0`=table base) on both sides; retail
writes the sum into `v1` (reusing the earlier-computed operand's
register) and this build writes it into `v0` (reusing the later-computed
operand's register) -- otherwise identical. **Four more variants tried,
all byte-identical to the 12/14 body (no change whatsoever):**

1. `entry = &idx[base];` (array-subscript commutativity, `a[i]==i[a]`
   in C) -- identical output. Reversing the array-subscript operand
   order textually doesn't reach the code generator's own internal
   canonicalization.
2. `entry = base + idx;` (plain pointer + int, no subscript) --
   identical.
3. `entry = idx + base;` (int + pointer, reversed textual order) --
   identical. Confirms (again, on a new construct) the project's
   already-documented finding that cc1 canonicalises pointer+integer
   addition to a fixed internal operand order regardless of which
   operand is written first in C -- see `func_800323A8.md`'s identical
   finding for its own field-offset additions.
4. Declared `entry` before `base` (reversed local declaration order) --
   identical.
5. Collapsed `entry` into a plain `u16 *p = &base[idx].count; return
   *p;` (narrower pointer type, same two-statement split) -- identical,
   still 12/14, same residue.

**This residue is the SAME "commutative addition operand-order,
cc1-canonicalised, not reachable from C" class `func_800323A8.md`
documents independently for its field-init additions** -- now confirmed
a second time, on an entirely different function and a different pair
of operand registers, that this specific sub-class of register/operand
choice resists every source-level lever tried across two functions in
this unit (source-order reversal, subscript-vs-pointer-arithmetic
spelling, declaration order, pointer width).

A second bounded permuter search (`timeout 300`, `-j 6`, seeded from THIS

### Proposed learning

**"Not fixable by reshaping" claims for a register-identity residue
should be re-tested with the SPECIFIC lever of splitting a combined
address computation into two independently-live locals (base pointer,
then indexed pointer) even when a single-expression version of the same
computation was already tried and failed** -- `rc = &D_8006DCB0[idx];`
(one statement) and `base = D_8006DCB0; entry = &base[idx];` (two
statements, same net computation) are NOT interchangeable inputs to
GCC 2.6.3's simple register allocator; only the two-statement form gave
the allocator a second genuinely live pseudo to work with, closing 5 of
7 residue words. This generalises the sibling `func_80032C60`'s own
already-known "the split was load-bearing" finding from an ASSIGNMENT
target to a READ target, and is now confirmed on two functions in this
unit. **However, the same lever tried fresh on `func_80032C60` itself
(this round, see that function's own report) REGRESSED it (13/14 -> 2/14
with drift)** -- so this is not a universal fix, and per-function testing
remains necessary; the lever helps when the function's existing register
pressure has slack for one more live value, and hurts when it doesn't.

## ROUND 26 (head): four more variants on the surviving two-word residue, all negative — and the residue's MECHANISM narrowed

Head-side adjudication while runners worked elsewhere. Bounded at four
variants by design, on a function that has now absorbed 20+ attempts across
rounds 16, 19 and 20; the point was to test one axis nobody had tried, not to
re-run the ones that are already documented negative.

**First, the round-20 body reproduces exactly.** Rebuilt in `main` at
commit 8f5e7ae: `build exit=2`, no compile-error hits, `12/14 words match`,
no drift warning. The two residue words are confirmed, byte for byte:

| word | retail | built |
| --- | --- | --- |
| `0x233D4` | `21186200` = `addu $v1, $v1, $v0` | `21104300` = `addu $v0, $v0, $v1` |
| `0x233D8` | `00006294` = `lhu $v0, 0($v1)` | `00004294` = `lhu $v0, 0($v0)` |

`tools/asm-differ/diff.py` confirms every other word aligns with no shift:
`$v1` holds `idx << 4` (computed in the `beqz` delay slot) and `$v0` holds
the table base on BOTH sides. The disagreement is solely which of the two
input registers the sum is coalesced into.

**The untried axis: make the addition an INTEGER add rather than a
pointer add**, so that cc1's pointer canonicalisation — which
`func_800323A8.md` and this report's round-20 section both document as
defeating every source-level operand reordering — has nothing to canonicalise.

1. **`off = idx * sizeof(RCntEntry); return *(u16 *)(off + (u32)D_8006DCB0);`**
   — scaled index written FIRST, as a plain `u32 + u32`. **Regressed to
   7/14**, and additionally changed the table-base `lw`'s destination
   register (`b0dc428c` -> `b0dc638c` at `0x233CC`), so it is strictly
   worse rather than a neutral alternate spelling.
2. **`entry = (RCntEntry *)(idx * sizeof(RCntEntry)); entry = (RCntEntry *)((u8 *)entry + (u32)D_8006DCB0);`**
   — the scaled index bound to a POINTER-typed pseudo first, so the sum's
   first operand is the index rather than the base. **7/14.** Casting the
   index into pointer type does not make it the coalescing target.
3. **`entry = D_8006DCB0; entry += idx;`** — compound assignment instead of
   a separate indexed-pointer local. **12/14, byte-identical residue.**
4. **`off = idx * sizeof(RCntEntry); base = D_8006DCB0; return ((RCntEntry *)((u8 *)base + off))->count;`**
   — scaled offset as its own named `u32` local, added to the base only
   inside the return expression. **12/14, byte-identical residue.**

**What this narrows.** The round-20 report characterised the residue as
"commutative addition operand-order, cc1-canonicalised". That is right
about the symptom and slightly wrong about the level: variants 1 and 2 DO
change the operand order at the source level and DO reach the code
generator (they change other words), so cc1 is not simply discarding the
order. What is invariant is the **coalescing choice** — the sum is
assigned to whichever input register held the POINTER-typed operand, and
when neither operand is pointer-typed (variant 1) the allocator picks
differently AND perturbs the surrounding load. Retail assigns the sum to
the register holding the SCALED INDEX, which is the one thing no
source-level spelling tried across three rounds has produced.

So the honest disposition is unchanged in score and sharper in cause:
**12/14, one coalescing decision, not reachable by operand-order
spelling, by operand TYPE, by statement split, by declaration order, or
by pointer width.** Restored to `INCLUDE_ASM`; `./build-and-verify.sh`
green in `main` afterwards (`build exit=0`, `OK: build matches retail`).

### Proposed learning

**"Commutative operand order" and "coalescing target" are different
residues that present identically, and the discriminator is cheap: change
the operand TYPES, not just their order.** If reversing the source order
changes nothing at all, the residue is cc1's expression canonicalisation.
If reversing the order changes nothing but changing an operand's type
perturbs OTHER words while leaving the residue in place — what happens
here — the decision is being made by the register allocator's coalescing,
below the point any expression rewrite can reach. The second kind should
not be filed under the first: they send the next attempt to opposite
levers, and this function has now spent attempts on the expression lever
across three rounds because of it.
