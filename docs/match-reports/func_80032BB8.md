## Residue: pure register identity, confirmed resistant to reshaping

Every instruction present matches retail's opcode and operand structure
one-for-one (14/14 in content, ignoring the two words affected by
whole-unit address drift while `func_80032C60` was also mid-fix). The
only disagreement: retail allocates the masked index to `$v1` from the
very first instruction (`andi $v1,$a0,0xffff`) and keeps `$v0` free for
the eventual `lhu`; this build allocates the index to `$a0` (coalesced
with the incoming parameter register) and uses `$v0`/other regs
differently downstream. Every subsequent instruction in the "valid"
branch is the same operation on the swapped register pair.

This is CLAUDE.md's named register-identity class: same instructions,
different registers, and the ban on `register T v asm("$N")` / operand
constraints applies squarely -- there is a plain C form (the one above),
this is not a GTE/COP2 case.

**Seven distinct C reshapes were tried, all producing the identical
register swap:**

1. `s32 idx = (u16)n;` inline, direct `return D_8006DCB0[idx].count;`
2. Same, with an explicit `RCntEntry *rc = &D_8006DCB0[idx];` pointer
   temp before the return
3. Declaration split from initialization (`s32 idx; idx = (u16)n;`)
4. `rc = D_8006DCB0 + idx;` (pointer arithmetic instead of array index)
5. `u16 *p = &D_8006DCB0[idx].count; return *p;`
6. Fully inlined, no named `idx` at all (`(u16)n` recomputed at both use
   sites) -- this additionally regressed the `idx>=3` comparison from
   `slti` back to `sltiu` (see `SetRCnt.md`'s signedness note), so it is
   strictly worse, not just equally stuck
7. Parameter declared `u16 n` directly (hoping the calling-convention
   copy-in would land in `$v1` the way `SetRCnt`'s masked index lands in
   `$t0`) -- no change at all

Notably, the ~identical-shaped sibling `func_80032C60` (write instead of
read, same guard, same table) allocates registers CORRECTLY as `$v1` with
no special handling once its statement order was fixed (see that
function's own report) -- so the difference is not "this whole pattern is
unreachable," it is specific to this exact function, likely an artifact
of `func_80032C60` having one more live value (the `1`/`0` return
constant) that perturbs GCC 2.6.3's simple pseudo-to-hardreg assignment
enough to avoid the coalescing that happens here. Not chased further; see
"Proposed learning" below.

### Proposed learning

Register-identity residues in short leaf functions (no calls, one
parameter, one comparison) may be sensitive to whether the function has
an "extra" live value competing for registers -- a sibling function one
instruction more complex allocated correctly with no changes. Not a fix,
but worth trying as a NEXT experiment before stalling: does adding a
genuinely-needed second live temporary (not a dummy) change the
allocation? Untested here for lack of a non-contrived way to add one to
this specific function.
