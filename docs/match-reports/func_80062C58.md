## What it does

An entity "mood" update handler with the same `(Entity *this,
EntityMoodHandlerArg *out)` shape as every sibling in this unit
(`func_80061A90`, `func_80062A40`, etc. -- see `include/Entity.h`'s
`EntityMoodHandlerArg`). On `out->unk4 == 0` it rerolls `this->unk44` via
`rand() % 3` (setting it to `0xB` or `0xC` on rolls 1/2); always refreshes
`out->unk10` via `slot148`; conditionally sets `out->unk1C = 0x1C`; then
runs a three-way dispatch on `this->unkFC` against `this->unk80/2` and
`this->unk80/4` thresholds (calling `slot130`+`slotC4`, or `slotC4` alone,
or `slot12C`, or nothing); then a `this->unk44==0xB` fast path that also
gates a `unk44>=0xC` "re-roll into 0xC/0xD" path on a `% 60 == 30` timer;
and finally a `unk4==0x208` closing check.

## Where it stalled

The ENTIRE remaining residue is inside one block: retail computes
`this->unk80 / 2` and `this->unk80 / 4` with a specific INTERLEAVED
schedule that starts preparing the `/4` division's "positive" numerator
(`$a2 = $v1`, i.e. `quarter_numerator = unk80`) as the delay-slot filler of
an EARLIER, unrelated branch (the `this->unkFC == this->unk80 - 1` equality
test, `vram=0x80062D24`), before the `/2` division's own three-instruction
sequence (`srl`/`addu`/`bgez`) even begins. This is GCC scheduling a
value with NO computation cost (just a register copy) into a "free" delay
slot far upstream of where it is used in the source. Tried and rejected
this round:

- Reordering `half`/`quarter`'s two statements (both orders tried):
  `quarter` first reaches 61/213 (best), `half` first reaches only 56/213.
- Hoisting `this->unkFC < half` into an explicit named local computed
  before the outer `if`: no effect on the generated bytes at all (confirmed
  byte-identical output with and without the hoist), so this is NOT a
  live-range/naming question.
- Computing `half`/`quarter` UNCONDITIONALLY before the
  `this->unkFC == this->unk80 - 1` test (rather than only in its `else`)
  to try to force the same eager scheduling retail shows: regressed to
  51/213 -- worse, not better.

None of these are the right lever. The residue looks like it needs the
`this->unkFC == this->unk80 - 1` branch's delay slot to be filled by
something equivalent to `$a2 = this->unk80` specifically, which nothing
in the "logical" source (the equality test has no use for `unk80` beyond
what it already reads) obviously motivates -- this may need a genuinely
different SHAPE for the quarter computation (e.g. an explicit
`s32 numer = this->unk80;` staged before the equality check, only used
later) rather than a reordering of the two division statements. Not tried
due to the round's attempt budget; a good next lever for whoever picks
this back up.

### Proposed learning

**A "free" register copy (`move $reg, $val` with zero computation cost)
can get scheduled by GCC 2.6.3 into the delay slot of a branch that has no
logical connection to it, arbitrarily far upstream of its actual use** --
this is a stronger and less intuitive form of the cross-statement
scheduling this project has already documented (e.g. `field = &dst->x`
computed unconditionally before an `if`, `func_8001CEB4`'s report this
round). Here the hoist target isn't even the nearest enclosing branch, it
is a SIBLING branch several statements earlier with no data dependency
connecting them at the C level. Reordering the two dependent statements
locally (which is the usual lever) was not enough; something about
DECLARING the eventual value earlier (a genuinely separate local, staged
before the branch it gets hoisted into) is more likely the right shape,
per the SIBLING STALL `Class6B5CC__CheckBoundsOverlap`'s own note about "deferred-self-
materialization residue (barrier as first statement)" -- a related but not
identical technique that's worth trying here too.
