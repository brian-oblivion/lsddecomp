# func_80061778

**Unit:** Entity_d · **Size:** 198 words · **Status:** STALL — tail-merge granularity, not a CFG/value error

## What it does

Another mood-dispatch handler in this unit's family
(`Entity *this, EntityMoodHandlerArg *out`). On `this->unk44==0`, calls
`func_8005E02C(this, 0x800)` (already matched in `Entity_b.c`, first
cross-unit caller); on a nonzero result runs a "detach" burst (two
`Class6B5CC__FaceTarget` calls with **swapped** first/second arguments between the two
calls — see below —, `slot15C`, `slot168`, `unk94->slot130(unk94,1)`,
resets `out`/`unkFC`) and sets `unk44=0xB`. A SEPARATE, freshly-reloaded
`this->unk44==0` check right after that (matches this unit's established
"independent `if`s each with their own `lw`" idiom, see `func_80061400`'s
report) runs `slot160`/`slot16C` and skips straight to the function's shared
tail. Otherwise: `out->unk4 % 100` seeds `out`'s fields again; an `unkFC`
range/value dispatch (`<3`, `<7`, `==0x64`, `==0xF0`) drives `slotCC`/
`slot130`/`unk94->slot134`; a further `unk44==0xC` sub-dispatch on `unkFC`
drives `slotCC`/`slotC4`/a `Class6B5CC__FaceTarget` call. The shared tail (reached
from every path) is an `unk94`-gated `slot144(...) < 0x200` check driving
`slot160`+`slot30(this, 0xA)`.

## Where it stands

**Every value, every branch target, every register the CONTROL FLOW and DATA
use is confirmed correct** — checked with `tools/asm-differ/diff.py`, not
just the word score. The entire function compiles byte-identical from the
prologue through the `out->unk4 % 100` block (address `0x51F78`–`0x520EC`,
about 90 words). The residue is confined to two `unkFC`-dispatch chains where
GCC 2.6.3's tail-merge (cross-jump) pass shares a **different amount** of the
trailing `jalr $vN` call sequence across sibling branches than retail does —
never a wrong value, never a missing/extra comparison, never a misrouted
branch target. Per CLAUDE.md's "a low score is not evidence of a distant
shape": the word score (best reached: 115/198 in-range, before the address
drift this causes makes the rest of the range uninformative) drastically
understates how close this is.

## The residue, characterized precisely

Two structurally similar four/three-way `if`/`else if` chains, each ending
several of its arms in an indirect call `(*v0)(...)` with the SAME `a2`
argument value across some (not all) of the arms. Retail's actual merge
depth differs between the two chains in a way source-level reshaping did not
reach:

### Chain 1 (`unkFC < 3` / `< 7` / `== 0x64` / `== 0xF0`)

Three of the four arms (`<3`, `<7`, `==0xF0`) reach a shared `L800619A4`
containing exactly `jalr $v0` / `nop` (**2 words**). Critically, `a2` is
**NOT** part of that shared block — `<3` and `<7` both want `a2=0`, but
`==0xF0` needs `a2=1`, so retail sets `a2` individually in **each** arm's own
jump delay slot and shares only the truly branch-independent 2 words.

The C written for this (verbatim, single-expression calls per the
established `%N`/receiver-timing lesson below):

```c
if (this->unkFC < 3) {
    this->methods->slotCC(this, 0x96, 0);
} else if (this->unkFC < 7) {
    this->methods->slotCC(this, (this->unkFC & 1) ? -0x32 : 0x32, 0);
} else if (this->unkFC == 0x64) {
    if (rand() & 1) {
        this->unk44 = 0xC;
        this->methods->slot130(this);
    }
} else if (this->unkFC == 0xF0) {
    this->unk94->methods->slot134(this->unk94, 1, 1);
}
```

compiles the `<3` and `<7` arms (both `a2=0`) into their OWN 3-word shared
block (`nop`/`jalr`/`move $a2,zero`) — a **pairwise** merge GCC found between
just those two — while the `==0xF0` arm gets its own separate, unmerged
`jalr`/`move $a2,1` tail. Total instruction count and CFG are both right;
only which bytes are physically shared, and where, differs.

### Chain 2 (`unkFC < 0x82` / `< 0xA0` / `< 0x12D` / else, inside `unk44==0xC`)

Here retail's actual merge is the OPPOSITE shape: it unifies THREE arms
(`<0x82`'s `slotCC(this,0xA,0)`, `<0xA0`'s `slotC4(this,-0x1E,0)`, and the
final else's `slotC4(this,-0x1E,0)` after a `Class6B5CC__FaceTarget` call) into ONE
shared 3-word block (`nop`/`jalr`/`move $a2,zero`) — even though `<0x82` and
the other two call a **different slot** (`slotCC` vs `slotC4`, different
`a1`). `a2=0` is common to all three here, so it merges into the shared tail.

```c
if (this->unk44 == 0xC) {
    if (this->unkFC < 0x82) {
        this->methods->slotCC(this, 0xA, 0);
    } else if (this->unkFC < 0xA0) {
        this->methods->slotC4(this, -0x1E, 0);
    } else if (this->unkFC < 0x12D) {
        /* nothing */
    } else {
        Class6B5CC__FaceTarget(this, this->unk94, 1, 0, 0);
        this->methods->slotC4(this, -0x1E, 0);
    }
}
```

compiles the `<0xA0` and final-else arms (literally identical
`slotC4(this,-0x1E,0)` calls) into their own shared block correctly, but the
`<0x82` arm (a DIFFERENT call, `slotCC`) gets its own separate ending instead
of joining that same shared block, where retail has all three converge.

**So: in Chain 1, my code over-merges a value-independent 2-of-3 pair that
retail keeps apart; in Chain 2, my code under-merges relative to retail's
observed 3-way unification.** These are opposite-direction misses on the
SAME mechanism (GCC 2.6.3's cross-jump pass), which rules out a single
uniform "always/never merge" fix and is why this classifies as a genuine
compiler-scheduling sensitivity rather than a source-shape bug.

## What was tried (each verified with a full rebuild; the receiver-timing ones also confirmed in an isolated `cpp|cc1|maspsx|as` reproducer)

1. **Ternary argument as a separate statement vs. inline in the call** — the
   `func_80061400`-derived lesson (single call expression, no intermediate
   local for a computed argument) DOES apply here and was necessary: with
   `a1val = (this->unkFC & 1) ? -0x32 : 0x32; this->methods->slotCC(this, a1val, 0);`
   split into two statements, the `<7` arm loaded `this->methods` into `$v0`
   (colliding with the `<3` arm's own `$v0` use, forcing an even BIGGER
   accidental merge). Inlining the ternary directly into the call fixed
   `this->methods` to load into `$a2` in that arm (matching retail) and
   improved the score from 99/198 to 115/198. This is real, confirmed
   progress — kept in the final body above — just insufficient on its own.
2. **Extra nesting** — wrapping the `==0x64`/`==0xF0` pair in an outer
   `else { ... }` (adding one level of block nesting without changing the
   CFG) produced byte-identical output to the flat `else if` chain. Rules out
   "GCC's crossjump only looks within one nesting level" as the mechanism.
3. **Isolated reproducer of Chain 1's shape** (own `Entity`/`Unk94Obj`
   structs, no surrounding context) did NOT reproduce the over-merge at all
   — the `<3` and `<7` arms compiled with fully separate, unmerged endings.
   This says the merge behavior is sensitive to register pressure/context
   from the REST of the function (everything before this dispatch, which
   otherwise matches retail exactly), not reproducible from the dispatch
   chain's shape alone — which is also why guessing further local reorderings
   without the real surrounding pressure is unlikely to converge quickly.
4. Considered `goto` to force retail's literal jump graph (per
   `func_8005C714`'s lore) — not attempted for real here because the
   diagnostic groundwork (item 3, and the fact that `goto` and equivalent
   `if`/`else if` lower to identical RTL, confirmed earlier this session on
   `func_80061198`) indicates `goto` would not change which tails GCC's
   cross-jump pass judges shareable; the pass operates after front-end
   lowering, on the CFG, not on `goto` vs `if` surface syntax.

## Proposed learning

- **GCC 2.6.3's cross-jump/tail-merge pass is not "merge whenever the tail
  bytes end up identical" in a simple, source-shape-controllable way — it
  can choose a SMALLER merge (fewer shared words, more precise per-branch
  register setup) even when a LARGER merge across more predecessors is
  value-compatible for a subset, and it can also choose to unify three
  DIFFERENT function-pointer calls' tails when the immediate/register content
  besides the call target is uniform.** Two sibling `if`/`else if` chains in
  the SAME function, both ending several arms in a same-value trailing
  argument before an indirect call, showed OPPOSITE merge-depth behavior
  (one under-merged relative to source, one over-merged) under the most
  direct, idiomatic C transcription. This is a sharper, second data point
  for the existing `func_8005C714`/`func_80026698` cross-jump lore in
  MATCHING-GUIDE.md — not a contradiction of it, but evidence that the
  pass's behavior in THIS compiler is sensitive to context beyond what a
  single isolated reproducer captures (confirmed: the same dispatch chain,
  extracted standalone, does not reproduce the over-merge seen in the real
  function). Do not assume a `goto` rewrite fixes a cross-jump granularity
  mismatch — it did not move a genuine over-merge in `func_80061198`'s
  earlier (misdiagnosed) case this session, and the mechanism (post-lowering
  CFG pass) gives no reason to expect it here either.
- **A function can be verified correct in EVERY control-flow and value
  respect and still not compile byte-exact**, purely because of which
  physical bytes an ancient optimizing pass decides to deduplicate. This is
  a distinct residue class from anything in MATCHING-GUIDE's "Reading a
  residue" list — closest to "instruction order only" but about SHARED
  code layout across multiple predecessors rather than one block's internal
  scheduling. Worth a MATCHING-GUIDE entry if a second instance turns up.
- **Do not re-stake this function on the same axis.** ~4 real
  reshaping attempts here (ternary-inlining, which helped; extra nesting,
  which didn't; goto, ruled out by the CFG-equivalence argument;
  isolated-reproducer probing, which showed the sensitivity is real and
  context-dependent) all varied HOW the calls are grouped/nested. The
  untried axis, per MATCHING-GUIDE's own advice about reports whose whole
  attempt history explored one branch of the space, is varying something
  about the REST of the function's register pressure (the ~90 words before
  the dispatch chains, which already match byte-exact) — but perturbing
  code that already matches, on the hope of shifting scheduling elsewhere,
  is a high-risk/low-confidence lever that should be attempted only with a
  concrete theory of WHICH earlier value's liveness affects this, not by
  guessing.

## HEAD FINDING, round 13: the reversed `Class6B5CC__FaceTarget` arguments are a DIRECTION FLAG

Runner echo (`func_80061778`, `Entity_d`) and runner bravo
(`func_80063144`, `Entity_e`) each independently flagged a
`Class6B5CC__FaceTarget` call site whose first two arguments are swapped relative
to every other known site. Both verified it against raw disassembly. The
head then surveyed **every** call site in the executable, and the swap is
not an outlier convention -- it is perfectly correlated with the FOURTH
argument:

| `$a3` | `$a0` | `$a1` | sites |
| --- | --- | --- | --- |
| 0 | `this` | `this->unk94` | 9 in asm + 19 already matched as C |
| 1 | `this->unk94` | `this` | 2 (the two flagged sites) |

Nine of nine `a3 == 0` sites pass `(this, unk94)`; two of two `a3 == 1`
sites pass `(unk94, this)`. Every matched C call site in `src/Entity_b.c`,
`src/Entity_c.c`, `src/Entity_d.c` and `src/Entity_e.c` is
`Class6B5CC__FaceTarget(this, this->unk94, 1, 0, 0)` -- byte-verified, so those 19
are evidence, not transcription.

Reading: `Class6B5CC__FaceTarget` is **symmetric in its first two parameters**, and
`$a3` names which way round the operation runs. The caller pre-swaps the
operands rather than the callee branching on the flag.

**Consequences, and the first one is why neither runner should have
retyped anything:**

- The extern signature is CORRECT as it stands. Both flagged sites were
  left untouched, which was the right call: this is not one site
  disagreeing with the type, it is two parameters that each accept either
  object.
- **It is a hypothesis about TYPES, not a conclusion.** `this` is an
  `Entity *` and `this->unk94` is an `Unk94Obj *`, and `Entity.h` records
  that `Unk94Obj` is explicitly NOT another `Entity` despite sharing the
  `+0x14 EntityPos *` convention. If both fit either slot, the real
  parameter type is most likely a COMMON BASE the two share rather than
  `Entity *`. That is worth resolving with `tools/classtable.py` against
  both objects tables before anyone declares it, and it is NOT resolved
  here.
- Do not "fix" a swapped site back to the common order. It is real.

Method note: two runners in different units flagging the same oddity is
what promoted this from a curiosity to a survey. A single sighting reads
as a transcription error; the second one is what justifies the corpus
sweep, and the sweep is what found the flag correlation that neither
sighting could see alone.

## ROUND 20 (runner echo): traced Chain 2's actual merge structure precisely -- it is a NESTED, two-level cross-jump, not a flat one; one fresh reshape tried on Chain 1, negative

Re-derived the exact retail bytes for Chain 2 directly from
`asm/nonmatchings/Entity_d/func_80061778.s` (not just re-reading this
report's prose) to understand precisely why retail's merge looks
"opposite" from Chain 1's. It is more specific than "retail unifies
three arms into one block": retail actually builds **two nested merge
targets**:

```
.L80061A0C:  lw v0,0(s0) / addiu a1,-0x1e / lw v0,0xc4(v0)   <- slotC4 setup (2 predecessors: <0xA0's direct branch, else's fallthrough after Class6B5CC__FaceTarget)
.L80061A18:  nop / jalr v0 / move a2,zero                     <- MINIMAL common suffix (3 predecessors: the above two, PLUS <0x82's own block, which jumps HERE DIRECTLY, skipping .L80061A0C's slotC4 setup entirely since it needs slotCC/a1=0xA instead)
```

`<0x82`'s own block computes `v0=slotCC` and `a1=0xA` (its OWN,
non-shared setup), then jumps straight past `.L80061A0C` to
`.L80061A18` -- i.e. retail's cross-jump pass found the maximal
pairwise-identical region between `<0xA0` and `else` first (6
instructions: the whole slotC4 setup plus the shared tail), THEN found a
SECOND, smaller maximal-common-suffix between THAT block's own tail and
`<0x82`'s differently-set-up block (3 instructions: just `nop`/`jalr`/
`a2=0`), and created a separate label for the second, smaller shared
region rather than either merging all three at the 3-word level or
leaving `<0x82` unmerged. This is a genuinely hierarchical, two-level
cross-jump -- not the single-level "these N blocks are identical"
decision `Entity__UpdateActivationState`'s residue shows.

**My build's actual behavior (confirmed via this round's own rebuild):
it finds the FIRST level (the 6-word `<0xA0`/`else` merge) correctly --
matching retail exactly for that part -- but does not perform the
SECOND, nested extraction that would let `<0x82` join the minimal
3-word suffix.** This is consistent with (though not proof of) GCC
2.6.3's cross-jump implementation finding one level of shared-suffix
opportunity per relevant pass invocation over this specific RTL shape,
and not iterating to find a second, smaller shared region once the
first, larger one is claimed -- for MY C's exact structure. Retail's
real source presumably differs in some detail (order of statements,
or something about the surrounding register pressure — this report's
own item 3 already showed an isolated reproducer does NOT show the
over/under merges at all, confirming context-sensitivity) that lets its
compiler find the second level too.

**One fresh reshape tried on Chain 1 this round, negative:** nested the
`<3`/`<7` pair inside an outer `if (unkFC < 7) { if (<3) A; else B; }`
guard (rather than the flat `else if` chain), on the theory that an
explicit shared outer test might discourage the compiler from
recognizing `<3` and `<7`'s tails as independently mergeable (since
Chain 2's evidence suggests the pass is sensitive to exactly this kind
of structural nesting). **Regressed: 107/198, worse than the flat form's
115/198.** Reverted immediately.

**Answering the coordinator's discriminator question directly, now with
Chain 2's mechanism precisely traced:** `Entity__UpdateActivationState` and
`func_80061778` are **NOT the same residue shape**, even though both are
symptoms of the SAME underlying GCC 2.6.3 pass (cross-jumping / tail
merging). The discriminator:

- **`Entity__UpdateActivationState`**: a single-level merge-COUNT question over a
  WHOLE, one-instruction statement. Exactly 3 predecessors reach an
  identical trivial block; retail unifies 2 of the 3; my build unifies
  all 3. There is no partial-suffix structure -- the shared unit IS the
  entire predecessor block.
- **`func_80061778`**: a multi-level, PARTIAL-SUFFIX merge-DEPTH
  question over blocks that are each a multi-instruction call setup +
  shared tail. Retail builds a two-level hierarchy of nested shared
  suffixes (6 words, then 3 words carved out of those same 6); my build
  finds only the first level. Chain 1 shows the opposite symptom
  (over-merging a pair retail keeps apart entirely, no nesting involved
  at all in that direction).

**The test that would falsify "these are one class":** applying the SAME
lever to both and getting the SAME (positive or negative) result on
each. This round supplies exactly that test and it comes back negative
for shared mechanism: the type-retype lever tried on `Entity__UpdateActivationState`
(see that report) has no applicable target in `func_80061778` at all
(no discarded-return-value call anywhere in either merge chain), and the
structural-nesting lever tried here (wrapping `<3`/`<7` in an outer
guard) was never tried on `Entity__UpdateActivationState` because it has no equivalent
shape to nest (there is nothing hierarchical about a flat 3-predecessor
merge onto one instruction). **Two instances, two different residue
shapes under one umbrella mechanism -- not yet a named, single
transferable class**, unlike the commutative-add operand-order class
this round's earlier work settled. Whoever finds a THIRD instance should
check which of these two shapes (whole-statement single-level vs.
partial-suffix nested) it matches before assuming either report's
attempt history applies.
