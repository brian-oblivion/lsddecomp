## What it does

`void func_8004C6A8(Obj866E8 *self, s32 arg1, s32 arg2)`, called from
`func_8004C620` as `func_8004C6A8(self, self->unk78 * 2, self->unk7A)`
whenever `self->unk68->unk4 == 0`. Resolves a signed/unsigned dual-width
field on a three-level pointer chain
(`self->unk6C->unk14->unk44`), fetches a `CC74QueryBuf` via
`self->methods->slot10C` (same shape as `func_8004CC74`'s own use of that
slot), copies a constant 8-word template (`D_8008E98C`) onto the stack,
patches three of its fields, and hands it to two uncarved library helpers
(`func_800160B0`, `func_80015618`). The template's (patched) fields then
drive a four-way unsigned-range dispatch on the earlier dual-width field,
selecting one of two near-symmetric branches that write
`self->unk80`/`unk84` (swapped between the two branches) and
`self->unk7C`/`unk7E` (each via a `>0`-gated `±1` adjustment against the
`CC74QueryBuf`'s two signed bytes and `self->unk78`). Both branches (and a
"do nothing extra" third path) converge on a shared clamp of a
descriptor-derived value against `±self->unk78`, added into either
`unk7C` or `unk7E` depending on which branch fired, before tail-calling
`func_8004C93C(self)` (this unit's OTHER round-13 register-identity stall,
see its own report).

## Where it stands

field-write blocks, and the final clamp/dispatch were all derived directly
from the disassembly and compile to the CORRECT shape (branch targets and
value computations check out against `asm-differ`) — this is not a logic
or CFG miss. The residue is address drift caused by a **missing

### Proposed learning (round 34)

**A value whose live range never crosses a function call can still be the
one retail promotes into a callee-saved register, and this is a distinct
mechanism from every other register-count residue documented so far**
(`func_8004CAF0`'s "give each value its own named local", `func_8004C93C`'s
pure permutation). Naming the value separately does not force the
promotion — cc1 CSEs a call-free single-use pointer expression back into
the call site regardless of source spelling (confirmed identical output
whether declared early, late, or not at all). The promotion looks like it
is driven by register pressure from CO-RESIDENT caller-saved-register
traffic elsewhere in the same statement region (four `v0`/`v1`/`a0`/`a1`
temps busy with the adjacent 8-word struct copy), not by the value's own
liveness — which means the lever, if one exists, is probably about
increasing pressure on the CALLER-saved pool at that exact program point,
not about the value itself. Not found this round; `volatile` made it worse
by forcing memory traffic unconditionally rather than only under real
pressure.

**Also confirmed (independently of this function's stall): `(u16)` casts
on an already-signed-typed field reliably reproduce a retail `lhu` via
GCC 2.6.3's sign-extend-then-truncate peephole**, extending the lever
already used for `self->unk78` elsewhere in this project to five sites in
one function, and to a read-BACK case (`self->unk7C += n` style) as well
as a plain read.

**And a `u16`-typed local that only ever feeds further arithmetic (never
truncated back to 16 bits by the source) can cost a real, byte-visible
`andi` retail does not have**, even when the field it was read from is
itself `u16` — the field's load already zero-extends; re-declaring the
destination narrower than "however wide the arithmetic needs to be" makes
cc1 re-assert the promotion. Prefer the natural wide type for a value fed
into open-ended arithmetic, reserving the narrow type for values immediately
stored back to a narrow field.
