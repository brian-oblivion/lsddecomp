# func_80055258 -- STALL, 8/110 words (length matches, 0x1B8), extra saved register from an address GCC caches that retail recomputes

Round 47 (bravo). Cold fresh, never worked before. Length matches retail
exactly once the body below is used (0x1B8 bytes / 110 words both sides,
confirmed via `build/lsdde.map`). First real diff off `asm-differ`: word 2
(`0x45a5c`), retail `sw $ra,0x14($sp)` vs built `sw $ra,0x18($sp)` -- the
built prologue reserves one extra stack word and pushes an extra saved
register (`$s1`) retail never uses.

## Signature (recovered with confidence)

```c
void func_80055258(void *arg0, void *arg1);
```

`arg0` is never referenced anywhere in the body (confirmed off the raw
bytes -- the same "dead extra parameter" idiom documented elsewhere in this
unit). Called from `func_80054F30`/`func_8005511C`/`func_80054FD8` (all
this unit) discarding any return value, and the epilogue never sets `$v0`
before `jr $ra` -- retyped from an earlier (wrong, never-verified) `void *`
forward declaration to plain `void`, consistent with the actual control flow.
This required widening the two pre-existing forward declarations elsewhere
in the unit (`func_80054F30`'s and `func_80054DA4`'s blocks) to match; both
are call sites that already discard the return value, so this changes
nothing about their own (already-matched, or independently-derived) bytes.

## The stall: retail recomputes `D_8008E0A4`'s address at each of 3 accesses; my build caches it

`D_8008E0A4` is written, then conditionally re-read-negated-rewritten, all
within a few instructions of each other with one `rand()` call in between.
Retail computes a fresh `lui $at,%hi(D_8008E0A4)` / offset pair at EACH of
the three accesses (three independent `lui` instructions, never reused).
My build instead promotes the address into a genuine callee-saved register
(`$s0` in the plain version, cascading a rename of the magic-constant
register from `$s0` to `$s1` and forcing an extra prologue/epilogue
save/restore) -- GCC 2.6.3's own CSE decided the address was worth caching
across the intervening call, where retail's actual compilation did not.

**Two things tried, neither fixed it:**

1. `*(volatile s32 *) D_8008E0A4` for both accesses -- no effect on the
   address caching (volatile blocks reordering/eliding the MEMORY access,
   not caching the address-of computation, which is what's actually being
   promoted here). Reverted.
2. A bare `__asm__("");` scheduling barrier immediately after the first
   store, before the `if (rand() & 1)` guard -- also no effect on the
   register allocation; per HARD RULE 6 a bare barrier only affects
   instruction ORDER and this residue is a register-identity promotion, so
   this was expected to be inert rather than banned. Reverted (removed,
   since it changed nothing and left clutter).

Neither `register T v asm("$N")` nor an operand constraint was tried or
used, per HARD RULE 6 -- this is a genuine STALL by that rule's own test.

**Interesting asymmetry, not yet explained:** the immediately-following,
textually-identical pattern for `D_8008E0AC` (write, conditional
negate-and-rewrite, with a `rand()` call in between) does NOT get cached in
either retail or my build -- both recompute fresh each time for `D_8008E0AC`.
Only the FIRST (`D_8008E0A4`) block differs between retail and mine. This
suggests the caching decision is sensitive to register pressure/CSE-table
state specific to that point in the function (plausibly: by the time
`D_8008E0AC`'s block runs, the magic-constant register is already
committed and there's no longer "room" to also cache an address, in EITHER
build), not a general rule about this idiom.

## Attempts

3 real builds: (1) initial body, 8/110, length matches, `$s0`/`$s1`
address-caching residue identified; (2) `volatile` cast on the `D_8008E0A4`
accesses, same 8/110 result (no effect); (3) bare `__asm__("")` barrier
after the first store, same 8/110 result (no effect) -- reverted (2) and
(3), restored `INCLUDE_ASM` with (1)'s plain body.

### Proposed learning

**`volatile` prevents eliding/reordering a memory ACCESS; it does not stop
GCC 2.6.3 from caching the ADDRESS-OF a global symbol in a register across
an intervening call.** Confirmed here: casting to `volatile s32 *` for
both the store and the later load-negate-store left the extra
callee-saved-register residue completely unchanged. If a future residue
looks like "GCC caches a global's address I don't want cached," `volatile`
is not the tool -- this remains an open question for that class of residue.
