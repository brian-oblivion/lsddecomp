# func_800336CC -- MATCHED (16/16 words)

`asm/nonmatchings/code_179d8_i/func_800336CC.s`, vram `0x800336CC`, unit

## Summary

Normalises a `u8` mode byte to a plain `0`/`1` and forwards it to
`func_80036AC8` (uncarved, first `glabel` in `psyq_SpuSetMute.s`) -- any
other input value returns without calling. Three attempts, two residues in
sequence.

```c
extern void func_80036AC8(s32 a0);

void func_800336CC(u8 a0)
{
    s32 mode;

    if (a0 != 0) {
        if (a0 != 1) {
            return;
        }
        mode = 1;
    } else {
        mode = 0;
    }
    func_80036AC8(mode);
}
```

## Attempt log

1. **`if (a0==0) func(0); else if (a0==1) func(1);`** -- compiled to TWO
   separate call sites (GCC did not unify them), one instruction short
   overall and with the wrong branch polarity. 3/16.
2. **Same branch order, with an explicit `s32 mode` local** set in each arm
   and a single `func_80036AC8(mode)` call after the if/else-if. GCC
   constant-propagated `mode` right back to two literal-argument call
   sites -- byte-identical to attempt 1. Confirms the double-call-site
   shape is a property of *branch order*, not of whether the argument
   passes through a named local.
3. **Flipped the branch nesting** -- test `a0 != 0` first (with the
   `a0 == 1` sub-test and its body nested inside the true arm) and put
   `a0 == 0` in the `else`:
   ```c
   if (a0 != 0) { if (a0 != 1) return; mode = 1; } else { mode = 0; }
   ```
   This reproduced retail's exact block order (the `a0==0` case is a jump
   target placed at the very end, right before the shared call; the
   `a0==1` case falls straight through into it) and merged to one call
   site. 15/16 -- one word short, and it was **not** a control-flow gap:
   `cc1`'s own `.s` output (`tools/gcc263/cc1` run in isolation) showed it
   scheduling a *redundant* `andi $4,$4,0x00ff` into the branch-delay slot
   right after the `jal`, where retail has `nop`. Root cause: `mode` was
   still typed `s32`, but the call site was still passing `a0` itself
   (the `u8` parameter) in an earlier iteration of this attempt -- passing
   an unsigned-char-typed lvalue as an `int` argument makes cc1 conservatively
   re-mask it for the integer promotion, even when the value was just
   assigned a small literal a line above. Passing the plain `s32 mode`
   local (never itself byte-typed) instead of reusing `a0` removed the
   promotion mask. 16/16.

### Proposed learning

Two, both worth folding into `docs/DECOMPILATION_LEARNINGS.md`:

1. **For `if (A) X; else if (B) Y; else Z;`, GCC 2.6.3 -O2's block *order*
   in the binary depends on which branch is written as the outer `if` vs
   the `else`, not just on the logical truth table.** Here, writing the
   `a0==0` case as the outer `else` (with the `a0==1` chain nested inside
   the outer `if (a0 != 0)`) reproduced retail's layout; the "obvious"
   ordering (test `a0==0` first, `else if (a0==1)`) produced a
   structurally different but semantically identical binary that is one
   instruction short and mismatches from word 2 onward. When a chained
   if/else-if scores short with a plausible-looking near-miss, try
   swapping which condition is the outermost `if` before suspecting
   anything else.
2. **Passing a byte-typed (`u8`/`s8`) local or parameter as an argument to
   an `int`/`s32`-typed callee parameter costs an extra defensive
   `andi 0xff` (or sign-extend) at the call site, even immediately after
   the variable was assigned a small literal.** cc1 does not prove the
   value is already clean; it re-applies the integer-promotion mask on
   every use of a byte-typed lvalue in an `int` context. If retail's call
   site has no such mask, the value being passed must already be a plain
   `int`/`s32`-typed local (or the parameter itself must not be re-used
   directly) -- introduce a separate `s32` temp rather than passing the
   byte-typed variable straight through.
