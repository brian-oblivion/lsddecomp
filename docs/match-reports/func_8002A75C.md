## How the pieces were verified before assembly

Each block above was checked against the RAW disassembly instruction-by-
instruction, not assumed from the sibling's C alone, because a byte-identical
INSTRUCTION SEQUENCE is the only thing that licenses reuse here (two
functions calling the same helper with the same args can still produce
different bytes depending on surrounding register pressure). All four
reused blocks matched their sibling's already-matched raw `.s` verbatim,
confirming this function's source genuinely duplicates (not calls) those
bodies -- consistent with the project's established finding that this GCC
does not auto-inline.

`counter`'s declaration was left uninitialized at the top and assigned
`counter = 0;` immediately before the `D_8006D60C & 0x10` check that follows
the port-close tail -- NOT at function entry -- because retail's `move
$s0, $zero` sits at that exact point (in the `beqz`'s delay slot), the same
lesson as `func_8002A400`'s report but applied at a different point in a
much larger function.

## The one remaining residue

Everything up to and including `*D_8006D8CC = 7;` inside the link-wait loop
matches retail byte-for-byte (confirmed via direct `objdump` comparison of
this build's `.o`, independent of the whole-image address drift). The first
divergence is exactly at the "close port" tail's lead-in:

**Retail materializes the FIRST `func_80029F10(1, 0, 0, 0)` call's `$a0=1`,
`$a1=0`, `$a2=0` THREE INSTRUCTIONS EARLY** -- immediately after the
link-wait loop's join point (`.L8002A87C`), a full ~30 instructions before
that call executes, BEFORE `D_8006D8DA = 0;` even begins. This is true even
though `$a0` provably already holds `1` at that point on every incoming
path (both the loop-entered and loop-skipped paths set it to `1` via their
own antecedent instructions) -- so from a pure dataflow standpoint the
re-materialization is redundant, which is itself informative: GCC 2.6.3
re-emitting a provably-redundant constant load is the signature of the
SOURCE literally mentioning the constant again at that point, not of an
optimizer choice.

This function's second, structurally identical
`func_80029F10(1, 0, 0, 0)` call (inside `if (D_8006D60C & 0x10)`) does NOT
show this behavior -- its args materialize normally, right before its own
call, exactly like ordinary C compiles. So the anomaly is specific to the
FIRST call, immediately following the loop.

**Four attempts, all rejected:**
1. Plain `func_80029F10(1, 0, 0, 0);` written after the tail (natural
   source position) -- args materialize late, matching the SECOND call's
   shape but not the first's. This is the body preserved above.
2. A bare `__asm__("")` barrier immediately after the link-wait loop (before
   `D_8006D8DA = 0;`) -- no change in output at all.
3. Extracting the three arguments into local variables (`arg_a = 1; arg_b =
   0; arg_c = 0;`) assigned at the point retail materializes them, then
   passed by name to the call -- no change; GCC constant-propagates them to
   the call site regardless of assignment position, ignoring source order
   for plain (non-volatile) locals.
4. The same three locals declared `volatile` -- changed the output, but in
   the wrong direction (grew to 800/784 bytes, +20, from separate stack
   slots for each volatile local rather than the intended 3-instruction
   pull-forward).

**Not yet tried**: whatever surrounding-code difference would make GCC's
list scheduler treat that specific point as register-pressure-free enough
to hoist independent constant loads there. Given four largely orthogonal
levers failed to reproduce it, this may need either the permuter (this is
exactly the class of one-instruction-position residue the permuter is
documented to be good at -- see `docs/MATCHING-GUIDE.md`'s permuter section)
or a structural insight about what retail's REAL source does differently
right after the link-wait loop that was not captured here.

### Proposed learning

**A provably-redundant constant re-materialization in retail's output (same
register, same value, reachable unconditionally from every predecessor) is
a strong signal that the SOURCE mentions the constant again at that exact
point** -- not that the compiler chose to recompute it. This is the
opposite intuition from what "redundant instruction" usually suggests (a
missed optimization), and it did not, by itself, reveal what source
construct would cause it; recorded so a future attempt does not have to
re-derive this observation before testing sourceconstructs against it.

## Round 19: two structural fixes, 58/196 -> 171/196 (runner charlie)

Picked this up on the head's second-pass brief ("not register-shaped,
nobody touched this round"). The original report's residue was framed
as a single 1-instruction scheduling gap; it is actually two separate,
much larger structural mistakes in this report's preserved body, both
now fixed.

### Fix 1: the first `func_80029F10(1, 0, 0, 0)` belongs BEFORE the close-port tail, not after (58 -> 161/196)

The preserved body called it as "one extra call this function adds on
top" of the reused `func_8002A510` tail -- i.e. positioned AFTER the
whole `D_8006D8DA = 0; ... *D_8006D8D0 = 0x1325;` sequence. Moving it to
immediately after the link-wait loop, BEFORE that sequence, produced a
huge jump: 58 -> 161/196, with the compiled length still exactly
matching retail's 196 instructions (confirmed via `objdump`, no drift).

This was verified as the load-bearing change, not a side effect of
something else: reverting ONLY the call's position (putting it back
after the tail, keeping everything else identical) reproduces the
original 58/196 exactly. Moving it forward again restores 161/196
exactly. The position of this one call, relative to the reused
`func_8002A510` tail, is the dominant defect in the original body -- not
the 1-instruction scheduling gap the original report focused on (that
gap is real but secondary, see below).

### Fix 2: the tail's two retry guards have the WRONG POLARITY (161 -> 171/196)

The preserved body's tail:
```c
if (func_80029F10(0xA, 0, 0, 0) == 0) { return -1; }
if (func_80029F10(0xC, 0, 0, 0) == 0) { return -1; }
```
Reading the disassembly at this point directly (`bnez v0,<epilogue>`
immediately after each call, with `li v0,-1` in the delay slot) shows
retail returns -1 when the call result is **non-zero**, and falls
through to the NEXT check (or the final `func_800299BC` call) only when
the result is zero -- the exact opposite of what the preserved body
tests. Flipping both to `!= 0` closed this entire tail region exactly:
161 -> 171/196, and this is now the ONLY residue left in the function.

### What's left: the same call, split by the compiler across ~90 bytes -- neither position tried reproduces it

With fix 1 applied, `func_80029F10(1, 0, 0, 0);` sits as one statement
right after the link-wait loop. Retail's actual instruction layout at
that exact point is stranger than either position this report has
tried: it loads `a0=1, a1=0, a2=0` RIGHT THERE (matching this fix
exactly) but defers `a3=0` and the `jal` itself to the END of the
close-port tail, ~90 bytes and a dozen unrelated instructions later.
Neither tested position reproduces this split:

- Call written after the tail (original body): args/call/nothing all
  materialize together, late -- 58/196 baseline for this region.
- Call written before the tail (fix 1): args/call/a3 all materialize
  together, early -- matches retail's ARGS position exactly but keeps
  the `jal`+`a3` early too, where retail wants them deferred.

**Retried this report's own rejected attempt #3 (named locals for the
three args, assigned early, called late) on top of the now-much-closer
function** -- regressed badly (57/196 with real drift), reproducing the
original finding that plain (non-`volatile`) locals get constant-
propagated back to a single call site regardless of assignment
position. This axis remains exhausted; the fix-1 position is strictly
better despite not closing this specific residue.

This residue is now confined to exactly 2 instructions
(`jal`/`move a3,zero`) landing 8 bytes early relative to retail, which
is a MUCH narrower target than the original report's framing suggested
-- a single call whose own argument setup and whose own call+a3 are
scheduled by cc1 at two different points, ~90 bytes apart, is not
reproducible from a single C call statement written at either endpoint.
This may be the permuter's best candidate in this function now that the
two structural defects are gone; not run this round (time budget), but
the scaffold should seed from THIS report's fix-1+fix-2 body, not the
original 58/196 one.

### Proposed learning

**When a report frames a residue as "N bytes short" from a SINGLE
preserved body, check whether a large, un-tried STRUCTURAL move (where
a reused/shared block's neighboring statement is positioned relative to
it) is available before trusting the byte count as the true gap size.**
Here the actual defect was two structural mistakes (call position
relative to a reused tail block, and guard polarity on two later
checks) that combined to look like "58/196, one big diffuse residue";
fixing them dropped the function to a single, narrow, well-characterized
2-instruction scheduling gap. The guard-polarity fix in particular is
the same lever documented elsewhere this round (`func_80032AD0`'s
block-order finding and its several confirmations) -- worth checking on
ANY `== 0` / `!= 0` return-early guard before assuming a residue is
something more exotic, even deep in a large function's tail where the
call chain looks unrelated to the smaller functions where this lever
was first found.
