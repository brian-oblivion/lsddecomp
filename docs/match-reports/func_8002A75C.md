## How the pieces were verified before assembly

Each block above was checked against the RAW disassembly instruction-by-
instruction, not assumed from the sibling's C alone, because a byte-identical
INSTRUCTION SEQUENCE is the only thing that licenses reuse here (two
functions calling the same helper with the same args can still produce
different bytes depending on surrounding register pressure). All four
reused blocks matched their sibling's already-matched raw `.s` verbatim,
confirming this function's source genuinely duplicates (not calls) those
bodies -- consistent with the project's established finding that this GCC
does not auto-inline.

`counter`'s declaration was left uninitialized at the top and assigned
`counter = 0;` immediately before the `D_8006D60C & 0x10` check that follows
the port-close tail -- NOT at function entry -- because retail's `move
$s0, $zero` sits at that exact point (in the `beqz`'s delay slot), the same
lesson as `func_8002A400`'s report but applied at a different point in a
much larger function.

## The one remaining residue

Everything up to and including `*D_8006D8CC = 7;` inside the link-wait loop
matches retail byte-for-byte (confirmed via direct `objdump` comparison of
this build's `.o`, independent of the whole-image address drift). The first
divergence is exactly at the "close port" tail's lead-in:

**Retail materializes the FIRST `func_80029F10(1, 0, 0, 0)` call's `$a0=1`,
`$a1=0`, `$a2=0` THREE INSTRUCTIONS EARLY** -- immediately after the
link-wait loop's join point (`.L8002A87C`), a full ~30 instructions before
that call executes, BEFORE `D_8006D8DA = 0;` even begins. This is true even
though `$a0` provably already holds `1` at that point on every incoming
path (both the loop-entered and loop-skipped paths set it to `1` via their
own antecedent instructions) -- so from a pure dataflow standpoint the
re-materialization is redundant, which is itself informative: GCC 2.6.3
re-emitting a provably-redundant constant load is the signature of the
SOURCE literally mentioning the constant again at that point, not of an
optimizer choice.

This function's second, structurally identical
`func_80029F10(1, 0, 0, 0)` call (inside `if (D_8006D60C & 0x10)`) does NOT
show this behavior -- its args materialize normally, right before its own
call, exactly like ordinary C compiles. So the anomaly is specific to the
FIRST call, immediately following the loop.

**Four attempts, all rejected:**
1. Plain `func_80029F10(1, 0, 0, 0);` written after the tail (natural
   source position) -- args materialize late, matching the SECOND call's
   shape but not the first's. This is the body preserved above.
2. A bare `__asm__("")` barrier immediately after the link-wait loop (before
   `D_8006D8DA = 0;`) -- no change in output at all.
3. Extracting the three arguments into local variables (`arg_a = 1; arg_b =
   0; arg_c = 0;`) assigned at the point retail materializes them, then
   passed by name to the call -- no change; GCC constant-propagates them to
   the call site regardless of assignment position, ignoring source order
   for plain (non-volatile) locals.
4. The same three locals declared `volatile` -- changed the output, but in
   the wrong direction (grew to 800/784 bytes, +20, from separate stack
   slots for each volatile local rather than the intended 3-instruction
   pull-forward).

**Not yet tried**: whatever surrounding-code difference would make GCC's
list scheduler treat that specific point as register-pressure-free enough
to hoist independent constant loads there. Given four largely orthogonal
levers failed to reproduce it, this may need either the permuter (this is
exactly the class of one-instruction-position residue the permuter is
documented to be good at -- see `docs/MATCHING-GUIDE.md`'s permuter section)
or a structural insight about what retail's REAL source does differently
right after the link-wait loop that was not captured here.

### Proposed learning

**A provably-redundant constant re-materialization in retail's output (same
register, same value, reachable unconditionally from every predecessor) is
a strong signal that the SOURCE mentions the constant again at that exact
point** -- not that the compiler chose to recompute it. This is the
opposite intuition from what "redundant instruction" usually suggests (a
missed optimization), and it did not, by itself, reveal what source
construct would cause it; recorded so a future attempt does not have to
re-derive this observation before testing sourceconstructs against it.
