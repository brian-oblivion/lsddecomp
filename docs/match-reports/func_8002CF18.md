## What it is

A voice-steal candidate scan over `D_8008E9D0` live channels (0x34-byte-stride
per-channel records): find a fully-free channel (both an "in use" flag byte
and a u16 both zero) and take it immediately; otherwise track the channel
with the lowest 3-level priority key (primary `s16`, tie-broken by lowest
secondary `u16`, further tied by highest tertiary `u16`); if none found at
all, fail with the channel count as a sentinel. On success it also walks
every channel bumping a per-channel counter, clears the winning channel's
counter and priority, and — if its flag byte reads exactly 2 — calls
`func_800375E8(0, 0xFFFFFF)`.

## Attempts and what each one fixed

Reconstructing this from first principles (m2c was not run; the control
flow was read directly off the `.s`, which was tractable since every
computed address is a `%hi`/`%lo` pair immediately followed by a use).
Starting point was a naive transcription using a signed `s32 idx` and plain
`for`/`if`/`&&` — that compiled to **157/167** words. Four fixes moved it to
163, each addressing a DIFFERENT axis (not a repeated guess on one):

1. **Loop-counter signedness.** `for (idx = 0; idx < D_8008E9D0; idx++)`
   with `idx` declared `s32` produces a `blez`-based pretest (`idx<count`
   treated as signed) where retail has a plain `beqz` (unsigned `count==0`
   reduction). Declaring `idx` as `u32` fixed the pretest instruction
   (`beqz`) without touching anything else -- this is the loop-bound
   SIGNEDNESS lever documented generically in `DECOMPILATION_LEARNINGS.md`.
2. **Explicit `(u8)` casts on `chosen`/`found` at the outer comparisons.**
   `if (chosen == 0x63)` compiles without a mask (chosen's raw 32-bit
   register value compared directly); retail masks first
   (`andi $v1,$s0,0xff`). Writing `if ((u8) chosen == 0x63)` and
   `if ((u8) found != 0)` reproduced the masks.
3. **`(u8)` cast on the tail increment loop's index too.** Without it,
   GCC's strength-reduction pass replaces retail's per-iteration
   `idx*0x34` (5 instructions: `sll`/`addu`/`sll`/`addu`/`sll`) with a
   `+0x34` increment (1 instruction) — retail does NOT do this reduction
   anywhere in this function, and the discriminator is that every array
   index retail computes is over an explicitly `(u8)`-masked value, which
   apparently defeats old GCC's induction-variable analysis (the masked
   value isn't recognized as a clean affine induction variable). Adding
   `(u8)` to the tail loop's `D_8008D988[idx]`/`D_8008D98A[idx]` restored
   the multiply-every-iteration shape.
4. **Duplicating the divide/lookup in each `if`/`else` arm was NOT needed
   here** (that fix mattered for the sibling function, see
   `func_8002D6A4.md`) — `func_8002CF18` has no such division split.

## What is still wrong (the residue)

**Class: cross-branch redundant-recompute elision (a "block order" family
member, but the specific mechanism is CSE surviving a branch join, not
fallthrough placement).** At the merge point after the two
"is this channel free" checks (`.L8002CFA8` in the `.s`, reached by two
separate `bnez` branches from the `D_8008D9A3`/`D_8008D98E` checks), retail
RECOMPUTES `idx*0x34` from scratch (5 instructions, `sll`/`addu`/`sll`/
`addu`/`sll`) even though the SAME value was just computed moments earlier
for the first two checks. My compiled C, using the identical `(u8) idx`
subexpression at the merge target, gets it CACHED across the branch instead
(GCC keeps the value live in a spare register and reuses it) — this is a
strictly SHORTER, valid compilation that simply isn't what retail's source
produced.

Tried and confirmed ineffective:

- **Rewriting the `&&` as two explicit `if (...) goto evalPriority;`
  statements.** Produced byte-IDENTICAL output to the `&&` form — GCC's
  front end lowers both to the same CFG, so this was never a surface-syntax
  question.
- **A bare `__asm__("")` placed at the top of the `evalPriority:` label.**
  No effect on the recompute (an optimization/CSE-across-branch decision,
  not an instruction-scheduling one — the barrier's documented scope in
  CLAUDE.md is order-only, and this residue is not an order residue).

**Not tried:** a barrier placed inside each predecessor block (right
before each `goto`), which might invalidate the cached value at its
SOURCE rather than at the target. This is the natural next lever if anyone
picks this back up — CLAUDE.md's `__asm__("")` scheduling-barrier rule
doesn't rule it in or out for this exact placement, so it would need to be
tried and measured, not assumed.

The instruction-count gap (163 vs 167 = **4 words short**) is consistent
with this ONE 5-instruction recompute being only PARTIALLY reproduced (one
of the ~9 similar-shaped joins in this function still ends up 4 words
short overall after everything else lines up) -- i.e. this residue may
recur at more than one merge point in the function (the tie-break ladder
has three nested equality checks, each a similar two-or-three-predecessor
join), not only the one inspected in detail above.

## Proposed learning

**A `(u8)`/narrow cast on an array index isn't just about matching
`andi` masks — it also appears to suppress GCC 2.6.3's loop
strength-reduction of `idx*stride` into `idx+=stride`.** Every function in
this unit that indexes a 0x34-stride table with a masked byte index
recomputes the multiply on every iteration; the moment the index is left
as a plain wide `s32`/`u32` with no explicit narrowing, the compiler
silently switches to the cheaper increment form. Worth adding to
`DECOMPILATION_LEARNINGS.md`'s residue list as a discriminator: an
unexplained "my loop is N words short and the retail body recomputes a
multiply my body doesn't" is very likely this, and the fix is a cast, not
a barrier.

available across it and reuse it. This matches `func_8002E308`'s

residue class barriers cannot reach at all" — the next lever has to break

index expression through a source form the front end doesn't recognize as
identical — untried this round, and unclear whether any such form exists
without also changing what retail's own recompute looks like structurally).

### Proposed learning (round 35)

**GCC 2.6.3's value-numbering/CSE sees through copy-propagation before the
value-availability pass runs** — assigning a same-valued local to a fresh
variable name (`idx2 = idx;`) and using the alias at the site of a
suspected hoist is NOT a working technique to present the compiler with a
"different" value; it collapses the alias back to the original before the
relevant optimization pass sees it. This closes off the last of the
"rename or alias to dodge CSE" family of ideas for this residue class —
combined with `func_8002E308`'s round-35 finding that an algebraic-identity
rewrite (`-(b-a)` for `a-b`) is equally transparent to it, the working
conclusion for this project's "value-hoist immune to barriers" class is
that NO surface-syntax rephrasing of an equivalent expression defeats it;
only a genuine change to the control-flow shape (not yet identified) is
left as a candidate lever.

**And the barrier was not merely inert padding — it cost three instructions
of real work.** `evalPriority:` is the join of two forward branches. GCC's
eager delay-slot filler copies a join block's first instruction into each
predecessor's delay slot and redirects the branch past it; retail does
exactly that, putting `andi $v0,$a3,0xff` (the `(u8)idx` recompute, needed

round 37's barrier sat at the head of that join and pinned it: three `nop`s
where retail has work. Deleting the barrier reproduced all three exactly.

**This is a genuine counter-example to the standing rule of thumb that a bare
`__asm__("")` is "order-only and therefore safe".** The CLAUDE.md test — does
removing it change WHICH REGISTER holds a value, or only instruction ORDER —
is still the right legality test and the barrier passes it. But passing the
legality test is not evidence it helps: **at a basic-block JOIN a barrier
also blocks delay-slot filling, which can cost instructions rather than move
them.** Discriminator: if your body has `nop`s in delay slots where retail
has real work, and you have a barrier at or near a label, remove the barrier
before anything else.

### Proposed learnings (round 65)

**1. A bare `__asm__("")` is order-only, but "order-only" includes DELAY-SLOT
order, and at a basic-block join that can cost instructions.** GCC's eager
delay-slot filler copies a join's first instruction into each predecessor's
delay slot; a volatile asm at the head of that join is not copyable and
blocks it. Here that was three `nop`s against retail's three real
instructions, and it had stood for four rounds inside a body whose length
was "exact". The legality test in CLAUDE.md (does it change which REGISTER
holds a value?) is unchanged and the barrier passed it — **passing the
legality test is not evidence the barrier helps.**

**2. "Exact length" is not a proxy for "structurally right", and a lever that
buys a word is exactly the kind that fakes it.** Two independent one-word
additions took this body from 165 to 167 while both made the instruction
sequence worse. When a length gap closes, check that the instruction COUNT
per basic block moved the way you expected, not just the total — funcdiff's
`insertions / deletions` and `positional skeleton diffs` are the figures that
notice, and here they read 29/29 and 118 at "exact length".

**3. A loop condition is a place a cast hides.** Every table subscript in
this body carried `(u8)idx` from round 26 onward; both loop CONDITIONS did
not, for four rounds, because the condition does not look like an index. If
the body masks an induction variable everywhere it is used as a subscript,
check whether retail masks it in the compare too.

**4. `extern T sym[]` + `sym[i].field` folds a non-zero field offset into the
symbol; a POINTER local does not.** `D_8008D988[i].unk2` became a second
`%hi/%lo` symbol reference (and a second `--addiu-at` expansion) at
`D_8008D988+2`, while retail kept a loop-invariant base register and a `2`
displacement. Assigning the array to a pointer local before the loop is what
gives GCC something to hoist. Worth reaching for whenever retail shows
`addu $x,$idx,$base` / `st $v,K($x)` with a small constant `K` and your build
shows a second symbol expansion instead.

**5. Prefer the instrument that counts INSTRUCTIONS when the residue is
register identity.** Raw word-match penalises every word a register rotation
touches, so it can rank a structurally-better body lower — measured here:
`u16 bestSec` is better on insertions/deletions (16/16 vs 20/20) and
asm-differ (1250 vs 1375) and worse on word-match (74 vs 79).
